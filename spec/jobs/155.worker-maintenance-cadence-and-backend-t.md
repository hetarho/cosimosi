Findings: review 14 R004 (P2) + R008 (P3). Decision: Questions #2 in the source report —
cleanup cadence and batch size are product build values in `spec/values.yaml`; poll interval
stays a composition-root argument with one named home.

- [ ] A1 Terminal-job cleanup runs on its own maintenance cadence (`nextCleanupAt`), not
      before every claim: an idle worker no longer issues a purge per poll tick, and a busy
      worker no longer issues one per completed job.
- [ ] A2 Cleanup cadence and batch size are generated from `spec/values.yaml`; a full batch
      permits a bounded drain; cleanup stays fail-open for product claims.
- [ ] A3 Tests cover: repeated idle claims within one window (one purge), a backlog (bounded
      drain), cleanup errors (claims proceed), multiple clock advances.
- [ ] A4 The duplicated one-second poll literal has a single named home shared by
      `cmd/worker` and `cmd/api`'s dev worker.
- [ ] A5 The backend tuning inventory is CLASSIFIED, each value with an owner: product/cache
      behavior that must be identical everywhere → `spec/values.yaml` (withdrawal status
      cache TTL + max entries, AI adapter cache entries); deployment-shaped values → named
      composition-root arguments (HTTP client timeouts); protocol/structural limits → stay in
      code with a comment stating the invariant. Zero unexplained literals remain in the
      inventoried set.
- [ ] A6 No behavior change beyond call frequency (same purge semantics); API suites green.
