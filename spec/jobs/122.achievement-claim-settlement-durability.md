# Job 122: Achievement claim settlement durability (refactor)

> Implementation work doc. Source spec: [code-review/10.jobs-94-115-achievement,-decorate-and-sh](../code-review/10.jobs-94-115-achievement,-decorate-and-sh.md).
> /cosimosi:implement-job 122 builds it via the two checklists below. When done, reflect the result into the
> SSOT (plan/policy/values) and set status: done. Write it in English.

Covers **R001** (P1) and **R005** (P3) — the batch's only finding where the documented invariant and the shipped
behavior disagree about something the user can lose, plus the sibling invariant that lands a user in exactly that state
deterministically.

The claim's transactional ordering is correct and this job does not change it. `claimed_at` is stamped and committed
BEFORE any credit moves, so double payout stays impossible, and the payout stays outside the claim transaction so this
context never becomes the transaction owner of the ledger's or the ornament catalog's tables (§2.3). What is missing is
the other half of an at-least-once design: a retry driver, and a state the retry can be seen in.

Today the intermediate state — claimed but uncredited — is unrepresentable. `service.go:85` collapses it
(`entry.Claimed = record.ClaimedAt != nil`), so the client hides the affordance, and the only thing holding the
recovery window open is a stale client cache that any of twelve unrelated `useInvalidateAchievements()` call sites
closes for good. The code's own stated guarantee (`claim.go:27-31`, `errors.go:57-60`, `rpc/reasons.go:11-13`) is
unreachable from the UI.

**Settled before building** (review 10 _Questions / Tradeoffs_, decided with the owner 2026-07-30):

- **Shape: a `paid_at` column.** The cheaper variant — keeping the row `claimable` until the payout lands — was
  rejected: the stamp-before-credit ordering IS the double-payout guard (`achievement.sql#ClaimAchievementReward`'s
  `claimed_at IS NULL` arm), so deferring the stamp would need a replacement guard for the thing that currently cannot
  go wrong. `claimed_at` keeps meaning "the user pressed the button"; `paid_at` means "the reward landed".
- **Retry driver: a settle job scheduled inside the claim transaction**, not a periodic cross-user scan of
  `achievement_progress`. A global product-table scan would need a `globalQueries` allowlist entry in
  `check-persistence-isolation.mjs`, whose own rule is that allowlisted scans are _platform-owned_ and product
  reads/writes stay user-scoped — and it would need new periodic scaffolding in a worker that today only polls the job
  queue. The queue route reuses the one global scan already sanctioned (`memory/jobs.sql#ClaimDueJob`), keeps every
  achievement statement user-scoped, and mirrors how the withdrawal sweep already reaches the worker.
- **No retry cap.** The sweep is unbounded, and a comment must state why it cannot spin forever: the boot guard already
  refuses to start on a reward naming an ornament the store catalog does not publish, and A8 below closes the
  neither-leg case. Every unsettled claim therefore has a payable leg.

## Acceptance Criteria (from code-review/10.jobs-94-115-achievement,-decorate-and-sh)

- [ ] A1 `achievement_progress` can represent claimed-but-unpaid. A nullable `paid_at TIMESTAMPTZ` is stamped by SQL
      `now()` (the context still owns no clock, [A1a]), and a DDL CHECK enforces that `paid_at` is non-null only when
      `claimed_at` is — an unclaimed row cannot be paid.
- [ ] A2 `payReward`'s success path stamps `paid_at` for the claim it just paid, through a `Store` port method. A
      replayed claim that finds the reward already paid stamps idempotently rather than failing.
- [ ] A3 The read distinguishes the two states. `Entry` carries the settled fact alongside `Claimed`,
      `AchievementEntry` carries it on the wire, and a claimed-and-unpaid row is a **different wire value** from a
      claimed-and-paid one. `service.go`'s `entry.Claimed = record.ClaimedAt != nil` no longer collapses them.
- [ ] A4 `claimState` in `@cosimosi/achievement` gains `'unpaid'`, derived from the server booleans only — no local
      "optimistically claimed" flag anywhere, matching `progress.ts`'s existing rule.
- [ ] A5 Both apps render `unpaid` with a retry affordance and its own copy (ko + en), and it reads as "받기 다시 시도"
      rather than anything that implies the reward was lost. `claimableCount`'s tab summary decides deliberately
      whether an unpaid row counts as waiting — whichever it is, rows and summary agree.
- [ ] A6 **The recovery window no longer depends on cache staleness.** After a payout refusal, invalidating the
      achievement read leaves the row actionable, because the server now reports it as unpaid. The twelve unrelated
      `useInvalidateAchievements()` call sites on both platforms can no longer strand a reward, and
      `AchievementList.tsx`'s comment about deliberately not invalidating on the payout refusal is corrected to match.
- [ ] A7 Recovery does not require the user to press again at all: an unsettled claim is drained by the worker. The
      settle job is scheduled inside the claim transaction, so a process death between the commit and the payout
      leaves the job enqueued; both reward legs stay idempotent on the claim id, so a replay credits once.
- [ ] A8 (R005) The catalog's reward-XOR invariant is boot-enforced, not test-only: a row with neither leg or both
      legs refuses the boot beside the existing unpublished-ornament check. The unit test in `catalog_test.go` stays.
- [ ] A9 **No behavior change on the happy path.** A successful claim still stamps `claimed_at` before any credit
      moves, still pays exactly one leg, still returns the same `ClaimResult`, and still reads as `claimed`. A second
      claim of a settled achievement is still an idempotent replay, not a refusal. Double payout is still impossible.
- [ ] A10 `pnpm check` green end to end, with the new SQL exercised against a real Postgres by the existing
      `pg/store_integration_test.go` path, and `pnpm lint:persistence` green with **no new `globalQueries` entry**.
