# Job 134: Sequence chrome test parity on mobile (refactor)

> Implementation work doc. Source spec: [code-review/11.jobs-116-128-demo,-sequence,-landing-and](../code-review/11.jobs-116-128-demo,-sequence,-landing-and.md).
> /cosimosi:implement-job 134 builds it via the two checklists below. When done, reflect the result into the
> SSOT (plan/policy/values) and set status: done. Write it in English.

Covers **R009 (P3)**. Test-only — this job adds coverage and changes no production code.

**The asymmetry.** The web `SequenceSpotlight` is 45 lines of declarative CSS class plus inline style
and **has** a test (`SequenceSpotlight.test.tsx`, 57 lines). The mobile fork is 84 lines carrying an
imperative animation lifecycle — `Animated.loop` construction, `loop.start()`, and a
`return () => loop.stop()` cleanup keyed on `[pulse, reducedMotion, rect]`
(`apps/mobile/src/features/highlight-next-control/ui/SequenceSpotlight.tsx:21-47`) — and has **no**
test.

The fork itself is legitimate and well-reasoned (RN has no CSS animation, as its own comment at `:16`
says). The coverage simply landed on the wrong side: the platform with the leak-capable implementation
is the untested one, and `apps/mobile/jest.guards.js`' pending-timer guard would not catch a stray
`Animated.loop` either, because a `useNativeDriver: true` loop registers no JS timer. So this class of
failure currently has neither a unit test nor a guard.

## Acceptance Criteria (from code-review/11)

- [ ] A1 `apps/mobile/src/features/highlight-next-control/ui/SequenceSpotlight.test.tsx` exists and
      mirrors the web suite's cases: renders nothing without a measured rect; positions the ring from
      the rect (with `RING_PADDING` applied on both axes); holds still under reduced motion.
- [ ] A2 It additionally covers the case the web fork cannot express: **unmounting stops the
      animation**, and a `rect` or `reducedMotion` change stops the previous loop before starting a
      new one. This is the assertion that justifies the job — the other three are parity.
- [ ] A3 The test passes under the existing mobile Jest harness with **no new console noise and no
      pending timer**, since `apps/mobile/jest.guards.js` fails a test on unexpected
      `console.error` / `console.warn` and fails a suite that leaves a long-lived timer pending.
- [ ] A4 **No production code changes.** If a genuine defect surfaces while writing the test, record it
      as a proposed finding rather than fixing it here — a coverage job that also changes behavior
      makes both halves harder to review.
- [ ] A5 The web suite is left as-is. This job closes the gap by raising mobile to web, not by
      trimming web.
