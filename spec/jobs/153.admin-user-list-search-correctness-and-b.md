Findings: review 14 R001 (P2) + the backend half of R002 (P2). Decision: Questions #1 in the
source report — keep the live Supabase traversal; search scans provider pages until a search
page fills or the provider is exhausted.

- [ ] A1 Search returns every matching account, not just matches on one raw provider page: a
      user whose email matches on provider page 3 is found from page 0 of the search.
- [ ] A2 Search semantics match the port contract (plan 58: email/id PREFIX) — or, if
      `contains` is deliberately kept, the port doc and plan 58 are updated to say so; either
      way the contract and the adapter agree.
- [ ] A3 `hasMore` describes the SEARCH-RESULT stream (search-scoped cursor/terminal flag),
      and an exactly-full last provider page no longer advertises a spurious next page.
- [ ] A4 `ListUsers` performs O(1) DB round trips per page: batch consumer-owned ports
      (`Balances(userIDs)`, `Counts(userIDs)`) backed by one grouped query per context, with
      missing-user defaults explicit; a query-count assertion pins it.
- [ ] A5 Adapter tests cover: no match on first raw page + match on a later page; a substring
      that is not a prefix; an exactly-full last page; the empty query.
- [ ] A6 Admin console behavior otherwise unchanged; API suites green.
