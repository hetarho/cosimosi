## Acceptance Criteria (from plan/74.achievement-catalog-model)

<!-- The source spec's acceptance criteria. After building, verify each is true in the running code. -->

- [ ] A1 A new supporting context `apps/api/internal/achievement` exists with `doc.go`, `types.go`, `catalog.go`, `service.go`, `ports.go`, `errors.go`, `pg/`, `rpc/` and **no** empty `domain/`/`app/` directory; it imports no other `internal/` context, and only `achievement/pg` imports `dbgen` (ARCHITECTURE §2.3/§2.4/§2.9 #2).
- [ ] A2 `AchievementServiceDeps` contains **no clock, no `Now` func and no time-typed field**, and no file under `internal/achievement` calls `time.Now`; `achieved_at`/`claimed_at` are written by SQL `now()` ([A1a]).
- [ ] A3 `Condition` has exactly two fields — a counter key and an integer target — with **no** time, duration, window, operator or second-counter field, so a streak / consecutive-login / per-day condition cannot be constructed ([A1a][A1]).
- [ ] A4 `Reward` has **no `TwinkleKind` field**; a stardust reward names a tier resolved from `achievement.reward_tier_{1,2,3}` and carries no literal amount, and exactly one of tier / ornament id is set per row (catalog self-test) ([A3]).
- [ ] A5 Goose migration `00023_achievement_progress.sql` (number reserved from the tree, §5.6) creates `achievement_counters (user_id, counter_key, value BIGINT, updated_at, PK (user_id, counter_key), CHECK (value >= 0))` and `achievement_progress (user_id, achievement_id, achieved_at, claimed_at, claim_id, PK (user_id, achievement_id), CHECK ((claimed_at IS NULL) = (claim_id IS NULL)))`; `pnpm db:migrate` applies and `pnpm db:down` reverses cleanly ([A4][U1]).
- [ ] A6 Neither table stores a per-event row or an event timestamp, and **no query in `db/queries/achievement/` performs date arithmetic** on any column ([A1a]).
- [ ] A7 `user_id` is part of both primary keys, every statement in `db/queries/achievement/achievement.sql` is conjunctively user-scoped, and `pnpm lint:persistence` passes with **no** new `platformTables` or `globalQueries` entry ([U1]).
- [ ] A8 There is **no `achievements` table**: the catalog is a Go table in `catalog.go`, and PRD §3.2 + UL §1.1 are amended to drop the `(achievements)` parenthetical ([A2]).
- [ ] A9 The counter-key set is **closed**, every key maps to exactly one [A2] axis, and each key is either accumulate-mode (`value + delta`) or reach-mode (`GREATEST(value, delta)`); an unknown key is refused as a wiring fault, and a composition-root test asserts every producer key constant is a member ([A2][A1a]).
- [ ] A10 `mood_variety` and `ornament_kind_variety` are maintained **inside `achievement`** by first-touch detection on their key families (`ON CONFLICT DO NOTHING` `:execrows`), so every condition remains a single-counter integer comparison; `mood_variety` cannot exceed 13, the `MOODS` length ([M2][A2]).
- [ ] A11 Counters are **monotonic** (no decrement path exists; the domain refuses `delta <= 0`) and `achieved_at` is never cleared — letting go, releasing a diary, or un-selecting an ornament never revokes an achievement or lowers a counter ([I1][A1]).
- [ ] A12 **No counter counts a constellation, a cluster, or a connected component.** The 별자리-규모 axis reads `neuron_share_depth` — activations on one `Neuron` — and no condition references an emergent structure ([I4], [A2]'s own correction).
- [ ] A13 `achievement` declares **no port into `memory`/`twinkle`/`store`/`account`** and queries only its own two tables; no type in the context carries a memory id, star, strength, mood, position or text field ([A6][I11]).
- [ ] A14 `proto/cosimosi/achievement/v1/achievement.proto` defines `AchievementService.ListAchievements` with `idempotency_level = NO_SIDE_EFFECTS`, an **empty** request message, no `user_id` field on any message, no `TwinkleKind` field, and no user-facing string field; `buf lint` passes and the method is classified **exactly once** in `packages/client-cache/src/http-policy.ts` as a user-scoped, non-shared-CDN GET ([U1][U9], ARCHITECTURE §2.7).
- [ ] A15 `ListAchievements` returns every catalog row with `progress = min(counter, target)` computed at read (no `progress` column exists), `achieved`/`claimed` flags, the resolved `reward_twinkle`, and a **server-fixed order**; a user with no rows in either table gets the full catalog at zero progress ([A4][U9], ARCHITECTURE §2.9 #3).
- [ ] A16 `ClaimAchievementReward` sets `claimed_at`/`claim_id` only when `claimed_at IS NULL`, so a second claim affects zero rows before any credit; the `PRIMARY KEY (user_id, achievement_id)` is the double-payout guard ([A4]).
- [ ] A17 The RPC handler is thin (map + call), carries no catalog logic, and its only refusal reason is `ACHIEVEMENT_SCOPE_REQUIRED` (ARCHITECTURE §2.9 #7).
- [ ] A18 No TS mirror of the catalog, the condition targets, or the evaluation exists, and no golden fixture is added — the server is the only evaluator (contrast [43.stardust-ledger](43.stardust-ledger.md)'s mirrored price curves).

## Implementation Checklist

<!-- How to build it, top to bottom. [P] = parallel (different files, no dependency). Flag (gen)/(migrate)/(gen:values). -->

> **Independent of the Epic N jobs at the code level** except for one join: the two ornament capstones reward
> [job 110](110.ornament-catalog-model.md)'s pinned achievement-only ids — **`star_shader.spire`** (`STAR_TOTAL`
> capstone) and **`background.floating-lines`** (`NEURON_SHARING` capstone). This job adds **no producer port and no
> `RecordProgress`**: nothing here can record progress by accident. Plan 75 does that.

**Tuning + schema**

- [ ] T001 **(gen:values)** `spec/values.yaml`: NEW `achievement` group with `reward_tier_1` / `reward_tier_2` /
      `reward_tier_3` (confirm the three amounts at implement, sized against `twinkle.earn_write` = 100 so a first
      reward reads as meaningful but never as a shortcut past writing) and `recovery_decay_stage_min` (the **pre-recall**
      decay stage that makes a recall count as 망각·회복 — a value, not catalog content, because plan 75 reads it at a
      `memory` call site and values is the only cross-context config channel). `claim_toast_ms` /
      `unlock_notice_max` belong to plan 76 — the group is created here, those two keys are not. `pnpm gen:values`.
- [ ] T002 **(migrate)** `apps/api/db/migrations/00023_achievement_progress.sql` (up **and** down, each table preceded by
      a comment naming the plan and its invariant tags): `achievement_counters (user_id, counter_key, value, updated_at,
PK (user_id, counter_key), CHECK value >= 0)` and `achievement_progress (user_id, achievement_id, achieved_at,
claimed_at, claim_id, PK (user_id, achievement_id), CHECK ((claimed_at IS NULL) = (claim_id IS NULL)))`.
      **No per-event row and no event timestamp** — an aggregate cannot answer "how many days in a row", so a streak is
      unanswerable from the schema. Timestamps come from SQL `now()`, which is what lets the Go context own no clock.
      Sync `schema.sql`; `pnpm db:migrate` then `pnpm db:down`. Take the next free number if `00023` is taken.
- [ ] T003 **(gen)** `apps/api/db/queries/achievement/achievement.sql` — the nine statements: `ListAchievementCounters`,
      `ListAchievementProgress`, `GetAchievementProgress`, `CreateAchievementCounter` (`:execrows`, the first-touch
      signal), `AddAchievementCounter` (`value + $3 RETURNING value`), `RaiseAchievementCounter`
      (`GREATEST(value, $3) RETURNING value`), `MarkAchievementAchieved`, `ClaimAchievementReward`
      (`SET claimed_at = now(), claim_id = $3 … AND claimed_at IS NULL` — a second claim affects zero rows **before** any
      credit), and the two purge deletes. All conjunctively `user_id`-scoped, `ON CONFLICT … DO NOTHING` only (never
      `DO UPDATE`), static sqlc. `pnpm gen:sql`; `pnpm lint:persistence` with **no** allowlist entry.

**The context (`/be-architecture` — a NEW supporting context on the `twinkle` recipe)**

- [ ] T004 `apps/api/internal/achievement/{doc.go,types.go,catalog.go,service.go,ports.go,errors.go}` + `pg/store.go` +
      `rpc/{server.go,reasons.go}`. `doc.go` is the charter and names both guards. `NewService(AchievementServiceDeps{Repo})
(*Service, error)` — **`{Repo}` and nothing else: no clock, no id minter.** `achievement` imports no other context.
- [ ] T005 `types.go` — `Condition{Counter CounterKey; Target int}` (**exactly two fields, forever**: no time type, no
      duration, no window, no second counter, no comparison operator, so a streak / "N per day" / "counter A while
      counter B" has nowhere to live) and `Reward{Tier RewardTier; OrnamentID string}` (**no `TwinkleKind` field**, so a
      `SMALL` reward is unexpressible rather than validated; the amount never appears — `Tier` resolves through the
      values keys).
- [ ] T006 The closed counter vocabulary with its **mode per key** (`accumulate` adds, `reach` takes
      `GREATEST(value, delta)`): the fourteen producer keys plus the two `achievement`-maintained derived counters
      (`mood_variety`, ceiling 13 = the `MOODS` length; `ornament_kind_variety`, ceiling 3 = the `OrnamentKind` arity).
      Mode lives in the definition, never at the call site — a producer has no field in which to invent a third
      semantics. Export the set + family membership so a composition-root test can assert every producer's local key
      constant is a member (a producing context cannot import these constants); an unknown key at runtime is
      `ErrUnknownCounterKey` and fails its transaction.
- [ ] T007 `catalog.go` — the nine `[A2]` axes as a Go table (`ID`, `Axis`, `Condition`, `Reward`), targets confirmed at
      implement per the plan's table. Exactly **two** capstones carry an ornament (`STAR_TOTAL` → `star_shader.spire`,
      `NEURON_SHARING` → `background.floating-lines`); every other reward including the `MOOD_VARIETY` 13-capstone is
      `GENERAL` Twinkle — no palette is ever a reward. **Declare no count**: the total is the table's length.
- [ ] T008 The catalog self-test: unique ids, non-empty axis, `Target >= 1`, every `Counter` in the closed set, and
      **exactly one reward leg** (`Tier == None` iff `OrnamentID != ""`). At the composition root — the one package that
      sees both catalogs without a context import — `apps/api/cmd/api/catalog_consistency_test.go` asserts every
      `OrnamentID` resolves to an ornament job 110 marks achievement-only, **1:1** in both directions.
- [ ] T009 `ports.go` — `Store` (the tx-bindable surface: `ListCounters`, `ListProgress`, `GetProgress`, `TouchCounter`,
      `AddCounter`, `RaiseCounter`, `MarkAchieved`, `MarkClaimed`, `PurgeUser`) and `Repo` (`Store` +
      `InAchievementTx`). `achievementpg.NewStore(db dbgen.DBTX) Store` mirrors `twinklepg.NewStore` verbatim so a
      producer's transaction can be bound through the `interface{ DB() dbgen.DBTX }` assertion plan 75 uses. The write
      methods ship here (this job owns the SQL) and are first **called** by plan 75 — the 43→44 precedent.
- [ ] T010 `Service` read behavior: the whole catalog with this caller's progress, `Progress = min(counter, target)` and
      `Achieved = counter >= target` **derived at read** (never stored), entries in a server-fixed order (axis order,
      then target ascending) so no client sorts, and `reward_twinkle` resolved from the tier's values key.
      `PurgeUser` deletes both tables for the caller only (the plan-62 sweep leg).
