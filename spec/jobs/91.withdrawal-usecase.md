## Acceptance Criteria (from plan/62.withdrawal-usecase)

<!-- The source spec's acceptance criteria. After building, verify each is true in the running code. -->

- [ ] A1 `Withdraw` stamps `users.deleted_at` with real-clock UTC and pairs it with exactly one scheduled sweep job due at `deleted_at + release.soft_delete_retention_days`; it creates **no** withdrawal ledger, group table, or per-effect rows. ([U10][X2])
- [ ] A2 `Withdraw` is idempotent: a second call inside the window returns the original `withdrawn_at` / `restore_deadline_at` and neither extends nor shortens the window, and the dedup key yields exactly one queued sweep. ([U10])
- [ ] A3 Every authenticated procedure except `RestoreAccount` is refused for a withdrawn scope **before any context read**, with `PLATFORM_ACCOUNT_WITHDRAWN` and `withdrawn_at` / `restore_deadline_at` metadata; the interceptor fails closed on lookup error or an unbound reader, and an absent `users` row is treated as not withdrawn. ([U1][U10])
- [ ] A4 A withdrawn user cannot obtain a new account without restoring: `SignUp` is refused for a scope whose `users` row carries `deleted_at`, so the [U11] signup bonus cannot be re-claimed by withdrawing. ([U11][G6])
- [ ] A5 `RestoreAccount` clears `deleted_at` and cancels the scheduled sweep inside the window, and refuses with `ACCOUNT_NOT_WITHDRAWN` or `ACCOUNT_RESTORE_WINDOW_EXPIRED` outside it; a failed cancellation cannot cause a purge, because the sweep re-derives due-ness from `users.deleted_at`. ([U10][X2])
- [ ] A6 After `RestoreAccount` the account is whole with no compensating writes: twinkle balance and ledger are unchanged, a stale `SMALL` anchor derives a fresh full grant with no carry, and ornament ownership/selection plus `achievement_progress.claimed_at` are restored rather than re-granted (no reward is paid twice). ([U10][G2])
- [ ] A7 The hard delete has **no client-reachable trigger**: no `PurgeAccount` RPC exists, `WithdrawRequest` carries no immediate-delete / window-skipping field, and no per-user request in `cosimosi.account.v1` carries a `user_id`. ([I1][U1])
- [ ] A8 The sweep runs only from the scheduled `withdrawal_sweep` job, reuses `release.soft_delete_retention_days` and the shipped `jobs` worker loop (no cron, no second retention key), fires for a user who never returns, no-ops when `deleted_at` is null, and retries at the true deadline when claimed early. ([I1][X2])
- [ ] A9 The sweep hard-deletes every per-user row of the withdrawn account across all registered contexts — memory aggregate + diaries + provenance + receipts + `universe_state` + `release_*`, twinkle balance + ledger, `auth_providers`, the user's own `invites`, `palette_preferences` while it exists — then the Supabase credential, then the `users` row; each leg is per-context, per-user-scoped, and idempotent under replay. ([I1][U1][X2])
- [ ] A10 The sweep never deletes another user's or the operator's rows: `invites` are purged only by `invites.user_id` (never `invitee_user_id`), an invite naming the withdrawn user as invitee survives as a null-tolerated dangling reference, already-credited counterpart ledger rows are untouched, and no `admin_*` row is touched. ([U1][I1])
- [ ] A11 Restore and sweep are mutually exclusive and crash-safe in either order: `users.deleted_at` is the single source of truth for both withdrawn-ness and due-ness, and the `users` row is deleted last as the completion marker. ([X2][I1])
- [ ] A12 `pnpm lint:persistence` passes, and its new hard-delete allowlist fails any `DELETE` on a `user_id`-bearing product table outside the release sweep and this unit's purge statements. ([I1][U1])
- [ ] A13 An integration test enumerates every `user_id`-bearing table from the migrations (minus operator tables) and asserts the sweep leaves zero rows for the swept user, with the in-flight job row as the only declared exception — so a later plan's new per-user table fails until its purge leg is registered. ([I1][U1])
- [ ] A14 Production refuses to boot when the scheduler, the credential directory, or the purge-leg set is unbound, and both worker composition roots handle `withdrawal_sweep` (a dead-lettered withdrawal job is a failing test, not a silent retention leak). ([I1])
- [ ] A15 `Withdraw` / `RestoreAccount` are POST mutations with no `NO_SIDE_EFFECTS` option and no `packages/client-cache/src/http-policy.ts` entry; handlers stay thin (map + call) and no proto or sqlc type reaches the use-case. (§2.7/§2.9 #4/#7)
- [ ] A16 `Export` is unchanged and callable up to the moment of withdrawal, and the withdrawn account's diaries stay intact and exportable for the whole window — no `Diary` body is ever updated by this unit. ([W6][I2])

- [ ] T008 **`Withdraw` — an idempotent pairing, enqueue first, mark second** (A1, A2) — `Withdraw(ctx, scope)`

      `account` may not own `memory`'s tables. (1) `Scheduler.Schedule(scope, now + release.soft_delete_retention_days)`

      `jobs_user_kind_dedup_key_unique` index (`00011:51`); (2)
      `UPDATE users SET deleted_at = now() WHERE user_id = $1 AND deleted_at IS NULL RETURNING deleted_at` in

- [ ] T009 **`RestoreAccount`** (A5, A6) — lock the `users` row; refuse with `ACCOUNT_NOT_WITHDRAWN` when
      `deleted_at IS NULL` and `ACCOUNT_RESTORE_WINDOW_EXPIRED` when `now >= deleted_at + retention`; otherwise clear
      `deleted_at` and call `Scheduler.Cancel(scope)`. A failed cancel is **safe**: the orphaned job re-reads
      `deleted_at`, finds it null, and completes as a no-op. After restore the account is whole with **zero
      compensating writes** — the twinkle ledger was never touched so the balance folds back; the `SMALL` reset
      anchor is simply stale so a fresh full grant derives (unspent prior `SMALL` is discarded — no carry, and
      deliberately no special handling); ornament ownership/selection and `achievement_progress.claimed_at` are
      **restored, never re-granted**, so no claimed reward is paid twice (A6).
- [ ] T010 **`SweepWithdrawnAccount(ctx, scope, now)` — the second call site of the one hard-delete mechanism**
      (A8, A9, A11) — triggered **only** by the scheduled `withdrawal_sweep` job. First re-derive due-ness from
      `users.deleted_at`, which is the single source of truth for both withdrawn-ness and due-ness: no `deleted_at`
      → complete as a **no-op** (exactly how the shipped sweep treats a group retired by `Restore`); `now` before
      `deleted_at + retention` → return a `RetryAt(deadline)` error, honored by the shipped `jobqueue` runner's
      `retryAtError` interface (`platform/jobqueue/runner.go:34`; the shipped precedent is
      `memory.retentionNotDueError`, `release.go:416`). So a stale or early job can **never** purge early, and no
      reconciliation scan across users is needed — **no `globalQueries` entry** is added. Then the legs, each in its
      own transaction (§2.3 — one context per transaction), each an idempotent `DELETE … WHERE user_id = $1`, in
      **this order**: (1) registered `UserDataPurger` legs, dependents first — `memory` → `twinkle` → (`store`,
      `achievement` once plans 71/74 register theirs); (2) `account`'s own dependents — `auth_providers`, `invites`
      **where `user_id`** = the withdrawn user (the inviter's own rows, **never** the lookalike `invitee_user_id`),
      `palette_preferences` while that table exists; (3) credentials — `SetUserBanned(true)` **then**
      `DeleteUser` (T011); (4) **`users` last**, so the row's existence is the "sweep incomplete" marker and any
      crash simply replays (A11). `admin_*` tables are **deliberately not swept**: operator state, not per-user
      product data (the `platformTables` category), and operator accountability requires the audit trail to outlive
      the accounts it describes — a stale promotion row is unusable once the credentials are gone (A10).
- [ ] T011 **The credential timing — ban at sweep, never at withdraw** (A5) — the rule the withdrawal contract fixes
      is **ban, not delete**, and the _order_ is what makes [U10]'s restore promise real: Supabase refuses sign-in
      for a banned user, so a user banned at withdrawal could never obtain a session and therefore could never call
      `RestoreAccount` — the ban would silently delete the restore promise. Therefore **at `Withdraw`:
      `users.deleted_at` only** (sign-in still works; the T007 gate makes every product procedure unreachable, so a
      valid JWT reads nothing — precisely the protection the gate exists to provide, and what keeps the restore
      screen reachable). **At the sweep:** `SetUserBanned(userID, true)` first (no new session can be minted while
      the purge runs), then `DeleteUser(userID)` as the last credential step. Deleting is **required, not
      optional**: it removes the last copy of the user's email (which we deliberately never stored), frees the
      address for a genuinely new signup, and — because a Supabase user id can then never recur — makes a swept
      account's `signup_bonus:<userID>` / `invite:<signupID>` dedup keys structurally unreachable even though their
      ledger rows are gone. Restore inside the window needs **no un-ban call at all**; `SetUserBanned(false)` exists
      for the operator-recoverable case where a sweep failed after banning. EXTEND job 89's promoted
      `platform/supabase` adapter with both methods (+ the `Fake`).

## Grounding

- Constitution ([I1]–[I13]): [00.overview](../plan/00.overview.md) §3 (_The constitution_), incl. the v2 risk
  register — **Epic K's [I1] row is this job's**. Most at risk here, each with its **structural** guard:
  - **[I1] "the system never deletes; only the user's own explicit deletion."** The hard delete has **no
    client-reachable trigger** — no `PurgeAccount` RPC and no "delete now" field, so bypassing the window is
    unrepresentable; the sweep reuses `release.soft_delete_retention_days` and the one `jobs` loop, so there is no
    second retention policy to drift; and T016's allowlist fails any future `DELETE` on a `user_id`-bearing product
    table that is not one of the two sweeps.

    chose to remove by withdrawing; no `UPDATE` touches a diary body anywhere in this job.
  - **[U1] per-user isolation** — every statement is `WHERE user_id = $1` and `pnpm lint:persistence` fails closed
    on a bare or `OR`-disjunct scope; the invite purge deletes only rows scoped by `invites.user_id` (inviter),
