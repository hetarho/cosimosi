## Acceptance Criteria (from changes/08.retire-the-named-palette-registry)

<!-- The source spec's acceptance criteria. After building, verify each is true in the running code. -->

- [ ] A1 A user's only stored color preference is `mood_colors`; `palette_preferences` does not exist in the schema, and a fresh `pnpm db:migrate` produces no such table.
- [ ] A2 `AccountService` exposes no palette-id RPC — `GetPalettePreference` and `SetPalettePreference`, their messages, and the generated Go/TS clients for them are gone; the three mood-color RPCs behave exactly as before.
- [ ] A3 `packages/emotion` exports no palette id, no palette registry, and no id-keyed lookup; a repository-wide search for `DEFAULT_PALETTE_ID`, `PALETTES`, `paletteById`, `paletteIds`, `resolvePaletteById`, `applyPalette`, `changePalette`, `readPalettePreference`, `paletteDisplayName` and `usePalettePreferenceStore` returns no hit in shipped code.
- [ ] A4 Signing in resolves the palette from `GetMoodColors` alone: the bootstrap issues no palette-preference request, still holds palette-dependent children until the colors are applied, and still falls back to the authored default when the read fails.
- [ ] A5 A mood with no stored row renders the authored default color, and a mood with a row renders that row's color — on web and mobile, unchanged from change 07.
- [ ] A6 Each mood still offers three recommendations with the same colors and the same ratio-or-silence rule as before this change; the alternative colors come from an authored table that no longer carries an id.
- [ ] A7 Signing out and into another account leaves no color from the previous account applied, with the reset driven by `resetMoodPalette()` rather than a palette-id session.
- [ ] A8 The per-mood editor is reachable from `/me` on web and mobile, from a slice named for what it does (`features/change-mood-colors`), and editing still applies live through the unchanged `setMoodPalette` seam with no `GetUniverse` refetch.
- [ ] A9 Withdrawal still purges `mood_colors` with the other account dependents, and the sweep's other deletions are unchanged.
- [ ] A10 No regression in the constitution: rendering remains palette-agnostic, the meaning layer and the brightness channel are untouched, the axis check remains warn-only, and the first-sign-in color screen and plan 80's take-once tour trigger keep their shape.
- [ ] A11 No orphan text: `spec/tech/emotion-model.md`, `spec/tech/account.md`, `spec/policy/ux/emotion-palette.md` and `spec/policy/ux/my-page.md` describe the per-mood-only model, the retired i18n keys (`settings_palette_selected`, `palette_name_cosimosi_default`, `palette_name_muted_dusk`) are removed from both locales, and plan 51 is updated to the as-built shape.
- [ ] A12 The gates are green: `pnpm gen` / `pnpm check:gen` clean after the proto change, Go build · vet · test pass, web build · lint pass, and the mobile source gate (typecheck · lint) passes.

**No tuning number moves.** This job adds and retunes nothing in `spec/values.yaml` — change 07's `palette.*` group
(`recommendation_count` · `stat_min_sample` · `hue_bucket_degrees` · `near_neutral_chroma_max` ·

a literal. If a task below is tempted to hardcode one, it is doing the wrong thing.

**The order is deliberate: the client stops consuming before the contract disappears.** Every step leaves the repo
building — FE first (the RPC still exists, just unused), then proto + Go, then the schema, then the docs. Deleting
proto first would break both apps mid-job.
