The web and mobile `UniverseCanvasWidget`s are a ~330-line duplicated fork of the same host logic, guard-invisible
(both files carry platform markers, so the promote-on-reuse comparison exempts them), and already drifted twice:
mobile still resolves picks through the graph — the exact optimistic-launch bug the web file documents having fixed
(R006) — and the two hosts disagreed on `antialias` while both mount PostFX (R007). **Built after jobs 136–137** so
the extraction carried their host-side fixes once instead of rebasing the fork twice.

## Acceptance Criteria (from code-review/12 — R006, R007)

- [x] A1 **The platform-pure host core exists once, in `packages/`.** The subscriptions, pick/navigation callbacks,
      sim-bridge wiring, latent-field generation, anchor resolution, and the composed scene layers live in one
      shared module consumed by both apps; each app's widget shrinks to a thin shell (canvas host + genuinely
      platform-different seams).
- [x] A2 **A just-launched star is pickable on mobile.** Mobile pick resolution goes through the entity stores
      (server truth + optimistic tail), matching the web's documented fix — tapping the newest star opens it before
      the next GetUniverse read. (R006.)
      — Structural: mobile has no pick-resolution code left to be wrong. `use-universe-scene.test.tsx` pins it —
      after the read lands with two rows, a launch appends a third to the store, and `focusMemory(2)` selects it while
      the projected graph still holds only two. Writing that test also surfaced why it had to be sequenced that way:
      seeding the store _before_ the read proves nothing, because `useUniverse` clears the mirrors while the query has
      no universe — the same clear that stops a signed-out read from leaving the previous user's data on screen.
- [x] A3 **`antialias` is decided once, with the rationale in code.** Both hosts make the same choice (expected:
      `antialias: false` with AA in the post chain, per the web comment that swapchain MSAA fights the post
      pipeline's resolve target) — or a native exception exists with a comment explaining why the tradeoff differs
      there. (R007.)
      — Native moved to `antialias: false`, matching web, with the reason in the code: both hosts mount `PostFX`, so
      the MSAA buffer native was asking for is one the composite never resolves from. No native exception is
      warranted — the platform least able to afford paying for AA twice is the one that was.
- [x] A4 **Genuinely platform-different seams remain forked and owned.** The hover/glimpse seam stays web-only; the
      worker-vs-inline sim spawner stays per-app; each remaining fork gets its own test, created in this job — the
      sim-spawner forks have none today (§3.5).
      — Both spawners now have one. Web's asserts the module-`type` option (a classic worker cannot import the ESM sim
      module) and the no-`Worker` fallback returning null rather than throwing at bridge construction. Native's
      asserts it declines _even when a `Worker` global exists_ — a polyfill or a test shim must not flip native onto a
      path its bridge cannot drive.
- [x] A5 **No behavior change beyond A2/A3.** Scene composition, navigation, palette/ornament behavior identical;
      `pnpm lint:fsd:layout` and the whole gate stay green.
      — The two widgets went from ~330 duplicated lines each to ~60 and ~50. Web keeps the DOM canvas host, the hover
      overlay and the Worker spawner; native keeps its surface, its null spawner and the two fidelity knobs
      (`latentStarCountMobile`, `fieldResolutionMobile`). The whole gate is green and `/demo` renders unchanged.
      One thing worth naming rather than leaving implicit: `lint:fsd:layout`'s normalized-equivalence pass still
      exempts these files (both carry platform markers), so it is **not** what keeps them thin now — the shared pair
      is. The exemption was never load-bearing in the direction one might hope; it is why the fork survived.

### T001 — the placement decision

`@cosimosi/universe-render` takes the core: it already owns the layer bindings and is the one package where domain and
visual vocabularies are allowed to meet (§3.4), which is exactly what the decoration→rendering translation is. The core
is a **pair**, not one module, and the split is forced rather than stylistic:

- **`useUniverseScene()`** must run OUTSIDE the canvas — React context does not cross the R3F reconciler, so anything
  reaching for the transport, the skin, or a machine has to be above it.
- **`<UniverseSceneLayers>`** renders INSIDE it and therefore takes everything as props.

Every host import was dispositioned by the declare-or-parameterize rule:

| import                       | outcome                                                                                      |
| ---------------------------- | -------------------------------------------------------------------------------------------- |
| `@cosimosi/universe`(+react) | already a dependency — imported directly                                                     |
| `@cosimosi/config`           | already a dependency                                                                         |
| `@cosimosi/emotion/react`    | already a dependency (`usePaletteVersion`)                                                   |
| `@cosimosi/force-sim`        | **declared** — node index + coordinate offsets are core work                                 |
| `@cosimosi/store`(+react)    | **declared** — the §3.4 decoration→rendering translation belongs in the core                 |
| `@cosimosi/state-machine`    | **declared** (+ `@xstate/react`, `xstate` dev) — the fallback navigation actor               |
| `@cosimosi/ui`               | **parameterized.** `reducedMotion` arrives as a boolean instead. `@cosimosi/ui` has a native |
|                              | fork and only a whole-barrel entry, so importing it to reach one hook would pull the entire  |
|                              | UI component surface into the rendering package for a preference read.                       |

The app-layer re-export shims (`features/launch-stars`, `features/change-mood-colors`, `shared/model`) were left alone:
still used by other slices, and the core reaches past them to the packages job 72 promoted them to.
