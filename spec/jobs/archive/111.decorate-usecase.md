## Acceptance Criteria (from plan/72.decorate-usecase)

<!-- The source spec's acceptance criteria. After building, verify each is true in the running code. -->

- [x] A1 `store.Service.Decorate` inserts the missing `ornament_ownerships` rows, upserts/deletes all three `ornament_selections` rows and debits Twinkle in **one transaction**; a failure at any step leaves no ownership row, no selection change and no ledger row. ([P8])
- [x] A2 The charged amount is the sum of the catalog prices of the ornaments the ownership insert **returned** inside that transaction. Two concurrent identical saves charge the full price exactly once and zero the second time, and `DecorateRequest` carries **no** amount, price or total field. ([P8][G7])
- [x] A3 Already-owned members of the selection cost nothing and re-selecting them writes **no** ledger row; a save that changes nothing is a successful no-op. ([P8])
- [x] A4 A purchase is paid from `GENERAL` only: `store`'s spend port has no tier field, `PlanSpend` returns `FromSmall: 0` for the purchase kind, and the ledger `CHECK` rejects `ornament_purchase` with a non-zero small draw. ([P9][G2a])
- [x] A5 Insufficient balance **refuses the whole save** with `STORE_INSUFFICIENT_TWINKLE` — a reason distinct from `TWINKLE_INSUFFICIENT` — carrying the blocking `ornament_id` and the `shortfall` as error metadata; nothing is bought, nothing is applied, nothing is deleted. ([P8][I1])
- [x] A6 An **unowned achievement-only** ornament in a save is refused with `STORE_ORNAMENT_NOT_PURCHASABLE` and is never purchasable at any price; the same ornament, once owned, is free to select. ([P11])
- [x] A7 An unknown ornament id, or an id whose kind does not match the field it arrived on, is refused with `STORE_ORNAMENT_UNKNOWN` before any write. ([P8])
- [x] A8 A purchase writes exactly **one** `ornament_purchase` earn/spend row per save, amount = the charged total, into the one append-only ledger; the balance stays derived from that ledger. ([G4][G7])
- [x] A9 The purchase spend is idempotent: a replay of the same save charges once, keyed by the newly-acquired ornament set, and no ownership is ever refunded, expired or re-purchased (the transaction surface exposes no ownership delete). ([P9])
- [x] A10 After the migration, `ornament_selections` is the **only** store of the chosen palette: `palette_preferences` is gone, its queries and its `account` read/write code are gone, and a user who had chosen a non-default palette in v1 still sees that palette after deploy. ([P10])
- [x] A11 `account.v1.SetPalettePreference` no longer exists on the wire; `account.v1.GetPalettePreference`† is unchanged for clients and is served by a read-through onto `store`'s published selection read. The shipped palette boot gate and its cache classification are untouched. ([P10])
- [x] A12 `account` contains no palette id, no default palette id and no registry allow-list after this unit; the color table remains solely `packages/emotion/src/registry.ts` and an `Ornament` row carries an id, never a color. ([I11][V10])
- [x] A13 The free default palette costs nothing and requires no purchase and no ownership row: an absent `ornament_selections` row **is** the default, and a selection row can never hold the default id. ([P10])
- [x] A14 `Decorate` reports achievement progress through a counter-only port whose payload is `(scope, tx, counterKey, delta)` — no memory id, strength, mood or text field exists on it — inside the same transaction, with a shipped no-op default. ([A2][A6][I11])
- [x] A15 `store` imports no other context and no other context imports `store`; the spend gate, the achievement recorder and the decorate store are consumer-owned interfaces bound in `apps/api/cmd/api/store.go`; the RPC handler contains no policy. (§2.2/§2.4/§2.9 #6/#7)
- [x] A16 Every new statement is scoped to the authenticated user, `pnpm lint:persistence` passes with no new `globalQueries`/`platformTables` entry, and no request message in `cosimosi.store.v1` carries a `user_id`. ([U1])

> **As-built deltas (all reflected into plan 72 and the SSOT docs).**
>
> - **T010–T013 (the palette cutover) were not implemented, because their subject no longer exists.** The named-palette
>   registry, both palette RPCs, `account.DefaultPaletteID`, `registryPaletteIDs`, `palette-ids.json` and
>   `change-palette.ts` were retired by change 08 / job 109, and `palette_preferences` was dropped in migration `00023`.
>   There is no second store to migrate, no read-through port to add and no FE write path to re-point. A10–A13 are
>   answered by that absence; A12 is verified (grep: `account` holds no palette id).
> - **No batched `INSERT … FROM unnest(…) RETURNING`** (T002). The persistence-isolation gate fail-closes on a
>   set-returning function in `FROM`; with at most one purchasable row per kind, a per-kind
>   `INSERT … ON CONFLICT DO NOTHING` read through `:execrows` carries the same "the insert is the authority" guarantee.
>   `decorate.sql` therefore holds only `DeleteOrnamentSelection`, and job 110's `InsertOrnamentOwnership` became
>   `:execrows`.
> - **`Decorate` lives in its own `decorate.go`**, same package as the reads.
> - **`ErrUnknownOrnamentID` is reused** rather than a new `ErrOrnamentUnknown` — one name per concept (§2.9 #1).
> - **A kind's default id normalizes to absence** in the request. The plan left an explicit default id writing a row,
>   which would have been a second representation of the default and a way to report progress for a save that changed
>   nothing.
> - **The withdrawal purger now takes the repository, not the service** (twinkle's shipped shape), because the store
>   service now needs the economy and the sweep needs neither the catalog nor the economy to delete rows.
>
> **Lands after [job 110](110.ornament-catalog-model.md)** (plan 71 owns the context, the catalog, the two tables and
> the published selection read). No new `spec/values.yaml` key: the two kind prices are job 110's and the spend keys are
> plan 65/66's.

## Review

- [x] Codex review (gpt-5.5, read-only) applied — 3 findings:
      **an explicitly submitted default id wrote an applied row and could farm achievement progress** (alternating the
      default id and an empty one looks like a change each time) → the request normalizes a default id to absence, and
      two tests pin it;
      **a refusal the economy raises without its arithmetic lost the item and the shortfall** → the typed refusal now
      carries the save's own `cost`, omits what the economy did not supply rather than reporting zeros, and names no
      item rather than guessing;
      **the ledger dedup namespace is shared with operator-supplied admin-grant ids**, so an operator who typed a grant
      id byte-identical to a computed purchase key would make one purchase free — **not fixed, deliberately**: that
      actor can already grant unlimited Twinkle (strictly the stronger capability), and namespacing the grant key
      retroactively would break the dedup of grants already written. Recorded in plan 72 as a known limit belonging to
      plan 66, which owns the ledger key semantics.
      `/code-review` is not model-invocable in this session; the diff was self-reviewed against the architecture
      self-audits instead.
