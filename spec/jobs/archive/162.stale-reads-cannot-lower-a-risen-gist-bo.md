## Acceptance Criteria (from code-review/15.full-codebase-runtime,-gate,-and-cross-p)

Finding: R004 (P2). `reconcileGistRiseState` keeps the seen stage monotonic
(`Math.max(previousStage, instance.stage)`, `GistStarLayer.tsx:138-141`) and refuses to re-arm the
ease for a non-rise — so the **animation** is guarded. The **position** is not: the frame mapper
composes the lift from the snapshot's own instance (`out[2] = liveZ + instance.zOffset`,
`GistStarLayer.tsx:199`, and the ease target at `:216`), and that `zOffset` is derived from that
read's possibly-stale stage (`zOffset: gistStageOffset(risen)`, `gist-star-channels.ts:91`).

Trace: a body settled at stage 2 (`seen = SETTLED`, `stageSeen = 2`) receives a refetch reporting
stage 1. Reconcile sets `stageSeen = max(2,1) = 2` and `continue`s, so `seen` stays `SETTLED`;
`byInstance` rebuilds as `SETTLED`; the mapper writes `liveZ + gistZOffset(1)`. The body drops from
stage 2's lift to stage 1's, with no ease, until a fresh read arrives. `softness` regresses the same
way (`gist-star-channels.ts:95`).

**As built — the invariant went upstream, not into the renderer.** T001/A4 planned to route the lift
and softness through the renderer's `stageSeen`. Two things pushed the fix up a layer instead:

- **Softness cannot be corrected after the fact.** It rides the geometry as an instance attribute
  that `InstancedNodeLayer` uploads in its own layout effect — and child effects run before the
  parent's, so `reconcileGistRiseState` always lands after the upload. Getting softness right means
  the snapshot must be built from the corrected stage, which happens during render.
- **Reading the floor during render is forbidden, correctly.** Feeding `stageSeen` into the
  projection from the memo trips `react-hooks/refs` ("Cannot access refs during render"), whose
  allowlist is a documented ratchet that may only shrink (`spec/plan/02.quality-gates.md` §Frontend and workspace
  checks). Adding a file to it to work around a
  lifecycle problem is the wrong direction.

So the one-way rule now lives in the episodic read-model store: `setAll` holds each memory's
`semanticStage` at its high-water mark, applied _before_ `sameStoredCollection`, so a response
differing only by a lower stage is recognized as no change and keeps the previous references. Every
consumer — the z lift, the softness, a detail surface's rung — is correct by construction, which is
what A4 asked for ("the single authority, not a second copy"), just one layer up. [C6a] is a domain
invariant, so the domain mirror is where it belongs (§3.4).

The renderer's existing `stageSeen` guard is kept unchanged: it still prevents an ease from
replaying, which is a separate concern from what is rendered.

**Considered and rejected:** a parallel `offsetByInstance` array built at reconcile time. It fixes
the z lift with no hot-path cost, but leaves softness (A3) unfixed for the reason above, and adds a
second authority the renderer has to keep in step.

**Follow-up left undone, deliberately:** `DemoUniverseScene`'s effect writes the staged scene into
these singletons with no cleanup, unlike the `/test` panel which clears on unmount. Harmless today —
`packages/demo/src/resolve.ts` resolves every memory at `semanticStage: 0`, so the floor is never
raised — but a demo that ever scripts a rise could not be replayed from the start. The constraint is
recorded in the store's comment. Not fixed here because the file sits beside unrelated in-flight work
and the risk is latent rather than live.

**T008:** the sibling layers reworked in the same batch (`AwakenNeuron`, `SpotlightDim`) carry no
monotonic guard over a snapshot field, so they do not share this shape. Nothing to fix there.

- [x] A1 A stale lower-stage read cannot move a risen gist body downward. After a body has settled at
      stage N, a snapshot reporting stage M < N renders it at stage N's lift — no drop, no ease
      downward, no teleport. This is [C6a]/[I10] holding on the rendered state, not only on the event.
- [x] A2 The same holds mid-rise: a lower-stage read arriving while a body is easing toward stage N
      does not retarget the ease downward or restart it.
- [x] A3 `softness` does not regress either. A body whose monotonic stage is N renders stage N's
      diffuse look, never a shallower stage's, for the same reason the lift must not regress ([V5]
      deepens with stage, and the stage is one-way).
- [x] A4 The monotonic stage is the **single** authority for what is rendered, not a second copy of
      it. `stageSeen` already holds the answer; the fix routes the lift and softness through it rather
      than introducing a parallel "effective stage" cache that could itself drift from `seen`/
      `byInstance`.
- [x] A5 Genuine rises are untouched: a first gist appearance eases up from offset 0, a deepening eases
      from the previous stage's lift, the bodies present at first hydration seed silently, and an empty
      advance still moves nothing (A8). The `[V8]` `onStageRise` seam still emits exactly one event per
      newly risen body, with the fresh stage.
- [x] A6 The projection stays pure and one-way (§3.4): `gist-star-channels.ts` gains no rendering
      vocabulary and no renderer state, and the visual layer still never writes back into the domain
      mirror.

- [x] T001 Decide where the monotonic stage resolves, and keep it one place (A4). The natural seam is
      `GistStarLayer`: `reconcileGistRiseState` already computes the monotonic value while it walks the
      snapshot, so it can record the effective stage per body alongside `seen`/`byInstance` in the same
      pass and in the same committed order. Resolving it inside `mapGistInstancePosition` instead would
      put a `Map` lookup back on the per-frame path that `byInstance` exists to remove — the comment at
      `GistStarLayer.tsx:59-64` explains why that indexing exists, so do not undo it.
- [x] T002 Carry the effective lift, not just the stage: `mapGistInstancePosition` needs
      `gistStageOffset(effectiveStage)` for both the settled branch (`:198-201`) and the ease target
      (`:216`). Keep `entry.startOffset` as-is — it is already the _previous_ stage's lift and is
      correct.
- [x] T003 Do the same for `softness` (A3). This channel is built in
      `createGistRenderSnapshot` (`GistStarLayer.tsx:97-107`) from `instance.softness`, which
      `gistStarInstances` derived from the stale stage — so the snapshot's channel arrays are built
      before the monotonic stage is known. Resolve the ordering deliberately: either pass the prior
      `stageSeen` into the snapshot build, or update the softness attribute during reconcile and mark it
      for upload. Whichever way, note it in a comment — this ordering is the subtle half of the fix.
- [x] T004 Check the pick path is unaffected: `gistSelectionAt` (`GistStarLayer.tsx:220-223`) returns
      the memory id and the stage. The id is what routes ([R8]) and carries no stage by design
      (`gist-star-channels.ts:42-46`), so a pick should stay on the snapshot's stage or move to the
      monotonic one — decide and state which, and confirm the server remains the authority for what a
      paid read actually returns.
- [x] T005 Add the A1 test in `packages/universe-render/src/GistStarLayer.test.tsx`: hydrate, rise to
      stage 2, let it settle, then reconcile a snapshot reporting stage 1 and assert the mapped z is
      still stage 2's lift (and that no rise event is emitted). This is the case the existing
      `'does not rise a body whose stage did not move'` test does **not** cover — that one uses an
      equal stage, so the `Math.max` guard is currently untested in the direction it was written for.
- [x] T006 [P] Add the A2 test (lower-stage read mid-rise does not retarget or restart the ease) and
      the A3 test (softness does not regress).
- [x] T007 [P] Add a test for the ordinary rise sequence (A5) if the existing coverage does not already
      pin it end to end — first appearance from offset 0, then a deepening from the previous lift, with
      one `onStageRise` event each.
- [x] T008 Check the sibling layers for the same shape before closing: `AwakenNeuron.tsx` and
      `SpotlightDim.tsx` were reworked in the same batch and both hold per-body lifecycle state against
      a refetched snapshot. If either derives a rendered value from a snapshot field that a monotonic
      guard also tracks, it has this bug too — fix it here or record it as out of scope with the reason.
