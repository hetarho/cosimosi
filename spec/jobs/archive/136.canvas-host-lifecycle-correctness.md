# Job 136: Canvas host lifecycle correctness (refactor)

> Implementation work doc. Source spec: [code-review/12.frontend-rendering-performance-audit](../../code-review/12.frontend-rendering-performance-audit.md).

Fixes the review's two P1s — the two canvas hosts made **opposite** lifecycle mistakes around the same
R3F-doesn't-know-WebGPU gap: the native host tears the device down on every re-render (R001), the web host never
tears it down at all (R002). **Built after job 139, before jobs 137/138**: the renderer bump established the
visual/test baseline, and the two later jobs touch the same host files.

## Acceptance Criteria (from code-review/12 — R001, R002)

- [x] A1 **A native host re-render never touches the WebGPU device.** With the scene mounted, a re-render of the
      composing widget (new `children` identity — e.g. a sweep-clock sample, a GetUniverse refetch, `useIsFocused`
      flipping, a mood pick) results in `root.render(children)` only: the same `WebGPURenderer` instance survives,
      `dispose()` is not called, no re-`init()` runs. (R001.)
- [x] A2 **Native DPR/backing-size, camera, tone-mapping, exposure, and clear-color changes hot-apply without
      teardown.** A DPR step resizes the live backing store/R3F root in place; `fov`/`far` reconfigure the live
      camera; tone/exposure mirror the web host's hot-apply pattern (`UniverseCanvas.tsx:78-83`), while native
      clear-color uses `renderer.setClearColor` in the new live-config effect (web currently sets clear only in its
      one-time `gl` factory). Genuinely device-shaped inputs (`forceWebGL`) may still rebuild, but only those, and
      the rebuild path stays leak-free (dispose-then-recreate exactly once).
- [x] A3 **The web host disposes its `WebGPURenderer` on unmount.** Unmounting a `<UniverseCanvas>` (route change,
      panel close) calls `renderer.dispose()` exactly once; a mount→unmount→mount cycle does not accumulate devices
      and produces no WebGPU validation errors. (R002 — R3F's own unmount path calls WebGL-shaped methods
      (`renderLists?.dispose()` / `forceContextLoss()`) that do not exist on `WebGPURenderer`, so our host must own
      this.)
- [x] A4 **The fork owns its test (§3.5).** The native host has a lifecycle test asserting: re-render with new
      children → same renderer, no dispose; unmount → dispose exactly once. The web host has the mirror test for
      dispose-on-unmount. Both survive StrictMode-style double-invoke where the platform runs it.
      — Both tests live in the package's own **vitest** arm (`src/canvas/*.test.tsx`, per-file
      `@vitest-environment jsdom`), not the mobile Jest arm: that arm's `moduleNameMapper` stubs the entire
      `@cosimosi/3d-renderer` package so Jest never loads `three`'s ESM, which means it structurally cannot see the
      native host. Reaching past the package's public entry from `apps/mobile` would break the boundary lint instead.
      `react-native`, `react-native-webgpu` and `three/webgpu` are mocked per file — upstream's shipped
      `react-native-webgpu` mock is not used, because these tests need the surface shim to report `clientWidth`/
      `clientHeight` and a working `getContext`, where the upstream mock deliberately returns `null` and throws. Adding
      `jsdom` · `@testing-library/react` · `react-dom` as devDependencies mirrors `packages/ui`'s existing setup; the
      package's other 10 test files keep the default node environment untouched. `apps/mobile/jest.guards.js` stays
      quiet (mobile jest is unchanged).
- [x] A5 **No behavior or visual change otherwise.** Scene output identical (headless CDP screenshot parity on web);
      all gates green (`pnpm check`).

### What the split turned up

Reading the two hosts against R3F's and three's actual code — rather than against their prop signatures — found three
bugs the review had not named, all of them consequences of the same R001/R002 root cause:

1. **The native DPR cap never applied.** The host hand-wrote `canvas.width = clientWidth * pixelRatio` and then pinned
   R3F's `dpr` to 1 "so it renders 1:1 into that already-scaled buffer". It does not: R3F's store subscription answers
   the first `setSize` with `gl.setPixelRatio(1)` + `gl.setSize(...)`, and three's `CanvasTarget.setSize` recomputes
   `canvas.width = floor(width × _pixelRatio)` — overwriting the hand-scaling every time. The cap now goes through
   `dpr` on the root, which is the seam that survives.
2. **`configure` cannot move the camera.** Its camera block is guarded on `state.camera === lastCamera`, false once a
   camera exists, so `fov`/`far` handed to a second `configure` are dropped in silence. Live camera changes now write
   to the camera captured through `onCreated`.
3. **A device rebuild left the old root's renderer in place.** `createRoot(canvas)` reuses `_roots.get(canvas)`'s store
   when one exists, and `configure` only runs the `gl` factory `if (!state.gl)`. The old teardown deletes that entry on
   a 500 ms timer, so a rebuild inside that window would have reused the renderer it had just disposed. It is survivable
   only because `getContext()` mints a fresh `GPUCanvasContext` — and a fresh canvas object — per call, which also means
   the old effect leaked one native surface context per prop change.

## Implementation Checklist

- [x] T001 `packages/3d-renderer/src/canvas/UniverseCanvas.native.tsx`: split the single effect
      (`:47-109`, deps `[children, dpr, fov, far, clearColor, forceWebGL, toneMapping, exposure]`) into
      (a) a **mount/device effect** — `getContext`, initial backing-store sizing, `createRoot(canvas)`,
      `configure({...})`, with cleanup (`unmountComponentAtNode` + `renderer.dispose()`) keyed **only** on inputs
      that genuinely require a new device (`forceWebGL`; keep the list minimal and comment why each is there);
      (b) a **children effect** — `root.current?.render(children)` keyed `[children]`, no cleanup;
      (c) a **live-config effect** — resolve `PixelRatio`/`dpr` to a number, resize `canvas.width`/`height`, update
      the existing root's size/camera (`fov`/`far`) through the supported configure/state seam, and write
      `toneMapping`/`exposure`/`clearColor` onto the live renderer. None of these changes may enter the device
      effect's dependency key. Update the `:46` comment ("memoize nothing here") to describe the new split.
- [x] T002 [P] `apps/mobile/src/widgets/universe-canvas/ui/UniverseCanvasWidget.tsx:263`: stop passing a fresh
