- [x] A2 `AccountService` exposes no palette-id RPC — `GetPalettePreference` and `SetPalettePreference`, their messages, and the generated Go/TS clients for them are gone; the three mood-color RPCs behave exactly as before.
- [x] A3 `packages/emotion` exports no palette id, no palette registry, and no id-keyed lookup; a repository-wide search for `DEFAULT_PALETTE_ID`, `PALETTES`, `paletteById`, `paletteIds`, `resolvePaletteById`, `applyPalette`, `changePalette`, `readPalettePreference`, `paletteDisplayName` and `usePalettePreferenceStore` returns no hit in shipped code.

- [x] A5 A mood with no stored row renders the authored default color, and a mood with a row renders that row's color — on web and mobile, unchanged from change 07.
- [x] A6 Each mood still offers three recommendations with the same colors and the same ratio-or-silence rule as before this change; the alternative colors come from an authored table that no longer carries an id.
- [x] A7 Signing out and into another account leaves no color from the previous account applied, with the reset driven by `resetMoodPalette()` rather than a palette-id session.
- [x] A8 The per-mood editor is reachable from `/me` on web and mobile, from a slice named for what it does (`features/change-mood-colors`), and editing still applies live through the unchanged `setMoodPalette` seam with no `GetUniverse` refetch.
- [x] A9 Withdrawal still purges `mood_colors` with the other account dependents, and the sweep's other deletions are unchanged.
- [x] A10 No regression in the constitution: rendering remains palette-agnostic, the meaning layer and the brightness channel are untouched, the axis check remains warn-only, and the first-sign-in color screen and plan 80's take-once tour trigger keep their shape.
