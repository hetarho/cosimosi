The runner calls `queue.Fail` from three places and `maintenanceQueue.Fail` cannot tell them apart —
it sees only `Fail(ctx, job, nextAttempts)`:

| Call site                            | Meaning                                | Should the retry-forever override apply? |
| ------------------------------------ | -------------------------------------- | ---------------------------------------- |
| `runner.go:200-206` (attempts spent) | policy dead-letter                     | **Yes** — this is the one it means       |
| `runner.go:134-144` (claim ceiling)  | hard loop-breaker (OOM/SIGKILL signal) | **No** — it is the only kill-loop guard  |
| `runner.go:146-157` (unhandled kind) | misconfiguration                       | **No** — retrying cannot grow a handler  |

So for `retention_sweep`, `withdrawal_sweep` and `achievement_settle` (`types.go:55-57`),
`job_max_claims: 20` — `values.yaml`'s "Hard loop-breaker" — is silently inert, and the runner logs
`"job %s dead-lettered after %d claims"` for a job it just rescheduled 60s out.

**T001 as decided: no new state, and no new tuning value.** The existing terminal state already
satisfies the containment requirement — `status = 'failed'` keeps the row (so nothing is deleted and
[I1] holds), is visible through the job-health aggregate `CountJobsByStatus` already feeds, and is
requeueable by an operator. What was missing was not a state but the _transition_: the runner's two
safety stops were being rewritten into a retry. So `DeadLetter` was added to the queue port as a
transition distinct from `Fail`, the pg adapter implements it as the same terminal write, and
`maintenanceQueue` deliberately does not declare it — the embedded queue answers it, which is what
makes the override impossible to re-widen by accident.

**Discovered while building, filed rather than fixed here:** `CountDeadLetteredJobs` counts
`status = 'failed' AND attempts >= max_attempts`, but a claim-ceiling stop carries the job's real
(low) attempts. So a ceiling dead-letter lands in the generic `Failed` bucket and never in the
`DeadLettered` one — true before this job for ordinary kinds too, and still true after. It is an
admin-metric contract question rather than a queue-correctness one, and inventing an attempts value
to satisfy the metric would put a false number in the row. Worth its own decision.

- [x] A1 A claim-ceiling breach on a retried-indefinitely kind is **contained**: the job does not
      return to `pending` at the base backoff to be re-claimed on the next cycle. Whatever containment
      T001 chooses (park / quarantine / long geometric backoff), a poisoned `withdrawal_sweep` can no
      longer occupy the queue head on a 60-second loop forever.
- [x] A2 A retried-indefinitely job is still never dropped by the **policy** path: exhausting
      `job_max_attempts` still retries it rather than marking it `failed`. The reason that rule exists
      — each of the three kinds is the only durable trigger for something the user cannot ask for a
      second time — is preserved exactly.
- [x] A3 An **unhandled kind** is no longer converted into an endless retry. A job whose kind has no
      registered handler reaches a terminal state (or the same containment as A1), so a
      misconfiguration surfaces instead of looping.
- [x] A4 Every log line reports what the queue actually did, not what the runner intended. Nothing
      logs `dead-lettered` for a job that was rescheduled, and nothing logs `failed` for a job that
      was retried — the two lines at `runner.go:142` and `runner.go:156` are the current offenders.
- [x] A5 The transitions are distinguishable **at the port**, not inferred from arguments: the queue
      interface expresses "policy dead-letter" and "safety dead-letter" as separate operations, so a
      wrapper cannot accidentally override both again. Ports stay consumer-declared (§2.4 — the
      runner is the consumer, so the interface belongs in `jobqueue`).
- [x] A6 A nil or empty-kind handler in `NewJobRunner`'s `extraHandlers` no longer registers silently.
      Today a duplicate kind returns `ErrDuplicateJobHandler` while a nil handler for a real kind is
      skipped by `continue` (`worker.go:101-112`), producing a worker that never processes that kind —
      the asymmetry cuts against §4 _Gates fail loudly_. Either reject it or document the lenient
      branch as deliberate with the caller that needs it. **As built: rejected.** A new sentinel
      `ErrInvalidJobHandler` is returned, with the empty/nil check moved AHEAD of the duplicate check so
      a malformed entry can never be silently skipped. Both layers deliberately keep a check —
      `jobqueue.NewRunner` still filters nil handlers downstream — because a skip at either one alone
      would be invisible at the other; the comment at the call site says so.
- [x] A7 No behavior change for the ordinary path: `embed`, `semanticize` and `consolidate` keep
      today's attempts/backoff/dead-letter behavior exactly, and the bounded terminal-job cleanup that
      rides `ClaimDue` (`worker.go:146-188`) is untouched.

- [x] T001 **Decide the containment behaviour first** — this is the open call flagged in the report's
      Questions #1, and it shapes every step below. For a claim-ceiling breach on a retried-indefinitely
      kind, "never drop it" and "always break a kill-loop" genuinely conflict. Options: park the job in
      a distinct non-`pending` state that an operator/admin surface can see and requeue; quarantine it
      and alert; or back off geometrically to a long ceiling so the loop survives but stops starving
      the queue. Choose with the ops surface in mind — `admin`'s `JobHealthReader` already publishes
      queue aggregates, so a parked state that is invisible there is only half a fix. Record the
      decision and its reasoning in the code.
- [x] T002 Split the port in `apps/api/internal/platform/jobqueue/runner.go`: keep `Fail` meaning
      "attempts exhausted — the policy dead-letter", and add a distinct operation for the safety
      transitions (e.g. `DeadLetter(ctx, job, cause DeadLetterCause) error` with causes
      `ClaimCeiling` / `UnhandledKind`). Consumer-declared, in the `Queue[J]` interface the runner
      already owns.
- [x] T003 Point the two safety call sites at the new operation: the claim-ceiling branch
      (`runner.go:134-144`) and the unhandled-kind branch (`runner.go:146-157`). Leave
