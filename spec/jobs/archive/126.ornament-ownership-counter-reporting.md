# Job 126: Ornament ownership counter reporting (refactor)

> Implementation work doc. Source spec: [code-review/10.jobs-94-115-achievement,-decorate-and-sh](../../code-review/10.jobs-94-115-achievement,-decorate-and-sh.md).
> /cosimosi:implement-job 126 builds it via the two checklists below. When done, reflect the result into the
> SSOT (plan/policy/values) and set status: done. Write it in English.

Covers **R007** (P3) — the mirror image of job 122's hole: a cross-context **report** that no path drives.

`store.GrantOwnership` (`apps/api/internal/store/service.go:143-167`) is the shared entry point for both ownership
legs — its own comment says so at line 135: _"Both legs land here — the purchase and the achievement reward"_ — and it
reports **no** achievement counter. The only `ornament_owned` producer is the decorate path
(`decorate.go:345`, reporting `len(ownedIDs)+len(acquired)`, and only when `len(changedKinds) > 0` per
`decorate.go:339-341`). So claiming `star_500` or `shared_neuron_8` — the two ornament capstones at
`achievement/catalog.go:83,107` — grows ownership without moving the counter that `ornament_3` / `ornament_8` /
`ornament_15` (`catalog.go:118-120`) read.

This is **bounded and self-healing, not wrong**: `ornament_owned` is a reach counter (`counters.go:131`), so the next
decoration save that changes something reports the true total and `GREATEST` catches up. But a user who claims a
capstone and never re-decorates sits below the ownership tier they have actually reached, and the delay is invisible.
`decorate.go:326-331` already documents an accepted one-save lag for concurrent saves; this second, longer-lived lag is
documented nowhere.

**Direction: report from the grant path.** Review 10 prefers it and the reason is structural — the counter is a
high-water mark, so an extra report can only ever be correct or a no-op. The documented-lag alternative stays available
as the fallback under one condition, stated at T002.

The shape this requires is worth knowing before starting: `GrantOwnership` runs **outside any transaction** today
(it calls `s.ownerships.InsertOrnamentOwnership` directly), while `AchievementRecorder.RecordProgress` takes an open
`EconomyTx`. Since `EconomyTx` is `any` (`ports.go:51`) and `DecorateTx` embeds `OwnershipStore`, wrapping the grant in
the existing `InDecorateTx` gives one transaction that can both insert and count — no new port and no new repo method.

Decisions taken while building:

- **T002 — report-from-grant was taken, not the documented-lag fallback.** Nothing forced the fallback: `EconomyTx` is
  `any` and `DecorateTx` already embeds `OwnershipStore`, so wrapping the grant in `InDecorateTx` needed no new port
  and no new repo method.
- **T003 — `record` did not fit, so the shared half was extracted.** `record` early-returns on
  `len(changedKinds) == 0`, and a grant changes no selection, so calling it would have reported nothing.
  `recordOwnershipTotal` is now the one ownership report both legs make — shared rather than duplicated because the
  two must agree that the value is a TOTAL; a delta from one and a total from the other would make the tiers
  unreachable or reachable twice.
- **T005/A8 — a report failure fails the whole grant.** The other direction loses a fact nothing re-derives (counters
  only move forward and only a later decoration save would repair it, which is the very lag this job closes). Failing
  is recoverable: the claim wraps a granter error as a retryable refusal, and job 122's drain replays the idempotent
  grant. Pinned by `TestGrantOwnershipRollsBackWhenTheCounterReportFails`.
- **The wiring check is ordered after the caller-fault guards**, so a bad argument still reads as a bad argument.
- **Both worker roots gained the store↔achievement late binding.** A grant now reports, so a root that bound a
  refusing recorder would make the settle drain fail forever on an ornament reward. `cmd/worker` and `cmd/api`'s dev
  worker both close the cycle the API root already closed, and both bind `Decorate` (the grant's transaction runner)
  while leaving `Spend` unbound — the drain never charges.
- **T008's integration test was proved to bite**: with the report removed it reports
  `ornament_owned = 0, want 1 with no decoration save in between`.
- `pnpm lint:comments` caught the first draft of the residual-lag note ("used to be") — rewritten to state what is true
  now rather than what changed.
