- [x] A1 `/diary` (web) and the diary-reader screen (mobile) offer a **two-option view toggle** (목록 / 달력) that swaps the list for a month calendar **within the same page** — no new route, no new screen, and the deletion mount plus the star-detail deep-link consumer stay mounted across the switch ([D12]).
- [x] A2 The calendar renders a **month grid** of 4–6 weeks × 7 days for the displayed month, with leading/trailing cells from the adjacent months, and marks **every day the user wrote on** ([D12]).
- [x] A3 A marked day whose diaries hold at least one live `EpisodicMemory` is marked with **that day's representative mood color**, computed as the **top slice of `toEmotionSlices`** over the day's `(mood, weight)` rows — inheriting its `weight desc, mood.localeCompare` tie-break and drop-≤0 normalization ([D12][M4]).
- [x] A4 A day that was **written but holds no live mood** (launched nothing, or all memories let go) is marked with a **neutral outline**, never `NEUTRAL`'s color; it is still distinguishable from an unwritten day ([M3][I1][X4]).
- [x] A5 **No color crosses the wire.** The consumed DTO carries `mood` names and weights only; every hue in the calendar comes from `moodColor`, and swapping the palette recolors the calendar with no code change ([M3][M6][I3]).
- [x] A6 The `weight` is **consumed, never recomputed**: the calendar applies no `EffectiveStrength`, no decay and no aggregation beyond `toEmotionSlices`' normalization ([M4][V3]).
- [x] A7 **Selecting a marked day** applies the date-range filter `{from: date, to: date}` and switches to the list view, so a day holding several diaries shows all of them ([D12][D8]); an unwritten cell is inert and exposes no control.
- [x] A8 Entering the calendar, stepping months and selecting a day **spend no Twinkle and advance no universe time**; the consumed read is `NO_SIDE_EFFECTS`, carries no `SpendGate` and no clock port, and the calendar exposes **no action-injection prop** through which a paid affordance could be mounted ([D11][T3][G4]).

- [x] A11 **Dates never pass through a `Date` UTC conversion**: the grid and the mark lookup operate on `YYYY-MM-DD` strings and integer `(y, m, d)` arithmetic, so no mark shifts a day for a user in a negative UTC offset ([W5]).
- [x] A12 A month is rendered **only when fully paged** (`next_page_token` empty); a partially loaded month shows the loading state rather than a representative computed from an incomplete row set.
- [x] A13 **On web the view and month are URL-backed** (`view`, `month` on the `/diary` `validateSearch` schema, injected as props — the page and widget never import the router); **on mobile both are screen-local state**. Mounting the calendar adds no history entry; stepping does.

- [x] A15 Letting go, releasing and restoring **invalidate the calendar key** (`use-let-go.ts`, `use-release.ts`, `use-restore.ts`); there is **no polling** and no interval refetch anywhere in this unit (§3.2).

## As-built findings that shape this job (verified 2026-07-28, after jobs 105/106 shipped)

The plan was written before [job 105](archive/105.diary-search-and-filter.md) / [job 106](archive/106.diary-list-completion.md)
landed. Four things it describes as "[68]'s, consumed here" turn out to be **partly unbuilt**, and one is **already
built**, so the checklist below is written against the tree rather than against the plan's prose.

1. **The RPC and its Go read are complete.** `GetDiaryCalendar` exists end to end — `proto/cosimosi/memory/v1/memory.proto`
   (`NO_SIDE_EFFECTS`, `GetDiaryCalendarRequest{from,to,page_token}` → `GetDiaryCalendarResponse{days,next_page_token}`,
   `DiaryDayDto{diary_date,moods}`, `DiaryDayMoodDto{mood,weight}`), `apps/api/internal/memory/calendar.go`, and
   `apps/api/internal/memory/rpc/server.go`. **No proto, SQL, migration or Go change belongs to this job.**
2. **The plan's consumption rule 1 already holds server-side** — `calendar.go` builds every returned day with
   `Moods: make([]DiaryDayMood, 0)`, so a written day that launched nothing or was fully let go arrives with an
   **empty** `moods` list rather than being absent. A2/A4 are therefore satisfiable without touching the read.
   The weight is `EffectiveStrength(BaseStrength, RecallCount)` summed per `(day, mood)`, server-side — A6's
   "consumed, never recomputed" is a rule about the client only.
3. **The http-policy classification is already registered.** `packages/client-cache/src/http-policy.ts` line ~141
   carries `MemoryService.method.getDiaryCalendar → userScopedUnaryReadPolicy` inside `memoryRpcCachePolicies`.
   This job **must not add a second entry** — `createRpcCachePolicyInterceptor` throws
   `"… has more than one RPC cache policy"` at composition time, which is the structural guard behind A8.
4. **The FE mirror and the query factory do NOT exist yet.** `packages/api-client/src/memory.ts` re-exports the
   generated calendar _types_ but has no `createGetDiaryCalendar*QueryOptions`/`*QueryKey`; `packages/memory/src/diary.ts`
   has **no `DiaryDayMood` mirror and no `diaryDaysFromDtos` mapper**. The plan lists the `DiaryDayMood` _noun_ as
   [68]'s (true — the Go type and the wire message are 68's), but the **TypeScript mirror is unbuilt**, so it is
   created here beside `diariesFromDtos`, its shipped precedent. This is the only place the job widens the plan's
   stated scope, and it widens no contract.
5. **The steiger diary-reader block already exists** (`apps/web/steiger.config.js`, the "diary-reader vertical"
   entry listing `entities/diary`, `features/read-diary-list`, `features/search-diary`,
   `features/recall-diary-stars`, `widgets/diary-reader`). A17's "scoped block registered" is satisfied by
   **extending that block** with `widgets/diary-calendar`, not by appending a second block — the calendar is the same
   vertical, and a duplicate scope would say otherwise.

**One consequence the plan leaves open, decided here: the month query's range is the displayed month only**
(`YYYY-MM-01` … that month's last day), never the full 4–6 week grid span. Two reasons, both forced rather than
chosen: `diary_reader.calendar_month_page_size` is `31` and its values comment states its purpose — "31 keeps every
civil month in one server-owned page" — so a grid-span request (up to 42 days) would guarantee a second round trip
and put A12's fully-paged rule on the hot path for every month; and A2 scopes the marks to "the displayed month",
with leading/trailing cells present for grid shape. **Out-of-month cells therefore render unmarked and visually
recessed, and are inert** — the same inert treatment as an unwritten day (A7).

## Grounding

- Constitution ([I1]–[I13]): [00.overview](../plan/00.overview.md) §3 (_The constitution_). At risk here, each with the
  **structural** guard rather than a runtime check:
  - **[T3]/[D11]** a read never advances the clock — `GetDiaryCalendar` carries no `SpendGate` and no clock port
    (`calendar.go` takes neither), and `DiaryCalendar` exposes **no action-injection prop**, unlike `DiaryList`'s
    `renderActions`. There is no slot a paid affordance could be mounted through.
  - **[D10]/[G1]** forgetting is not undone for free — the calendar's DTO has **no text field of any kind**
    (`DiaryDayDto{diary_date, moods}`), so a snippet or a highlighter is unrepresentable here, not merely forbidden.
  - **[M3]/[M6]/[I3]** color is emotion, from one entry point — the wire carries `mood` names only; the widget holds no
    mood→color literal and resolves every hue through `moodColor`; the no-live-mood cell uses a **border token**, so
    `NEUTRAL`'s hue can never stand in for "unknown".
  - **[I1]/[I2]** nothing is deleted and the original is untouched — a released diary loses its mark through [68]'s
    `release_groups` anti-join and regains it on Restore, because exclusion is not a copied flag; an all-let-go day
    keeps its mark (the outline), because the day _was_ written.
- Architecture (placement): [ARCHITECTURE.md](../ARCHITECTURE.md) — **§3.1** (six layers, one-way imports; `widgets` =
  a self-contained block a page drops in; segments by technical role, never `components/`), **§3.2** (control state in
  XState, server truth in TanStack Query with **invalidation only, no polling** — this unit declares **no machine**),
  **§3.4** (the one-way domain→visual projection: the calendar speaks `Mood`, color exists only at the render edge),
  **§3.5** (pure cross-app code lives in `packages/`), **§2.7** (unary only; every `NO_SIDE_EFFECTS` method classified

## Deviations from this checklist, and why

Three places where the tree forced a different answer than the checklist wrote. All are reflected in
[plan/70](../plan/70.diary-calendar-view.md); none widens a contract.

1. **T011/T012/A17 — the slice is `features/diary-calendar`, not `widgets/diary-calendar`.** T013 correctly puts the
   toggle and the view branch in `widgets/diary-reader/ui/DiaryReaderBlock.tsx` (that is where the header, restore
   section and deep-link consumer are as-built). But a `widgets/diary-calendar` would then have to be imported by
   `widgets/diary-reader`, and FSD forbids same-layer cross-import — `eslint-plugin-boundaries` allows
   `widgets → features` only, and the sanctioned same-layer exception is `entities`↔`entities` via `@x`. The list view's
   own slice is already `features/read-diary-list`, and the calendar is its peer (the second shape of the same archive),
   so `features/diary-calendar` is both legal and consistent. Slice name, shared pure module and ui-only fork unchanged;
   steiger + boundaries + `lint:fsd:layout` all green.
2. **T002 — the FE mirror is nested, not a flat triple.** The checklist specified
   `DiaryDayMood { diaryDate, mood, weight }` with `diaryDaysFromDtos` flattening into it. A flat list cannot represent a
   **written day with an empty `moods` list**: it contributes zero rows and becomes indistinguishable from a day never
   written — exactly the distinction A2/A4 rest on. Shipped as `DiaryDay { diaryDate, moods: DiaryDayMood[] }` +
   `DiaryDayMood { mood, weight }`, which is also the faithful mirror of [68]'s two Go types, and `monthMarks` takes
   `readonly DiaryDay[]`.
3. **T003 — three exports beyond the stated four.** `stepMonth`, `monthDateRange` and `resolveCalendarMonth` joined the
   pure module because the hook needs the month's range (T006) and the grid needs prev/next stepping (T020) and the
   initial month (T019). Deriving those in the hook or the widget would duplicate `daysInMonth` + month wrapping outside
   the module that owns the integer-date arithmetic, and would create a second site where a `new Date` parse could creep
   back in against A11. All three are covered by `diary-calendar.test.ts`.
