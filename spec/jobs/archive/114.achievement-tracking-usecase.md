## Acceptance Criteria (from plan/75.achievement-tracking-usecase)

<!-- The source spec's acceptance criteria. After building, verify each is true in the running code. -->

- [x] A1 Every producing context declares its own `AchievementRecorder` port whose only payload is `(scope, tx, counterKey, delta)` and whose only return is `error`; no signature on the path carries a memory id, name, mood, strength, stage, text, or timestamp, and no return value can flow back into the producing write. ([A6][I11])
- [x] A2 The recorder is called from exactly these sites, each inside the transaction that produced the fact: `memory.PersistEncoded`, `memory.Recall`, `memory.RecallDiaryStars`, `memory.ViewSemantic`, `memory.Release` (the 놓아주기/soft-delete path — never `LetGo`, which seals neurons and releases nothing), `store.Decorate`, and `account`'s invite settlement (`ResolveInviteSettlement`). A rolled-back action advances no counter. (§2.8)
- [x] A3 Every key this unit emits is a member of [74.achievement-catalog-model](74.achievement-catalog-model.md)'s closed 16-counter vocabulary and is exported as a constant by its producing context; no producer invents a key, and no family member is built from anything but a closed enum in the producing context. ([A2])
- [x] A4 `cmd/api` refuses to boot when the union of the producers' emitted keys differs in either direction from the keys the catalog reads, and when any catalog reward names an ornament id absent from `store`'s catalog. ([A2][A3])
- [x] A5 A past-dated diary that launches no `EpisodicMemory` advances **no** counter — the recorder call sits after the monotonic launch guard, where the write-earn grant already sits. ([I10][T1][G6])
- [x] A6 `decay_recovered` is emitted at the recall moment from the pre-recall decay stage of the same anchor snapshot the spend is priced from, and only the resulting count (never the stage) crosses the port. ([A2] 망각·회복)
- [x] A7 `RecordProgress` refuses a non-positive delta, writes the counter through 74's `TouchCounter`/`AddCounter`/ `RaiseCounter` primitives, marks each candidate whose target the counter now meets via 74's `MarkAchieved` (`ON CONFLICT DO NOTHING`), and `achieved_at` is stamped by Postgres `now()` exactly once, never overwritten; **no `progress` column exists and this unit adds no SQL statement**. ([A2])
- [x] A8 `achievement` holds **no time source**: `AchievementServiceDeps` has no `Now` field, condition evaluation reads only `(progress, threshold)`, and no streak or real-time condition can be expressed. ([A1a])
- [x] A9 `achievement` reads and writes **only its own two tables** (`achievement_counters` · `achievement_progress`, through 74's store) — it queries no `diaries`, `episodic_memories`, `neuron_activations`, `synapses`, `twinkle_ledger_entries` or `ornament_ownerships` table, and imports no other context. (§2.2)
- [x] A10 A met condition pays nothing: the reward is credited only by an explicit `ClaimAchievement` call, which stamps `claimed_at` before any credit. An unachieved or unknown achievement is refused with nothing written. ([A4])
- [x] A11 Claiming twice credits once: `claimed_at` is set under the `(user_id, achievement_id)` uniqueness, both payout legs are idempotent on the derived claim id (`achievement:<claimID>` in the ledger, `ON CONFLICT DO NOTHING` on ownership), and a repeat claim replays the same result instead of refusing — so a crash between the claim and the payout heals and no reward is lost or doubled. ([A4][G7])
- [x] A12 The reward is **exactly one leg** — `GENERAL` Twinkle or, rarely, an ornament, never both (74's XOR `Reward`); **`SMALL` is unrepresentable** — no reward type, port, or proto field carries a `TwinkleKind`, and the earn path credits general only. ([A3])
- [x] A13 A claim's credit is an ordinary append-only ledger entry with reason `achievement_claim`, visible in the `/me` stardust history; this unit adds no `EntryReason`, no ledger DDL, and no second ledger. ([G3][G7])
- [x] A14 A claim changes no star's position, strength, emotion, forgetting state or gist stage, and deletes nothing — the only rows written are `achievement_progress`, one ledger entry, and at most one ownership row. ([A6][I11][I1])
- [x] A15 `ClaimAchievementRequest` carries no `user_id`, no amount and no counter; every read and write is scoped to the authenticated user; `pnpm lint:persistence` passes with no new allowlist entry; the handler contains no policy. ([U1], §2.9#7)
- [x] A16 Production fails to boot with any recorder or granter unbound; the no-op recorder is reachable from tests only.

**The producer ports (one per producing context; `achievement` imports none of them)**

- [x] T001 `apps/api/internal/memory/ports.go` — `AchievementRecorder.RecordProgress(ctx, scope, tx EconomyTx,
counterKey string, delta int) error` + a `NoAchievementRecorder` no-op for tests. Four properties are the point:
      the payload **cannot describe a memory** (no id, name, mood, strength, stage, text or date), the return is
      `error` alone (so an achievement outcome cannot influence the transaction that produced the fact — which is what
      makes plan 76's notice a _read_), the producer **reduces before it reports** (every meaning-layer measurement is
      compared against its threshold inside the producing context and crosses as a count), and **a recorder error aborts
      the causing transaction** — deliberate, because the pre-recall decay depth is unrecoverable afterwards, so a
      silently diverging counter would be unfixable. Do not copy `NoEarnOnWrite`'s silent-nothing into production.
- [x] T002 [P] The twin port on `store` (identical, with `store.EconomyTx` — job 111 already declares it) and on
      `account` (tx as bare `any`, so this job introduces no new exported type name there).

**The `memory` call sites — every counter, at the point the fact becomes true**

- [x] T003 `memory/launch.go` `PersistEncoded`, emitted **after** the monotonic launch guard at the same point as the
      shipped `EarnPort.OnDiaryLaunched` — a past-dated diary is saved and counts nothing: `diary_written` +1,
      `episodic_memory_launched` +the launched row count, `neuron_shared` +1 per neuron reaching its **2nd** activation,
      `neuron_share_depth` = the most memories now sharing one neuron (**reach**), `mood_recorded:<MOOD>` +1 per memory
      (family member built from the closed mood enum, never from user data).
- [x] T004 `memory/recall.go` `Recall` + `RecallDiaryStars`: `recall_performed` +1 **per recalled memory** (the diary
      cost is the sum of its per-memory recalls), and `decay_recovered` +1 per memory whose **pre-recall** decay stage
      ≥ `values.AchievementRecoveryDecayStageMin`, captured from the same anchor snapshot the spend is already priced
      from — one computation, no extra read. This is the single reason a pull/recompute design was rejected.
- [x] T005 [P] `memory/view_semantic.go` `ViewSemantic`: `gist_viewed` +1 and `semantic_stage_depth` = the stage just
      served (**reach**, 1..4) — the [A2] axis is observed at the view moment because the call-site list is exhaustive
      and holds no worker-side site where the risen stage changes. Record the amendment in the policy doc.
- [x] T006 [P] `memory/release.go` `Release`: `episodic_memory_released` +1 per soft-deleted memory. `LetGo` seals
      neurons and releases nothing — it emits none.
- [x] T007 [P] `account` invite settlement: `invite_settled` +1 **under the inviter's scope**, minted from the resolved
      inviter id via `platform.NewUserScope` (the shipped `twinkle.ClaimInvite` precedent). The invitee gets no counter —
      the axis is an inviter fact.
- [x] T008 The `store.Decorate` legs are job 111's emissions (`decoration_saved`, `ornament_owned`,
      `ornament_kind_decorated:<KIND>`); this job binds the concrete recorder behind them. Export each producing
      context's emitted key set (`memory.AchievementCounterKeys`, `store.…`, `account.…`) for the boot guard.

**The two use-cases on `achievement.Service` (composing job 113's write primitives)**

- [x] T009 `Service.RecordProgress(ctx, scope, store Store, counterKey, delta)` — `Store` arrives already bound to the
      caller's transaction (the `CheckAndSpend(…, ledger, …)` shape): refuse `delta <= 0` with
      `ErrProgressDeltaInvalid` (no axis is decrementable, so it can only be a bug) → `TouchCounter`, whose `created`
      return is the **first-touch signal** that bumps the family's variety counter in the same transaction →
      `AddCounter` for accumulate keys / `RaiseCounter` for reach keys, each returning the new value → resolve the
      candidate rows from the in-code catalog (`counterKey → []Achievement`) and `MarkAchieved` each whose target the
      value now meets. Progress is **never stored**; evaluation is `counter >= target` over two ints with **no time
      input**, and `AchievementServiceDeps` still has no `Now`.
- [x] T010 `Service.ClaimAchievement(ctx, scope, achievementID) (ClaimResult, error)` — resolve the row
      (`ErrAchievementNotFound`) → in `achievement`'s **own** transaction, one conditional update through `MarkClaimed`
      (the row is the lock; concurrent claims serialize and exactly one updates) → zero rows updated means: row absent →
      `ErrAchievementNotAchieved` (**nothing is credited** — a met condition is a precondition, never a payout); row
      present and already claimed → fall through as a **replay** → commit, then pay. Return `ClaimResult{TwinkleAmount,
OrnamentID, TwinkleTotal}` with **exactly one** reward leg set.
- [x] T011 The claim id is **derived, not minted**: `claimID = achievementID`, unique per user because the ledger's dedup
      index is `UNIQUE (user_id, dedup_key)` and the progress key is `(user_id, achievement_id)` — so every replay
      recomputes the identical dedup key. A repeat claim is an **idempotent replay returning the same reward**, never an
      `ALREADY_CLAIMED` refusal: refusing would strand the reward in exactly the crash window this pairing heals.
- [x] T012 The two granter ports, paid **after** commit as an idempotent pairing (not one cross-context transaction,
      which would make `achievement` the transaction owner of another context's tables):
      `TwinkleGranter.EarnAchievementReward(ctx, scope, claimID, amount) (generalTotal int, err error)` over the shipped
      `twinkle.Service.EarnAchievementReward` with dedup key `achievement:<claimID>` (so the credit lands as an ordinary
      append-only `achievement_claim` earn row and shows in `/me` like everything else), and
      `OrnamentGranter.Grant(ctx, scope, claimID, ornamentID)` over job 110's ownership insert
      (`ON CONFLICT DO NOTHING`). Neither port has a `TwinkleKind` parameter — `SMALL` stays unrepresentable.

## Review

- [x] `/code-review` applied (rejections noted with reason) · for non-trivial logic, `/codex:review --background`

**Reviewed by codex (gpt-5.5) plus two parallel review agents. One finding was a deployment blocker.**

Applied:

- **`cmd/worker` — the binary the container runs — could not boot.** `account.NewService` became
  unconditional-required in this job, and that second composition root was never given the recorder; it also carried only
  **two** of the four withdrawal purge legs, so the production sweep was leaving ornament and achievement rows behind a
  hard-deleted account ([I1][U1]). Both fixed, and a test now constructs the runner so a forgotten seam fails CI instead
  of the deploy.
- **`neuron_shared` missed every crossing that jumped over two.** Testing `depth == 2` after the launch loses the common
  case of a neuron in one memory that two of a diary's memories also activate — it lands at three and reported nothing,
  while `neuron_share_depth` happily recorded 3. Now `before < 2 && after >= 2`, with `before` derived by subtracting the
  launch's own memberships.
- **"Achieved" could be unclaimable.** The read derives `achieved` from the counter while the claim needed a stored row,
  so adding a tier on an existing counter (or lowering a target) would show every qualifying user a claim button that
  answered "not achieved". The claim now promotes a counter that already meets its target, inside the same transaction.
- **A reach report of zero was refused before the mode was resolved**, contradicting the rule that a high-water report of
  zero is a legitimate observation — `store.Decorate` can pass `ornament_owned = 0`, and the save would have rolled back.
- **The boot guard's exemption was too broad and its test was a copy.** `KnownCounterKey` admitted any vocabulary key, so
  a catalog that stopped reading a counter still booted; the exemption is now the family membership it was meant to be, a
  producer emitting a _derived_ key is refused, and the test drives the shipped body instead of a reimplementation of it.
- **`store`'s recorder silently defaulted to the no-op** while memory's and account's were required — the exact drift the
  guards exist to prevent. Now required.
- **The nil-tx → pool fallback applied to every recorder**, so a transactional producer passing a nil handle would have
  written a counter outside the transaction that could roll back. The fallback is now account-only (its settlement is a
  locked statement sequence, not one transaction) and the transactional recorders refuse.
- **Lock order unified** — the purge took the two tables in the opposite order from a counter report, an AB/BA deadlock
  between a sweep and an in-flight launch for the same user.
- One duplicate sentinel merged (`ErrAchievementNotFound` was byte-identical to `ErrUnknownAchievementID`), and the three
  `Store` test fakes in this package merged into one.

Rejected, with reason:

- **Storing the resolved reward on `achievement_progress`** so a replay reports what it actually paid. Real, but only
  reachable by re-tiering or re-pointing an already-claimed row between deployments, and the fix needs the columns plan 74
  deliberately does not have. Recorded in [tech/achievements.md](../../tech/achievements.md) §9 instead: changing a shipped
  row's reward is a data change requiring a migration, not a content edit.
- **Serializing decoration saves so `ornament_owned` is exact.** Two concurrent saves report the same pre-read total, so
  the counter lags the table by one until the next save. A high-water mark can only be late, never wrong, and it
  self-heals; an advisory lock on every save for the sake of a count is the wrong trade. Documented at the call site so
  nobody "fixes" it with a re-read, which cannot see the other transaction anyway.
- **Extracting the `interface{ DB() dbgen.DBTX }` assertion** (now in three roots) and **a shared test-deps builder** for
  the `ServiceDeps` literals that every new required port touches. Both are real, both span files outside this job's
  blast radius — refactor-job candidates.
