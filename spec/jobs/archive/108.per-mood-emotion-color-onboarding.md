## Acceptance Criteria (from changes/07.per-mood-emotion-color-onboarding)

<!-- The source spec's acceptance criteria. After building, verify each is true in the running code. -->

- [x] A1 A user's emotion colours are stored **per mood**; a mood the user never chose has no stored row and renders the authored default colour.
- [x] A2 Skipping the screen stores **nothing** — no rows, and no durable "skipped" or "seen" record anywhere.
- [x] A3 The first-sign-in colour screen appears **after the nickname gate and before the universe**, on web and mobile, and shows thirteen stars — one per mood — against a bare night sky.
- [x] A4 Choosing a colour updates that mood's star **live** on the same screen, beside the other twelve.
- [x] A5 Each mood offers **three** recommendations. A recommendation whose bucket sample is at or above the `spec/values.yaml` floor shows its share; one below the floor shows **no ratio at all**.
- [x] A6 The aggregate counts choices into twelve 30° OkLCH hue buckets plus one near-neutral bucket; two colours in the same bucket count as one preference, and a bucket's displayed swatch is the most-chosen colour within it.
- [x] A7 The aggregate exposes counts only — no user id, and no read that resolves to an individual account.
- [x] A8 A stored colour's lightness lands on one of the emotion steps of the 2D ladder (L 0.80 / 0.72 / 0.63); its hue and chroma are exactly what the user chose.
- [x] A9 Choosing a colour within the configured ΔE (OkLab) of a colour already given to another mood raises an on-screen notice, and does not block the choice.
- [x] A10 "나머지는 추천값으로 진행" is reachable at every moment of the screen and enters the universe immediately.
- [x] A11 The per-mood editor is reachable from `/me` after onboarding, and edits apply through the unchanged `setMoodPalette` seam with no `GetUniverse` refetch.
- [x] A12 Every tuning number the change introduces lives in `spec/values.yaml` — none is hardcoded in a component, a query, or a Go handler.
- [x] A13 No regression: rendering remains palette-agnostic, the meaning layer and the brightness channel are untouched, the axis check remains warn-only, the nickname gate keeps its shape, and plan 80's take-once tour trigger still fires on a first sign-in.

## Deviations from this checklist, and why

1. **T005/T011 — the legacy whole-palette id is not the per-mood fallback and its unreachable picker is not
   co-mounted.** The generated checklist called it a "coarse choice", but the source change is explicit that the
   stored preference is now per mood, every absent row uses `cosimosi-default`, and `muted-dusk` is a
   recommendation set rather than a stored preference. The old schema/RPC remain unchanged for compatibility.
2. **T010/T012 — one new shared presentation layer was required.** The existing `StarLayer` is bound to episodic
   memory state and cannot render thirteen transient onboarding choices. A feature-local rendering recipe would
   duplicate the shipped body/channel wiring in both apps, so `MoodStarLayer` lives in `universe-render`, takes
   only resolved colors plus `onSelect`, and reuses the shipped star source and deterministic field. No existing
   body, sky, nebula, brightness, memory, or layout behavior changed; the adapter has no account/preference input.
