> Implementation work doc. Source spec: [code-review/11.jobs-116-128-demo,-sequence,-landing-and](../../code-review/11.jobs-116-128-demo,-sequence,-landing-and.md).

Covers **R009 (P3)**. Test-only — this job adds coverage and changes no production code.

**The asymmetry.** The web `SequenceSpotlight` is 45 lines of declarative CSS class plus inline style
and **has** a test (`SequenceSpotlight.test.tsx`, 57 lines). The mobile fork is 84 lines carrying an
imperative animation lifecycle — `Animated.loop` construction, `loop.start()`, and a
`return () => loop.stop()` cleanup keyed on `[pulse, reducedMotion, rect]`
(`apps/mobile/src/features/highlight-next-control/ui/SequenceSpotlight.tsx:21-47`) — and has **no**
test.

The fork itself is legitimate and well-reasoned (RN has no CSS animation, as its own comment at `:16`
says). The coverage simply landed on the wrong side: the platform with the leak-capable implementation
is the untested one, and `apps/mobile/jest.guards.js`' pending-timer guard would not catch a stray
`Animated.loop` either, because a `useNativeDriver: true` loop registers no JS timer. So this class of
failure currently has neither a unit test nor a guard.

## Completion note

### The suite, and what it costs the implementation to break

Nine cases in
`apps/mobile/src/features/highlight-next-control/ui/SequenceSpotlight.test.tsx`, following
`SequenceGuide.test.tsx`'s RN render setup and the web suite's stub seam (only `useReducedMotion` is
mocked — the real tokens, the real `StyleSheet` and the real `Animated` all stay). Five are parity with
web: decorative/non-modal, the ring standing off the rect by `RING_PADDING` on **both** axes, the tuned
pulse period split across the two legs, a static opacity of `1` under reduced motion, and nothing rendered
at all without a measured rect.

**Four are the lifecycle** — the case the web fork cannot express, and the reason the job exists:
unmount stops the loop, a new rect stops the previous one, a rect going `null` stops it, and the motion
preference turning on stops it.

`Animated.loop` is **wrapped rather than replaced**, so the component composes and drives a genuine loop
and the handles asserted against are the ones it was actually given. A stub returning `{ start, stop }`
would keep passing even if the production code stopped building a real loop.

### DoD sanity — the lifecycle test earns its name

Removing `return () => loop.stop()` from the production component turns **exactly the four lifecycle
cases red** (`4 failed, 5 passed`) and leaves the five parity cases green. Restored afterwards;
`git diff` on the component is empty. A lifecycle test that passes against the broken implementation is
not a lifecycle test — this one does not.

### A3 — the guards stayed silent

`pnpm --filter @cosimosi/mobile test`: **22 suites, 92 tests, all passing**, with no console
error/warning drained by `jest.guards.js` and no pending-timer failure in `afterAll`. No fake timers were
needed, so none are installed. Teardown stops every captured loop and restores the spy in `afterEach`,
before the spy is restored — a failing assertion cannot leak a running animation into the next case.

### T007 — the sibling slices, surveyed and NOT widened into

The other three mobile chrome slices are a materially weaker case than R009's, and deliberately left:

| slice                   | mobile / web lines | lifecycle? | tested?     |
| ----------------------- | ------------------ | ---------- | ----------- |
| `show-sequence-caption` | 55 / 48            | none       | neither arm |
| `skip-sequence`         | 41 / 33            | none       | neither arm |
| `replay-onboarding`     | 37 / 33            | none       | neither arm |

Two things separate them from the spotlight. None contains a `useEffect`, an `Animated`, a `setTimeout`
or a `setInterval` — they are declarative, so there is no teardown to leak. And the gap is **symmetric**:
their web peers have no test either, so this is not the asymmetry R009 named (web covered, mobile not) but
ordinary thin coverage on a declarative slice. Recorded here for the next review rather than folded in.

### SSOT — `test-harness.md` was the wrong home

The After-completion step pointed at [tech/test-harness.md](../../tech/test-harness.md) "if it inventories
per-slice coverage". It does not — that doc owns the `/test` diagnostics route (panels, capabilities, the
fake-helper rule), and a per-slice coverage list there would be a second source of truth against the
files themselves.

The durable rule this job establishes went to its actual owner instead:
**[ARCHITECTURE.md](../../ARCHITECTURE.md) §3.5**, which owns the `*.native` fork rule, now states that a
fork owns its own test — and says why it matters most when a fork trades a declarative construct for an
imperative lifecycle, including the reason the pending-timer guard cannot substitute (a
`useNativeDriver: true` loop registers no JS timer).

### A4 / A5 — nothing else moved

`SequenceSpotlight.tsx` is unedited (verified by `git diff` after the sanity check restored it), the web
suite is untouched, and no defect surfaced while writing the test — so there is no proposed finding beyond
T007's note above.
