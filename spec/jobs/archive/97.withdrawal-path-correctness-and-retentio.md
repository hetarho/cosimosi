# Job 97: Withdrawal path correctness and retention config (refactor)

> Implementation work doc. Source spec: [code-review/09.epic-k-account-runtime-and-gate-audit](../../code-review/09.epic-k-account-runtime-and-gate-audit.md).
> /cosimosi:implement-job 97 builds it via the two checklists below. When done, reflect the result into the
> SSOT (plan/policy/values) and set status: done. Write it in English.

Covers **R004**, **R005**, **R006**, **R009** (P2) and **R017** (P3) — the whole withdrawal vertical in one unit.
R004 is the sharp one: the dedup identity is a contract between two processes, duplicated as a bare string literal in
four places with no parity guard. If one copy drifts, `RestoreAccount` cancels nothing, reports success, and the sweep
hard-deletes the restored user's data at the deadline.

**Decide before building** (Questions / Tradeoffs in review 09): is the 30-day account-restore window genuinely the same
policy number as the diary-release window? If product intends them to move together, the fix is one shared, renamed
scalar with a comment saying so. If they are separate promises, they need separate scalars. This changes T005–T007.

Decision: **separate scalars, with no duration change**. Account restoration and diary release are independent product
promises that may evolve separately, so withdrawal uses `account.withdrawal_retention_days: 30` while release consumers
remain on `release.soft_delete_retention_days: 30`.

## Acceptance Criteria (from code-review/09.epic-k-account-runtime-and-gate-audit)

- [x] A1 The withdrawal sweep's dedup identity exists in exactly **one** place, published by the context that owns the
      `jobs` table (`memory`), and both `cmd/api` and `cmd/worker` consume it. The literal `"withdrawal:" + scope.UserID()`
      appears zero times outside that definition.
- [x] A2 A test proves enqueue/cancel parity across the two binaries: the identity `Withdraw` schedules with is the same
      one `RestoreAccount` cancels, and the assertion fails if either side is edited alone. Today
      `withdrawal_composition_test.go` asserts only the production credential refusal.
- [x] A3 The purger adapters (`memory`, `twinkle`) and the withdrawal scheduler are declared once, not once per binary.
      The `errors.New("memory purge requires the in-flight withdrawal job id")` string exists in one place.
- [x] A4 The account-withdrawal retention window resolves from its own named source per the T005 decision, and
      `release.soft_delete_retention_days`' comment no longer claims "Only full delete uses it" while three other call
      sites read it. Both apps' withdrawal copy and both Go call sites agree on one value.
- [x] A5 The retention duration is computed once per side rather than independently in `account` and `platform`.
- [x] A6 An authenticated RPC no longer pays an uncached DB round-trip for the withdrawn-status check. The uncached read
      remains the miss branch, so behavior is unchanged — only the number of round-trips falls.
- [x] A7 A committed withdrawal followed by a failed sign-out no longer reports the withdrawal as failed. The user is not
      left signed in on an account every RPC rejects with `ACCOUNT_WITHDRAWN`; the client falls back to a local session
      teardown. Fixed once for both apps, not twice.
- [x] A8 `Withdraw` does not enqueue a sweep job for a scope that has no `users` row, so a never-provisioned caller
      cannot leave inert job rows behind.
- [x] A9 **No behavior change** to the withdrawal contract: the restore window length, the sweep's serialization on the
      locked `users` row, the disjointness of "sweep refuses before the deadline / restore refuses after it", the purge
      leg ordering (foreign contexts → account dependents → credentials → the `users` completion marker), and
      `RestoreAccount`'s interceptor exemption all stay exactly as they are.
