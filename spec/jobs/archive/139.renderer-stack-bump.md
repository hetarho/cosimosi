Two renderer-critical dependencies are behind on fixes that land exactly on this repo's hottest paths (R005):
`react-native-webgpu` 0.5.16 → **0.8.1** (0.6.0 fixed iOS-simulator instanced-draw instabilities — the whole scene
is instanced draws; 0.6.2 thread-safe native caches; 0.8.0 ships a Jest mock; 0.8.1 texture-copy fix), and three
0.185.0 → **0.185.1** (patch fixes), and R3F 9.6.1 → **9.7.0**. The pre-implementation recheck the job called for
found 9.7.0 published on npm (2026-07-31), contradicting this doc's earlier reading that only 9.6.1 existed — the
rule that produced the right answer was "recheck at implementation and bump only to an actually published stable
release", not the version number written down ahead of time. **Landed first, before job 136**, so 136's
screenshot/lifecycle baseline and every later review-12 verification run use the final renderer stack.

      (`^0.5.16` today — the package declares no peer range for it, only a `peerDependenciesMeta` optional flag);
      iOS pods and Android gradle rebuilt; the universe scene renders correctly on the iOS simulator **and** at
      least one physical device (§3.5's pre-1.0 caveat: pin exact, test on hardware), with instanced draws
      (star / cell-star / gist layers) spot-checked.
      — Pinned **exact `0.8.1`** (no caret) in both manifests, per §3.5's pre-1.0 rule; the explicit optional
      `peerDependencies` entry was left implicit (the `peerDependenciesMeta` flag alone is how the repo already
      declares it, and adding a range would re-introduce the drift this pin removes). `pod install` re-resolved the
      pod to `0.8.1`; the same run also picked up `RNSVG 15.15.5`, which `react-native-svg` had been declaring in
      `package.json` without ever reaching `Podfile.lock` — a pre-existing lock drift, fixed incidentally.
      **Physical-device verification is not possible in this environment** (no paired iOS device); the simulator
      build is the evidence recorded here, and hardware spot-check of the instanced layers remains outstanding.
- [x] A2 **R3F targets a published stable release and keeps the native-entry patch valid.** Run the current-docs
      gate at implementation time. If 9.6.1 is still latest, retain it and its existing one-line
      `package.json` `react-native`-field redirect; if a newer stable is actually published, bump to that version,
      regenerate the patch, and rename the `pnpm.patchedDependencies` key. In either branch both canvas hosts init
      and render as before, and the chosen version/release-note evidence is recorded here.
      — **9.7.0 is published** (npm `time`: `2026-07-31T16:20:20Z`), so the audit's target is valid after all and
      the job preamble's "not published" reading was stale. Bumped every manifest to `^9.7.0`, renamed the patch
      file + `pnpm.patchedDependencies` key to `@react-three/fiber@9.7.0`, and confirmed the redirect survived the
      rebase (the installed `@react-three/fiber/package.json` `react-native` field reads
      `dist/react-three-fiber.cjs.js`, not the `native/` entry). The patch needed no content change — 9.7.0 did not
      move the field's surrounding lines. Release notes are reconciler-side and land squarely on this repo's hosts:
      children reordering now syncs correctly, `dispose`/`onUpdate` host props update instead of being overwritten,
      instance reconstruction no longer bails out behind `React.memo`, event priorities match react-dom.
- [x] A3 **three is 0.185.1** everywhere it is declared (apps + packages, one version). `@types/three` moved to
      `^0.185.1` alongside it. The two packages' `three` **peer** range stays `>=0.185`: a peer range states what a
      host may supply, and the packages are genuinely compatible with 0.185.0 — narrowing it to the patch would
      assert a break that does not exist. Only the declared/installed version is one workspace-wide number.
- [x] A4 **Mobile Jest uses the upstream mock where it simplifies ours.** If 0.8.0's shipped Jest mock covers what
      hand-rolled test shims do today, replace them; otherwise record why not in this doc.
      — **Not adopted: there is nothing to replace.** The mobile arm never loads `react-native-webgpu` at all — its
      `moduleNameMapper` stubs the whole `@cosimosi/3d-renderer` package (`jest.mock.3d-renderer.tsx`), because the
      real blocker is `three` shipping ESM that the host-only jest config does not transform. Wiring
      `react-native-webgpu/jestSetup.js` in today would add a `setupFiles` entry that no suite exercises. The
      upstream mock does become the right tool the moment a suite renders the native host itself
      (`Canvas` → plain `View`, `useCanvasRef`, and a `getContext` that returns `null` rather than fake GPU state) —
      job 136's native lifecycle test is that moment, so the adoption decision moves there rather than being
      pre-empted here.
- [x] A5 **No behavior or visual change.** Headless CDP screenshot parity on web (landing hero + universe); mobile
      device spot-check; full `pnpm check` green including mobile jest with its guards
      (`apps/mobile/jest.guards.js`) quiet.
      — `pnpm check` green end to end (lint · typecheck · all test arms including mobile jest · web build · blog
      build · go vet/build · `check:gen`). Headless-Chrome CDP capture of `/` and `/demo` renders the scene with a
      1280×800 canvas and no page errors or WebGPU validation messages. **Byte-comparison is not the parity test
      here**: the scene animates off a wall-clock time uniform, so consecutive captures of an unchanged build differ
      — parity was read as "same composition, no new console/validation output". One upstream warning surfaces
      (`THREE.Clock: This module has been deprecated. Please use THREE.Timer instead`), emitted by R3F's own store
      (`new THREE.Clock()` in its `dist/events-*.js`), not by any repo code; it is R3F's migration to make.
