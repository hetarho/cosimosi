## Result

### What the archive does now

`DiaryList` mounts a viewport of rows and nothing else. Measured in a headless browser over a 400-entry fixture at 900px
tall: **127–190 DOM elements and 11–17 mounted rows, flat across every scroll position and every page loaded** — where
the unwindowed list cost ~10.4 elements per row without bound (T001's table). Row spacing is byte-identical to the old
`gap-2` (every measured inter-row gap is exactly 8px, no overlap, no blank band at any scroll offset).

The list is **window-scrolled**, so it uses `useWindowVirtualizer` and measures its own document offset rather than
wiring a scroll element. Rows are absolutely positioned inside a `<ul>` carrying the full scroll height; the gap comes
from the virtualizer's `gap` option, which is why `row_gap_px` exists as a value instead of a Tailwind class. The keyset
sentinel keeps its position after that height, so paging still fires at the true end of the archive — verified live
(the document grew 4521 → 6631 → 8837px as the sentinel loaded pages) and in a test that drives the observer directly.

Three things this turned up that are worth keeping in view:

- **The offset has to be measured when the list appears, not when the component mounts.** The archive renders a loading
  line first, so a mount-time `ref` read is always null and a `[]`-dep effect never runs again. The list node is held
  as state instead. Both reviewers found this independently; the browser probe had missed it because the overscan was
  absorbing the error.
- **A focused row is pinned into the range.** Windowing unmounts rows, and unmounting the focused one drops keyboard
  focus to `<body>` mid-scroll. A `rangeExtractor` keeps it mounted until focus leaves. Rows outside the window are
  still absent from tab order — that part is inherent to windowing and is now recorded in plan 69.
- **The row-height estimate was wrong by 20%.** A closed row measures 114px, not the 96 first written; an estimate
  below the truth makes the page grow under the reader as rows are measured. The value is now the measured number.

### A3 — the other two lists, decided

- **`AchievementList`: not windowed, and not deferred either.** It renders the server's catalog — 39 rows in
  `apps/api/internal/achievement/catalog.go` — with no paging at all. Its length is content, not history, so there is
  no cliff to reach and a windowing layer over it would be pure cost.
- **`TwinkleLedgerList`: re-deferred, with the reason recorded in the file.** It is keyset-paged at 50/page and grows
  by one row per earn or spend, so it is the same class of cliff as the archive. But its rows are cut into day
  sections, so windowing means first flattening headers and entries into one index space — a change to the shape the
  day grouping is expressed in. Its stale comment ("No virtualization library — … the diary list follows the same
  shape later") is now replaced with the real reason and the trigger: a real account's ledger reaching the low
  thousands. Mobile's ledger keeps its documented non-`FlatList` nesting; no mobile work here.

## T001 measurement (2026-08-07) — precondition NOT met

Server-rendered `DiaryList` at increasing row counts (throwaway probe, not committed):

| rows | DOM elements | per row | HTML   |
| ---- | ------------ | ------- | ------ |
| 20   | 211          | 10.6    | 18 KB  |
| 100  | 1,043        | 10.4    | 87 KB  |
| 500  | 5,203        | 10.4    | 437 KB |
| 1000 | 10,403       | 10.4    | 873 KB |

A closed row costs ~10.4 elements — an `li`, its button, the date, the preview and the mood dots, none of them
animated. Two things keep this off the critical path today. The DOM holds **what has been paged in, not what the
archive contains**: `diary_reader.page_size` is 20 and rows accumulate only as the sentinel fires, so reaching even
5,000 elements takes a user deliberately scrolling 25 consecutive pages in one session — an archive of a thousand
entries opens at 211 elements like every other one does. And the product is still invite-gated pre-launch, so no real
archive is anywhere near the "high hundreds" the review named as the trigger.

Re-run this probe when dogfooding reports a slow archive, or when one account's entry count passes ~500 — the
arithmetic above turns straight into a decision.
