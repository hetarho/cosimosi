> **The delta in one line:** the count target stops being a wall (a one-scene diary is a valid split), and when the
> repair loop does give up it says so as a transient, content-free, reported failure instead of a spend limit — while a

**Domain — the soft floor and the violation it names (`internal/memory`, pure)**

- [x] T002 In `apps/api/internal/memory/encode.go`, give the repair loop a typed violation instead of a bare

- [x] T003 Split the single count instruction in two, each naming the count actually returned: **over-count** — merge
      the adjacent scenes that belong to one event, down to at most `encode.max_memories`; **under-count** — if the
      entry truly is one continuous event it may stay one memory, otherwise look again for the event boundary that was
      missed. Keep `memoryCountInRange` as the one owner of the target predicate and add the accepted-floor predicate
      beside it (both read the generated constants — no literal 1, 2 or 5 anywhere).
- [x] T004 `repairUntilValid`: make the under-count **soft**. A count below the target but at or above
      `encode.min_memories_accepted` is re-prompted at most `encode.under_count_nudges` times; once that budget is
      spent the count is accepted and stops being reported as a violation for the rest of the loop, while every other
      invariant keeps the full `encode.max_revise_retries` budget and stays hard. A count below the accepted floor
      cannot occur (`parseExtractResult` refuses an empty list) and stays an `ErrEncodeInvalidSplit`-class breach.

- [x] T005 On exhaustion return `ErrEncodeRetryExhausted` wrapping **the violation kind only** — never the

      Where the kind is a count case, carry the observed count too (a number is not content).
- [x] T006 `apps/api/internal/memory/launch.go` — `PersistEncoded`'s bound becomes

## Review

- [x] `/code-review` applied (rejections noted with reason) · for non-trivial logic, `/codex:review --background`

`/code-review` is not model-invocable in this repo (its skill sets `disable-model-invocation`), so the diff was
reviewed by hand against this job's criteria, and Codex (`gpt-5.5`, read-only) reviewed it in parallel. Four findings,
all applied — three of them made a claim this job had already written down actually true:

1. **The nudge was spending the repair budget** (`encode.go`). One shared `attempt` counter meant a single-scene
   diary got 2 passage repairs where a two-scene diary got 3 — the same penalty for a legitimate day that this
   change exists to remove. The nudge now has its own counter; a count below the accepted floor still repairs (and
   is never a nudge), so termination is unchanged. Covered by the re-prompt assertions in
   `TestEncodeStillEnforcesTheOtherInvariantsOnAnAcceptedCount`.
2. **An empty `memories` array was a generic internal error** (`ai/extractor.go`). The schema carries no `minItems`,
   so a provider can return one; this doc claimed it was `ErrEncodeInvalidSplit`-class, and now it is. The
   client-visible code is unchanged (that class maps to `Internal` — an adapter breach is not the writer's fault),
   but operators keep the canonical predicate.
3. **`detail_` prefixing defeated the sensitive-attribute guard** (`platform/interceptors.go`). `metadata["diary"]`
   became `detail_diary`, which normalizes away from the blocked `diary`. The guard now runs on the metadata's own
   keys before prefixing. Latent today (the only reported reason emits kind + count), load-bearing for the next one.
4. **A panicking reporter could mask the refusal** (`platform/interceptors.go`). Reporting now recovers, so a
   refusal that was deliberately not masked cannot become a masked `Internal` because telemetry failed — which is
   what the comment beside it already promised.

Codex found no issue in the `Cacheable` hook (returned, charged, not cached; the `body` closure is safe) or in the
multi-`%w` cap translation.

rendering Korean copy). Reproduced on a clean `HEAD` worktree before touching anything, so it is untouched here.
