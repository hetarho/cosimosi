## Acceptance Criteria (from code-review/15.full-codebase-runtime,-gate,-and-cross-p)

Finding: R002 (P2). `bodyWithinOutputBudget` estimates the body against a split of **one memory
carrying nothing but the body** (`encode.go:318`) — no name, no mood, no neurons — while the domain
guarantees all three on every memory (`validateSplitStructure`, `hasRequiredSemanticNeurons`). Measured
against the shipped estimator at `max_output_tokens: 6000`: the guard admits a Korean body of up to
**5983 runes**; that same body as the **minimal** admissible split (1 memory, 1 name, 1 mood, 1
semantic neuron) already estimates **6024**, and as an ordinary 5-memory split **6295**. The trap band
for the 5-memory shape is **5690–5983 runes**.

**As built.** T001 chose approach (a), corrected: the reservation prices the structure a split cannot
_avoid_, not a guess at a typical split. "Worst admissible" is unbounded above — neuron count and
name length have no ceiling — and that unbounded part is exactly what the `output_too_large`
re-prompt can take back, so pricing it would refuse diaries a terser split fits. What is priced is
the floor: `max_memories` memories (a five-scene day is admissible and the writer has no say), the
costliest mood and neuron-type strings from their closed enums (derived from the catalogues, so
adding a member re-prices the guard), and names at their smallest legal size.

Two things the build corrected against the audit:

- **The A1 property test caught the first implementation.** `validateSplitStructure` requires a
  non-empty passage on _every_ memory, so putting the body in one memory and leaving four empty was
  not an admissible split — the reservation was a fiction. The passages are now distributed across
  the reserved memories, which is also the honest model ([E1]: they jointly quote the diary).
- **The ceiling moved far less than the review estimated:** 5983 → **5871** runes, 112 rather than
  ~300. The review's number came from a modelled 5-memory split with 10-rune names and three neurons
  each; the actual floor is much cheaper. The largest admitted body's cheapest legal split now lands
  exactly on the 6000-token budget.

No `values.yaml` key was needed: the reservation is a formula over values that already exist, which
the config rule explicitly exempts. That is strictly better than option (b) — there is no second
number to keep in step with `max_memories`.

- [x] A1 There is no body the pre-flight guard admits for which the minimal admissible split
      overflows `encode.max_output_tokens`. Concretely: for the largest body
      `bodyWithinOutputBudget` accepts, `estimateOutputTokens` of a worst-case admissible split of
      that body is `<= values.EncodeMaxOutputTokens`. This is the property, not the number — it must
      hold if any of `max_memories`, `min_semantic_neurons` or `max_output_tokens` is retuned.
- [x] A2 A body inside today's trap band is refused **before any LLM call**, with
      `ErrEncodeBodyTooLong` (→ `MEMORY_ENCODE_BODY_TOO_LONG`), not after the repair budget burns
      down with `EncodeRetryExhausted{Kind: output_too_large}` (→ `MEMORY_ENCODE_RETRY_EXHAUSTED`).
      The writer is told to shorten the entry, which is the only thing that helps.
- [x] A3 The repair budget is never spent on `ViolationOutputTooLarge` caused by body length alone.
      A `ViolationOutputTooLarge` reaching `repairableViolation` now means genuine name/neuron
      verbosity — the one thing its instruction ("shorter memory names and keep only the essential
      neurons", `encode.go:293`) can actually fix.
- [x] A4 The overhead the guard reserves is an owned, explained number — derived from
      `encode.max_memories` / `encode.min_semantic_neurons`, or an explicit reserved-overhead key in
      `spec/values.yaml` with its reasoning — never an unexplained literal in `encode.go` (§4 _Config
      is build-time and generated_).
- [x] A5 No behavior change for bodies comfortably inside the budget: an ordinary diary still reaches
      the extractor on the first call, still gets the same split, and `Encode`/`ReviseSplit` return
      exactly what they do today. The golden semanticization fixtures are untouched.
- [x] A6 The in-guard and the output guard remain provably ordered rather than merely sharing a helper
      — the drift `encode.go:315-316` claims is impossible ("the same token model … so the two cannot
      drift apart") is enforced by a test, since the token model was always shared and the _shape_ was
      what diverged.
