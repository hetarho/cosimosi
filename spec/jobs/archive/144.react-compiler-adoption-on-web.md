Adopts React Compiler 1.0 (stable 2025-10) on `apps/web` — automatic memoization across all the canvas-adjacent
React UI, on the React 19.2 the repo already runs. The review's Questions section records the compatibility posture:
the compiler memoizes render code, not `useFrame` loops, so the R3F idiom is unaffected, but the scene packages
must be spot-checked (mutation-adjacent components may need `"use no memo"`). Build after job 138 and stage it:
lint/diagnostics first (no compiler transform), compiler second, mobile deferred until web proves it out.

### T003 — the compiler memoizes away locale switching, so it is NOT adopted

**Decision (owner, 2026-08-09): do not adopt the transform on web.** The diagnostics above are the delivered value and
they stay; the compiler stays out of the build until locale is a real React input. What follows is why, kept because it
is the argument the follow-up has to answer.

The wiring itself is correct and was verified end to end before being reverted. On `@vitejs/plugin-react@6.0.2` the
current docs' path is `@rolldown/plugin-babel` with `reactCompilerPreset()`, **not** the pre-6.0.0
`react({ babel: { plugins: [...] } })` option this job's T003 was written against. Under it the build is green, the
transform reaches workspace-package sources (they resolve to real paths under `packages/`, outside the plugin's
`node_modules` exclude), and it emits **518 memo-cache slots**.

Then `pnpm check` fails two web tests — and they are not test artifacts:

```
× i18n-provider   > re-renders mounted message copy after the active locale changes
× AccountProfile  > applies and stores locale before the write, then rolls both back on refusal
```

Both pass with the transform off and fail with it on. The cause is structural, not local. This app reads copy by
calling `m.me_title()` **during render** — a module-level global that `setActiveLocale` mutates. Plan 95's design makes
that work by re-rendering through `LocaleRenderBoundary` while keeping mounted state intact (its docstring says so, and
the test asserts a counter survives the switch). A re-render only helps if it re-evaluates: the compiler sees a
component whose output depends on nothing reactive, caches its JSX, and the copy keeps its first language forever.

Reading mutable module state during render is a rules-of-React violation, so the compiler is not wrong — but the fix is
a change with a UX decision inside it. Four ways out were put to the owner, with their real costs:

1. **Don't adopt the compiler on web** — keep the diagnostics, which are most of the value, and stop here.
   **← chosen.** Cost now: nothing. What is given up is unquantified: the compiler's render win here was never
   measured, while its cost was — see the bundle delta below.
2. **Make `m` a hook** (`const m = useMessages()` per component) — all 709 call sites stay textually identical and
   ~200 files gain one line (117 web/packages + 80 mobile). State is preserved and the compiler sees a reactive input.
   Module-level message tables (e.g. `LedgerEntryRow`'s `REASON_LABEL`) would still read the global and need their own
   answer.
3. **Key `LocaleRenderBoundary` on the locale** — one line, and copy updates everywhere. It remounts the subtree, so a
   reader switching language mid-form loses what they typed; that contradicts the state-preservation contract
   `packages/i18n/src/react.ts` documents and the i18n-provider test pins.
4. **Migrate off the `globalVariable` locale strategy** to paraglide's hook/context strategy — correct by
   construction, but an i18n architecture change across web, mobile and `packages/`, which is its own plan rather than
   a stage inside this job.

**The prerequisite, named:** locale must reach components as a React input (option 2 or 4) before the transform can go
in. Until then, enabling it silently breaks language switching — which is why `apps/web/vite.config.ts` carries the
reason in the plugin list rather than leaving the absence to look like an oversight, and why
`plan/02.quality-gates.md` now says "diagnostics only" in so many words.

Dependency hygiene: `babel-plugin-react-compiler@1.0.0` and `@rolldown/plugin-babel@0.2.3` were installed, verified and
removed. The manifests were clean, but `pnpm-lock.yaml` kept both as resolved optional peers of `@vitejs/plugin-react`
— so they were still being installed on every `pnpm install` while no `package.json` declared them. Re-resolving that
entry drops both (and moves the plugin 6.0.2 → 6.0.5, a patch bump that comes with the re-resolve).
