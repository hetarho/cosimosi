# Job 131: Correct the demo run model recall ladder (refactor)

> Implementation work doc. Source spec: [code-review/11.jobs-116-128-demo,-sequence,-landing-and](../code-review/11.jobs-116-128-demo,-sequence,-landing-and.md).
> /cosimosi:implement-job 131 builds it via the two checklists below. When done, reflect the result into the
> SSOT (plan/policy/values) and set status: done. Write it in English.

Covers **R003 (P2, the one confirmed runtime bug in the batch)** and **R010 (P3, hygiene in the same
function)**.

**The bug, precisely.** A demo recall sets `currentText` to the reconsolidated reading
(`use-demo-run.ts:261`) but `applyFacts` (`:352-359`) rebuilds the memory as `{ ...memory, ...facts }`,
where `memory` is the resolved fixture — so `decayStages` stays the ladder authored from the
**original** text (`packages/demo/src/resolve.ts:103`). `currentDecayText`
(`packages/universe/src/current-decay-text.ts:32-33`) returns `memory.currentText` only at stage 0 and
`memory.decayStages[stage - 1]` above it. So: recall a memory, then push the clock far enough that the
stage climbs back to 1 or more, and `DemoEntryReader.tsx:38` renders the erosion of the text the memory
had _before_ it was recalled. The reconsolidated reading is not eroded — it is discarded.

**Why this is demo-only.** Production has the same write shape
(`packages/universe/src/recall-star.ts:44-50` also leaves `decayStages` alone) but self-heals: the
server regenerates the ladder and the next `GetUniverse` refetch replaces the mirror. The demo has no
server and no refetch, so the fixture ladder is permanent. **Do not "fix" `applyRecallResult`** — it is
correct for its context, and changing it would be an unscoped production change.

**Owner decision to settle before building** (review 11, _Questions / Tradeoffs_): store the
recomputed ladder on `DemoMemoryFacts` beside `currentText` (the value it is derived from), rather than
recomputing inside `applyFacts` on every projection. `projectScene` already re-runs on every state
change, so the recompute-on-read option would run `decayStageText` per memory per render for no
benefit. Recommendation is the stored form; note it in the job if the implementer disagrees after
seeing the code.

## Completion note

### T001 — the test failed first

`erodes the reconsolidated reading after a recall, never the original text` failed against the unfixed
model with exactly the finding's symptom: after a recall plus twelve monthly jumps the reader showed
`"The kitchen xxxx was still on when we xxxx home. …"` — the erosion of the **pre-recall** text — where
the reconsolidated reading's own stage-1 erosion was expected. It passes after the fix.

### The recompute condition is broader than T004 specified

T004 said to recompute "whenever `currentText` actually changes", on the stated grounds that an absent
`reconsolidatedTexts[memoryId]` leaves the text unchanged and so would only be "recomputed to an equal
value". **That premise is false, and codex caught it.** The ladder is a function of the text _and_ the
seed, and a recall reshapes the seed on every pass ([V5]) — so a text-preserving recall still changes
which words erode. Verified against the shipped function on the real fixture text: seeds `499965575`
and `499973494` produce visibly different stage-1 redactions.

Two common paths were affected:

- **a repeat recall** — `reconsolidatedTexts` is already applied, so only the seed moves;
- **the first recall of any memory the fixture wrote no `reconsolidatedText` for** — which, since free
  play recalls any star, is most of them.

Both would have shown the _previous_ form's word loss under the current form: the same class of bug as
R003, one level down. So the ladder is recomputed on **every** recall, and the condition is gone. A1–A3
are unaffected (a launch still stores the authored array untouched), and a second regression test —
`re-erodes on a recall that reshapes the form but not the words` — pins it. That test was confirmed to
fail against the conditional version.

### A5 — `recallEntropy` output, precisely

The inner `% Number.MAX_SAFE_INTEGER` was a true no-op: `>>> 0` already bounds the value below 2³². The
**outer** one was not mathematically dead — it would begin to matter at `nthRecall ≥ ~1.137 × 10¹²`
recalls in a single sandbox session. Output is identical across all three shipped set ids for the first
200,000 recalls (checked exhaustively), which is the whole reachable domain. Stating it rather than
repeating A5's "unchanged for every input", which is not quite true.

### T007 / T008 — checked, deliberately unchanged

- `derivedSemanticStage(fixture, facts, run.clock)` at the recall site is passed the **pre-recall**
  `facts` on purpose: the floor is the stage reached _before_ the re-anchor, which is what [C7] means.
  Passing the new facts would read the stage back through the reset anchor and floor it at zero. Left
  as-is, with a comment so the next reader does not "fix" it.
- **The landing walkthrough is genuinely immune**, re-verified rather than assumed. Its clock is
  `fadeDay` from the `fade` step onward and no later step moves it, while `recall` sets
  `lastRecalledUniverseTime` to that same day — so elapsed time is 0, the stage is 0, and
  `currentDecayText` never reaches the ladder. `walkthrough.ts` was **not** changed; two assertions were
  added to the existing mirror test (`universeTime` unchanged, `focusText` still the whole
  reconsolidated reading), because the immunity is a property of the step order and nothing else pinned
  it.
