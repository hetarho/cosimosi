## Acceptance Criteria (from plan/61.signup-and-invite-usecase)

<!-- The source spec's acceptance criteria. After building, verify each is true in the running code. -->

- [x] A1 `SignUp` accepts exactly four inputs — nickname, timezone, locale, invite token — and creates the `users` row plus the initial `auth_providers` row read from the directory. No other information is requested, and a client-supplied provider claim is ignored. ([U6][U5])
- [x] A2 A nickname is accepted only when its trimmed rune length is within `account.nickname_min_length`..`account.nickname_max_length` and it carries no control characters or line breaks; nicknames are **not** unique. Violations return `ACCOUNT_NICKNAME_INVALID`. ([U6])
- [x] A3 A timezone that does not resolve as an IANA location is **rejected** with `ACCOUNT_TIMEZONE_INVALID`; it is never silently defaulted. An unknown locale **coerces** to the default. Zone resolution works in the production `distroless/static` image. ([U7])
- [x] A4 `SignUp` is idempotent: a retried or concurrent call returns the existing profile, overwrites no field, and re-binds no invite. ([U6])
- [x] A5 Arriving through an invite link binds the invite automatically; there is **no request field and no RPC** through which a user could type an invite code. An unknown, expired, self-, already-bound, or withdrawn-inviter token binds nothing, returns `invite_bound = false`, and does **not** fail the signup. ([U8])
- [x] A6 `SignUp` credits **nothing** — no ledger row is written on any signup path, and the request/response carry no amount or balance field. ([U11][G6])
- [x] A7 The `invites` row is created **at bind time** by `AcceptInvite`, from the inviter id inside the token [60](../plan/60.account-profile-model.md) verified; this unit adds no mint query, no `GetInviteLink` RPC, and no statement that looks a token up across users. ([U8][U1])
- [x] A8 The invite reward and the signup bonus settle only from the launch path: the reward fires from `memory.SignupSettlementPort`, once per launched diary, after the monotonic guard admits the diary — a past-dated diary that launches no star settles nothing, and no wire method can trigger a settlement. ([G6][I10])
- [x] A9 A settlement pays both sides only when all four [G6] conditions hold: distinct live inviter, ≥1 launched `EpisodicMemory` (structural, via the trigger), per-inviter rewarded count below `twinkle.invite_reward_max_per_inviter`, and an email-verified invitee (implicit for `GOOGLE`). Failing any one pays neither side. ([G6])
- [x] A10 Settlement is exactly-once and crash-recoverable: credits are written before `invites.rewarded_at` is stamped, both legs are keyed `invite:<inviteID>` / `invite_signup:<inviteID>`, the bonus is keyed `signup_bonus:<userID>`, and a replay writes nothing new. No reward is ever reversed. ([G3][G7][I1])
- [x] A11 The one-time signup bonus grants `twinkle.earn_signup_bonus` to `GENERAL` with reason `signup_bonus`, at most once per account, and only behind the same launched-star condition. There is no login or attendance earn. ([U11][G3])
- [x] A12 `twinkle.UnavailableInviteResolver` is replaced at `cmd/api/account.go` by the resolver backed by `account.Service.ResolveInviteSettlement`; production **fails to boot** with the settlement port or the resolver unbound. ([G6])
- [x] A13 The settlement ports carry only `(scope)` and `(scope, token)`; no memory id, mood, strength, coordinate, or diary body is expressible on them, and `account` imports neither `memory` nor `twinkle`. ([I11], §2.2/§2.4)
- [x] A14 Every `invites` statement is inviter-scoped except `FindSettleableInviteForInvitee`, which is single-row, authenticated-invitee-keyed, and allowlisted in `check-persistence-isolation.mjs` with the reason stated in the SQL comment. `BindInviteToInvitee` remains conjunctively scoped by the verified inviter id and needs no exception; `pnpm lint:persistence` passes. ([U1])
- [x] A15 Handlers are thin — proto↔domain mapping plus a use-case call; no proto or sqlc type reaches the use-case; the directory, invite store, and both granters are consumer-owned interfaces. (§2.7/§2.9 #4/#6/#7)
- [x] A16 This unit adds no migration, no ledger DDL change, and exactly one new `EntryReason` constant (`signup_bonus`); the closed-set test is extended rather than replaced ([66.earn-and-purchase-spend](../plan/66.earn-and-purchase-spend.md) owns the reason set and the ledger DDL).

## Grounding

- Constitution ([I1]–[I13]): [00.overview](../plan/00.overview.md) §3 (_The constitution_), incl. the v2 risk
  register. Most at risk here, each with its **structural** guard (plan 61 Grounding):
  - **[G6] farming** — settlement is **unreachable from the wire**: there is no RPC that settles, the only caller is
    `memory.SignupSettlementPort`, and that port fires only after the monotonic launch guard admits a diary. "≥1
    launched star" is therefore true **by construction**, not by a check.
  - **[U11] farming the bonus** — `SignUp` declares no economy port and `SignUpResponse` has no balance field, so no
    signup path can pay anything; the bonus is reachable only through the settlement port.
  - **[U1] per-user isolation** — every `invites` statement carries `user_id = $param` except the invitee-side
    read, which is single-row and authenticated-invitee-keyed; `pnpm lint:persistence` gates the rest and the
    allowlist diff is reviewed as a [U1] change, not as tooling config.
  - **[I11] meaning-layer inviolability** — the settlement ports carry `(scope)` and `(scope, token)` only: no field
    for a memory id, mood, strength or coordinate, so an invite reward cannot touch the meaning layer.
  - **[I10] forward-only time** — the hook sits where `EarnPort.OnDiaryLaunched` sits, after `CanLaunchAt`'s early
    return: a past-dated diary that launches no star settles nothing.
  - **[I1] the system never deletes** — signup and settlement only insert and stamp; no invite row is deleted and no
    reward reversed.
- Architecture (placement): [ARCHITECTURE.md](../ARCHITECTURE.md) **§2.2** (`account` is a supporting context;
  contexts integrate through published behavior, never another's tables), **§2.3** (stay in the one-package shape —
