# Job 135: Close out unpayable achievement claims (refactor)

> Implementation work doc. Source spec: [code-review/11.jobs-116-128-demo,-sequence,-landing-and](../code-review/11.jobs-116-128-demo,-sequence,-landing-and.md).
> /cosimosi:implement-job 135 builds it via the two checklists below. When done, reflect the result into the
> SSOT (plan/policy/values) and set status: done. Write it in English.

Covers **R008 (P3, PLAUSIBLE)** — the most speculative finding in review 11, and the only one that
**must not be built before its owner decision is settled**.

**The gap.** `SettleClaims` (`apps/api/internal/achievement/claim.go:180-186`) skips a row whose
achievement has left the catalog: `row, published := LookupAchievement(...)`, and when `!published` it
`continue`s without settling or otherwise closing the row. The loop's filter at `:177` is
`if !record.Claimed() || record.Settled() { continue }`, so the row stays in scope on every future
call. It sits at `claimed_at NOT NULL, paid_at NULL` forever.

**Why that is not merely untidy.** Per the design's own statement of what that state means
(`claim.go:28-31`): "the row can SAY it: `paid_at` is stamped only once a leg returns, so the read
answers claimed-and-unsettled and the client keeps a retry affordance instead of hiding the row." So
the user is left with a permanent retry affordance for a reward that can never land. The existing
comment is candid that no retry will help — but _skipping_ is not the same as _closing_, and the
current representation has no way to say "abandoned", so it says "still owed".

**Owner decision to settle FIRST** (review 11, _Questions / Tradeoffs_). The code comments are unusually
clear that this state is understood, which raises a real possibility that it is intentional. Choose one
before writing code:

- **(a) Product rule** — "a claimable achievement never leaves the catalog." Then the correct fix is a
  **boot-time assertion**, not a new column. Cheaper, more honest, and it matches the existing
  composition-root refusals (`claim.go:161-164` notes the root already refuses to boot on a reward with
  no payable leg, both legs, or an unpublished ornament — this is the same family of check).
- **(b) It can happen** — then the row needs a way to say "abandoned", plus a read that presents it as
  closed rather than pending.

**Recommendation: (a).** It is a smaller change, it fits an existing pattern, and it converts a runtime
mystery into a startup failure. Build (b) only if the product genuinely intends to retire achievements
after they are claimable. **The checklist below branches — do only the chosen arm.**

## Owner decision — settled: **neither arm. R008 is refuted.**

T002's trace (the evidence review 11 admitted it had not gathered, and the reason it marked R008
PLAUSIBLE) decided the arm by removing both of them.

**The read cannot show the row.** `ListAchievements` (`apps/api/internal/achievement/service.go:85`)
iterates **the catalog** — `for _, row := range catalog` — and joins each catalog row to the caller's
progress record. A progress row whose achievement id has left the catalog is therefore projected into
**no `Entry` at all**. It cannot be answered as claimed-and-still-owed, and no client has a row to draw a
retry affordance on. R008's stated harm — "the user is left with a permanent retry affordance for a reward
that can never land" — **does not exist**.

**And there is no third surface.** `ListProgress` has exactly two non-test consumers: that read, and
`SettleClaims` itself. `GetProgress` has one — the claim path, which has already resolved a published id.
No admin query touches `achievement_progress`; the whole table is read by two statements
(`ListAchievementProgress`, `GetAchievementProgress`), both conjunctively user-scoped.

So:

- **Arm (b) is unimplementable as specified.** A6b asks that "the read surface presents such a row as
  closed". There is no row in the read to present. Delivering it would mean first making the read
  progress-driven — a far larger change that would _create_ the affordance R008 feared, in order to then
  suppress it.
- **Arm (a) is unimplementable as specified.** A5a asks the composition root to refuse to boot "when a
  claimable achievement id is absent from the published catalog". The catalog is a compile-time Go var, so
  at boot it **is** the definition of what exists — an id absent from it does not exist to be checked
  against. The existing refusals (`reconcileRewards`, `reconcileCounterKeys`) all compare the catalog to
  another **compile-time** set, which is exactly why they work. The only place a de-published id appears is
  a user's row in the database, and the root cannot scan that: §4's per-user isolation, and this codebase
  states `ClaimDueJob` is the one global scan it sanctions.

**How narrow the state actually is.** `ClaimAchievement` pays **synchronously** (`payReward` runs in the
claim call; the drain is only the retry leg), so reaching this row needs a deploy that drops the achievement
while some user's claim is still unsettled. There are two ways to be unsettled, and **only one of them lost
anything**: the payout failed, or it succeeded and the settle stamp did not — `stampSettled` swallows its
error by design, so a paid leg with a missing `paid_at` is a normal transient state. (An earlier draft of
this decision said the payout must have failed; codex refuted that.)

**What is accepted, explicitly.** The row costs one catalog lookup per drain, forever, and a genuinely
earned reward silently never lands with no operator signal. Both are accepted as cheaper than the
alternatives above. If the product ever does intend to retire claimable achievements as a routine
operation, the honest change is not a column but a **progress-driven read** — and that is a plan, not a
refactor.

**The deliverable is therefore a test and two documents**, not a code change: the state is already closed,
and nothing recorded that it was.

## Completion note

### What was built

Neither arm — see the settled decision in the preamble. Both arms' criteria (A5a/A6a, A5b/A6b) and their
tasks are left **unticked**: neither was built, and ticking them would misreport what shipped.

Three things landed:

1. **`TestSettleSkipsAnAchievementThatLeftTheCatalog`** (A2) in `claim_test.go`. It arranges the state
   directly — no sequence of calls against one binary can produce it, since the claim path refuses an
   unpublished id — and asserts all four halves: the drain skips without error, nothing is paid, a second
   drain is equally silent, and **the row reaches no `Entry` in `ListAchievements`** while the payable row
   beside it is answered normally and settled. That last assertion is the refutation turned into a guard:
   a read that ever **exposed** a de-published progress row would fail this test rather than quietly
   reopening the affordance.
2. **The `!published` comment** in `claim.go`, which described skipping without saying why skipping is
   _closing_. It now names the catalog-driven read, the deploy-plus-failed-payout narrowness, and the test.
3. **[tech/achievements.md](../tech/achievements.md) §9.1**, recording the semantics: why there is no
   `abandoned_at` column and no third state, that `ListProgress` has exactly two consumers, and what is
   accepted (one lookup per drain; a silently lost reward).

### Acceptance criteria

- **A1** — a claimed row whose achievement left the catalog cannot sit in a state the read reports as
  claimed-and-still-owed. True, and true before this job: the read is catalog-driven. Now pinned.
- **A2** — covered, and it runs (`--- PASS: TestSettleSkipsAnAchievementThatLeftTheCatalog`).
- **A3** — no behavior change on the payable path, in the strongest available sense: **no production logic
  was touched at all.** The only non-test, non-doc edit in the diff is a comment. `stampSettled` swallowing
  its error, `SettleClaims` attempting every row before reporting the first failure, and
  `retriedIndefinitely` are all untouched.
- **A4** — per-user isolation preserved; no statement added or changed. `pnpm lint:persistence` green.

### Review

`/codex:review` was run against the **argument**, not just the diff — the diff is a comment, so the thing
worth reviewing was the refutation itself. It was asked to refute each claim in turn: that the read is
catalog-driven, that `ListProgress` has only two consumers, that no boot-time check is meaningful, that the
claim path pays synchronously, and whether the new test would actually fail if the read changed.
Independently re-verified here by grep: `achievement_progress` is read by exactly two statements, both
user-scoped; `GetProgress`'s only caller is the claim path with an already-published id; no admin query
touches the table.

### What codex changed

It could not refute the main argument — it re-derived claim 1 independently (`ListAchievements` emits only
`for _, row := range catalog`; the RPC maps only returned entries; both apps' retry buttons derive from
`entry.claimed && !entry.rewardSettled`, so no entry means no affordance), confirmed claim 2's surface
list, and agreed claim 4 holds for a compile-time assertion. Three corrections were applied:

1. **The narrowness claim was false.** I had written that the state needs a payout that _failed_.
   `stampSettled` swallows its error, so a **successful** leg with a failed settle stamp leaves the same row
   shape — a path the suite already pins at `claim_test.go`'s `TestClaimSucceedsWhenOnlyTheSettleStampFails`.
   Corrected in the decision above, in `claim.go`'s comment and in the tech doc. It makes the state _less_
   harmful than stated, not more: in that half, the reward did land.
2. **A real bug in the new test.** It built an `ornaments` fake and then passed a _different_
   `&fakeOrnamentGranter{}` into the service, so the "paid something" assertion was watching a granter
   nothing could call. The case still passed (the payable row is twinkle-only), which is exactly why this
   is worth recording — it would have gone on passing while asserting less than it reads as. Fixed.
3. **An overstated guard.** "Fails if the read ever becomes progress-driven" is too broad: a
   progress-driven read that filtered unknown ids would pass. The claim is now the accurate one — it fails
   if the read **exposes** a de-published progress row.

### Suggested for the next review

Not a defect, and deliberately not fixed here: a stranded reward produces **no operator signal**. If that
is worth closing, the cheap form is a counter or a log line at the skip — observability, not a lifecycle
state. Recorded rather than added, because this finding turned out not to justify touching the payout path
at all.
