# Job 130: Split the web bundle at the route seam (refactor)

> Implementation work doc. Source spec: [code-review/11.jobs-116-128-demo,-sequence,-landing-and](../../code-review/11.jobs-116-128-demo,-sequence,-landing-and.md).
> /cosimosi:implement-job 130 builds it via the two checklists below. When done, reflect the result into the
> SSOT (plan/policy/values) and set status: done. Write it in English.

Covers **R001 (P1)**. The measured baseline from a real `pnpm build:web`:
`apps/web/dist/assets/index-*.js` is **3.1 MB raw / ~920 KB gzipped**, one of only two emitted JS files.
Job 120 made the landing page the public origin root, so that is what every cold visitor and every
crawler downloads before the hero paints — including the admin console, the whole demo sandbox and its
three fixture sets, and the entire signed-in universe.

**Owner decision to settle before building** (review 11, _Questions / Tradeoffs_): the landing page
genuinely needs part of `@cosimosi/3d-renderer` for `LandingHeroScene`/`LandingWalkthroughScene`, so
"lazy-load three.js" is not on the table. This job takes the **conservative split** — the boundary is
"the signed-in product + admin + demo", leaving the renderer, landing, login and blog-not-found in the
entry chunk. A reduced renderer entry for the landing's two scenes is a larger change and deliberately
**not** in scope; if the entry chunk is still unacceptable afterwards, that is a follow-up job with its
own measurement, not scope creep here.

## Completion note

### A2 — measured, before and after

Both numbers are from a real `pnpm build:web`. The honest figure is **every `modulepreload` in
`dist/index.html`**, not the entry chunk alone: rolldown (Vite 8) splits the entry's own static
dependencies into sibling chunks that the browser fetches before first paint, so quoting the entry chunk
by itself would understate what a visitor downloads.

|                                                        | raw                  | gzip (`gzip -c \| wc -c`) | JS files emitted |
| ------------------------------------------------------ | -------------------- | ------------------------- | ---------------- |
| **before** — one chunk, nothing else preloaded         | 3,140,910 B (3.0 MB) | 893,790 B (873 KB)        | 2                |
| **after** — entry chunk alone                          | 930,406 B (909 KB)   | 300,396 B (293 KB)        | 39               |
| **after** — all preloaded JS (the real cold-load cost) | 2,697,187 B (2.6 MB) | 785,788 B (767 KB)        | —                |

So the entry chunk proper is **−70%**, and what a cold visit actually downloads is **−14% raw / −12%
gzipped**. The gap between those two numbers is the point: **`three.js` is 1,619,372 B of the 2.6 MB
remainder** and reaches the entry as a _static_ dependency of the landing's own two scenes, exactly the
constraint this job's owner decision put out of scope. It is now an isolated chunk (`src-B4cshaE1.js`)
rather than inlined, which is what makes the follow-up measurable.

### Deviations from the checklist, and why

1. **Two more routes converted than T002 listed: `/test` and `/design`.** Both are diagnostics surfaces
   that `beforeLoad`-gate on `diagnosticsEnabled`, so a shipped build can never render them — yet they
   were 176 kB of every stranger's cold path (measured by building both ways). They are neither the
   public entry surface T003 protects nor the renderer the owner decision exempts, so leaving them in
   the chunk the front door blocks on would be the same defect R001 names. Recorded here rather than
   assumed.
2. **T002 said "convert in `route-screens.tsx`"; the screens moved to `app/routes/screens/`.** A chunk
   boundary is cut per _module_, so a lazily-imported screen that still shares a file with a static one
   lands right back in the entry chunk. `route-screens.tsx` keeps the static half.
3. **A3's limit is calibrated to the renderer chunk (1,700 kB), not to the entry chunk (930 kB).** A
   limit between the two would warn on `src-B4cshaE1.js` on _every_ build, and a gate that always fires
   is the same as no gate — the opposite of §4. The entry chunk's own number is recorded above and in
   `route-splitting.test.ts`, which is the ratchet that actually bites.
4. **`/me`'s `?tab=` parsing moved from `pages/me` to `app/routes/me-search.ts`** (the `diary-search.ts`
   seam). `validateSearch` runs before any chunk is fetched, so the tab vocabulary must be in the entry
   chunk — and a value import from `pages/me`'s barrel dragged `MePage` plus its nine features in with
   it, which measurably defeated the lazy boundary (`me-route` chunk: 0.29 kB → 20.14 kB once fixed).
   The type comes across as `import type`, which is erased. Reaching past the barrel to
   `pages/me/model/tabs.ts` was tried first and correctly rejected by `steiger`
   (`fsd/no-public-api-sidestep`).
5. **T007 needed no assertion changes.** `router.load()` awaits each match's route chunk
   (`loadRouteChunk` → `component.preload()`), so the existing synchronous `renderToString` assertions
   still hold against lazily-imported screens. Two new cases were added instead, for the routes T009
   names that had no coverage: `/demo` (the one _public_ route now behind a dynamic import) and
   `/blog/anything`.

### Review findings applied

- **`Object.hasOwn`, not `in`** (`me-search.ts`). The first draft's `value in ME_TAB_IDS` walked the
  prototype chain, so `/me?tab=toString` would have passed validation and crashed `MePage` destructuring
  `TAB_VIEWS[activeTab]`. Found in the self-review, independently confirmed by codex. Pinned by a test
  over `toString` / `__proto__` / `constructor`.
- **Overstated claim corrected.** The comment and test said an unusable `?tab=` "leaves the address bar
  clean"; `validateSearch` drops the key from the _match's_ search, while the raw query string survives a
  cold load until the next navigation. Not a regression — a false statement, now accurate.
- **Test could not see the leak it exists to prevent** (codex). `route-splitting.test.ts` only checked
  that a route component has `.preload`, so a future value import in `me-search.ts` would have
  reintroduced `MePage` into the entry chunk with every assertion still green. Added a source-level
  assertion (via `?raw`, the precedent in `copy-honesty.test.ts`) that any `pages/` import there is
  `import type`.
- **Not applied:** none rejected.
