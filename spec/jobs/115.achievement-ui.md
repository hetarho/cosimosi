## Acceptance Criteria (from plan/76.achievement-ui)

<!-- The source spec's acceptance criteria. After building, verify each is true in the running code. -->

- [ ] A1 The `/me` achievements tab renders the full catalog returned by `ListAchievements` in the **server-fixed order**, grouped under the nine [A2] axis headings, with unachieved rows present and readable; the FE sorts, filters and evaluates nothing, and no condition, target or reward amount is computed client-side. ([A2][A4][U9])
- [ ] A2 Each row shows a determinate progress meter reading `progress`/`target` **verbatim from the wire**, rendered through a NEW `packages/ui` `progress` primitive pair with `role="progressbar"` / `accessibilityRole="progressbar"` and correct value/min/max. ([A2][U9])
- [ ] A3 A row is exactly one of `locked` / `claimable` / `claimed`, derived by a pure function from the two server booleans; the 받기 button exists **only** in `claimable`, and no optimistic state can make an unpaid row look paid. ([A4])
- [ ] A4 Pressing 받기 issues `ClaimAchievement{achievement_id}` and nothing else — the request carries no `user_id`, no amount, no ornament id and no counter — and the mutation fires only from a press handler, never from an effect, mount, or focus. There is no auto-claim path in the codebase. ([A4][U1])
- [ ] A5 A successful claim opens a reward reveal naming the granted `GENERAL` amount and the new total (and, when present, that an ornament was granted), dismissible and offering **no** navigation; the reveal is a dialog, not a self-dismissing toast, so the recognition moment [A4] asks for cannot be missed. ([A3][A4])
- [ ] A6 A claim invalidates the `AchievementService` read and the twinkle balance, and — only for an ornament reward — [71]'s `GetCatalog`; the stardust tab shows the credit as an ordinary ledger row on next open. No surface polls. ([G7], ARCHITECTURE §3.2)
- [ ] A7 Only one claim can be in flight at a time, enforced by a single `asyncCommandMachine` instance whose context holds the achievement id and no server data; **no new machine file is authored** in either app. (ARCHITECTURE §3.2)
- [ ] A8 A repeat claim is treated as success, not an error: no `ALREADY_CLAIMED` mapping exists, and `ACHIEVEMENT_REWARD_UNAVAILABLE` surfaces copy stating the reward is kept, **leaving the button enabled** so the replay can heal it. `ACHIEVEMENT_NOT_ACHIEVED` / `ACHIEVEMENT_NOT_FOUND` additionally invalidate the list. ([75.achievement-tracking-usecase](75.achievement-tracking-usecase.md))
- [ ] A9 The [A5] unlock notice is derived **only** by diffing consecutive `ListAchievements` results — no push, no subscription, no polling, and no RPC in this unit that could report an achievement. ([A5], ARCHITECTURE §2.7)
- [ ] A10 The first resolution after mount enqueues nothing, so a returning user with unclaimed achievements sees no toast burst at sign-in; at most `values.achievement.unlockNoticeMax` notices are enqueued per resolution. ([A5])
- [ ] A11 The notice carries the achievement's name and where it waits — no reward figure, no button, no navigation — and dismisses after `values.achievement.claimToastMs`. ([A5])
- [ ] A12 `useInvalidateAchievements()` is called from every in-session progress-recording resolution: the four surfaces that already invalidate the twinkle balance, plus the release/let-go resolution and the decoration save. ([A5], plan 75's call sites)
- [ ] A13 Exactly **one** `Toast` element can exist in the tree: `packages/ui` owns a queued toast context, one forked host per app renders the head entry, and both the error path and the achievement notice push into it. `useErrorToast` consumers and `presentAppError` are unchanged.
- [ ] A14 `packages/achievement` and both feature slices depend on **none** of `@cosimosi/memory`, `@cosimosi/memory-logic`, `@cosimosi/universe`, `@cosimosi/emotion`, `@cosimosi/store` or `@cosimosi/3d-renderer`, enforced by package manifests plus a scoped `no-restricted-imports` group; no type, prop or handler in this unit names a memory, star, position, strength, mood, decay stage or gist stage. ([A6][I11], [00.overview](00.overview.md) §3)
- [ ] A15 No `store_*` message key is read and no ornament is named on this surface; an ornament reward renders as one `achievement_*` line. ([P11])
- [ ] A16 Every string resolves through `packages/i18n` in **both** `en.json` and `ko.json` under the `achievement_*` prefix, regenerated with `pnpm gen:messages` and gated by `check:gen`; `pnpm lint:raw-strings` passes; an achievement id with no copy entry falls back to a plain label and remains fully claimable.
- [ ] A17 The tab and the notice ship on **web and mobile** with `packages/achievement` consumed verbatim and only `ui` forked; `me_achievements_pending` and its copy are retired with **both** placeholder rows they described (web's `TAB_VIEWS` row and mobile's inline `tabViews` row), including the mobile `App.test.tsx` assertion on that key. ([00.overview](00.overview.md) §4, [64.my-page](64.my-page.md))
- [ ] A18 `/me?tab=achievements` remains a valid deep-link target with the list as its landing content — [67] is **already shipped** and already routes its insufficient-balance recovery here (today it dead-ends on the placeholder), so this is a live regression surface, not a future contract. ([64.my-page](64.my-page.md))

**Tuning**

- [ ] T001 **(gen:values)** Two keys in the `achievement` group job 113 created: `claim_toast_ms` (the unlock notice's
      dwell — longer than a glance, **shorter than** `errors.toast_auto_dismiss_ms` = 6000, because an error must be read
      and an achievement only noticed; the key name deliberately stays as-is) and `unlock_notice_max` (the per-resolution
      notice cap). `pnpm gen:values`.

**The shared package (`packages/achievement` — a v2 domain mirror is a package, never `entities/`)**

- [ ] T002 `achievement.ts` — `AchievementView` (proto DTO → FE mirror) + the axis re-export.
- [ ] T003 [P] `achievement-copy.ts` — the id→copy projection in the exact shape of `packages/emotion/src/mood-label.ts`:
      a `Record` of `{title, body}` message accessors (`m.achievement_<id>_title` / `_body`) plus `axisLabel(axis)` over
      the nine axes, static accessors so `gen:messages` / `check:gen` / `lint:raw-strings` see them. An id with **no**
      copy entry falls back to `achievement_untitled` and **still renders its progress and its 받기 button** — copy
      completeness is a content gate, claimability is a correctness one. A package test asserts the `Record` covers every
      id the app knows.
- [ ] T004 [P] `progress.ts` — `progressRatio(progress, target)` (display arithmetic over two server integers) and
      `claimState(entry)` → `locked | claimable | claimed`, a pure function over **two server booleans**: no local
      "optimistically claimed" state and no optimistic patch, so a failed claim can never leave a row looking paid.
- [ ] T005 [P] `unlock-diff.ts` — `newlyAchieved(previous, next)`, a pure set diff with **no clock**, where
      `newlyAchieved(undefined, next)` returns `[]` by construction so the first resolution of a session notifies
      nothing.
- [ ] T006 `react/achievements.ts` (`useAchievements()` · `useInvalidateAchievements()`) and `react/claim.ts`
      (`useClaimAchievement()`, which invalidates **only** the `AchievementService` key — the other invalidations are
      composed at the feature, which keeps this package free of a `@cosimosi/store` dependency).

**The two primitives and the one toast host**

- [ ] T007 `packages/ui/src/primitives/progress.tsx` + `progress.native.tsx` — the determinate meter pair, reading
      `progress`/`target` verbatim. Add its specimen to the design showcase.
- [ ] T008 `packages/ui/src/toast-queue.ts` — `ToastQueueContext`, `usePushToast()`, `ToastEntry{id, variant, message,
durationMs}`; platform-pure (React only — **no DOM, no i18n**, `message` is an already-resolved string), exported
      from both `index.ts` and `index.native.ts`, modelled on `packages/errors/src/react.ts`.
- [ ] T009 `apps/{web,mobile}/src/app/providers/toast-provider.tsx` (**NEW**) holds the queue and renders **the head
      entry only** through the shipped `Toast`, shifting on dismiss or timeout. Edit `error-provider.tsx` on both apps so
      `showError` **pushes** `{variant: presentation.severity, message, durationMs: VALUES.errors.toastAutoDismissMs}`
      instead of holding its own state and `Toast` — `ErrorToastContext` and `presentAppError` stay exactly as they are
      and no consumer of `useErrorToast` changes. At most one `Toast` exists in the tree, so two owners cannot overlap.

**The tab (`features/achievement-list`, composed by `pages/me`)**

- [ ] T010 `AchievementList` renders the server-fixed order **verbatim and sorts nothing**, grouped under the nine axis
      headings, with every unachieved row present and readable. Each row: title, one-line body, the determinate meter,
      the reward line, and the `claimState` affordance (`locked` → meter only · `claimable` → the enabled 받기 button ·
      `claimed` → a quiet 받았어요 line). A header states how many rewards are waiting
      (`achievement_claimable_count`) — the **only** summary; **no badge, dot or count** on the tab label or the universe
      HUD, because a nag would undo the trade a manual claim is making.
- [ ] T011 The reward line: a stardust reward shows the server-resolved amount; an ornament reward shows the single
      `achievement_reward_ornament` line and **does not name the ornament** — [P11] puts the item's identity in 우주
      꾸미기 next to its acquisition condition, and a second name for the same object on a second surface is the drift the
      one-key-one-role rule exists to prevent.
- [ ] T012 Bind the shipped `asyncCommandMachine` (`packages/state-machine`) with the pressed `achievementId` as its
      command id — **no new machine**. One claim in flight at a time, so a second row's button cannot start a second
      claim and the double-claim window narrows to the server's `UNIQUE (user_id, achievement_id)` guard.
- [ ] T013 On `succeeded` open **`RewardRevealDialog`** — the shipped `Dialog` pair, deliberately **not** a toast,
      because a self-dismissing toast is exactly a moment that can be missed. It names the amount and the new total,
      names an ornament reward as an ornament, offers a single dismissal, and offers **no navigation** (sending the user
      to 우주 꾸미기 from a reward would turn claiming into a funnel). Compose the two extra invalidations here: the
      shipped `useInvalidateTwinkleBalance()`, and — only when `grantedOrnamentId` is non-empty — job 110's `GetCatalog`.
- [ ] T014 Map the five `ACHIEVEMENT_*` reasons through `packages/errors` onto the shared toast host. Pin the
      non-obvious one: `ACHIEVEMENT_REWARD_UNAVAILABLE` means the claim **was recorded** and the payout failed, so its
      copy says the reward is kept and to try again and **the button stays enabled** — disabling it would strand the
      reward in the crash window the replay heals. `ACHIEVEMENT_NOT_ACHIEVED` / `ACHIEVEMENT_NOT_FOUND` mean a stale
      list: toast **and** invalidate. There is no `ALREADY_CLAIMED` reason to map.

**The notice ([A5] — a diff of a read, never a push)**

- [ ] T015 `features/achievement-notice/ui/AchievementNoticeHost` mounts `useAchievements()` once per session and, on
      every resolution, runs `newlyAchieved` against a `useRef` snapshot of the previous `{id → achieved}` map; ids that
      flipped and are still unclaimed become notices, capped at `unlock_notice_max` per resolution with the rest dropped
      (the tab, not the toast, is where achievements are confirmed). One line naming the achievement and where it waits —
      **no reward figure, no button, no navigation**; dwell is `claim_toast_ms`. The queue is **component state, not
      Zustand**: a store surviving sign-out would carry one user's unlock into another's session, so its lifetime _is_
      the guarantee.
- [ ] T016 Mount the host **inside the authenticated subtree only** — web in `AuthenticatedLayout`
      (`app/routes/route-screens.tsx`), mobile in the authenticated branch of `app/navigation/NavigationRoot.tsx`. That
      one placement is the guard for three things at once: a signed-out visitor never fetches `ListAchievements`,
      `/demo` cannot mount the watcher, and sign-out unmounts the snapshot ref.
- [ ] T017 Add `useInvalidateAchievements()` to the resolved-action handlers that already invalidate the balance
      (`widgets/{recall-flow,star-detail,diary-reader,stardust}`) **plus** the two progress-recording actions that move
      no Twinkle: the **Release resolution** in `widgets/deletion-flow` (a new seam — that widget invalidates nothing
      today; a let-go records nothing) and the save resolution in job 112's decoration panel. Exhaustive against plan
      75's in-session producer sites; the invite settlement happens before the watcher mounts and surfaces on the next
      read.

**Copy, tests, SSOT**

- [ ] T018 i18n under `achievement_*`: the per-id `_title`/`_body` pairs, the nine axis labels,
      `achievement_claimable_count`, `achievement_reward_twinkle`, `achievement_reward_ornament`,
      `achievement_untitled`, the notice line, and the five reason strings. Voice: restrained and plain — 받기 / 받았어요,
      no exclamation, no decorative emoji, no congratulation the product has not earned. `pnpm gen:messages`;
      `lint:raw-strings` gates it.
- [ ] T019 Tests: the first resolution notifies nothing; a burst is capped; the queue dies with its host; `claimState`
      covers the three states and nothing else; a failed claim leaves the row unclaimed; `REWARD_UNAVAILABLE` keeps the
      button enabled; an unknown id renders `achievement_untitled` and stays claimable; only one claim can be in flight;
      the copy `Record` covers every known id; one `Toast` element exists with an error's severity and dwell preserved.
- [ ] T020 SSOT at implement: NEW `spec/policy/ux/achievements.md` (the tab, the three states, the dialog-not-toast
      reveal, the capped figure-free notice, no badge outside the tab, and the widened one-host toast contract so a later
      surface does not add a third portal); append the five reasons + the stays-enabled rule to
      `spec/policy/platform/errors.md`; record the `progress` primitive and the toast-queue contract in
      `spec/tech/design-system.md` and the `achievement_*` id→copy projection in `spec/tech/i18n.md`. No new
      `tech/*.md` file — the context doc is plans 74/75's `tech/achievements.md`.
