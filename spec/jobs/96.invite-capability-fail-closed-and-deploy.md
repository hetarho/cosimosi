# Job 96: Invite capability fail closed and deploy credential gating (refactor)

> Implementation work doc. Source spec: [code-review/09.epic-k-account-runtime-and-gate-audit](../code-review/09.epic-k-account-runtime-and-gate-audit.md).
> /cosimosi:implement-job 96 builds it via the two checklists below. When done, reflect the result into the
> SSOT (plan/policy/values) and set status: done. Write it in English.

Covers **R003** (P1), **R013** (P3), and **R015** (P3) — one theme: _silent degradation where the neighbour fails
closed_. Today a production API without `INVITE_TOKEN_SIGNING_KEY` runs with the whole [G6] invite chain inert and
nothing to distinguish it from "nobody used an invite".

**Decide before building** (Questions / Tradeoffs in review 09): fail closed at boot, or degrade loudly? The review
recommends **fail closed in production** because the invite reward has economic consequences and a silent half-working
state is worse than a refused deploy — but this is the owner's call, and it changes T002/T003. Confirm it first.

## Acceptance Criteria (from code-review/09.epic-k-account-runtime-and-gate-audit)

- [ ] A1 One consistent fail-closed policy applies to every credential the account context needs. The invite signer no
      longer degrades silently while its sibling `requireProductionCredentialDirectory` hard-fails 20 lines away in the
      same file: in production, a missing `INVITE_TOKEN_SIGNING_KEY` either refuses composition (recommended) or is
      logged/alerted at boot — never both silent and inert.
- [ ] A2 `acceptInvite` distinguishes "capability unavailable" from "token invalid/replayed". A verification failure
      caused by an absent signer is no longer indistinguishable from an expected best-effort refusal; the unavailable
      case is observable (logged/counted), while a genuinely invalid or replayed token stays a silent no-op as designed.
- [ ] A3 `INVITE_TOKEN_SIGNING_KEY` is present in `.env.production.example` with an accurate comment, and in the deploy
      script's `require_nonempty_env` list, so a production deploy without it fails before pull/quiesce.
- [ ] A4 The `.env.example` comment states the full blast radius. It currently mentions only that `GetInviteLink` fails
      closed and omits that **signup-time invite binding silently no-ops** — the more damaging half.
- [ ] A5 A probe test proves the production refusal actually fails, in the same style as
      `TestProductionWorkerRejectsMissingCredentialDirectory` — the guard is proven by a violation, not by reading it.
- [ ] A6 The worker's no-op reward granters no longer conform silently: if a future caller reaches `SettleSignup` in the
      worker process, it fails loudly instead of completing successfully having credited nothing.
- [ ] A7 The deploy health/CORS verification runs for **staging as well as `main`**, with origins parameterized per
      environment rather than hardcoded to production.
- [ ] A8 **No behavior change** in the configured path: with the key present, invite issuance, binding, settlement, and
      the [G6] lifetime cap behave exactly as today. Nothing about the HMAC payload, token format, or TTL changes.
