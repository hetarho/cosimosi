# Job 123: Achievement notice host shared seam (refactor)

> Implementation work doc. Source spec: [code-review/10.jobs-94-115-achievement,-decorate-and-sh](../code-review/10.jobs-94-115-achievement,-decorate-and-sh.md).
> /cosimosi:implement-job 123 builds it via the two checklists below. When done, reflect the result into the
> SSOT (plan/policy/values) and set status: done. Write it in English.

Covers **R002** and **R003** (both P2) — one seam, seen from two sides. Both are cases where a comment asserts a
property the code does not have, which is review 10's leading cross-cutting theme.

`AchievementNoticeHost.tsx` is **byte-identical** in both apps (56 lines, `cmp` confirms it), and platform-pure: it
returns `null`, touches no DOM and no RN element, and its only app-relative import is `shared/i18n`. What is duplicated
is 40 lines of real logic — the `pushNotice` shape, the `formatNotice` resolver, and the `lastUserId` ref effect whose
comment explains a development-mode double-effect hazard that now has to be maintained twice.
`packages/achievement/src/react/unlock-notice.ts:8-11` already names this exact risk and claims both hosts are "a short
shell over this". The extraction stopped one layer short.

Meanwhile `SESSION_SCOPED_TOAST_OWNERS` (`packages/ui/src/toast-queue.ts:60-65`) declares itself the SSOT for the
session-scoped owner tag — "so adding a session-scoped toast is one edit in one place" — and has **zero consumers**.
The tag it should own is a private `NOTICE_OWNER = 'achievement-notice'` literal, duplicated in both hosts. Three
copies of one magic string with a comment asserting there is one.

**Direction (review 10 offers two; this job takes (b)).** Give the constant the consumer its comment describes, rather
than deleting it. The reason is that the real session boundary already exists and is already the right place: both apps
mount `SessionScopeBoundary onScopeChange={resetScope}` inside `WebClientCacheProvider` / the mobile equivalent, which
sits **inside** `WebToastProvider` — so `useToastQueue()` is reachable there. Moving the drop into that boundary makes
the constant load-bearing, removes the `lastUserId` ref effect and its double-effect hazard from both hosts, and puts
the scope-change drop beside every other per-user reset instead of in a feature.

      contains no duplicated logic, no diff, no cap, and no scope-change effect.

      `packages/ui`, and the pushing surface and the dropping surface cannot disagree about it.

      surface for whoever signs in next, and the queue still never learns a user id. The development-mode

      home is a scope-change callback rather than an effect keyed on identity, so the reasoning changes and the comment
