## Architecture Baseline

The rules judgment was measured against:

- **Backend domain-first Go (§2.3–2.4).** Context packages own behavior; `pg`/`rpc` are adapters that
  map row↔domain and proto↔domain; ports are consumer-declared; `cmd/` is the only place that sees
  every concrete. Cross-context integration goes through published behavior, never another context's
  tables (§2.3).
- **Forbidden patterns (§2.9).** No business logic in the RPC handler (#7); no computed relationship as
  source of truth (#3); no proto/sqlc types inward (#4); no implementation-side interfaces (#6).
- **Derived, not stored (§4).** Anything computable from stored facts is computed at read time.
- **Config is generated (§4).** Tuning scalars flow `spec/values.yaml` → `pnpm gen:values`, never as
  code consts.
- **Per-user isolation (§4).** Every product table carries `user_id`; every statement is conjunctively
  scoped; enforced semantically by `pnpm lint:persistence`.
- **FSD + promote-on-reuse (§3.1, §3.5).** Six layers, one-way imports. "If two slices need the same
  thing it promotes **down** a layer — never copied sideways." Pure cross-app code lives in
  `packages/`; a `*.native.tsx` sibling exists only where a primitive genuinely differs.
- **Gates fail loudly (§4).** No warning suppression, no force-exit; every documented rule needs an
  executable guard _and_ a probe proving a violation fails.
- **The constitution.** `[I1]` (the system never deletes; only the user's own withdrawal),
  `[I11]` (customization cannot touch the meaning layer), and the guardrail table's ban on giving
  emergent structures a type or table.

The achievement epic holds up unusually well against this baseline: the catalog is code rather than a
table ([I1]/§2.9 #3), progress is derived at read time, the context imports neither the economy nor the
ornament catalog (both arrive as consumer-owned ports closed at the composition root), the service is
deliberately given **no clock** so a streak condition is unexpressible, and boot-time reconciliation
refuses to start on producer/catalog counter-key drift. The findings below are mostly at the seams
around it, not in its core.

## Findings

### R001 A post-commit payout failure strands an achievement reward permanently, with no recovery surface

- Priority: **P1**
- Area: backend `achievement` claim lifecycle + both apps' achievement list
- Evidence:
  - `apps/api/internal/achievement/claim.go:36-78` — `ClaimAchievement` commits `claimed_at` inside
    `InAchievementTx`, then calls `s.payReward(...)` **after** the commit.
  - `apps/api/internal/achievement/claim.go:114-133` — `payReward` returns
    `ErrRewardUnavailable` if either leg fails; nothing rolls back the stamp.
  - The design intends this to self-heal. `claim.go:27-31`: _"That leaves exactly one intermediate
    state — claimed but uncredited, after a crash — and it is RECOVERABLE rather than lost: a repeat
    claim falls through as a replay and pays through the same dedup keys."_ Echoed at
    `apps/api/internal/achievement/errors.go:57-60` and `rpc/reasons.go:11-13`.
  - But the read cannot express the intermediate state:
    `apps/api/internal/achievement/service.go:85` sets `entry.Claimed = record.ClaimedAt != nil` —
    claimed-and-paid and claimed-and-unpaid are the same wire value.
  - So the client hides the affordance: `packages/achievement/src/progress.ts:18-21`
    (`if (entry.claimed) return 'claimed'`) and
    `apps/web/src/features/achievement-list/ui/AchievementRow.tsx:41-48` — the `Button` renders only
    for `state === 'claimable'`. Same on mobile (`apps/mobile/.../AchievementRow.tsx`).
  - The one thing holding the recovery window open is a **stale client cache**.
    `apps/web/src/features/achievement-list/ui/AchievementList.tsx:80-88` deliberately does _not_
    invalidate on the payout refusal: _"Every other refusal — including the payout one, where the claim
    IS recorded — leaves the row as it is so the button stays pressable and the replay can heal it."_
  - That window is closed by any of **twelve** other call sites. `useInvalidateAchievements()` is
    called from `StardustOverlay.tsx:59`, `DeletionFlowSheet.tsx:105`, `DecorationPanelSheet.tsx:71`,
    `GistViewSheet.tsx:84`, `RecallFlowSheet.tsx:182`, `DiaryReaderBlock.tsx:215` — on **both**
    platforms. One refetch answers `claimed: true`, the button is gone for good.
  - No server-side reconciliation exists: `grep -rni "unpaid\|reconcile.*claim" apps/api --include='*.go'`
    returns nothing, `apps/api/cmd/worker/main.go` registers only the withdrawal purge leg
    (`main.go:73`), and the admin context has no achievement surface at all
    (`grep -rn achievement apps/api/internal/admin proto/cosimosi/admin` → empty).
- Why it matters: a single transient failure of `twinkle.EarnAchievementReward` or
  `store.GrantOwnership` — a pooler blip, a deploy restart between the commit and the payout — silently
  and permanently destroys a user's reward. Both the capstone ornaments (`star_500`,
  `shared_neuron_8`) and every tier-3 stardust payout (400 twinkle) are exposed. The user is told
  "받음"; the operator has no query that finds the gap; the code's own stated guarantee is unreachable.
  This is the one finding in the batch where the documented invariant and the shipped behavior
  disagree about something the user can lose.
- Recommendation: make the unpaid state representable and reachable, rather than relying on cache
  staleness. Cheapest correct shape: since `claim_id` is already the dedup key both legs carry, add a
  `paid_at TIMESTAMPTZ` (or a `reward_settled BOOLEAN`) to `achievement_progress`, stamp it in
  `payReward`'s success path, and surface `claimed && !paid` as a distinct `ClaimState` (`'unpaid'`)
  whose affordance is "받기 다시 시도". Add a worker sweep over `claimed_at IS NOT NULL AND paid_at IS
NULL` so recovery does not depend on the user pressing again at all — the legs are already idempotent
  on the claim id, so the sweep needs no new dedup reasoning. Failing that, at minimum keep the row
  `claimable` server-side until the payout lands.
- Suggested job split: one job — "achievement claim settlement is durable and recoverable" — covering
  the migration, `payReward`, the proto field, `progress.ts`, both `AchievementRow`s, and the worker
  sweep. R005 belongs with it.

### R002 `SESSION_SCOPED_TOAST_OWNERS` has no consumer, and the SSOT it claims to be is contradicted by two duplicated literals

- Priority: **P2**
- Area: `packages/ui` toast queue + both apps' achievement notice host
- Evidence:
  - `packages/ui/src/toast-queue.ts:60-65` declares the constant with an explicit SSOT rationale:
    _"The owners whose entries belong to one signed-in session. Named here rather than in either app so
    the session boundary and the pushing surface cannot disagree about the tag — and so adding a
    session-scoped toast is one edit in one place."_
  - It is re-exported from `packages/ui/src/index.ts:10` and `packages/ui/src/index.native.ts:19`.
  - It has **zero consumers**. `grep -rn "SESSION_SCOPED_TOAST_OWNERS" apps packages` matches only the
    declaration and the two barrels.
  - The tag it is supposed to own is instead a private literal, duplicated per app:
    `apps/web/src/features/achievement-notice/ui/AchievementNoticeHost.tsx:56` and
    `apps/mobile/src/features/achievement-notice/ui/AchievementNoticeHost.tsx:56` both declare
    `const NOTICE_OWNER = 'achievement-notice'`.
  - There is also no "session boundary" consumer of the kind the comment describes: the host does its
    own per-`userId` drop (`AchievementNoticeHost.tsx:44-49`), so the constant's stated purpose is
    served by nobody.
- Why it matters: three copies of one magic string with a comment asserting there is one. The next
  session-scoped toast owner will be added to whichever copy the author happens to find, and the
  drop-on-scope-change will silently miss it — the exact failure the constant was written to prevent.
  A comment that contradicts the code is worse than no comment (`spec/principle/code-comments.md`).
- Recommendation: pick one direction and make it true. Either (a) delete
  `SESSION_SCOPED_TOAST_OWNERS` and let each host own its tag — then fix the comment; or (b) preferred,
  give it the consumer it describes: export the owner tag as a named constant from `packages/ui`
  (`ACHIEVEMENT_NOTICE_TOAST_OWNER`), have both hosts import it, and move the scope-change drop into
  the session boundary iterating `SESSION_SCOPED_TOAST_OWNERS` — which also removes the duplicated
  `userId`-watching effect from both hosts. (b) composes with R003.
- Suggested job split: one job with R003 — "the achievement notice host is one shared seam".

### R003 `AchievementNoticeHost.tsx` is byte-identical in both apps, and the FSD gate structurally cannot see it

- Priority: **P2**
- Area: FSD promote-on-reuse + `scripts/lint-fsd-layout.mjs` coverage
- Evidence:
  - `cmp apps/web/src/features/achievement-notice/ui/AchievementNoticeHost.tsx
apps/mobile/src/features/achievement-notice/ui/AchievementNoticeHost.tsx` → **identical** (56 lines).
    `features/achievement-notice/index.ts` is identical too.
  - The file is platform-pure: it renders nothing (`return null`, line 52), touches no DOM and no RN
    element, and its only app-relative import is `../../../shared/i18n/index.ts`.
  - The duplication is 40 lines of real logic, not a barrel: the `pushNotice` shape, the
    `formatNotice` resolver, and the subtle `lastUserId` ref effect whose comment
    (lines 42-43) explains a development-mode double-effect hazard — reasoning that now has to be
    maintained in two places.
  - `packages/achievement/src/react/unlock-notice.ts:8-11` states the intended shape and names this
    exact risk: _"Both apps' hosts are a short shell over this … the body was duplicated
    byte-for-byte at first, which is exactly the drift the promote-on-reuse rule prevents (an edit had
    to be written twice, and the next one would eventually be written once)."_ The extraction stopped
    one layer short.
  - The R4 guard cannot catch it. `scripts/lint-fsd-layout.mjs:29-30`:
    `PURE_MODULE_SEGMENT = /(^|\/)(api|model|lib|config|shared)(\/|$)|(^|\/)app\/(providers|model)(\/|$)/`
    — a path under `features/<slice>/ui/` matches no arm, so `lint-fsd-layout.mjs:135-155` skips the
    pair before hashing it. `pnpm lint:fsd:layout` passes.
- Why it matters: ARCHITECTURE §3.1 says duplication "promotes **down** a layer — never copied
  sideways", and §3.5 restricts a native sibling to primitives that "genuinely differ". This one does
  not differ at all. The gate that exists to enforce exactly this reports success, so the rule is
  documented-but-unenforced for the whole `ui` segment — and `ui` is where a platform-pure hook shell
  most plausibly lands.
- Recommendation: promote the body into `packages/achievement/src/react/unlock-notice.ts` as
  `useAchievementNotice({ push, dropByOwner, userId, formatNotice })`, leaving each app a genuine
  shell that only resolves `m.achievement_notice` and the toast queue. Then widen R4: a file under a
  `ui` segment that contains no platform import (no `react-native`, no JSX intrinsic beyond none, no
  DOM global) is a pure module for R4's purposes. Add a probe fixture so the widened rule is proven to
  fail, per §4's "enforced, not hoped".
- Suggested job split: one job with R002. The R4 widening can also absorb R006's guard-scope fix.

### R004 The achievement RPC handler is the only context adapter with no test, and it owns two total-by-convention mappings

- Priority: **P2**
- Area: `apps/api/internal/achievement/rpc` test coverage
- Evidence:
  - `ls apps/api/internal/*/rpc/*_test.go` → `account`, `admin` (×2), `memory`, `store`, `twinkle`.
    `apps/api/internal/achievement/rpc/` contains only `reasons.go` and `server.go`.
  - Confirmed by the gate's own output: `pnpm test:api` reports
    `? github.com/cosimosi/api/internal/achievement/rpc [no test files]`.
  - What is untested:
    - `rpc/server.go:103-126` `protoAxis` — a 9-arm switch that is total only by convention, with
      `default:` falling through to `ACHIEVEMENT_AXIS_UNSPECIFIED`. A tenth axis added to
      `catalog.go:24-33` without a proto arm serializes silently as UNSPECIFIED; the FE groups by the
      wire value (`packages/achievement/src/achievement.ts:45-59`, deliberately response-driven), so
      the rows render under an unresolvable heading rather than failing.
    - `rpc/server.go:131-144` `domainError` — the error→reason classification, including the
      `ErrRewardUnavailable → CodeUnavailable/reasonRewardUnavailable` arm that R001's entire recovery
      story depends on, and which the FE branches on at `AchievementList.tsx:83-88`.
    - `rpc/server.go:51-54` the RFC3339 `achievedAt` formatting and its zero-time empty-string case.
  - A wire-type asymmetry also sits unexercised here: `rpc/server.go:60` maps the same quantity as

  `claim_test.go`, `service_test.go`, plus a real-DB `pg/store_integration_test.go` and
  `cmd/api/achievement_integration_test.go` — which makes the handler gap look like an oversight
  rather than a decision.
- Recommendation: add `apps/api/internal/achievement/rpc/server_test.go` in the shape of
  `store/rpc/server_test.go`: assert `protoAxis` is total over `achievement.Catalog()`'s axes (so a new
  axis fails the test rather than degrading the wire), table-test `domainError` over all five
  sentinels, and cover the blank-id and zero-`AchievedAt` cases. Settle `rewardTwinkle` on one wire
  width while the proto is still young.
- Suggested job split: one job — "achievement transport adapter coverage and wire-type consistency".

### R005 The catalog's reward-XOR invariant is test-only, while its sibling invariant is boot-enforced

- Priority: **P3**
- Area: backend `achievement` catalog / composition root
- Evidence:
  - `apps/api/internal/achievement/types.go:31-33` states the invariant and names its owner: _"Reward
    is one leg, exactly: a stardust tier, or an ornament id — never both, never neither (the catalog
    self-test's invariant)."_
  - It is checked only in `apps/api/internal/achievement/catalog_test.go:48-53`.
  - The adjacent invariant is enforced at boot instead:
    `apps/api/cmd/api/achievement.go:135-152` `reconcileAchievementRewardOrnaments` already iterates
    `achievement.Catalog()` and refuses to start when a reward names an ornament the store catalog does
    not publish as achievement-only.
  - The consequence of a neither-leg row is not a benign no-op: `Reward.Twinkle()`
    (`types.go:41-52`) returns `0` for `RewardTierNone`, `payReward` (`claim.go:128-129`) passes it to
    `EarnAchievementReward`, and `apps/api/internal/twinkle/service.go:436-438` rejects
    `amount <= 0` with `ErrGrantAmountInvalid` → wrapped as `ErrRewardUnavailable`. Every user who
    claims that row lands in R001's stranded state, deterministically.
- Why it matters: two invariants of equal weight over the same table, enforced at two different
  strengths. The test does run in CI, so this is defense-in-depth rather than a live defect — but the
  boot guard is already looping over the same rows, so closing it is ~4 lines, and the failure mode it
  prevents is silent permanent value loss rather than a crash.
- Recommendation: move (or mirror) the XOR check into `reconcileAchievementRewardOrnaments`, renaming
  it to something like `reconcileAchievementRewards`, so a malformed catalog row fails the boot the way
  an unpublished ornament id already does. Keep the unit test.
- Suggested job split: fold into R001's job — same file, same failure mode.

### R007 An achievement-granted ornament never reports `ornament_owned`, so the reach counter lags the table

- Priority: **P3**
- Area: backend `store` ↔ `achievement` counter reporting
- Evidence:
  - `apps/api/internal/store/service.go:143-167` `GrantOwnership` is the shared entry point for both
    ownership legs (its own comment, line 135: _"Both legs land here — the purchase and the achievement
    reward"_). It inserts the ownership row and reports **no** achievement counter.
  - The only `ornament_owned` producer is the decorate path:
    `apps/api/internal/store/decorate.go:345` reports it as
    `len(ownedIDs)+len(acquired)`, and only when `len(changedKinds) > 0`
    (`decorate.go:339-341`).
  - So claiming `star_500` or `shared_neuron_8` — the two ornament capstones
    (`apps/api/internal/achievement/catalog.go:83,107`) — grows ownership without moving the counter
    that `ornament_3` / `ornament_8` / `ornament_15` (`catalog.go:118-120`) read.
- Why it matters: bounded and self-healing rather than wrong — `ornament_owned` is a **reach** counter
  (`counters.go:131`), so the next decoration save that changes something reports the true total and
  `GREATEST` catches up. But a user who claims a capstone and then never re-decorates sits below the
  ownership tier they have actually reached, and the delay is invisible. `decorate.go:326-331` already
  documents an accepted one-save lag for concurrent saves; this second, longer-lived lag is not
  documented anywhere.
- Recommendation: decide and record which it is. Either report `ornament_owned` from the grant path
  (it would need the ownership count, so likely a small read inside `GrantOwnership`'s transaction), or
  state the lag explicitly next to `decorate.go`'s existing note so the next reader does not treat it
  as a bug. Prefer the former: the counter is a high-water mark, so an extra report can only ever be
  correct or a no-op.
- Suggested job split: small backend job, groupable with R005 under "achievement counter and reward
  edge cases".

## Cross-Cutting Themes

- **The comment is the specification, and it has started to outrun the code.** This batch's comments
  are unusually good — they carry the _why_, name the alternatives rejected, and cite invariants. That
  makes them load-bearing, and three findings are cases where the prose asserts a property the code
  does not have: the recoverable-claim guarantee with no client that can trigger it (R001), the
  single-source owner tag that is duplicated twice (R002), and the "short shell over the package" host
  that is a byte-identical fork (R003). The root cause is not carelessness — it is that a comment
  describing an _intended end state_ was written while the last extraction step was still pending, and
  nothing executable notices the difference.
- **Guard scope drifted behind where files actually live.** Two guards pass because their path/segment
  filters no longer reach the code the rule is about: R4's `PURE_MODULE_SEGMENT` misses
  `features/*/ui` (R003), and the comment lint's `SRC_GLOBS`/`CODE_EXT` miss `proto/` (R006). Both were
  correct when written. Neither is wrong about _what_ to forbid — only about _where_ to look. Worth a
  standing habit: when a new file kind or segment starts holding pure/SSOT content, re-read the guard
  that claims to cover it.
- **Cross-context payout is transactionally honest but operationally incomplete.** The decision to pay
  rewards _after_ the claim commits is right (§2.3 — achievement must not own twinkle's or store's
  tables), and both legs are genuinely idempotent on the claim id. What is missing is the other half
  of that trade: an at-least-once design needs a retry driver. R001 and R005 are the same hole seen
  from two angles, and R007 is the mirror image — a cross-context _report_ that no path drives.
- **Enforcement asymmetry between siblings.** Equal-weight invariants get unequal strength: the
  ornament-publication check runs at boot while the reward-XOR check is a unit test (R005); five
  contexts test their RPC adapter and one does not (R004). Both are cheap to level up precisely because
  the stronger mechanism already exists next door.

## Questions / Tradeoffs

- **R001's shape.** A `paid_at` column is the honest fix but touches the migration chain and the proto.
  A cheaper variant — keep the row `claimable` until the payout lands — needs no schema change, but
  makes `claimed_at` no longer mean "the user pressed the button", which the double-payout guard
  (`achievement.sql:63-68`) currently relies on. Worth deciding before the job, not during it.
- **Does the worker sweep need a cap?** An unpaid-claim sweep that retries a permanently-failing leg
  (e.g. a catalog row whose ornament was unpublished) would retry forever. The boot reconciliation
  (`achievement.go:135-152`) makes that specific case unreachable, so a plain unbounded sweep may be
  acceptable — but it deserves an explicit note rather than silence.
- **R003's promotion and the i18n seam.** The host's only genuinely app-local dependency is
  `shared/i18n`. Promoting the body means the shared hook takes `formatNotice` (already its shape) plus
