## Architecture Baseline

- **Backend, domain-first Go.** Composition root → context behavior → domain, dependencies inward
  only. proto types and sqlc rows are infrastructure mapped at `rpc/` and `pg/` adapters; ports are
  declared by the consumer. `platform/` carries no business meaning. Cross-context reads go through
  published behavior, never another context's tables.
- **Frontend, six-layer FSD** applied identically by web and mobile: `app → pages → widgets →
features → entities → shared`, one-way, same-layer cross-import only via `entities/A/@x/B`. `app`
  and `shared` are non-sliced but **segmented, never flat** — `app` into
  `providers`/`routes`|`navigation`/`model`/`styles`, with only `App.tsx`·`main.tsx`·`index.css` at
  the root. Pure cross-app code lives in `packages/` from the start, not extracted later.
- **web↔mobile parity.** Everything under `model`/`api` and all of `packages/` is shared verbatim; a
  `*.native` sibling exists only where a primitive genuinely differs, and a fork owns its own test.
- **Control state in XState, data in Zustand/Query, per-frame data in refs.** Render code may not
  write an external store.
- **Config is build-time and generated.** Tuning scalars flow `values.yaml` → `pnpm gen:values` →
  TS/Go constants; deployment settings use the ops configuration seam. Neither lives as an
  unexplained code literal.
- **Gates fail loudly, and a gate's scope is part of the rule.** A claimed executable rule needs both
  a scanner and a negative probe that proves an offender actually fails. Documented-but-unenforced,
  or a guard whose allowlist has drifted from where files live, is a defect in the rule.
- **The constitution** ([I1]–[I11]) is judged at behavior boundaries, not inferred from green tests.
  Relevant here: [I1] the system never deletes, [I2] the source Diary is never rewritten, [I5]
  position is emergent and never stored, [I10] time and stage rises move one way only, and [C6a]
  a semantic stage is one-way.

### R001 A too-broad admin search tells the operator they hit an allowance

> This finding understated the drift. The gate it recommends found **10 reasons unregistered somewhere**
> on this same tree, not one — see the Outcome section and
> [job 159](../jobs/archive/159.admin-search-reason-copy-and-reason-regi.md).

- Priority: P2
- Area: error taxonomy, admin console, SSOT registry drift
- Evidence:
  - The backend emits the reason: `reasonUserSearchTooBroad = "ADMIN_USER_SEARCH_TOO_BROAD"`
    (`apps/api/internal/admin/rpc/reasons.go:18`), mapped as
    `apperr.Domain(connect.CodeResourceExhausted, reasonUserSearchTooBroad, err, nil)`
    (`apps/api/internal/admin/rpc/server.go:350-351`). The chain from the provider is correct:
    `ErrSearchScanTruncated` (`apps/api/internal/platform/supabase/directory.go:243-248`) is
    translated to `admin.ErrUserSearchTooBroad` at the composition root
    (`apps/api/cmd/api/admin.go:107-111`).
  - The FE reason registry does not contain it. `ERROR_REASONS` lists fourteen `admin*` reasons
    (`packages/errors/src/core.ts:19-32`) — `adminForbidden` through `adminSecretboxDisabled` — and
    `ADMIN_USER_SEARCH_TOO_BROAD` is absent.
  - `reasonMessage()` therefore has no case for it (`packages/errors/src/presentation.ts:40-95`), so
    `presentAppError` falls through to `codeMessage(Code.ResourceExhausted)`
    (`presentation.ts:22`, `111-112`) → `m.error_resource_exhausted()` →
    `"현재 한도에서는 이 작업을 마칠 수 없어요."` (`packages/i18n/messages/ko.json:444`) /
    `"That action cannot be completed with the current allowance."` (`en.json:444`).
  - The authoritative registry is also unupdated: `spec/policy/platform/errors.md` §2 tabulates every
    admin reason (lines 72-77) without this one, while the same file's rule reads "Adding a canonical
    domain error requires a unique reason, an existing/coherent Connect code, mapping coverage, and
    this registry update."
  - The repo already diagnosed this exact trap for a different reason and fixed it — the comment
    above the encode case reads "The coarse resource-exhausted line said '한도', which sent the writer
    looking for a limit that was never reached" (`presentation.ts:50-51`). The admin path now
    reproduces the bug that comment describes.
- Why it matters: the search failed because the prefix was too rare to resolve within
  `admin.search_scan_max_accounts` (5000), which the operator fixes by typing a _longer_ prefix. The
  copy instead tells them they are out of allowance, which is not true and suggests waiting or
  raising a quota. The whole point of adding a distinct reason was to say something the coarse code
  cannot, and none of that reaches the console. Plan 59 permits unmapped reasons to fall back, so no
  gate fails — the omission is invisible.
- Recommendation: add `adminUserSearchTooBroad` to `ERROR_REASONS`, give it a `reasonMessage()` case
  with copy that names the remedy ("narrow the search"), add the `ko`/`en` message keys, and add the
  row to `spec/policy/platform/errors.md` §2 marked `reason copy`. Consider making the drift
  mechanical rather than remembered: a gate that parses the `reasonX = "..."` constants out of each
  `internal/*/rpc/reasons.go` and asserts every one appears in both `ERROR_REASONS` and the policy
  table would have caught this and would catch the next one.
- Suggested job split: one job — the reason plumbing plus copy plus the registry row, with the
  reason-parity gate as its second half.

### R002 The encode pre-flight budget admits diaries no legal split can fit

- Priority: P2
- Area: memory encode use-case, LLM cost, error accuracy
- Evidence:
  - `bodyWithinOutputBudget` estimates the body against a split of exactly one memory carrying
    nothing but the body: `estimateOutputTokens(ExtractResult{Memories: []ExtractedMemory{{SourceText: body}}})`
    (`apps/api/internal/memory/encode.go:318`). That shape has no name, no mood and no neurons.
  - Every admissible split has all three. `min_memories_accepted: 1` and `min_semantic_neurons: 1`
    (`spec/values.yaml:410,416`) make one memory with a name, a mood and one semantic neuron the
    floor; `validateSplitStructure` rejects a blank name or an unknown mood outright
    (`encode.go:233-241`), and `hasRequiredSemanticNeurons` enforces the neuron
    (`encode.go:337-345`).
  - `estimateOutputTokens` charges that structure real tokens — 52 ASCII characters plus the mood per
    memory and 22 plus the type per neuron (`encode.go:357`, `365`) — none of which the pre-flight
    check models.
  - Reproduced against the shipped estimator with `max_output_tokens: 6000`
    (`spec/values.yaml:426`): the guard admits a Korean body of up to **5983 runes**; that same body
    as the **minimal** admissible split (1 memory, 1 name, 1 mood, 1 semantic neuron) estimates
    **6024** — already over — and as an ordinary 5-memory split estimates **6295**, over by 295. The
    trap band for the 5-memory shape is bodies of **5690–5983 runes**.
  - Inside that band `repairableViolation` returns `ViolationOutputTooLarge` (`encode.go:292-294`),
    which is not a soft nudge, so the loop spends all of `max_revise_retries: 3`
    (`spec/values.yaml:419`) on real `ReviseSplit` calls (`encode.go:211-223`) and returns
    `&EncodeRetryExhausted{Kind: ViolationOutputTooLarge}`.
  - That is the outcome the guard was written to prevent. Its own docstring: "The writer is told
    before a single LLM call, instead of after the repair budget burns down on a violation no
    re-prompt can fix (a shorter split would break coverage)" (`encode.go:31-33`), and the check is
    documented as using "the same token model the output guard uses, so the two cannot drift apart"
    (`encode.go:315-316`) — the token model is shared, but the _shape_ it is applied to is not.
  - The repair instruction for this violation asks for "shorter memory names and keep only the
    essential neurons" (`encode.go:293`), which cannot recover ~300 tokens from a body of 5983 runes.
    The re-prompt is unanswerable by construction.
- Why it matters: a writer with a long-but-legal diary pays three billed LLM calls and a long wait,
  then gets `MEMORY_ENCODE_RETRY_EXHAUSTED` — which `presentation.ts:52-53` renders as the split not
  coming together — instead of `MEMORY_ENCODE_BODY_TOO_LONG`, which would tell them to shorten the
  entry. They have no way to learn what to change, and every retry costs again.
- Recommendation: estimate the pre-flight check against the worst admissible split rather than a bare
  single memory — `max_memories` entries, each with `min_semantic_neurons` neurons, a mood, and a
  named allowance for the name/neuron-name budget — or subtract that as an explicit reserved-overhead
  value in `values.yaml`. Either way the two estimates must be provably ordered, so add a test that
  asserts the largest body the in-guard admits still fits as a worst-case split, and a test for a
  body just inside the band returning `ErrEncodeBodyTooLong` rather than retry-exhausted.
- Suggested job split: one job with R003 (both are backend correctness in the encode/worker path) or
  standalone; the reserved-overhead value belongs in `values.yaml` with its reasoning.

### R003 The worker's hard loop-breaker is disabled for the three kinds that most need it, and the log claims otherwise

- Priority: P2
- Area: job queue, worker safety, operability
- Evidence:
  - `maintenanceQueue.Fail` converts any `Fail` for a retried-indefinitely kind into an
    attempts-resetting retry: `return q.JobQueue.Retry(ctx, job, 0, q.now().Add(delay))`
    (`apps/api/internal/memory/worker.go:190-199`). The kinds are `retention_sweep`,
    `withdrawal_sweep` and `achievement_settle` (`apps/api/internal/memory/types.go:55-57`).
  - The runner calls `queue.Fail` from **three** places, and `maintenanceQueue` cannot tell them
    apart — it sees only `Fail(ctx, job, nextAttempts)`:
    1. the policy dead-letter it means to override, after `max_attempts`
       (`apps/api/internal/platform/jobqueue/runner.go:200-206`);
    2. the **hard claim ceiling** (`runner.go:134-144`);
    3. an **unhandled kind** (`runner.go:146-157`).
  - The claim ceiling is the queue's only defence against a job that kills its worker before it can
    record a failure. Its own comment: "Dead-letter a job that has been re-claimed past the hard
    claim ceiling without ever finishing — the signature of a handler that kills its worker (panic
    that escapes, OOM, SIGKILL) every run, which would otherwise loop forever since a killed worker
    never records a failure" (`runner.go:130-133`). `values.yaml` calls it the "Hard loop-breaker …
    Set well above job_max_attempts so ordinary transient retries never trip it"
    (`spec/values.yaml:308-311`, `job_max_claims: 20`).
  - A panic is already recovered into an ordinary failure (`runner.go:182-189`), so the ceiling exists
    precisely for the unrecoverable cases — and for those three kinds it now does nothing: the
    "dead-letter" is rewritten into `Retry(job, 0, now+60s)` (`job_backoff_base_ms: 60000`,
    `spec/values.yaml:303`), so the job returns to the head of the queue a minute later, forever.
  - The runner then logs a dead-letter that did not happen:
    `r.logf("job %s dead-lettered after %d claims", ...)` runs unconditionally after the `Fail` call
    succeeds (`runner.go:142`).
  - Same shape for an unhandled kind: `r.logf("job %s failed: unhandled kind %q", ...)`
    (`runner.go:156`) after a `Fail` that was converted into a retry.
- Why it matters: `withdrawal_sweep` is the job that deletes a withdrawn account's data. If one such
  job is permanently poisoned — a row shape that OOMs the worker, a migration mid-flight — the worker
  is killed, re-claims it, and is killed again on a 60-second cycle with no ceiling, and every other
  user's embed/semanticize work behind it starves. The operator's one signal that this was contained
  is a log line that says "dead-lettered", so the containment is believed to have happened. The
  never-dead-letter policy is right for these kinds; extending it over the _safety_ transitions is
  what makes it unsafe.
- Recommendation: give the queue port a way to distinguish the transitions, so the override applies
  only to the policy dead-letter — e.g. a distinct `DeadLetter(ctx, job, reason)` the runner calls
  for the ceiling and the unhandled kind, with `Fail` keeping today's attempts-exhausted meaning, and
  `maintenanceQueue` overriding only `Fail`. Then make the log line follow what the queue actually
  did rather than what the runner intended. For the retried-indefinitely kinds a ceiling breach
  should still stop the loop and alert loudly (park the job, or back off geometrically to a long
  ceiling) rather than reschedule at the base backoff. Add a test that a claim-ceiling breach on
  `withdrawal_sweep` does not return the job to `pending`.
- Suggested job split: one job — the queue-port transition split, the `maintenanceQueue` narrowing,
  and the log/text correction belong together.

### R004 A stale lower-stage read drops a risen gist body downward

- Priority: P2
- Area: universe rendering, gist stage lifecycle, [C6a]/[I10]
- Evidence:
  - `reconcileGistRiseState` guards the _animation_ against a stale read: the seen stage is kept
    monotonic with `Math.max(previousStage, instance.stage)`
    (`packages/universe-render/src/GistStarLayer.tsx:138-141`) and a non-rise `continue`s
    (`GistStarLayer.tsx:145-147`). The comment states the intent: "The seen stage never goes down: a
    stage is one-way ([C6a]), so a lower stage here is a stale read racing a fresh one. Recording it
    would replay the rise when the fresh read returns" (`GistStarLayer.tsx:136-137`).
  - The _position_ is not guarded. `mapGistInstancePosition` composes the lift from the snapshot's
    instance, not from `stageSeen`: for a settled body `out[2] = liveZ + instance.zOffset`
    (`GistStarLayer.tsx:198-200`), and mid-rise it eases toward the same `instance.zOffset`
    (`GistStarLayer.tsx:216`).
  - `instance.zOffset` is derived from the snapshot's own possibly-stale stage:
    `zOffset: gistStageOffset(risen)` where `risen` is that read's `semanticStage`
    (`packages/universe/src/gist-star-channels.ts:74-91`).
  - Trace: a body settled at stage 2 has `seen[nodeId] === SETTLED` and `stageSeen[nodeId] === 2`. A
    refetch returns stage 1. Reconcile sets `stageSeen` to `max(2,1) = 2` and `continue`s, so `seen`
    keeps `SETTLED`; `byInstance` is rebuilt as `SETTLED` (`GistStarLayer.tsx:168-170`); the mapper
    takes the `entry === SETTLED` branch and writes `liveZ + gistZOffset(1)`. The body jumps from
    stage 2's lift to stage 1's, with no ease, until a fresh read arrives.
  - `softness` regresses the same way — it is also computed from the stale `risen`
    (`gist-star-channels.ts:95`), so the body briefly renders a shallower stage's look.
  - No test covers a lower-stage read. The suite's nearest case is
    `it('does not rise a body whose stage did not move, however often it is reconciled')`
    (`packages/universe-render/src/GistStarLayer.test.tsx:164`), which exercises an _equal_ stage. The
    `Math.max` guard added for the stale case is itself untested.
- Why it matters: [C6a] and [I10] make a stage rise one-way, and this is a visible downward move of
  the one body the whole layer exists to lift. The guard's author anticipated the stale read and
  stopped the replay, so the remaining half reads as covered. It is also the cheap half to get wrong:
  `stageSeen` already holds the authoritative monotonic stage, and the renderer simply does not
  consult it.
- Recommendation: make `stageSeen` the authority for what is rendered, not only for what animates —
  resolve the effective stage as `max(stageSeen, instance.stage)` and derive both the lift and the
  softness from that, so a stale snapshot cannot lower a body. Add tests for a lower-stage read after
  a settled rise (position and softness must not regress) and for one arriving mid-rise.
- Suggested job split: one job with the renderer-lifecycle fix and its two tests; keep it separate
  from the backend findings.

### R005 CI never runs the production frontend build, so the script written to catch a deploy-breaking bug is dead

- Priority: P2
- Area: CI parity, deploy safety
- Evidence:
  - The production frontend build is `pnpm build:site` — `"build:site": "pnpm build:blog && pnpm
build:web && node scripts/stage-blog.mjs"` (`package.json:119`). `DEPLOY.md:38` names it as the
    single build command, and `wrangler.jsonc:6` records it as the dashboard build command.
  - CI runs only `pnpm check` (`.github/workflows/ci.yml`, final step). `check` contains
    `pnpm build:web && pnpm build:blog` (`package.json:120`) — **the opposite order**, and no
    `stage-blog` step at all. `grep` for `stage-blog`/`build:site` across `.github/` returns nothing.
  - `stage-blog.mjs` exists specifically because that ordering is dangerous, and says so: "Vite
    empties `outDir` when it builds, so a copy staged before the web build is silently deleted and
    the deploy goes out with `/blog/**` missing — a production 404 that nothing in the build output
    complains about. Hence the two assertions below: this refuses to run before the web build, and
    refuses to succeed if the staged tree does not actually contain a page and its assets afterwards.
    The ordering bug becomes a build error" (`scripts/stage-blog.mjs:4-8`).
  - Those two assertions (`scripts/stage-blog.mjs:23-30`) never execute in CI. `deploy-backend.yml`
    covers only the Go API — there is no frontend deploy workflow, so the Cloudflare Pages build is
    the first and only place `build:site` runs.
- Why it matters: the repo turned a silent production 404 into a build error and then left that build
  error out of CI. A regression in `stage-blog.mjs`, in the blog's output path, or in the ordering
  passes `pnpm check` green and fails at the Cloudflare build — or worse, succeeds there and ships
  `/blog/**` missing. §4's "a gate's scope is part of the rule" is exactly this case: the guard
  exists, and nothing runs it.
- Recommendation: have CI build the site the way production does. Either replace `check`'s two build
  steps with `pnpm build:site`, or add a `build:site` step after `check` in `ci.yml`. Prefer the
  former so one command is the only build path and the orders cannot diverge again. While there,
  reconcile `check`'s `build:web && build:blog` order with `build:site`'s.
- Suggested job split: one job with R006 and R007 — all three are gate/CI coverage holes.

### R006 The mobile shared-client probe is never executed by any gate

- Priority: P2
- Area: mobile test coverage, web↔mobile parity, seam without consumer
- Evidence:
  - `apps/mobile/src/app/providers/api-client.probe.ts` exports two probes,
    `probeSharedPlatformClientImport` (the `@cosimosi/api-client` facade round-trip) and

  - Nothing references the file. `grep -rn 'api-client.probe' apps/mobile` over `.ts/.tsx/.js/.json`

  - No test runner picks it up. `apps/mobile/jest.config.js` spreads `@react-native/jest-preset` and

    preset defines neither (verified: both `undefined`). Jest's defaults therefore apply
    (`**/__tests__/**/*.[jt]s?(x)` and `**/?(*.)+(spec|test).[jt]s?(x)`), and a `.probe.ts` suffix
    matches neither.
  - The web counterpart is a real, running test: `apps/web/src/app/providers/api-client.test.ts`
    (`describe('web api-client import probe')`) asserts
    `response.requestId === 'web-import-probe'` under vitest, and vitest picks up `*.test.ts`.
  - So mobile has strictly less coverage than web on the shared transport seam, and additionally the
    client-cache half of the probe has no web equivalent at all — that intent is exercised nowhere.
    The file still typechecks (it is under `src`), which is what makes it look wired.
- Why it matters: this probe's whole value is proving the shared `packages/*` transport and cache
  facades actually resolve and run under Metro/RN module resolution — the failure mode §3.5 warns
  about, and the one a web-only test cannot catch. It has been silently inert. §4's "gates fail
  loudly" and §3.5's "a fork owns its own test" both point the other way.
- Recommendation: rename it to `api-client.test.ts` and give it real assertions (mirroring the web
  test, plus one for the client-cache path), so the default `testMatch` runs it. Then close the class
  of bug rather than the instance: no other `*.probe.ts` should exist under a runner that ignores it
  — either add `.probe.ts` to the mobile `testMatch` deliberately, or add a small guard asserting
  every file under `apps/*/src` matching `*.probe.*` is reachable by that app's runner.
- Suggested job split: with R005 and R007 as one gate-coverage job.

### R007 The app-layer segment contract is enforced against files but not directories

- Priority: P3
- Area: FSD enforcement, guard scope drift
- Evidence:
  - `ARCHITECTURE.md` §3.1 states the app layer is "SEGMENTED, never flat", names the closed set
    (`providers` / `routes`|`navigation` / `model` / `styles`, with only `App.tsx`·`main.tsx`·
    `index.css` at the root), and asserts the enforcement: "This app-layer contract — the rule
    `steiger` and `eslint-plugin-boundaries` do **not** cover — is enforced by `pnpm lint:fsd:layout`
    (`scripts/lint-fsd-layout.mjs`), so a provider dropped flat in `app/` fails the gate, not just
    review."
  - The gate only inspects **files**: the guard is
    `if (!entry.isDirectory() && CODE_EXT.test(entry.name) && !APP_ROOT_ALLOW.has(entry.name))`
    (`scripts/lint-fsd-layout.mjs:158`). A directory at the app root is skipped by the
    `!entry.isDirectory()` term, so an unknown _segment_ is never checked — even though the failure
    message the gate prints enumerates the closed set: "Move it into a segment (app/providers ·
    app/routes|navigation · app/model · app/styles)" (`lint-fsd-layout.mjs:160-162`).
  - The segments are read and printed but not validated: the main block collects directory names and
    only `note()`s them — `note(\`${app}/src/app segments: ${segments.join(', ')}\`)`
(`lint-fsd-layout.mjs:231-235`).
  - A live offender passes today: `apps/mobile/src/app/diagnostics/` (`DiagnosticsScreen.tsx`,
    `index.ts`) is not one of the four documented segments, and `pnpm lint:fsd:layout` reports
    `ok('app layout, mobile pages placement, and cross-app pure-module ownership are valid')` in the
    green gate run.
- Why it matters: an entire unknown segment is a larger violation than the single loose file the gate
  does catch, and it is the shape that actually occurs — nobody drops one file at `app/`'s root, they
  add a folder. The documentation claims coverage the scanner does not provide, which is the specific
  drift §4 calls out ("a claimed executable architecture rule must have both a scanner and a negative
  probe").
- Recommendation: validate app-root directories against the same closed set the error message
  already names, and extend `scripts/lint-fsd-layout.test.mjs` with a negative case planting an
  unknown segment. Then decide `app/diagnostics/` on the merits — it looks like a `pages` slice or an
  `app/providers` concern; whichever it is, move it or amend §3.1 to admit the segment explicitly.
- Suggested job split: with R005 and R006 as one gate-coverage job; the `app/diagnostics/` placement
  decision may need a quick call before the gate can go green.

### R008 The `shared/model` i18n-of-XState seam drifted between web and mobile

- Priority: P3
- Area: web↔mobile parity, promote-on-reuse
- Evidence:
  - Both apps carry `src/shared/model/xstate-react.ts`, a pure re-export barrel over

  - The export sets differ. Web exports four —

### R010 A stale `node_modules` fails the gate with a type error that names neither cause nor cure

- Priority: P3
- Area: developer environment, gate preflight
- Evidence:

## Cross-Cutting Themes

- **A guard was written, and then not run.** R005 (CI never invokes `stage-blog.mjs`), R006 (no runner
  matches `*.probe.ts`), R007 (the segment set is checked against files, not directories) and R009
  (no negative probe; the composition root unscanned) are all the same root cause, and it is the one
  §4 names: "a gate's scope is part of the rule". In each case the _rule_ is written down and the
  _scanner_ exists; what is missing is the wiring that makes an offender fail. This repo's probe
  infrastructure (`probe-workspace.mjs` and the hermetic `.probe-ws-*` pattern) is genuinely good —
  strong enough that its absence in a given gate is easy to miss, because every neighbouring gate has
  one.
- **A guard that models the wrong shape.** R002 is not a missing check but a check applied to a shape
  the domain cannot produce: the pre-flight budget models a split with no name, no mood and no
  neurons, while the domain guarantees all three. The comment claiming the two estimates "cannot
  drift apart" is true of the token model and false of the shape it is applied to — the kind of
  divergence that survives review precisely because a shared helper looks like a shared contract.
- **A one-way invariant enforced on the event but not on the state.** R004 keeps `stageSeen`
  monotonic and then renders from the stale snapshot anyway; R003 makes "never dead-letter" true of
  the policy transition and accidentally true of the two safety transitions as well. Both are partial
  implementations of a correct rule, and in both the code holding the right answer is already in
  scope at the point of the bug — `stageSeen` in one, the transition's identity in the other.
- **The last mile of the error taxonomy is manual.** R001's reason exists, is mapped to a coherent
  Connect code, is unit-tested backend-side, and still says the wrong thing to the operator, because
  three artefacts a human must remember (`ERROR_REASONS`, `reasonMessage`, the policy §2 table) went
  unupdated. Plan 59's deliberate "unmapped reasons fall back" makes the omission silent by design,
  so nothing but a parity gate will catch the next one.
- **Two hand-maintained copies drift where the gate compares for equality.** R008's seam evades
  `lint:fsd:layout` _because_ it diverged — a comparison predicated on normalized equivalence cannot
  see a pair that stopped being equivalent. Any future promote-on-reuse rule wants a
  same-path/different-content signal, not only a same-content one.

## Questions / Tradeoffs

- **R003's containment policy for the retried-indefinitely kinds.** "Never dead-letter" and "always
  break a kill-loop" genuinely conflict for `withdrawal_sweep`: dead-lettering strands a legal
  deletion obligation, and retrying forever starves the queue. The recommendation above parks and
  alerts rather than dropping, but which of park / long-geometric-backoff / operator-visible quarantine
  is right is a product-and-ops call, and it decides the shape of the queue-port change.
- **R002's reserved overhead.** Sizing the pre-flight against the _worst_ admissible split
  (5 memories × the neuron budget) will refuse some diaries that a 2-memory split would have fit,
  which trades a rare wasted-retry failure for a slightly lower hard ceiling. The alternative — a
  fixed reserved-overhead value — is looser but keeps the ceiling near today's. Both need
  `max_output_tokens` to stay under `ai.per_call_token_cap`, so whichever is chosen belongs in
  `values.yaml` with the reasoning, not in code.
- **R008's web app-shell machine.** Whether web is _missing_ an `app/model` machine or whether its
  router legitimately is its shell control state is a §3.2 design question, not a refactor. If the
  answer is "web should have one", that is a change doc rather than a finding fix.
- **R007's `app/diagnostics/` placement.** Tightening the gate makes this directory fail, so the
  placement decision (a `pages` slice? an `app/providers` concern? an admitted fifth segment?) has to
  land before or with the gate change.
- **R001's parity gate scope.** A gate asserting every `rpc/reasons.go` constant appears in
  `ERROR_REASONS` would have caught this, but plan 59 deliberately does _not_ require FE copy for
  every reason (§Non-goals, line 75). The gate should therefore assert _registry_ membership
  (`ERROR_REASONS` + the policy table) and leave `reasonMessage` copy optional — otherwise it will
  fight a documented non-goal.
