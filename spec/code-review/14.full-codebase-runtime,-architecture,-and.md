## Architecture Baseline

- Backend code follows domain-first Go: composition root → context behavior → domain, with proto,
  sqlc/pgx, and vendor SDK types mapped only at adapters. Cross-context reads use consumer-owned
  ports; per-user persistence remains scoped except explicitly reviewed platform/operator scans.
- Web and mobile apply the same six-layer FSD dependency direction. Pure cross-app behavior belongs
  in `packages/*`; platform forks stay narrow and independently tested.
- Control state belongs in XState, server data in Query, shared client data in Zustand, and
  per-frame renderer data in refs/typed buffers. Render code may not create external-store writes.
- Product UI imports i18n through each app's `shared/i18n/index.ts`; only that seam and the platform
  locale adapter may import `@cosimosi/i18n` directly.
- Tuning scalars have an explicit owner: product-shaping values flow through
  `spec/values.yaml` → generated TS/Go constants, while deployment/runtime settings use their ops
  configuration seam. Neither category should live as unexplained code literals.
- The constitution's privacy, append-only history, consent, and server-authority rules are judged at
  behavior boundaries, not inferred from passing tests. A claimed executable architecture rule must
  have both a scanner and a negative probe that proves an offender fails.

## Findings

### R001 Supabase user search filters only one raw page, so valid matches disappear

- Priority: P2
- Area: admin user directory, pagination/search correctness
- Evidence:
  - Plan 58 defines `query` as an email/id **prefix** match (`spec/plan/58.admin-console.md:252-265`),
    and the consumer-owned port repeats that contract (`apps/api/internal/admin/ports.go:54-59`).
  - The Supabase adapter fetches exactly the requested unfiltered provider page, derives `hasMore`
    from that raw page's length, then applies a case-insensitive **contains** filter only to those
    rows (`apps/api/internal/platform/supabase/directory.go:151-168`).
  - The UI resets to page zero as the query changes and renders `admin_users_empty` whenever that
    filtered page is empty (`apps/web/src/features/admin-users/ui/UsersSection.tsx:23-27,51-62`). A
    match on a later provider page is therefore presented as no result even though the raw page may
    still expose a Next button.
  - The adapter test places its only matching user in the first and only returned page
    (`apps/api/internal/platform/supabase/directory_test.go:16-44`), so it conforms to the bug rather
    than testing the advertised cross-page contract.
- Why it matters: the shipped `ListUsers` acceptance criterion is not true. Operators can fail to
  find a real account, `contains` returns a broader set than the specified prefix search, and
  `hasMore` describes the provider page rather than the search-result stream. A last provider page
  containing exactly `pageSize` rows also advertises a spurious next page.
- Recommendation: give search its own correct pagination model. If the provider cannot filter,
  scan provider pages until one search page is filled or the provider is exhausted and return a
  search-scoped cursor/terminal flag; for a larger directory, project the minimal auth metadata into
  a searchable platform-owned index. Add tests where the first raw page has no match, the next page
  does, a substring is not a prefix, and the last raw page is exactly full.
- Suggested job split: backend directory/search semantics and tests first, then update the admin RPC
  pagination shape/UI only if a cursor or explicit search-submit boundary is required.

### R002 One admin page can issue 201 sequential DB reads, and typing can repeat the fan-out

- Priority: P2
- Area: admin user list hot path, cross-context batch ports, web query lifecycle
- Evidence:
  - The default admin page size is 50 (`spec/values.yaml:600-601` and generated
    `apps/api/internal/platform/values/values_gen.go:288`). `ListUsers` iterates accounts serially and
    calls `Balance` and `Counts` once per user (`apps/api/internal/admin/service.go:245-266`).
  - One balance call reads the user's profile/timezone and then the balance row
    (`apps/api/internal/twinkle/service.go:237-249`); one count call executes separate diary and star
    count statements (`apps/api/internal/memory/pg/admin_stats.go:10-23`). Together with
    `ListPromoted`, an unfiltered full page performs `1 + 50 × 4 = 201` sequential DB round trips
    after the directory HTTP call.
  - The React Query key consumes the raw `query` state and the text field updates it on every
    keystroke, with no debounce or submit boundary
    (`apps/web/src/features/admin-users/ui/UsersSection.tsx:23-28,51-58`).
- Why it matters: latency and database load grow linearly with the page size, one failed enrichment
  aborts the entire page, and ordinary typing can start several expensive generations of the same
  fan-out. The admin console is low-volume, but 201 serial network round trips makes it fragile even
  at its configured page size.
- Recommendation: make the consumer-owned ports batch-shaped (`Balances(userIDs)` and
  `Counts(userIDs)` returning admin-owned maps), implement each context with one scoped grouped query,
  and preserve missing-user defaults explicitly. Debounce the search using a generated value or use
  an explicit submit action; ensure superseded requests are cancelled. Add a query-count integration
  assertion so the page remains O(1) in DB round trips.
- Suggested job split: one admin-list scalability job can cover R001 and R002 because correct
  search pagination determines which IDs the batch enrichment receives.

### R003 The grant form silently truncates numeric input and clears it before success

- Priority: P2
- Area: admin stardust mutation, irreversible operator input
- Evidence:
  - The amount control is `type="number"` with only `min={1}`, while submission uses
    `Number.parseInt(amount, 10)` and immediately converts the result to `BigInt`
    (`apps/web/src/features/admin-users/ui/UsersSection.tsx:130-138,165-173`). Valid number-input
    strings such as `1.9` and `1e2` therefore submit `1` rather than being rejected or submitting the
    displayed value.
  - The amount and note are cleared immediately after dispatch, before the promise resolves
    (`apps/web/src/features/admin-users/ui/UsersSection.tsx:136-140`), so a server refusal also destroys
    the operator's input.
  - The server correctly accepts only `0 < amount <= admin_grant_max` and records/credits the grant
    append-only (`apps/api/internal/admin/service.go:281-336`); there is no feature-local UI test under
    `apps/web/src/features/admin-users/` covering parse or failure behavior.
- Why it matters: an operator can create the wrong permanent credit while the UI appears to accept
  the typed number. The server cap prevents an over-limit grant but cannot recover intent lost through
  client-side truncation, and the append-only accounting model deliberately has no delete/undo path.
- Recommendation: parse with `Number`, require a safe integer within the generated max, set
  `step={1}`/`max`, and show validation before minting the idempotency key. Make `runAction` return the
  action promise and clear fields only after success. Cover decimals, exponent notation, cap overflow,
  double-submit, server refusal, and success.
- Suggested job split: a focused admin mutation-integrity job; keep the server as the authority and
  treat UI validation as intent preservation, not security.

### R004 Terminal-job cleanup runs before every queue claim instead of on a maintenance cadence

- Priority: P2
- Area: worker queue maintenance, database efficiency
- Evidence:
  - `maintenanceQueue.ClaimDue` invokes the global `PurgeTerminalJobs` statement before every
    underlying claim (`apps/api/internal/memory/worker.go:122-143`).
  - The runner immediately claims again after every successful job and waits only when no work was
    found (`apps/api/internal/platform/jobqueue/runner.go:94-109`). Production and development both
    pass a one-second poll interval (`apps/api/cmd/worker/main.go:47` and
    `apps/api/cmd/api/worker.go:32-35`).
  - The purge is a bounded but global ordered scan/delete (`apps/api/db/queries/memory/jobs.sql:223-252`).
    The unit test asserts one cleanup for one claim but does not exercise repeated idle or busy claims
    (`apps/api/internal/memory/worker_test.go:13-34`).
- Why it matters: an idle worker executes up to 86,400 cleanup attempts per day; a busy worker
  executes one per completed job with no interval at all. Multiple replicas multiply the scans. The
  bounded delete protects lock duration, not call frequency, so housekeeping competes with product
  queue traffic even when nothing is old enough to delete.
- Recommendation: schedule cleanup with a separate `nextCleanupAt` maintenance cadence (and a
  configurable batch size). If a batch is full, permit a bounded drain; otherwise back off until the
  next window. Keep cleanup fail-open for product claims, and test repeated empty claims, a backlog,
  cleanup errors, and multiple clock advances.
- Suggested job split: one worker-maintenance job, sharing the value/ops classification work in R008.

### R005 Negative import probes mutate real source roots and are not concurrency-safe

- Priority: P2
- Area: readiness gates, FSD/import enforcement probes
- Evidence:
  - Both boundary probes create deliberate offenders under the real
    `apps/{web,mobile}/src/{pages,entities}` trees, run ESLint, and remove the directories only in
    `finally` (`scripts/probe-web-boundary.mjs:16-38,42-74,106-120` and
    `scripts/probe-mobile-boundary.mjs:16-38,42-74,106-120`).
  - The demo and sequence probes use the same pattern under real product slices
    (`scripts/probe-demo-isolation.mjs:7-20,52-68,71-94` and
    `scripts/probe-sequence-isolation.mjs:44-56,71-99`); the package-lint probe also creates fixtures
    under three real package `src` trees (`scripts/probe-packages-lint.mjs:12-26`).
  - Ordinary web/mobile lint scans those same source roots before running its own probe
    (`apps/web/package.json:10-14`, `apps/mobile/package.json:9-11`). Unique directory suffixes prevent
    name collisions but do not hide one process's intentional violations from another process.
  - During this audit, `pnpm lint` twice failed only because a concurrent `pnpm test`/`pnpm check`
    process had a `.probe-*` or `__boundary_probe_*` fixture alive. After the other process ended, the
    unchanged tree passed standalone `pnpm lint` and the exact `pnpm check`.
- Why it matters: the repository's highest-level readiness signal is non-hermetic in concurrent
  developer/agent workflows. A false red wastes investigation time and can interrupt an otherwise
  correct implementation; an interrupted process can also leave fixtures visible until its cleanup
  runs.
- Recommendation: run all negative fixtures in an isolated temporary workspace/worktree that mirrors
  the app config but is outside every production scanner. If that is not feasible, serialize the
  complete scan+probe entry points with one repository lock; locking only the probe does not protect
  an ordinary lint process that scans while another probe is active. Add a test that overlaps two
  probe/gate processes.
- Suggested job split: tooling-hermeticity job covering both web and mobile probes and their
  concurrency regression test.
- Cross-reference: review 13 R012 records the same defect observed live from the other side (that
  session's `pnpm check` failed on this session's probe fixtures). Treat the two findings as one
  job; this entry has the fuller inventory and the recommendation.

- Priority: P3
- Area: comment hygiene enforcement
- Evidence:
  - The policy forbids change/ticket numbers and history narration without limiting that rule to
    `src` (`spec/principle/code-comments.md:1-11`).
  - The scanner's narration patterns include `plan` and `job`, but not `change`, and its negative
    probe likewise has no `change NN` case (`scripts/lint-comment-history.mjs:33-57,74-118`). Thus
    in-scope source retains `change 03/04/10` references, for example
    `apps/api/internal/ai/voyage/client.go:28-32`, `apps/api/internal/ai/models.go:8-12`,
    `apps/api/internal/admin/ports.go:123-129`, and `packages/demo/src/pick.ts:21-25`, while the gate

    `apps/web/vite.config.ts:33-38` contains `Job 144`, despite the same green gate.
- Why it matters: the probe proves only the subset encoded in its own regex, so its success overstates

  the decay the principle exists to prevent.
- Recommendation: add `change/refactor/review` ticket forms to the comment-only matcher and probe;
  include executable app config files (while continuing to exclude generated/vendor output); and
  rewrite current hits as timeless constraints. Preserve narrow CLI-example exemptions where the

  should retain its own negative fixtures.

  `packages/3d-renderer/src/layers/adaptive-dpr.ts:6`), and diff-narration comments in Go the

### R007 Mobile bypasses the app-owned i18n seam in 19 production files

- Priority: P3
- Area: mobile FSD parity, i18n import boundary
- Evidence:
  - The i18n SSOT says product code consumes each app's `shared/i18n/index.ts`, with only the platform
    locale adapter importing the pure package directly (`spec/tech/i18n.md:9-28`). The mobile barrel
    exists at `apps/mobile/src/shared/i18n/index.ts:1-17`.
  - Web enforces that rule with `no-restricted-imports`
    (`apps/web/eslint.config.js:140-163`). Mobile's only restricted-import override protects the
    sequence boundary (`apps/mobile/.eslintrc.js:63-97`) and contains no i18n rule.
  - A production-only inventory, excluding the barrel and locale adapter, finds 19 direct imports.
    Examples include `apps/mobile/src/pages/login/ui/LoginPage.tsx:6`,
    `apps/mobile/src/pages/universe/ui/UniversePage.tsx:18`,
    `apps/mobile/src/app/providers/profile-gate.tsx:15`, and
    `apps/mobile/src/features/account-profile/ui/AccountProfile.tsx:15-21`.
- Why it matters: web and mobile no longer have the same dependency seam. Direct message calls happen
  to work today, but mobile product code bypasses the barrel that owns React reactivity and domain
  projections; a future seam change can compile on web and drift silently on mobile.
- Recommendation: extend the mobile barrel with the pure exports production callers genuinely need,
  migrate the 19 files, and mirror web's restriction while preserving the locale-storage exception.
  Decide explicitly whether tests may import locale reset helpers directly or must use a test barrel,
  then probe both a violation and each allowed path.
- Suggested job split: mobile i18n convergence + enforcement job, with no behavior or copy change.

### R008 Backend cache, timeout, and worker knobs bypass the declared config/ops ownership

- Priority: P3
- Area: config-value SSOT, backend operational tuning
- Evidence:
  - Architecture says tuning scalars are generated and never hardcoded
    (`spec/ARCHITECTURE.md:457-461`); the config SSOT distinguishes generated product shaping from
    environment/ops runtime settings (`spec/tech/config-values.md:7-14,72-84`).
  - Account withdrawal admission hardcodes a five-second cache TTL and 4,096-entry limit
    (`apps/api/internal/account/withdrawal.go:14-17,88-117`). The AI adapter cache hardcodes 1,024
    entries (`apps/api/internal/ai/hash.go:9,21-35`).
  - Worker polling is duplicated as one second in two binaries, while cleanup's batch size is another
    code literal (`apps/api/cmd/worker/main.go:47`, `apps/api/cmd/api/worker.go:32-35`,
    `apps/api/internal/memory/worker.go:13`). Vendor/admission HTTP timeouts are likewise scattered,
    for example `apps/api/internal/ai/deepseek/client.go:26-33`,
    `apps/api/internal/ai/voyage/client.go:33-39`, and `apps/api/cmd/api/main.go:20-24`.
- Why it matters: these values control DB load, stale admission windows, memory footprint, queue
  latency, and outage behavior, but their ownership cannot be reviewed from either `values.yaml` or
  deployment config. Duplicated values can drift (the two worker modes already have separate names),
  and R004 cannot be tuned without another code edit.
- Recommendation: classify the inventory rather than blindly moving every number. Product/cache
  behavior that must be identical belongs in `values.yaml`; deployment-specific timeouts/polling
  belong in validated env/ops config; protocol or structural limits stay in code with a comment/test
  explaining the invariant. Generate or inject the resulting values and add a focused audit/probe for
  the categories the repository can identify safely.
- Suggested job split: backend tuning-ownership job; land the worker subset with R004 and handle the
  account/AI/HTTP inventory as a second checklist if the blast radius is too broad.

### R009 The optimistic client-cache transaction is a tested export with no production consumer

- Priority: P3
- Area: client-cache seam, unused abstraction
- Evidence:
  - `beginOptimisticMutation` implements snapshot cloning, rollback, settle, and invalidation across
    130 lines and is exported publicly (`packages/client-cache/src/optimistic.ts:25-73,75-168` and
    `packages/client-cache/src/index.ts:9-16`). `client_cache.optimistic_rollback_ms` is generated for
    its default (`spec/values.yaml:11-16`, `packages/client-cache/src/defaults.ts:9-16`).
  - A repository-wide reference inventory finds consumers only in the implementation and
    `packages/client-cache/src/client-cache.test.ts`; the diagnostics page merely displays the value
    (`apps/web/src/pages/test/lib/platform-panel-components.tsx:214-223`). No production mutation calls
    the helper.
  - Actual optimistic behavior uses separate hand-built seams: profile locale catches and rolls back
    the external locale store (`apps/web/src/features/account-profile/ui/AccountProfile.tsx:72-82`),
    while release/restore update Zustand-owned deletion state then invalidate Query
    (`packages/universe/src/react/use-release.ts:20-46`,
    `packages/universe/src/react/use-restore.ts:19-45`).
- Why it matters: a substantial, green-tested abstraction and generated tuning value imply a shared
  rollback policy that the product does not use. It adds maintenance and compatibility surface while
  real mutations continue to evolve independently.
- Recommendation: choose one real TanStack Query mutation whose ownership fits full-query snapshot
  rollback and adopt the helper end to end, or delete the unused export, clone machinery, diagnostics
  row, and value until such a consumer exists. Do not force Zustand/external-store workflows through a
  Query-specific abstraction merely to justify it.
- Suggested job split: small client-cache seam-decision job after inventorying the intended future
  consumers; adoption and deletion are mutually exclusive outcomes.

## Cross-Cutting Themes

- **Contracts are stronger than their tests.** Admin search, grant input, i18n ownership, and comment
  policy are all written clearly; shallow fakes or incomplete probes verify a smaller behavior and
  keep the full gate green.
- **Scalar ports do not compose into list surfaces.** Correct single-user domain APIs became a
  serial N×M fan-out when the admin page reused them one row at a time. Cross-context isolation is
  sound, but it needs batch-shaped consumer ports at list boundaries.
- **A guard must be hermetic and symmetric.** The FSD probes prove the intended rule but mutate the
  tree they guard; the comment probe and mobile i18n config cover only part of their policy. Negative
  fixtures are valuable only when their scope matches production and concurrent runs cannot observe
  one another.
- **Foundations need consumers.** Generated values and reusable helpers should arrive with a product
  caller or remain out of the public surface; otherwise they become a second, unexercised architecture.

## Questions / Tradeoffs

Decided 2026-08-15 (standard backend conventions; these are the binding inputs for the jobs cut
from this report):

1. **Directory search** — DECIDED: keep the live Supabase Admin API traversal; no
   platform-owned projection at current directory size. Search gets its own correct model on
   top of it: scan provider pages until one search page fills or the provider is exhausted,
   with a search-scoped cursor/terminal flag. Revisit a projection only if the directory grows
   enough to make the traversal slow.
2. **Cleanup cadence** — DECIDED: product build values in `spec/values.yaml` (cadence and batch
   size), shared by all workers — matching how every other worker knob is owned. Poll interval
   stays a composition-root argument (deployment-shaped), but its duplicated literal gets one
   named home.
3. **Mobile test i18n imports** — DECIDED: test files may import `@cosimosi/i18n` directly for
   deterministic locale reset; the restriction covers production code only, and the exception is
   encoded in the lint rule itself (executable, not tribal).
4. **`beginOptimisticMutation`** — DECIDED: no named near-term consumer exists → delete the
   export, clone machinery, its test, the diagnostics row, and the
   `client_cache.optimistic_rollback_ms` value. Real mutations keep their hand-built seams; the
   abstraction returns only with a concrete consumer.
