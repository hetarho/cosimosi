# Code Review 12: Frontend rendering performance audit

> Read-only code-quality and architecture review. This report records refactor
> opportunities only; implementation belongs in `spec/jobs/`. Write it in English.

## Scope

The frontend rendering path across the whole codebase, requested with a focus on rendering speed and
optimization — React re-renders, WebGL/WebGPU efficiency, and whether current (2025–2026) libraries
and techniques apply here. Surfaces reviewed:

- `packages/3d-renderer` (canvas hosts, layers, TSL shader art, skins, bodies) — including the
  uncommitted working-tree changes (`UniverseCanvas.tsx`, `UniverseCanvas.native.tsx`,
  `tone-mapping.ts`, `star-shapes.ts`, `presets.ts`, `spec/values.yaml`), reviewed as-is.
- `packages/universe-render`, `packages/universe` (sim bridge, stores, `use-universe`),
  `packages/force-sim`, `packages/config`.
- `apps/web` (canvas widget, routes, providers, bundle output) and `apps/mobile` (canvas widget
  fork, navigation, native host wiring).
- Backend and non-rendering domain logic are out of scope except where they feed the render path
  (the GetUniverse read).

A parallel web-research pass (versions verified against npm on 2026-08-04) grounds the
"modern options" recommendations; its applicable results are folded into findings R005/R010 and the
Questions section rather than kept as a separate wishlist.

## Architecture Baseline

Rules this report judges against:

- **§3.2** — control state in XState, data in Zustand/Query/refs; per-frame loops read machines via
  `getSnapshot()`; **never drive 60 fps from React state**.
- **§3.3** — force-sim is a pure `tick(dt)` run **in a Web Worker** on web; the renderer only reads
  coords into instance matrices/uniforms; **instancing/batching first**; R3F 9 + `WebGPURenderer`
  (WebGL2 fallback) + TSL; post via three's node pipeline.
- **§3.4/§3.5** — visual vocabulary only in rendering layers; `packages/*` stay platform-pure; a
  `*.native` fork exists only where the platform genuinely differs, and a fork owns its own test.
- **§4** — tuning scalars live in `spec/values.yaml` → `pnpm gen:values`, never hardcoded; derived
  state is computed at read time, not stored.
- Versions on the tree: three `0.185.0`, R3F `9.6.1` (patched: the patch repoints the
  `react-native` entry to the web build so the manual native root drives the standard reconciler),
  react `19.2.7`, zustand `5.0.14`, react-native `0.86.0` (new architecture on),
  `react-native-webgpu 0.5.16`. No drei, no React Compiler — memoization is entirely manual.

## Findings

### R001 Native canvas host tears down the WebGPU device on every re-render of its children

- Priority: **P1** (CONFIRMED)
- Area: `packages/3d-renderer` / `apps/mobile`
- Evidence: `packages/3d-renderer/src/canvas/UniverseCanvas.native.tsx:109` — the effect that
  creates the manual R3F root ends with
  `}, [children, dpr, fov, far, clearColor, forceWebGL, toneMapping, exposure])`, and its cleanup
  (`:101-108`) runs `unmountComponentAtNode(canvas)` + `renderer.current?.dispose()`. `children`
  is fresh JSX on every render of the host component, and `dpr` is a fresh array literal at the
  call site (`apps/mobile/src/widgets/universe-canvas/ui/UniverseCanvasWidget.tsx:263`
  `dpr={[1, VALUES.rendering.maxPixelRatio]}`). So **any** re-render of `UniverseCanvasHost`
  disposes the WebGPU device, unmounts the R3F root, then re-creates both and re-inits — a full
  device + pipeline + TSL shader rebuild. The comment at `:47` ("The scene is re-rendered into the
  root on every prop change (below); memoize nothing here") shows the intent was a cheap
  `root.render(children)`, not a teardown.
- Confirmed re-render triggers of the mobile host (each one = a device rebuild):
  `apps/mobile/src/app/navigation/NavigationRoot.tsx:64` (`useIsFocused()` → navigating to
  `/me`/`/diary` and back), the page's own `useQuery(GetUniverse)`
  (`apps/mobile/src/pages/universe/ui/UniversePage.tsx:137`), the sweep clock
  (`UniverseCanvasWidget.tsx:180`, up to 24 samples per time acceleration), palette version,
  ornament preview, `newNeuronIds`, tour transitions, and a mood pick during signup
  (`apps/mobile/src/features/choose-mood-colors/ui/ChooseMoodColors.tsx:30,43`).
- Why it matters: this is the single largest mobile perf defect — seconds-scale hitches (WebGPU
  init + full WGSL recompile) at exactly the moments the product animates (acceleration sweeps,
  launches, onboarding), plus GPU memory churn on a phone.
- Recommendation: split the one effect into (a) an init/teardown effect keyed on the genuine
  device inputs (`fov/far/clearColor/forceWebGL` — or apply tone mapping the way the web host
  does, without teardown: `UniverseCanvas.tsx:78-83`) and (b) a render effect that only calls
  `root.current?.render(children)` keyed on `[children]`; hoist `configure()`'s size/dpr handling
  out of the children path; pass a numeric `dpr` from the widget.
- Suggested job split: "native canvas host lifecycle" job (pairs with R002).

### R002 Web canvas host never disposes the WebGPURenderer — one leaked device per canvas unmount

- Priority: **P1** (CONFIRMED that no disposal exists in our code; the R3F-internals trace is
  PLAUSIBLE, quoted below)
- Area: `packages/3d-renderer` / `apps/web`
- Evidence: `packages/3d-renderer/src/canvas/UniverseCanvas.tsx:92-111` — the `gl` factory
  creates `new THREE.WebGPURenderer(...)` and stores it in a ref; the component has **no cleanup
  effect** and never calls `dispose()`. R3F v9's own unmount path only calls
  `gl.renderLists?.dispose()` and `gl.forceContextLoss()`
  (`node_modules/@react-three/fiber/dist/events-b389eeca.esm.js:15871-15873`) — neither method
  exists on `WebGPURenderer`, so the device, its pipelines and render targets outlive the canvas.
  The native sibling explicitly documents and does the disposal it needs
  (`UniverseCanvas.native.tsx:104-107`) — the two hosts made opposite lifecycle mistakes.
- Why it matters: every canvas unmount leaks a WebGPU device: landing (two scenes) → login →
  universe already leaks two; `/design` mounts 11 canvases web-side
  (`apps/web/src/pages/design/lib/states-panel.tsx:143,188,260` etc.) and 8 on mobile's design
  panel. Long SPA sessions accumulate devices until the browser starts failing adapter requests.
- Recommendation: register a cleanup that disposes the renderer on unmount (e.g. an effect keyed
  on the renderer ref once `frameloop` flips, or R3F `onCreated`/root-unmount hook), mirroring the
  native host's comment. Verify with the headless CDP loop that a mount/unmount cycle does not
  grow `navigator.gpu` device count / GPU memory.
- Suggested job split: same "canvas host lifecycle" job as R001.

### R003 A GetUniverse refetch with identical data restarts the sim worker, recompiles the sky shader, and rebuilds every instance channel

- Priority: **P2** (CONFIRMED structure; PLAUSIBLE on exact frequency — see below)
- Area: `packages/universe` / `packages/3d-renderer` / `apps/web` + `apps/mobile`
- Evidence, link by link:
  - `packages/universe/src/react/use-universe.ts:32-35` maps `query.data` → a fresh
    `UniverseSnapshot` per data identity; nothing configures `structuralSharing`, and connect-es
    responses are Message class instances TanStack's `replaceEqualDeep` does not recurse into —
    so a byte-identical refetch is expected to produce a new identity (this last step is the
    PLAUSIBLE link; the rest is unconditional).
  - `packages/universe/src/episodic-memory-store.ts:18-22` — `setAll` writes a brand-new `byId`
    object and `ids` array on every call, no content-equality bail (`use-universe.ts:61-65` calls
    it on every universe identity change).
  - `apps/web/src/widgets/universe-canvas/ui/UniverseCanvasWidget.tsx:71-78` — `graph` and
    `nodeIndex` memo on `[universe]`, then `bridge.start(graph)`;
    `packages/universe/src/sim-bridge.ts:73-115` — `start()` **terminates and respawns the
    Worker** and re-runs `createForceSimulation` validation.
  - `packages/3d-renderer/src/layers/SkySphere.tsx:103-108,113-123` — `weights` is a new array
    whenever `stops` identity changes (`UniverseCanvasWidget.tsx:221-227` rebuilds stops from
    `universe`), and the material `useMemo` keys on `weights` → a full TSL sky-material
    recompile per refetch even when the numeric weights are unchanged.
  - Store identity churn also rebuilds `StarLayer` channels
    (`packages/universe-render/src/StarLayer.tsx:55-81` keys on `[byId, ids, universeTime]`) and
    re-uploads instance attributes (`InstancedNodeLayer.tsx:157-180`).
- Trigger cadence: `staleTime` is 30 s (`packages/client-cache/src/defaults.ts:29` ←
  `timings.defaultStaleMs`), `refetchOnWindowFocus` is never disabled — so every tab refocus
  after 30 s runs the full cascade. On mobile the same cascade additionally lands on R001's
  device teardown.
- Why it matters: the product's most common background event (a refetch that changes nothing)
  costs a worker respawn (layout continuity is preserved via `remapCoordinateBuffer`, but boot +
  validation re-run), a sky shader compile hitch, and full channel/attribute re-uploads.
- Recommendation: add a content-equality bail at one seam — cheapest is the store (`setAll` keeps
  the previous `byId/ids` when contents match id-by-id), or memoize `universeFromResponse` by a
  response fingerprint. Independently: key `SkySphere`'s material on weight _content_ (e.g.
  joined string) rather than array identity, and let `bridge.start` no-op when the graph is
  topology-identical (node/edge ids + weights unchanged).
- Suggested job split: "refetch identity cascade" job.

### R004 Purchased star shapes vary per-instance geometry cost by ~900× with no budget or LOD

- Priority: **P2** (CONFIRMED)
- Area: `packages/3d-renderer` (bodies)
- Evidence: `packages/3d-renderer/src/assets/bodies/star-shapes.ts` — the shipped default `facet`
  resolves to a 20-triangle icosahedron, while `urchin` builds
  `new THREE.Mesh(new THREE.SphereGeometry(1, 96, 96), material)` (`:400`, ≈18k tris **per star
  instance**), `contour` 64×64 (`:467`), `plasma` 48×48 (`:434`), `bubble` 40×40 (`:300`). The
  shape is a user decoration (`StarLayer.tsx:40` `shape` prop from the ornament registry), so a
  universe with N memories multiplies N × the chosen tessellation with no cap, no LOD, and no
  values.yaml knob.
- Why it matters: a few hundred memories wearing `urchin` is millions of vertices per frame on
  the very display path the decoration shop monetizes — the paid option is the slow option, and
  nothing in CI or values guards the budget.
- Recommendation: normalize tessellation budgets per shape (displacement detail belongs in the
  fragment/vertex shader via TSL, not raw subdivision), or add distance-based LOD; record the
  per-shape budget in `values.yaml` next to the other rendering scalars so a new shape PR has to
  state its cost.
- Suggested job split: "geometry budget" job (with R008).

### R009 Per-frame instanced writes never skip clean frames: five layers recompose and re-upload every matrix every frame

- Priority: **P3** (CONFIRMED)
- Area: `packages/3d-renderer` / `packages/universe-render`
- Evidence: `packages/3d-renderer/src/layers/InstancedNodeLayer.tsx:182-247` — the `useFrame`
  loop recomposes all `count` matrices and sets `instanceMatrix.needsUpdate = true`
  unconditionally, even on frames where the coordinate buffer did not swap (worker `inFlight`
  frames reuse the same buffer — `sim-bridge.ts:116-126`) and after the sim has converged. Five
  instanced layers mount in a typical scene. Also per frame:
  `packages/universe-render/src/AwakenNeuron.tsx:118-125` rewrites its full 32-slot capacity
  (`AWAKEN_CAPACITY`) even when no flare is playing;
  `packages/universe-render/src/GistStarLayer.tsx:140` does a string-keyed `Map.get` per gist
  instance; `InstancedNodeLayer.tsx:193-198` re-looks-up the vertex-scale attribute by name each
  frame. (For balance: the loops allocate nothing — scratch objects are hoisted — and no
  `useFrame` in the repo touches React state or a store; §3.2 is genuinely upheld.)
- Why it matters: steady-state CPU + GPU-upload work proportional to node count on every frame,
  paid even when the universe is visually still — the main JS-thread cost on mobile, where the
  sim also runs inline (`apps/mobile/src/widgets/universe-canvas/lib/sim-worker-spawner.ts:8-10`,
  documented).
- Recommendation: version the coordinate buffer (bridge increments a counter per swap) and let
  contiguous-slot layers skip recompose/upload when neither buffer version, channels, nor
  animation inputs changed; give `AwakenNeuron` an "idle → skip" early-out; cache the attribute
  ref. Longer-term (research-backed): move matrix composition to a TSL compute pass over storage
  buffers so coordinates upload once per sim tick instead of per frame.
- Suggested job split: "per-frame efficiency" job (with R010).

### R010 No adaptive quality or battery path: DPR is static, reduced motion keeps full frame cost, nothing gates on visibility

- Priority: **P3** (CONFIRMED absent — searched, not present)
- Area: `packages/3d-renderer` / both apps
- Evidence: no `invalidate()`/`frameloop="demand"` anywhere (the ambient sky/twinkle animation
  justifies `always` while visible); no `performance.regress`/adaptive-DPR — the only control is
  the static `maxPixelRatio: 2` cap (`spec/values.yaml:47`, `UniverseCanvas.tsx:88`); reduced
  motion freezes time uniforms but still renders every layer at full rate every frame
  (`SkySphere.tsx:136-142`, `StarField.tsx:126-132`); no `AppState`/visibility gate on the native
  render loop (web inherits rAF's hidden-tab pause; RN does not). drei's `PerformanceMonitor`/
  `AdaptiveDpr` are not adoptable (drei v11, the WebGPU line, is unfinished — 39% complete as of
  2026-08), but the pattern is ~50 lines against `setDpr`.
- Why it matters: low-end phones and battery-conscious sessions get the same cost as a desktop
  GPU; a sustained-fps sample driving DPR between 1 and the cap is the cheapest big lever on
  mobile, and an `AppState` gate stops paying for a backgrounded app.
- Recommendation: hand-roll a small fps-window monitor that steps DPR down/up between 1 and
  `maxPixelRatio` (values-seamed thresholds); pause the native frameloop on `AppState !== 'active'`;
  optionally drop to a lower DPR while `reducedMotion` is on. Add `r3f-webgpu-perf` (dev-only)
  as the measurement HUD — the only maintained R3F perf HUD that speaks WebGPU.
- Suggested job split: "per-frame efficiency" job (with R009).

### R012 BandFog builds four separate materials (four WGSL compiles, four draws) that differ by one constant

- Priority: **P3** (CONFIRMED)
- Area: `packages/3d-renderer`
- Evidence: `packages/3d-renderer/src/layers/BandFog.tsx:36-60` — the slice loop constructs a
  disc `Mesh` per band, each with its own `MeshBasicNodeMaterial` (`:42`) whose node graph varies

- Suggested job split: "config-seam hygiene" job or "geometry budget" job — small either way.

### R014 Web hover-glimpse state lives in the canvas host, re-rendering the whole scene tree on every star boundary crossing

- Priority: **P3** (CONFIRMED mechanism; bounded cost — verified the memos hold)
- Area: `apps/web` widget
- Evidence: `apps/web/src/widgets/universe-canvas/ui/UniverseCanvasWidget.tsx:173-180` —
  `hoveredMemoryId` is `useState` in `UniverseCanvasHost`; `handleMemoryHover` fires from
  per-instance pointer events (`InstancedNodeLayer.tsx:286-302`, raycast on every pointer move
  with `frustumCulled={false}`), so crossing from star to star re-renders the host and all 11
  scene layers. Verified the damage is contained: the functional update dedupes same-id moves,
  `StarLayer`'s channels memo (`StarLayer.tsx:55-81`) and `InstancedNodeLayer`'s layout effect
  keys hold, so no GPU re-upload happens — it is pure React reconciliation cost, web-only (the
  mobile fork has no hover).

  exactly when frame headroom matters; the fix is small and removes a whole class of "the host

  that subscribes alone), so the canvas subtree never re-renders on hover. Consider
  `three-mesh-bvh` (0.9.14, renderer-agnostic) on star-body geometry if pointer-move raycasts
  ever profile hot.
- Suggested job split: "refetch identity cascade" job (same subscription-placement theme) or a
  standalone micro-job.

## Cross-Cutting Themes

1. **WebGPU-era lifecycles wired against WebGL-era assumptions (root cause of R001, R002).** R3F
   v9's disposal contract predates `WebGPURenderer`, so the web host silently leaks (R3F's
   unmount path calls WebGL-shaped methods that don't exist) while the native host — forced to
   hand-roll a root — over-scoped its teardown to every render. The two hosts made _opposite_
   mistakes around the same gap. Any fix should land as one documented lifecycle contract in
   `packages/3d-renderer`, not two app-side patches.
2. **Identity-based invalidation without content equality (R003, R014, parts of R009).** The
   query → mapper → store → widget → layer chain propagates _identity_ changes, and no seam
   asserts _content_ equality — so the cheapest event in the system (a no-op refetch) buys the
   most expensive work (worker respawn + shader recompile). One content-bail at the store or
   mapper collapses the whole cascade.
3. **The two-app fork has started drifting (R006, R007, the antialias contradiction, R011's
   camera constants).** The FSD promote-on-reuse gate deliberately exempts platform-marked `ui`
   files, so ~330 duplicated host lines are guard-invisible; the drift predicted by that
   exemption has now happened twice. Promoting the platform-pure host core is the structural fix.
4. **The values.yaml seam eroded at the renderer's edge (R008, R011, R012).** Domain and sky
   tuning flow through `gen:values` faithfully, but layer-level scalars (counts, tessellation,
   camera feel, frozen times) accreted as hardcoded defaults — plus one orphaned key describing a
   design the code rejected. The seam needs a sweep, not a policy change.
5. **The modernization story is additive, not corrective (R005, R010).** The architecture bets
   (WebGPU-first, TSL, worker sim, instancing, no-drei) are all validated by the 2026 ecosystem —
   WebGPU is Baseline since Jan 2026 (Safari 26 shipped it), TSL/node post is the recommended
   path, drei's WebGPU line is _still_ unfinished. What's available now: React Compiler 1.0
   (stable 2025-10) for the non-canvas React tree, R3F 9.7.0's batched instance reconstruction,
   react-native-webgpu 0.8.x stability fixes, TSL compute/storage buffers as the long-term
   coordinate path, and `r3f-webgpu-perf` for measurement.

## Questions / Tradeoffs

- **Landing ships three.js on first paint — standing decision, worth a revisit?**
  `apps/web/vite.config.ts:63-72` documents the 1.62 MB renderer chunk (444 kB gz, modulepreloaded
  from `dist/index.html`) as deliberate: the landing's two scenes import it statically, and the
  split boundary is owned by `spec/tech/web-routing.md`. Options if it's ever revisited: defer the
  walkthrough scene (below the fold) behind an idle/viewport dynamic import so first paint only
  pays the hero, and/or a "reduced renderer entry" as that doc anticipates. Also: the entry chunk
  itself is 1.15 MB (360 kB gz) — worth a bundle-visualizer pass; and `import * as THREE from
'three/webgpu'` defeats tree-shaking (known upstream issue three#31102 when mixing `three/tsl` +
  `three/webgpu` under Vite).
- **`frameloop="demand"` is _not_ recommended globally** — the ambient sky/twinkle animation is
  the product. An idle mode (demand + periodic invalidate when the app is backgrounded or reduced
  motion is on) is the only defensible variant; R010's DPR lever is cheaper and safer first.
- **React Compiler 1.0 adoption order:** add `eslint-plugin-react-hooks@latest` recommended preset
  first (compiler rules run without the compiler — zero risk), then enable
  `babel-plugin-react-compiler` via `@vitejs/plugin-react` for `apps/web`. R3F's
  mutate-in-`useFrame` idiom is compatible (the compiler memoizes render code, not loops), but the
  scene packages should be spot-checked; `"use no memo"` is the escape hatch. Mobile (babel
  preset) can follow once web proves it out.
- **`FrameTick` mounts last, so the sim pump runs after the layers read the buffer** (web widget
  `:337`, mobile `:320`) — every frame renders coordinates one tick stale. Harmless visually
  (one frame at most), but if it is _intended_ ordering it deserves a comment; if not, mounting
  `FrameTick` first (or a negative useFrame priority) removes the latency for free.
- **Has anyone run the WebGL2 fallback lately?** `forceWebGL` exists for parity testing
  (`UniverseCanvas.tsx:28`), and ~17% of global users (older iOS/Android) will get the fallback.
  Worth one headless CDP pass with `forceWebGL: true` per release; TSL compiles to GLSL but the
  bloom/post path degrades differently.
- **TSL compute for the coordinate path** (storage buffers / `instancedArray`) would eliminate the
  per-frame CPU matrix composition entirely (R009's long-term answer) — high ceiling, M–L cost,
  and the WebGL2 fallback must keep the CPU path, so it's a dual-path commitment. Defer until
  R009's cheap skips are in and profiling says more is needed.
- **`@three.ez/instanced-mesh`** (dynamic capacity — would delete the `key={instanceCount}`
  remount — per-instance culling, LOD) fits this scene's shape exactly, but its WebGPURenderer
  compatibility is unverified. Spike before any adoption.
- **Mobile sim placement:** the inline JS-thread fallback is documented and fine at current graph
  sizes (`sim-worker-spawner.ts:2-7`); if it ever profiles hot, the repo already ships
  `react-native-reanimated 4.5` + `react-native-worklets 0.10`, and
  `react-native-webgpu-worklets` (Software Mansion Labs) demonstrates three-on-worklet-threads —
  experimental, but the seam (`SimWorkerSpawner`) is already shaped for it.
