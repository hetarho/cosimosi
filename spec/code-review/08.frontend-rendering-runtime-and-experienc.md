## Architecture Baseline

- Frontend placement follows Feature-Sliced Design; app composition points inward and platform-pure behavior is
  promoted into packages. The web/mobile boundary probes and layout gate enforce this and passed.
- The renderer is deliberately shared. `@cosimosi/3d-renderer` owns Three/R3F and platform hosts, while
  `@cosimosi/universe-render` owns shared R3F domain-to-visual projections. App slices compose them but do not import
  Three directly.
- Coordinates are derived, ephemeral data. The force simulation writes typed buffers; R3F layers read them in
  `useFrame`; no coordinate enters React state or persistence.
- Web runs the simulation in a module Worker. React Native currently selects the inline bridge because it has no
  standard Worker primitive.
- Rendering can reduce fidelity on mobile, but product laws and domain-to-visual semantics stay shared.
- XState owns navigation modes/ids; mutable position buffers and camera objects stay out of machine context.
- `spec/values.yaml` is the source for tunable runtime scalars. Product-level visual behavior must remain consistent
  with the concept invariants, especially emotion affecting appearance rather than position.

The architecture is sound at the ownership level. The highest-risk gaps are at the platform host boundary: React
lifecycle versus the manual native R3F root, native input, app visibility, and the lack of a measured workload contract.

### R001 Native scene updates tear down and recreate the manual WebGPU/R3F root

- Priority: P1
- Status: CONFIRMED
- Area: React Native renderer lifecycle
- Evidence:
  - `packages/3d-renderer/src/canvas/UniverseCanvas.native.tsx:39-99` performs root creation/configuration,
    `root.render(children)`, root unmount, and renderer disposal in one effect whose dependencies include `children`.
  - `apps/mobile/src/widgets/universe-canvas/ui/UniverseCanvasWidget.tsx:65-76` changes its scene children when the
    universe query resolves or the projected graph changes, and `:169-186` changes them on a live palette update.
  - The async renderer factory stores the renderer before `await gpuRenderer.init()` at
    `UniverseCanvas.native.tsx:64-72`, while cleanup may dispose it at `:91-97`; a fast scene update can therefore
    overlap teardown with an in-flight initialization.
- Why it matters:
  - A normal parent render creates a new React element tree, so the effect cleanup unmounts the entire R3F scene and
    disposes the WebGPU renderer instead of reconciling the new children into the existing root.
  - Initial data arrival, a refetch, a launched-memory update, or a palette change can rebuild the WebGPU device,
    pipelines, materials, and scene. The likely device symptoms are a blank interval, compile hitch, lost camera
    continuity, duplicated asynchronous initialization, or a surface that fails to recover.
- Recommendation:
  - Separate the lifetime into three concerns: create/configure the root for the canvas host; reconcile
    `root.render(children)` without cleanup when scene children change; unmount and dispose only when the native canvas
    host actually unmounts.
  - Fence asynchronous initialization with a generation/cancellation token so a stale factory cannot publish or
    return a renderer after disposal.
  - Handle DPR/size/camera configuration changes in place where R3F supports it; if a true renderer replacement is
    required, make that an explicit, rare transition rather than a side effect of any child update.
  - Add a host-level lifecycle test with a fake root/renderer proving that repeated child renders create one root and
    one renderer, preserve the camera, and dispose exactly once.
- Suggested job split: `Native canvas root lifecycle and async-init fencing` (can include R007 and the native part of
  R008).

### R002 Mobile has no free rotate, zoom, or pan input

- Priority: P1
- Status: CONFIRMED
- Area: Native universe navigation
- Evidence:
  - `packages/3d-renderer/src/layers/NavigationRig.tsx:40-42` explicitly says native gesture input is a future sibling.
  - `NavigationRig.tsx:69-72` creates `TrackballControls` only when `canAttachDomControls` accepts the host element.
  - `packages/3d-renderer/src/layers/dom-controls.ts:1-7` deliberately rejects the react-native-webgpu canvas shim
    because it has no `ownerDocument`.
  - Machine-driven focus/fly remains active, but the idle branch at `NavigationRig.tsx:97-110` can only update a
    controls object that does not exist on native.
- Why it matters:
  - The universe is the primary product surface, but a mobile user cannot freely inspect it. Picking a star and
    machine-driven glides do not replace spatial exploration, especially for understanding clusters and relationships.
  - This is an intentional MVP omission, not an accidental FSD violation, but it is now a direct experience gap.
- Recommendation:
  - Define platform-neutral camera commands for rotate, pinch zoom, and two-finger pan, then add a native input adapter
    at the sanctioned platform boundary. Keep camera limits and glide arbitration shared.
  - Gesture input should cancel or blend with an active focus/fly transition predictably and feed reduced-motion
    behavior where appropriate.
  - Verify one-finger rotation, pinch, two-finger pan, inertia, interruption, picking coexistence, and screen-edge
    behavior on iOS and Android devices.
- Suggested job split: `Native universe gesture navigation and camera-command port`.

### R003 The mobile universe keeps an always-on render/simulation path while unfocused

- Priority: P2
- Status: CONFIRMED mechanism; device cost is PLAUSIBLE until measured
- Area: Mobile navigation, AppState, GPU/JS lifecycle
- Evidence:
  - `apps/mobile/src/app/navigation/NavigationRoot.tsx:19-26` computes `useIsFocused()` and passes `active` to the
    universe page.
  - `apps/mobile/src/pages/universe/ui/UniversePage.tsx:52-57` documents that screens remain mounted in the native
    stack, but `active` is used only by `DeletionFlowSheet` at `:159`.
  - The canvas remains mounted at `UniversePage.tsx:116-120`, and the native renderer is configured with
    `frameloop: 'always'` at `packages/3d-renderer/src/canvas/UniverseCanvas.native.tsx:86`.
  - The canvas path has no `AppState` or equivalent visibility handling; the only mobile `AppState` use is unrelated
    login flow cleanup.
- Why it matters:
  - Navigating to diary/settings leaves no application-level signal to pause the universe's frame callbacks,
    simulation, instance-buffer uploads, post-processing, or presentation calls.
  - Depending on native-stack and surface behavior, some final presentation may be suppressed, but the app does not
    guarantee that JS/GPU work stops. This risks battery drain, heat, and contention with the foreground screen.
- Recommendation:
  - Pass a single visibility state (`focused && AppState === 'active'`) to the universe widget/canvas host.
  - Pause the render loop and simulation pumping while hidden, then resume the same root, camera, graph, and
    coordinate buffers without reinitialization.
  - Add lifecycle tests for focus/background transitions and a device trace proving hidden-screen frame work drops to
    zero.
- Suggested job split: `Mobile universe visibility-aware frame lifecycle` (can pair with R002).

### R004 Workload grows with the full lifetime graph while mobile simulation allocates and never sleeps

- Priority: P2
- Status: CONFIRMED architecture; the exact device failure threshold is PLAUSIBLE until benchmarked
- Area: Force simulation, per-frame scene updates, API/render workload contract
- Evidence:
  - `proto/cosimosi/memory/v1/memory.proto:137-142` defines an empty `GetUniverseRequest` and returns repeated memories,
    neurons, and synapses with no cursor or workload budget.
  - `apps/api/internal/memory/pg/store.go:533-560` loads all four universe collections for the user.
  - React Native deliberately returns no worker at
    `apps/mobile/src/widgets/universe-canvas/lib/sim-worker-spawner.ts:3-9`; the inline bridge calls `sim.tick(dt)` on
    the JS thread at `packages/universe/src/sim-bridge.ts:131-155`.
  - Every positive tick rebuilds forces and coordinates at `packages/force-sim/src/simulation.ts:71-78`.
    `spec/values.yaml:381,385` decays alpha but clamps it to `0.02`, so the simulation never reaches a sleeping state.
  - Barnes-Hut builds a new octree every tick at `packages/force-sim/src/barnes-hut.ts:33-67`, allocating node objects
    at `:70-82` and eight-slot child arrays at `:107-110`.
  - Rendering also performs CPU-side O(N/E) work and buffer uploads each frame:
    `packages/3d-renderer/src/layers/InstancedNodeLayer.tsx:174-225` rewrites every active instance matrix, and
    `FatLineLayer.tsx:151-193` recalculates and uploads every ribbon vertex.
- Why it matters:
  - The product intentionally accumulates memories. A workload that is safe for a new account can cross the frame
    budget later without any contract, because response size, simulation work, JS allocation/GC, CPU matrix work, and
    GPU upload volume all grow together.
  - Web isolates the solver in a Worker but still pays the render uploads. Mobile pays both solver and render work on
    the JS-facing runtime, where dropped gestures and slow overlays are especially visible.
- Recommendation:
  - First establish representative graph fixtures and profile breakpoints on target devices; do not guess a global
    hard cap.
  - Add convergence/sleep to the physical layout and wake it only on graph mutations or deliberate reheat events.
    Ambient shader motion may remain active independently.
  - Reuse/pool Barnes-Hut storage or move mobile simulation behind a real off-thread/native execution adapter.
  - Introduce a render workload strategy for mature universes: spatial/semantic LOD, clustering, culling, dirty
    uploads, and/or lower simulation cadence with interpolation. Preserve the complete universe in the domain model;
    renderer LOD is preferable to silently paginating away product facts.
  - Move ribbon billboarding and endpoint expansion toward GPU attributes/storage where supported, after profiling
    proves the CPU/upload path is a bottleneck.
- Suggested job split: `Universe performance contract and representative benchmark`, followed by
  `Simulation sleep/off-thread mobile execution` and `Large-universe rendering LOD` based on measured results.

### R005 Critical native rendering behavior has neither device proof nor a performance gate

- Priority: P1
- Status: CONFIRMED
- Area: Verification readiness
- Evidence:
  - `spec/tech/rendering.md:5-8` says mobile is source-gate verified but on-device/simulator rendering is still
    pending; the same qualification remains at `:339`.
  - `spec/jobs/archive/17.rendering-foundation.md:51` leaves the on-device/simulator verification task unchecked.
  - `apps/mobile/jest.mock.3d-renderer.tsx:1-25` replaces the real canvas, navigation, post-processing, node layers,
    filament layer, and frame tick with passthrough/no-op components.
  - `packages/3d-renderer` has four logic/material tests, but none mounts the native host or asserts root/renderer
    lifetime. The audit found no FPS/frame-time/GPU-time sampling or adaptive quality controller in the runtime.
- Why it matters:
  - The green mobile test suite cannot catch R001-R003, shader/device incompatibility, present timing, GPU memory
    pressure, or gesture latency because the relevant implementation never executes.
  - A rendering-first product needs an explicit experience budget. Without one, changes can be visually correct and
    fully green while regressing startup, p95 frame time, heat, or device compatibility.
- Recommendation:
  - Make a small target-device matrix part of release readiness: at minimum one constrained Android class, one current
    Android class, and representative older/current iPhones.
  - Define and record budgets for time-to-first-stable-frame, p95 foreground frame time, dropped-frame bursts,
    hidden-screen work, memory after repeated route/palette cycles, and representative small/medium/large graphs.
  - Add deterministic host lifecycle tests with injected renderer/root factories, plus a manual or automated device
    smoke path that exercises actual react-native-webgpu rendering.
  - Add sampled production diagnostics for initialization failure and sustained frame stalls without collecting memory
    content or other sensitive facts.
  - Use measured quality tiers to adjust DPR, bloom, field resolution, star counts, and simulation cadence; avoid a
    device-model blacklist when runtime capability/frame data can drive the choice.
- Suggested job split: `Rendering experience budgets, native smoke matrix, and adaptive-quality telemetry`.

### R006 Web ships the renderer and every route in one large eager entry chunk

- Priority: P2
- Status: CONFIRMED
- Area: Web startup and code delivery
- Evidence:
  - `apps/web/src/app/routes/route-screens.tsx:10-14` eagerly imports admin, diary, login, settings, and universe pages.
  - `apps/web/src/app/routes/route-tree.tsx:5-16` also eagerly imports design/test pages and all route-screen
    components; no route-level dynamic import exists.
  - The production build emitted one main application chunk at 2,651.11 kB minified / 763.33 kB gzip and produced
    Vite's `>500 kB` warning. The only separate JavaScript asset was the 11.97 kB simulation worker.
- Why it matters:
  - Signed-out and bootstrapping users download and parse the Three/WebGPU universe stack before they can use the login
    surface. Authenticated users also parse unrelated admin, diary, design, and test code before the first universe
    frame.
  - On mobile-class browsers, parse/compile and main-thread startup can be as important as transfer size.
- Recommendation:
  - Convert route components to lazy route chunks, especially login versus the authenticated universe subtree and
    dev-only design/test pages.
  - Start loading the universe chunk once authentication is known or predictively during a successful sign-in, while
    preserving a stable loading shell and an initialization error state.
  - Measure first content, renderer-module readiness, and first stable frame before and after; do not treat chunk count
    alone as success.
- Suggested job split: `Web route-level code splitting and authenticated renderer preloading`.

### R007 A rejected web renderer initialization can leave a permanent blank canvas

- Priority: P2
- Status: CONFIRMED failure-path gap; occurrence rate is unknown
- Area: Web WebGPU/WebGL initialization and error recovery
- Evidence:
  - `packages/3d-renderer/src/canvas/UniverseCanvas.tsx:52-55` starts with `frameloop='never'`.
  - `UniverseCanvas.tsx:60-75` calls `renderer.init().then(() => setFrameloop('always'))` with no rejection handler,
    cancellation fence, or explicit initialization state.
  - The page error boundary contains React/render errors, but a detached asynchronous Promise rejection is not thrown
    through that boundary.
- Why it matters:
  - If WebGPU initialization or its fallback rejects, the frame loop never starts and the user can see an inert/blank
    canvas while the intended renderer fallback UI is never selected.
  - A late resolution after unmount can also call state update code owned by an obsolete host.
- Recommendation:
  - Own `initializing | ready | failed` explicitly, catch initialization errors, dispose stale renderers, and surface a
    retryable error through the renderer boundary.
  - Fence completion by host generation/unmount and record only coarse capability/error diagnostics.
  - Add tests for resolve, reject, unmount-before-resolve, and retry.
- Suggested job split: `Renderer initialization state and recoverable failure path` (can pair with R001).

- Priority: P2
- Status: CONFIRMED mechanism; visible hitch severity is PLAUSIBLE
- Area: Live visual updates and shader/buffer continuity
- Evidence:
  - Both widgets explain that module-level palette state is invisible to layer memos and use React keys as the

## Cross-Cutting Themes

- **The inner frame architecture is disciplined.** Simulation coordinates live in typed refs, layers update inside
  R3F rather than React state, bodies are instanced, filaments are batched, and web simulation is off-thread. The
  primary lifecycle defect is outside that inner loop: the native host destroys the optimized scene on ordinary
  React updates.
- **Shared source does not eliminate platform obligations.** Web/mobile share the graph and visuals well, but native
  still needs its own root lifecycle, gestures, app visibility, presentation verification, and device budgets.
- **The product has a lifetime-growth workload.** Optimization decisions need graph-size fixtures and budgets, not
  only today's new-account dataset.
- **Continuity is the experience metric.** Camera identity, first stable frame, palette transitions, route
  transitions, and recoverable initialization matter as much as average FPS.

## Questions / Tradeoffs

- Should the complete universe remain simultaneously visible at every scale, or may the renderer cluster/LOD distant
  bodies while the domain and navigation index retain all facts? The latter is recommended for scale, but the visual
  semantics need product approval.
- Can the physical layout sleep once velocity/energy converges while shader ambience keeps moving? This separates
  “the universe feels alive” from “Barnes-Hut must run forever” and is the recommended default.
- What is the supported mobile device floor and minimum acceptable frame rate? Suggested initial measurement classes
  are 60 fps (16.7 ms) for current devices and a stable 30 fps (33.3 ms) reduced-quality tier for the supported floor,
  but release budgets should be explicitly chosen.
- Native uses `antialias: true` at `UniverseCanvas.native.tsx:65-70`, while web disables swapchain antialiasing because
  post-processing owns AA at `UniverseCanvas.tsx:65-67`. This may be a justified native difference or unnecessary MSAA;
  validate GPU cost and PostFX correctness on device before changing it.
