## Architecture Baseline

The rules this report judges against:

- **FSD, one-way imports** (§3.1): `app → pages → widgets → features → entities → shared`; slices
  expose one `index.ts`; `app`/`shared` are segmented, never flat; segments are `ui`/`model`/`api`/
  `lib`/`config` by technical role. Enforced by `steiger`, `eslint-plugin-boundaries` and
  `pnpm lint:fsd:layout`.
- **Pure cross-app code lives in `packages/`** (§3.5), both apps consumers from the start; a
  `*.native.tsx` sibling exists only where a primitive genuinely differs; promote-on-reuse rather than
  copy sideways.
- **Control state in XState, data in Zustand/refs** (§3.2); machine context stays JSON-serializable
  and holds id references only.
- **Domain-first Go** (§2): `cmd/` composes, context packages own behavior, ports declared
  consumer-side, proto/sql mapped at the two anti-corruption boundaries, no business logic in handlers
  (§2.9 #7), no server-authoritative client-derived state (§2.9 #8).
- **Cross-cutting** (§4): per-user isolation on every persisted row and query; gates fail loudly;
  a gate's scope is part of the rule; derived state computed at read time, not stored; **config is
  build-time and generated** — tuning scalars flow `spec/values.yaml` → `pnpm gen:values`, never
  hardcoded.
- **The constitution** (`concept.md` §9–10): the demo and the tour are the batch's stress test of it —
  `[I10]` monotonic universe time, `[I8]` recall restores accessibility not content, `[I2]` the diary
  is never rewritten, `[I5]` positions are emergent and unstored, `[I11]` customization cannot
  overwrite the meaning layer. The demo's exemption is expressible only because it is page state; the
  tour runs over a real account where nothing is exempt.
- **i18n / raw-string / comment discipline**: public copy goes through the i18n seam
  (`lint:raw-strings`), comments explain current code and never process or history
  (`lint:comments`, `spec/principle/code-comments.md`).

The engine/tour/demo work honours this baseline unusually well: `SequenceStep` has no `run`/`action`
field, so "the engine acted for the user" is unrepresentable; `packages/onboarding`'s two closed unions
make a step that spends stardust a compile error rather than a review catch; the demo keeps every
exemption in page state and `scripts/probe-demo-isolation.mjs` proves the import block bites. The
findings below are the gaps around that core, not in it.

## Findings

### R001 The public landing page ships the entire application as one 3.1 MB chunk

- Priority: P1
- Area: `apps/web` build / app-layer routing — the public acquisition surface
- Evidence: `apps/web/src/app/routes/route-screens.tsx:19-27` statically imports every page —
  `AdminPage` (:19), `DemoPage` (:20), `BlogNotFoundPage` (:21), `LandingPage` (:22),
  `DiaryReaderPage` (:23), `LoginPage` (:25), `MePage` (:26), `UniverseHomePage` (:27) — with no
  `React.lazy` or dynamic `import()` anywhere in the file. `apps/web/vite.config.ts` declares no
  `build.rolldownOptions.output.codeSplitting`, no `manualChunks` and no `chunkSizeWarningLimit`.
  Measured from a real `pnpm build:web`: `apps/web/dist/assets/index-DAQIHaF7.js` is **3.1 MB raw /
  ~920 KB gzipped**, and it is one of only two emitted JS files (the other is the 16 KB force-sim
  worker). The build itself warns: `(!) Some chunks are larger than 500 kB after minification`.
- Why it matters: job 120 made the landing page the **public origin root** — the front door every
  first-time visitor and every crawler hits before they have any reason to trust the product. As
  built, that first paint requires downloading the admin console, the entire demo sandbox and its three
  fixture sets, the whole three.js `WebGPURenderer` + TSL renderer stack, the diary reader, `/me` and
  the signed-in universe. None of it is reachable from the landing page's own routes. This directly
  undermines the headline deliverable of this batch: the landing and blog exist to convert cold
  traffic, and ~920 KB gzipped before the hero paints is the single largest cost on that path. It is
  also the one finding here that no gate can see — `pnpm check` is green, and the size warning is
  advisory text on stdout.
- Recommendation: route-level code splitting at the `app/routes` seam. Split at minimum
  `AdminPage`, `DemoPage`, `UniverseHomePage`/`DiaryReaderPage`/`MePage` (everything behind the auth
  gate) and the `@cosimosi/3d-renderer` + `universe-render` graph they pull in, leaving the landing,
  login and blog-not-found routes in the entry chunk. Then set `build.chunkSizeWarningLimit` **down**
  toward the entry chunk's new size so a regression fails loudly rather than warning quietly — §4's
  "gates fail loudly" applied to bundle size. Note the landing legitimately needs some of the renderer
  for `LandingHeroScene`/`LandingWalkthroughScene`, so the split boundary is "the signed-in product",
  not "all of three.js".
- Suggested job split: one job — "split the web bundle at the route seam and gate the entry chunk
  size".

### R002 The spec scaffold templates emit unsubstituted placeholders, and `format:check` enforces the corruption

- Priority: P1
- Area: `scripts/templates` — the SSOT authoring workflow
- Evidence: `scripts/templates/code-review.md:4-5` reads `title: { { TITLE } }` /
  `created: { { DATE } }`, and `scripts/templates/change.md:3,5` reads `plan: { { PLAN } }` /
  `title: { { TITLE } }`. `scripts/new-code-review.mjs:33` substitutes via
  `fill(..., { NN: nn, TITLE: title, DATE: localDate() })`, which matches the literal `{{TITLE}}` —
  so the spaced form never substitutes. **This report is the proof**: `pnpm spec:code-review` created
  it with `title: { { TITLE } }` and `created: { { DATE } }` in the frontmatter, which had to be
  filled by hand. `{{NN}}` survives only because it is quoted (`review: '{{NN}}'`), and line 9's
  `# Code Review {{NN}}: {{TITLE}}` survives because it is in a heading, not YAML.
  The mechanism is YAML, not MDX: unquoted `{{TITLE}}` parses as a nested flow mapping, so Prettier's
  YAML formatter normalizes it to `{ { TITLE } }`. Verified both directions against the repo's pinned
  Prettier 3.9.4: restoring `title: {{TITLE}}` makes `npx prettier --check` **fail**
  (`[warn] scripts/templates/code-review.md`), while `title: '{{TITLE}}'` **passes**
  (`All matched files use Prettier code style!`). `scripts/templates/` is not in `.prettierignore`,
  and `format:check` is the second step of `pnpm lint`.
- Why it matters: this is enforcement-vs-intent drift with the gate on the wrong side. `pnpm lint`
  actively requires the broken form, so the corruption is not a one-off slip someone can fix — a
  correct template fails CI. Every future `pnpm spec:code-review` and `pnpm spec:change` silently
  produces a doc whose `title`, `created` and `plan` frontmatter is garbage; `plan:` on a change doc is
  load-bearing (it names the plan being modified, which `spec:job` reads). `plan.md` and `job.md` are
  currently intact, which is luck rather than design — any future placeholder added unquoted to a
  frontmatter block gets corrupted by the next `pnpm format`.
- Recommendation: quote every frontmatter placeholder in all four templates
  (`title: '{{TITLE}}'`, `created: '{{DATE}}'`, `plan: '{{PLAN}}'`), matching `review: '{{NN}}'`'s
  existing form — proven above to both survive Prettier and substitute correctly. Then add a probe in
  the `test:guards` family that scaffolds each of the four doc kinds into a temp dir and asserts no
  `{{` or `{ {` survives in the output, so the next unquoted placeholder fails a gate instead of
  shipping a broken doc. `check-spec-hygiene.mjs` is the natural home.
- Suggested job split: one job — "quote the scaffold placeholders and probe the scaffolds' output".

### R003 A demo recall's reconsolidated reading is silently replaced by the original text's erosion

- Priority: P2
- Area: `apps/web/src/pages/demo` model — `[I8]`/`[I2]` fidelity in the sandbox
- Evidence: `apps/web/src/pages/demo/model/use-demo-run.ts:261` sets
  `currentText: run.resolved.reconsolidatedTexts[memoryId] ?? facts.currentText` on recall, but
  `applyFacts` (:352-359) rebuilds the memory as `{ ...memory, ...facts }` — and `memory` is the
  resolved fixture, so `decayStages` stays the ladder authored from the **original**
  `memoryText.currentText` (`packages/demo/src/resolve.ts:103`,
  `packages/demo/src/diary-set.ts:89`). `packages/universe/src/current-decay-text.ts:32-33` then reads
  `if (stage <= 0) return memory.currentText; return memory.decayStages[stage - 1] ?? memory.currentText`,
  and `apps/web/src/pages/demo/ui/DemoEntryReader.tsx:38` renders exactly that.
- Why it matters: reachable by ordinary free play, which is unbounded by design. Recall a memory
  (beat 6, or any memory once free play starts) → the reader shows the reconsolidated reading and the
  clock's last-recall anchor resets to 0. Press the month jump enough times that the stage climbs back
  to ≥ 1 → the reader now shows `decayStages[stage-1]`, the erosion of the text the memory had
  _before_ it was recalled. The reconsolidated reading is not eroded; it is discarded. That inverts
  the one thing beat 6 exists to teach — `[I8]`'s "the same scene, come back a little changed" — and
  it is the demo's most-watched moment. Production has the same shape in
  `packages/universe/src/recall-star.ts:44-50` (`applyRecallResult` sets `currentText` and leaves
  `decayStages`) but self-heals: the server regenerates the ladder and the next `GetUniverse` refetch
  replaces the mirror. The demo has no refetch and no server, so the fixture's ladder is permanent —
  this is a demo-only divergence, not a shared bug. Only the scenario's recall target is affected
  (it is the only memory with a `reconsolidatedText`), which is precisely the memory the tutorial
  points at.
- Recommendation: when a recall changes `currentText`, recompute the ladder from the new text with
  the production function the fixtures were authored with —
  `decayStageText(newText, index + 1, newSeed)` over `VALUES.forgetting.stageWordRemovalRatios`, the
  same call `packages/demo/src/integrity.test.ts:220` already pins fixtures against. Store it on
  `DemoMemoryFacts` beside `currentText` (the two facts change together) and have `applyFacts`
  prefer it. This adds no demo-only _rule_ — it reuses the shipped erosion function, so the
  `[I13]`/`[Z6]` isolation argument is unchanged. Extend `use-demo-run.test.ts` with a
  recall-then-advance-time case; the current suite never advances time after a recall, which is why
  46 green fixture tests and a green `pnpm test` do not catch this.
- Suggested job split: pair with R010 as one "demo run-model correctness" job.

### R004 No package in `packages/` is linted at all — 23 packages, including every React seam

- Priority: P2
- Area: root gate scope (`pnpm lint`) vs `spec/ARCHITECTURE.md` §4 "gates fail loudly"
- Evidence: no `package.json` under `packages/` declares a `lint` script (checked all 23), and no
  `eslint.config.*` or `.oxlintrc.json` exists anywhere under `packages/` (only
  `apps/web/.oxlintrc.json` and `apps/web/eslint.config.js`, plus mobile's). The root `lint` script in
  `package.json` reaches packages only through the bespoke Node scanners (`lint:language`,
  `lint:raw-strings`, `lint:comments`, `lint:style-escapes`, `lint:fsd:layout`); the two real
  JS/TS linters are `lint:web` (`pnpm --filter @cosimosi/web lint` → `oxlint --deny-warnings` with
  cwd `apps/web`) and `lint:mobile` (`eslint . --max-warnings=0` with cwd `apps/mobile`). Neither
  can see `packages/`.
- Why it matters: `packages/` is where the cross-app core lives, so it is the highest-leverage code
  in the repo and the least checked. This batch alone added `packages/sequence/src/react.ts` (a hook
  file with four `useEffect`s, a `setTimeout` lifecycle, a promise whose result is written to state
  after an `await`, and a 9-entry `useMemo` dependency array), plus `packages/onboarding`,
  `packages/demo` and changes to `packages/ui`/`achievement`/`auth`. None of it is checked by
  `react-hooks/exhaustive-deps`, `no-floating-promises`, `no-unused-vars` or
  `@typescript-eslint/no-misused-promises`. Two concrete consequences already visible: R006's unused
  dependency, and the fact that a stale-dependency bug in the engine's `useDwellAdvance` /
  `useAnchorRect` — exactly the class `exhaustive-deps` exists to catch — would ship green. This is
  the cluster per-job verification structurally cannot catch, because every job's own suite passes.
- Recommendation: add a linter to the workspace packages. Cheapest path that matches the repo's
  existing shape: one shared flat config at the repo root for `packages/**/*.{ts,tsx}` with
  `typescript-eslint` recommended + `react-hooks` (the plugin the seams need), wired as a new root
  `lint:packages` script inside `pnpm lint`. Expect a first-run backlog; land it as
  `--max-warnings` at the current count and ratchet to 0, rather than blocking on a clean sweep.
  Add the CI counterpart implicitly — `pnpm check` already runs `pnpm lint`, so no workflow edit is
  needed.
- Suggested job split: one job on its own — "lint the workspace packages".

### R005 `packages/demo`'s dependency declarations are inverted

- Priority: P2
- Area: `packages/demo` package manifest
- Evidence: `packages/demo/package.json:21` declares `@cosimosi/i18n` a **devDependency**, yet
  production source imports it: `packages/demo/src/diary-set.ts:2` and
  `packages/demo/src/resolve.ts:10` both `import type { Locale } from '@cosimosi/i18n'`. Conversely
  `:15` declares `@cosimosi/config` a **dependency**, but its only importer is the test —
  `packages/demo/src/integrity.test.ts:3` (`import { VALUES } from '@cosimosi/config'`); no
  production file in the package references it. Compare `packages/onboarding/package.json:15`, which
  correctly puts `@cosimosi/i18n` in `dependencies`.
- Why it matters: the manifest is the package's contract about what it needs to run, and the
  isolation arguments in this batch are explicitly _made from dependency lists_ —
  `packages/onboarding/src/anchors.test.ts:88-93` asserts its dependency set as the proof that "the
  tour created a memory" is unrepresentable, and `packages/demo/src/index.ts:5-8` makes the same
  argument in prose. A manifest that misstates which deps are production-reachable weakens exactly
  that argument. It does not break today only because both imports are `import type` and erased at
  compile time; the moment anyone needs a runtime value from `@cosimosi/i18n` here (a locale list, a
  formatter), it becomes a real resolution failure under a `--prod` install or a stricter pnpm
  `dependency-resolution` setting.
- Recommendation: move `@cosimosi/i18n` to `dependencies` and `@cosimosi/config` to
  `devDependencies`. While there, consider giving `packages/demo` the same manifest assertion
  `packages/onboarding` has — it is the package whose dependency closure carries the `[I13]` argument,
  and it is currently the one without the test that pins it.
- Suggested job split: fold into the R006 hygiene job.

### R006 `packages/onboarding` declares a React peer dependency nothing uses, and a test pins it there

- Priority: P3
- Area: `packages/onboarding` package manifest + its own guard test
- Evidence: `packages/onboarding/package.json:19-21` declares `"peerDependencies": { "react": ">=19" }`

### R007 The landing walkthrough's tuning scalars are hardcoded while the demo's equivalents went to `values.yaml`

- Priority: P3
- Area: config seam (`spec/ARCHITECTURE.md` §4, `spec/tech/config-values.md`)
- Evidence: `apps/web/src/pages/landing/model/walkthrough.ts:107` declares
  `WALKTHROUGH_FADE_SPAN_DAYS = 150` and `:110` declares `WALKTHROUGH_MIRROR_RECALLS = 5` as module
  constants. Both feed production domain math — the first becomes the `universeTime` that
  `currentDecayText`/`effectiveElapsedDays` read (:184-187, :228), the second becomes the
  `recallCount` that `effectiveStrength` reads to weight the sky (:208, :244). `spec/values.yaml`
  has no `landing:` or `walkthrough:` group (checked), while the **same batch** added
  `demo.time_travel_month_days: 30` and `demo.mask_lift_linger_ms: 2400` plus
  `sequence.caption_dwell_ms` / `sequence.highlight_pulse_ms` (`spec/values.yaml:566-593`).
- Why it matters: `WALKTHROUGH_FADE_SPAN_DAYS` is the same _kind_ of number as
  `demo.time_travel_month_days` — universe-days a scripted step advances a clock, tuned against the
  decay stage interval so a stage boundary is crossed — and its own comment says exactly that ("long
  enough that the production decay crosses at least one word-loss stage … short enough that nothing
  hits the deepest stage"). That is a product-shaping scalar tuned against other generated values,
  which is `config-values.md` §1's definition. The inconsistency is what makes this worth fixing:
  the batch established where these belong and then placed two of them elsewhere, so the next author
  has two contradictory precedents to copy. (The genuinely visual constants nearby —
  `RING_PADDING_PX = 8`, `CAPTION_BAND_HEIGHT_PX = 112`, `ATTACH_GAP_PX = 12`,
  `AWAKEN_DURATION_S` — are correctly code, per §4's carve-out for visual language, and are **not**
  part of this finding.)
- Recommendation: add a `landing:` group to `spec/values.yaml` with `walkthrough_fade_span_days` and
  `walkthrough_mirror_recalls`, run `pnpm gen:values`, and read them from `VALUES.landing.*` — the
  file already imports `VALUES` at `walkthrough.ts:1`. Leave `WALKTHROUGH_EPOCH` in code: a fixed
  authored date is content, not tuning.
- Suggested job split: fold into the R010 config/hygiene job, or into R003's demo-model job since
  both touch the same class of decision.

### R008 A de-published achievement leaves a permanently unsettled claim the drain re-reads forever

- Priority: P3
- Area: `apps/api/internal/achievement` — the settle drain
- Evidence: `apps/api/internal/achievement/claim.go:180-186`, inside `SettleClaims`' loop over every
  unsettled row: `row, published := LookupAchievement(record.AchievementID)`, and when
  `!published` the row is `continue`d — skipped without ever being settled or otherwise closed out.
  The loop's filter at :177 is `if !record.Claimed() || record.Settled() { continue }`, so the row
  stays in scope on every future call. Migration `00026`'s `paid_at` is the only settled marker
  (`apps/api/db/migrations/00026_achievement_paid_at.sql:13-16`).
- Why it matters: the row sits at `claimed_at NOT NULL, paid_at NULL` forever. Per the design's own
  statement of what that state means — `claim.go:28-31`, "the row can SAY it: `paid_at` is stamped
  only once a leg returns, so the read answers claimed-and-unsettled and the client keeps a retry
  affordance instead of hiding the row" — the user is left with a permanent retry affordance for a
  reward that can never land, and the drain re-lists and re-skips the row on every subsequent
  settle for that user. The code comment is candid that no retry will help ("No leg exists to pay and
  no retry will make one appear"), but skipping is not the same as closing: the chosen
  representation has no way to say "abandoned", so it says "still owed". Low priority because it
  requires an achievement to leave the catalog after being claimed, which is a deliberate operator
  act, not a runtime path — hence PLAUSIBLE rather than CONFIRMED (I did not trace the FE
  achievement-list surface to confirm the affordance renders).
- Recommendation: decide what the state _is_ and let the row say it. Either stamp `paid_at` with a
  sentinel-free companion column (`abandoned_at`) when the catalog no longer publishes the id, or
  settle it and record the reason — then teach the read to present it as closed rather than pending.
  Whichever is chosen, add the case to `claim_test.go`; the current suite covers the payable legs but
  not the de-published one.
- Suggested job split: one small backend job, or defer — it is the most speculative finding here.

### R009 The mobile `SequenceSpotlight` fork is the complex one and the untested one

- Priority: P3
- Area: web↔mobile parity / test coverage (`spec/ARCHITECTURE.md` §3.5)
- Evidence: `apps/web/src/features/highlight-next-control/ui/SequenceSpotlight.tsx` is 45 lines of
  declarative CSS class + inline style and has a test —
  `apps/web/src/features/highlight-next-control/ui/SequenceSpotlight.test.tsx` (57 lines). The mobile

- Why it matters: the fork itself is legitimate and well-reasoned (the comment at :16 is right that

  catch it, because a `useNativeDriver: true` loop registers no JS timer. So the platform with the
  leak-capable implementation has neither a unit test nor a guard that covers this class.
- Recommendation: add a mobile `SequenceSpotlight.test.tsx` mirroring the web cases (renders nothing
  without a rect; positions from the measured rect; holds still under reduced motion) plus the one the
  web cannot have — that unmounting stops the loop. `apps/mobile/src/widgets/sequence-guide/ui/SequenceGuide.test.tsx`
  already exists as the harness precedent.
- Suggested job split: fold into a small "sequence chrome test parity" job, or into R004's linting
  job as the same theme (packages/mobile checks are the thin ones).

### R010 Dead modulo in the demo's recall entropy

- Priority: P3
- Area: `apps/web/src/pages/demo` model — hygiene
- Evidence: `apps/web/src/pages/demo/model/use-demo-run.ts:387-393`. Inside the loop,
  `hash = (Math.imul(...) >>> 0) % Number.MAX_SAFE_INTEGER` — `>>> 0` already coerces to a uint32, so
  the value is `< 2**32` and the `% Number.MAX_SAFE_INTEGER` (`2**53 - 1`) can never do anything. The
  trailing `return (hash + nthRecall * 7919) % Number.MAX_SAFE_INTEGER` is likewise unreachable in
  practice for any plausible `nthRecall`.
- Why it matters: cosmetic only — the function is correct and deterministic, which is all `[Z5]`
  asks. It is worth recording because a no-op modulo reads as a deliberate range guard and invites the
  next reader to preserve it, or to copy the pattern somewhere the widths differ and it matters.
- Recommendation: drop both `% Number.MAX_SAFE_INTEGER` operands and keep the `>>> 0`, which is the
  operation actually doing the bounding.
- Suggested job split: pair with R003 in the demo run-model job.

## Cross-Cutting Themes

1. **The gate's _scope_ is where the holes are, not the gate's strictness.** Every bespoke scanner in
   this repo is sharp — `probe-demo-isolation.mjs` proves its own rule bites, `lint-fsd-layout.mjs`
   grew a genuinely subtle purity heuristic this batch, `lint-public-copy.mjs` and
   `lint-comment-history.mjs` both ship probes. And `pnpm check` is fully green. What is missing is
   coverage of whole _regions_: no JS/TS linter reaches `packages/` at all (R004), no gate sees bundle
   size (R001), and no gate checks that the scaffolds produce valid documents (R002). All three are
   invisible to per-job verification precisely because each individual job's suite passes.
2. **`format:check` is a code-modifying gate, and one of its outputs is wrong.** R002 is the sharpest
   case: Prettier's YAML pass rewrote `{{TITLE}}` into `{ { TITLE } }`, and because `format:check`
   runs inside `pnpm lint`, the repo now _requires_ the broken form. A gate that rewrites source is a
   gate that can institutionalize a defect, and this one did — in the templates that seed every future
   spec document.
3. **The sandbox reuses production functions faithfully but inherits production's dependency on a
   refetch it does not have.** R003 is the concrete instance: `applyRecallResult` and the demo's
   `recall` both leave `decayStages` stale after changing `currentText`, which is harmless server-side
   because the next read replaces the mirror. The demo copied the _shape_ of the write without the
   _repair_ that makes the shape safe. Worth watching wherever the demo mirrors an optimistic write,
   since the reasoning ("the shipped function does it this way") will look correct every time.
4. **Two placement precedents were set in the same batch and they disagree.** The demo's and engine's
   tuning scalars went to `spec/values.yaml`; the landing walkthrough's stayed in code (R007), and the
   package manifests disagree about where `@cosimosi/i18n` belongs (R005 vs
   `packages/onboarding/package.json`). Neither is harmful today; both give the next author a
   contradictory example to follow.

## Questions / Tradeoffs

- **R001's split boundary.** The landing page genuinely needs part of `@cosimosi/3d-renderer` for
  `LandingHeroScene`/`LandingWalkthroughScene`, so "lazy-load three.js" is not available. Is the right
  line "everything behind the auth gate + admin + demo", leaving the renderer in the entry chunk? That
  is the conservative split and still removes the admin console, the demo and three fixture sets. A
  more aggressive option — a reduced renderer entry for the landing's two scenes — is a bigger change
  and should probably be a separate decision.
- **R003's storage location.** Recomputing the ladder on recall means `DemoMemoryFacts` grows a
  `decayStages` field, i.e. the page's fact record gets a little further from the fixture's shape. The
  alternative (recompute inside `applyFacts` on every projection) keeps the state smaller but runs
  `decayStageText` per memory per render. Given `projectScene` already re-runs on every state change,
  storing it with `currentText` — the value it is derived from — seems clearly right, but it is a
  judgment call worth stating in the job.
- **R004's ratchet.** A first `eslint packages/**` run will almost certainly report a backlog across
  23 packages. Landing it at the current count and ratcheting down keeps the batch shippable but means
  the gate is temporarily not at 0, which sits awkwardly beside §4's "gates fail loudly". Worth an
  explicit decision rather than discovering it mid-job.
- **R008 may be intentional.** The code comments are unusually clear that this state is understood and
  that no retry helps. If the product answer is "an achievement never leaves the catalog once
  claimable", the correct fix is a startup assertion to that effect rather than a new column — cheaper
  and more honest.

- **Demo effect-ordering clears the freshly-written read models.** `DemoUniverseScene`'s store-write

  has filled the stores.

  `<View pointerEvents="box-none">` (`SequenceGuide.tsx:54`) while web wraps in nothing, but each web

  `SequenceCaption.tsx:30`), so the non-modal promise holds on both. Not a divergence.
- **`captionStyle` / `resolveCenteredCaptionPlacement` are web-only, so mobile drifted.** Both

- **`packages/onboarding` duplicates `packages/sequence`.** They share filenames (`script.ts`,

  the two closed unions the engine is generic over. Correct promote-on-reuse, not duplication.
- **The blog's soft 404.** `not_found_handling: "single-page-application"` answers a miss with HTTP
  200, so `BlogNotFoundPage` is a soft 404. Deliberate and documented, with mitigations
  (`noindex` set imperatively at `BlogNotFoundPage.tsx:20-26`, plus a sitemap listing only real

- **The landing walkthrough has R003's stale-ladder bug too.** It does not: the walkthrough is
