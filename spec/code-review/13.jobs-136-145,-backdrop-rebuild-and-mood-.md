### R001 A stage rise teleports the settled gist body DOWN to the sim z before easing up — and the test pins the bug

- Priority: P2 | Verdict: CONFIRMED
- Area: `packages/universe-render`
- Evidence: `reconcileGistRiseState` re-arms `{ start: null, startZ: 0 }` for BOTH a first
  appearance and a stage deepening (`GistStarLayer.tsx:141-143` — `const rose = !isNew &&
instance.stage > previousStage … state.seen.set(instance.nodeId, { start: null, startZ: 0 })`).
  On the next frame `mapGistInstancePosition` seeds the ease origin from the sim buffer:
  `entry.startZ = buffer[offset + 2] ?? 0` (`GistStarLayer.tsx:191`). For a first appearance
  that is right; for a 1→2 deepening the body was settled at the previous stage's neocortex
  band z (`gistCoordinate` always ≥ `neocortexZMin`, `packages/memory-logic/src/semanticization.ts:54`),
  so on the rise frame it snaps down across the whole band gap and re-rises. The file's own
  contract says the opposite: "A stage rise moves that one body upward on a one-way ease
  ([I10] — the rise never reverses)" (`GistStarLayer.tsx:219`). The test conforms to the bug:
  `GistStarLayer.test.tsx:138-140` asserts `out` = `[10, 11, 12]` where `12` is the SIM z,
  under the comment "The ease starts from where the body actually is" — where the body
  actually was is the stage-1 band z (`16`).
- Why it matters: the one-transforming-gist-star centrepiece (change 11 / job 145) visibly
  reverses its signature move exactly when it should shine — a deepening plays as a fall
  through the BandFog onto the episodic star, then a rise. The green test canonicalizes it.
- Recommendation: on a `rose` re-arm, seed `startZ` from the previous stage's band z
  (derivable from the prior `stageSeen` value via the same projection) or the last drawn z;
  fix the test to assert the band-z origin.
- Suggested job split: single small job, renderer-only.

### R002 Full-state Decorate + widened kind set: a stale client's save silently deletes the three new selections

- Priority: P2 | Verdict: CONFIRMED
- Area: `apps/api/internal/store` · `proto/cosimosi/store/v1`
- Evidence: `DecorateRequest` fields 3–5 (`gist_shader_ornament_id`, `mote_ornament_id`,
  `mote_field_ornament_id`, `store.proto:97-99`) are plain `string`, and the save is
  deliberately "a full-state write, not a patch" (`decorate.go:26-28`); `resolveRequest`
  turns an empty id into "this kind's free default" and `applySelection` deletes the row.
  The wire cannot distinguish "client predates these kinds" from "client chose the default".
- Why it matters: during any deploy window (stale cached web bundle, unshipped mobile build)
  every Decorate from an old client reverts the user's saved gist-shader/mote/mote-field
  selections to defaults — silently, and it even feeds `ornament_kind_decorated:*`
  achievement counters for the "changes". Ownership survives, so no money is lost.
- Recommendation: make the three new fields `optional` with absence = keep, or refuse a
  request whose field-count generation lags the kind set. Decide before the kind set widens
  again.
- DECIDED (2026-08-15, Questions #5): accepted for now — no job. The exposure window is
  negligible at current user count. Standing obligation: any job that widens the ornament
  kind set again must resolve this first.

## Cross-Cutting Themes

1. **Guards drift from where the code lives.** The comment-history guard scans everything
   except the config files where process comments actually land (R007); the backdrop budget's
   documented scope predates the store selling combinations past it (R003); the reset
   registry gained one new store but not the other born in the same range (R006); the
   mood-claim protocol lives in a comment (R014). The pattern from review 01/02 — documented
   ≠ enforced — recurs at smaller scale: each rule has a guard, but the guard's domain
   lagged the code's.
2. **Web-first delivery accrues one-directional parity debt — and only sometimes writes it
   down.** The stardust split turned out to be plan-recorded intent (R008, refuted), but the
   hints (R009), fork tests (R011), a11y naming and reachable-value ranges (R016), and sheet
   gestures (touch gestures shipped to the pointer platform first) landed web-first with no
   marker saying whether the mobile half is pending or out of scope. The fix is less "port
   everything" than "record the line the way plan 67 did".
3. **A green test can canonicalize a bug.** R001's rise-origin assertion pins the sim z
   under a comment claiming the opposite; the fake-conforms failure mode review 02 flagged
   is alive.
4. **Deploy-window semantics are nobody's checklist item.** R002 (full-state write vs stale
   clients) and R014's fingerprint change are both correct end-state designs whose
   _transition_ silently loses or mislabels user data; neither job doc mentions the window.
5. **The config seam is respected in aggregate, ambiguous in the particulars.** The range
   moved ~20 knobs INTO values.yaml correctly (adaptive DPR, star-field counts, prices), yet
   two subsystems seam one knob and hardcode its siblings with no ruling either way (R010) —
   and the sheet-gesture hooks pose the same open question (R018, Questions #1).
