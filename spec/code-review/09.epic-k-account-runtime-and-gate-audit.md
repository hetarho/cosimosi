## Architecture Baseline

The rules judged against, and where they live:

- **Toolchain parity is executable.** `.node-version` pins `22.22.1`; CI consumes it via `node-version-file` and pins Go
  `1.26` to match `apps/api/go.mod`. The local runtime (Node 24.18.0) is _newer_ than the pin but satisfies `engines`.
- **One gate, one CI job.** `.github/workflows/ci.yml` runs exactly `pnpm check`, and `check` = `check:node && lint &&
typecheck && test && build:web && build:blog && vet:api && build:api && check:gen`. There is no second entry point to
  drift against — CI parity is structurally sound (see Verification Notes for the one hole).
- **Backend = domain-first Go** (§2.2–2.4): `cmd/` composes, context packages own behavior, ports are consumer-owned,
  `pg`/`rpc` are the only sqlc/proto boundaries, and no row or DTO leaks inward.
- **Per-user isolation is semantic, not token-based** (§4): `scripts/check-persistence-isolation.mjs` requires every
  product `CREATE TABLE` to own a `user_id` column and every product statement's relations to reach a `user_id`
  parameter through conjunctive equality; deliberate cross-user scans are allowlisted one-by-one with a reason. Epic K
  extended it with an `[I1]` hard-delete allowlist.
- **Frontend = FSD, applied identically by both apps** (§3.1, §3.5): one-way layer imports, segmented `app` layer, `ui`
  shared by default with `*.native.tsx` siblings only where a primitive genuinely differs, and pure cross-app modules
  promoted to `packages/` rather than copied sideways. `scripts/lint-fsd-layout.mjs` enforces the app-layer contract and
  a promote-on-reuse rule (R4) that `steiger`/`eslint-plugin-boundaries` cannot express.
- **Config is build-time and generated** (§4): tuning scalars live in `spec/values.yaml` → `pnpm gen:values`, never as
  code consts, and each scalar's comment is its SSOT rationale.
- **Comments explain current code only** (`spec/principle/code-comments.md`): no plan/job/ticket numbers, no history.
  `scripts/lint-comment-history.mjs` enforces a tight high-confidence pattern set.

## Findings

### R001 The repository gate is intermittently red: a job-queue test asserts a global claim drained _its_ job

- Priority: P1
- Area: backend test isolation / gate reliability (`apps/api/internal/memory/pg`)
- Evidence: `pnpm check` on the clean tree at `89fb5bdd` exited 1 with
  `--- FAIL: TestSyncDefersRiseThenWorkerMaterializesIt` /
  `consolidate_convergence_test.go:451: materialized = stage 0 pending 0x36c45ad387b8 ladder <nil>, want stage 4 with a
stored ladder and no pending`. The unsound step is
  [consolidate_convergence_test.go:437-439](apps/api/internal/memory/pg/consolidate_convergence_test.go#L437-L439):
  `worked, err := runner.RunOnce(ctx)` followed by an assertion about _this_ memory. `RunOnce` drains through
  `ClaimDueJob`, which is a deliberately global, cross-user claim — it is allowlisted as such at
  [check-persistence-isolation.mjs:33](scripts/check-persistence-isolation.mjs#L33) — ordered
  `ORDER BY j.next_run_at, j.created_at, j.id` over every user's rows
  ([jobs.sql:4-21](apps/api/db/queries/memory/jobs.sql#L4-L21)). Three tests in this package call `RunOnce`
  ([release_test.go:504](apps/api/internal/memory/pg/release_test.go#L504),
  [store_integration_test.go:864](apps/api/internal/memory/pg/store_integration_test.go#L864), and this one) against one
  shared test database, and 31 sites in the package enqueue jobs. No test truncates `jobs`; the package has no
  `t.Parallel()` and no `t.Cleanup` for the queue.
- Why it matters: `worked == true` proves _a_ job ran, not that _this_ job ran. Any other due row — one left pending by
  an earlier test in the same run, or a retry whose backoff `next_run_at` matures mid-run — satisfies the assertion's
  precondition while this test's semanticize job stays pending. That is exactly the observed end state (`stage 0`,
  pending still set, ladder `nil`). The consequence is worse than one flaky test: `pnpm check` _is_ the CI job, so this
  makes the only merge gate randomly red, which trains reviewers to re-run rather than read. Verdict: **CONFIRMED** —
  reproduced once in a full gate run; 5 subsequent isolated runs and 3 concurrent-package runs were green, so the
  baseline is intermittent rather than broken.
- Recommendation: make the drain assertion identity-bearing instead of count-bearing — have the test claim and assert on
  a specific job id (or add a queue-draining loop that runs until this memory's job is terminal), and give the package a
  `t.Cleanup` that removes the jobs it enqueued. Do not "fix" it by retrying `RunOnce`; that hides the same unsoundness.
  Separately, print the dereferenced pending stage rather than the pointer (see R016).
- Suggested job split: job A — job-queue test isolation.

### R002 A profile-driven locale change updates the store but re-renders nothing

- Priority: P1
- Area: i18n seam, web + mobile app layer
- Evidence: Epic K added a _second_, later locale write. `LocaleBootstrap` sets the locale from the profile query in an
  effect — [locale-bootstrap.tsx:13-16](apps/web/src/app/providers/locale-bootstrap.tsx#L13-L16), mirrored at
  [apps/mobile/src/app/providers/locale-bootstrap.tsx](apps/mobile/src/app/providers/locale-bootstrap.tsx). The locale
  is an external store with a subscriber list ([locale.ts:58-84](packages/i18n/src/locale.ts#L58-L84)), and `m` is the
  _same_ export from both `@cosimosi/i18n` and `@cosimosi/i18n/react` ([react.ts:5](packages/i18n/src/react.ts#L5)) —
  so re-rendering depends entirely on some component calling `useActiveLocale()`. Only three non-test call sites exist.
  On web the sole app-level one is
  [i18n-provider.tsx:33-38](apps/web/src/app/providers/i18n-provider.tsx#L33-L38): `const locale = useActiveLocale()`
  followed by `return <>{children}</>`. On mobile there is **no** app-level subscriber at all —
  [i18n-provider.tsx](apps/mobile/src/app/providers/i18n-provider.tsx) never calls the hook; the only mobile subscriber
  is `app/diagnostics/DiagnosticsScreen.tsx`.
- Why it matters: when a store notification re-renders `WebI18nProvider` alone, its `children` prop is the identical
  element object it received (its parent did not re-render), so React's referential-identity bailout skips the entire
  subtree — the provider re-runs, `document.documentElement.lang` updates, and no `m.*()` call is re-evaluated. Mobile
  has not even that. The user-visible failure is in plan 64's shipped my-page language toggle:
  [AccountProfile.tsx:73-81](apps/web/src/features/account-profile/ui/AccountProfile.tsx#L73-L81) optimistically calls
  `setActiveLocale(next)`, but only `AccountProfile` itself re-renders (its own query data changed) — the `/me` header,
  the tab labels, and every other mounted surface stay in the previous language until a navigation. The same holds for
  first load: a Korean profile on an English browser paints English and stays English. The mobile provider's comment
  ("Product screens render only after the boot gate — by then this effect has run") was true for _device_ negotiation
  and is now stale, because the profile write lands after product screens have painted. Verdict: **CONFIRMED** on the
  code path; the React bailout step is argued rather than executed, so treat that one link as the thing to re-check
  first when fixing.
- Why the tests do not catch it: [locale-bootstrap.test.tsx:44-45](apps/web/src/app/providers/locale-bootstrap.test.tsx#L44-L45)
  asserts `getActiveLocale()` is `'ko'` and that a literal `<span>product-child</span>` still rendered. It never asserts
  that a component calling `m.*()` changed its output, so it passes identically whether or not anything re-renders — a
  test that conforms to the bug.
- Recommendation: make the locale a real render input rather than a side-channel. Either have the provider subscribe and
  key its subtree on the locale (so the bailout cannot apply), or expose the locale through context so consuming
  components re-render on change; add the missing mobile subscriber either way. Then change the test to assert _rendered
  copy_ flips, not the store value.
- Suggested job split: job B — locale reactivity across both apps.

### R003 `INVITE_TOKEN_SIGNING_KEY` is absent from production config, and its absence silently kills invite binding

- Priority: P1
- Area: degraded-config policy, backend composition + deploy gate
- Evidence: the key is documented only for dev — [.env.example:44-47](.env.example#L44) — and appears in **neither**
  `.env.production.example` nor the `require_nonempty_env` list the deploy commit added
  ([deploy-backend.yml](.github/workflows/deploy-backend.yml), which validates `SUPABASE_PROJECT_URL`,
  `SUPABASE_SERVICE_ROLE_KEY`, `COSIMOSI_CORS_ORIGINS` only). Unset, `inviteSignerFromEnv` returns
  `account.UnavailableInviteSigner{}` with **no** production check
  ([account.go:234-248](apps/api/cmd/api/account.go#L234-L248)) — unlike its sibling
  `requireProductionCredentialDirectory`, which hard-fails in production 120 lines above
  ([account.go:114-123](apps/api/cmd/api/account.go#L114-L123)). The signer then returns `ErrInviteLinkUnavailable` for
  every MAC ([invite.go:42-46](apps/api/internal/account/invite.go#L42-L46)), and `acceptInvite` maps _any_
  verification error to a best-effort no-op: `if err != nil { return false, nil }`
  ([signup.go:137-140](apps/api/internal/account/signup.go#L137-L140)).
- Why it matters: `GetInviteLink` fails loudly (`FailedPrecondition` / `ACCOUNT_INVITE_LINK_UNAVAILABLE`) — that part is
  documented and fine. But **signup-time invite binding fails silently**: no invite row is written, `SignUpResponse.invite_bound`
  is `false`, no log, no error, and the whole `[G6]` invite-reward chain (bind → settle → credit both legs) is inert
  with nothing to distinguish it from "nobody used an invite". The `.env.example` comment describes only the
  `GetInviteLink` half, so the blast radius is understated in the one place an operator would look. The deploy commit
  that shipped this was explicitly titled "validate backend runtime credentials"; this is the credential it missed.
  Verdict: **CONFIRMED** by reading the composition and the swallow site.
- Recommendation: pick one policy and apply it symmetrically. Either fail closed in production (mirror
  `requireProductionCredentialDirectory` for the signer) or keep degrading but make it observable and gated: add the key
  to `.env.production.example` and `require_nonempty_env`, and distinguish "capability unavailable" from "token
  invalid" at the `acceptInvite` swallow so the unavailable case is logged rather than indistinguishable from a replay.
- Suggested job split: job C — invite-capability config fail-closed + deploy gate.

### R004 The withdrawal dedup identity is duplicated across two binaries with no parity guard

- Priority: P2
- Area: backend composition root (`cmd/api` ↔ `cmd/worker`)
- Evidence: `apps/api/cmd/api/account.go` and `apps/api/cmd/worker/main.go` declare four structurally identical adapter
  pairs — `accountWithdrawalScheduler`/`workerWithdrawalScheduler`, `accountMemoryPurger`/`workerMemoryPurger`,
  `accountTwinklePurger`/`workerTwinklePurger` — differing only in the type-name prefix. Compare
  [account.go:125-172](apps/api/cmd/api/account.go#L125-L172) with
  [main.go:163-210](apps/api/cmd/worker/main.go#L163-L210): the `PurgeUser` bodies and the
  `errors.New("memory purge requires the in-flight withdrawal job id")` string are character-for-character the same.
  The dedup key literal `"withdrawal:" + scope.UserID()` appears **four** times across the two files
  ([account.go:136](apps/api/cmd/api/account.go#L136), [account.go:146](apps/api/cmd/api/account.go#L146),
  [main.go:174](apps/api/cmd/worker/main.go#L174), [main.go:184](apps/api/cmd/worker/main.go#L184)). The only test in
  the area, [withdrawal_composition_test.go](apps/api/cmd/worker/withdrawal_composition_test.go), asserts the
  production credential refusal and nothing about parity.
- Why it matters: the dedup key is a **contract between two processes**, not composition detail. `Withdraw` enqueues it
  from `cmd/api`; `RestoreAccount` cancels it by the same string, and `CancelUserJob` deletes strictly by
  `(user_id, kind, dedup_key)` ([jobs.sql:48-53](apps/api/db/queries/memory/jobs.sql#L48-L53)). If one copy is edited
  and the other is not, `Cancel` matches zero rows and returns success — restore reports OK while the sweep job survives
  and hard-deletes the restored user's data at the deadline. Nothing in the gate would notice; both files compile, both
  tests pass. §2.9#1 ("renaming a concept across layers") and the promote-on-reuse rule both point the same way.
- Recommendation: publish the dedup identity once from the owning context (`memory`, which owns the jobs table) as a
  constructor over `platform.UserScope`, and have both binaries consume it. The purger adapters are pure glue over
  published behavior and can collapse into one shared declaration the two composition roots both wire.
- Suggested job split: job D — single-source the withdrawal composition.

### R005 Account withdrawal retention reuses the diary-release scalar, whose SSOT comment now contradicts the code

- Priority: P2
- Area: config seam (`spec/values.yaml` → `gen:values`)
- Evidence: `release.soft_delete_retention_days` is documented as belonging to one specific promise —
  [values.yaml:421-427](spec/values.yaml#L421-L427): "a **diary release** is a soft-delete kept restorable for this many
  real-clock days… **Only full delete uses it**". Epic K made account withdrawal a second consumer, on both sides of the
  wire: [account/withdrawal.go:12-14](apps/api/internal/account/withdrawal.go#L12-L14),
  [platform/withdrawn_scope.go:42-44](apps/api/internal/platform/withdrawn_scope.go#L42-L44), and the user-facing copy in
  both apps ([web WithdrawAccount.tsx:44](apps/web/src/features/withdraw-account/ui/WithdrawAccount.tsx#L44),
  [mobile WithdrawAccount.tsx:44](apps/mobile/src/features/withdraw-account/ui/WithdrawAccount.tsx#L44)). Meanwhile the
  epic _did_ add an `account:` block with its own scalars ([values.yaml:32-38](spec/values.yaml#L32)), so the omission
  is an oversight rather than a deliberate coupling.
- Why it matters: two distinct product promises — "30 days to change your mind about a diary" and "30 days to restore
  your account" — now share one number, and the retention duration is recomputed independently in two Go packages. A
  future product decision to change either window silently changes both, and the SSOT comment actively misleads the next
  reader into thinking it is safe to touch. §4 makes `values.yaml` the tuning SSOT and §1 makes one concept one name;
  this is one name doing two jobs.
- Recommendation: add `account.withdrawal_retention_days` (initially 30) and point the account context, the platform
  admission gate, and both apps' copy at it; correct the `release` comment to stop claiming sole use. Factor the
  duration computation so it is derived once per side rather than in two packages.
- Suggested job split: job E — split the retention scalar.

### R006 Every authenticated RPC now pays an uncached account-status DB round-trip

- Priority: P2
- Area: hot-path efficiency, `apps/api/internal/platform`
- Evidence: [withdrawn_scope.go:34](apps/api/internal/platform/withdrawn_scope.go#L34) calls
  `reader.WithdrawnAt(ctx, userID)` for every authenticated, non-exempt procedure. That resolves to
  `SELECT deleted_at FROM users WHERE user_id = $1` ([withdrawal.sql:3-6](apps/api/db/queries/account/withdrawal.sql#L3-L6))
  via [account/pg/store.go:237-252](apps/api/internal/account/pg/store.go#L237-L252). There is no cache, no negative
  cache, and the exempt set contains exactly one procedure (`RestoreAccount`,
  [account.go:108-110](apps/api/cmd/api/account.go#L108-L110)).
- Why it matters: the withdrawn state is a rare, slow-moving fact — it changes at most twice per account lifetime — but
  it is now read on the hot path of every request, including the batched high-frequency unary writes §2.7 designs for.
  In production the pool is the Supabase transaction pooler, so this is a network round-trip per RPC, not a local
  socket. It is cheap to fix now and gets more expensive to fix as call volume grows.
- Recommendation: add a short-TTL per-user cache in front of the reader (seconds are ample given a 30-day window), or
  fold the status into the auth interceptor's existing claim resolution so the check rides an already-required lookup.
  Keep the uncached path as the miss branch so behavior is unchanged.
- Suggested job split: job F — account-status read on the hot path.

### R007 A platform-pure module is duplicated in both apps and escapes the promote-on-reuse guard twice over

- Priority: P2
- Area: FSD placement + guard strength (`scripts/lint-fsd-layout.mjs`)
- Evidence: `apps/web/src/app/providers/locale-bootstrap.tsx` and `apps/mobile/src/app/providers/locale-bootstrap.tsx`
  are identical except for the exported function name (`LocaleBootstrap` vs `MobileLocaleBootstrap`) — `diff` reports a
  single changed line. The module imports only `react`, `@connectrpc/connect-query`, `@tanstack/react-query`,
  `@cosimosi/api-client`, and `@cosimosi/i18n`; the mobile copy contains zero `react-native` imports. The R4 guard misses
  it for two independent reasons: its path filter is
  `PURE_MODULE_SEGMENT = /(^|\/)(api|model|lib|config|shared)(\/|$)/`
  ([lint-fsd-layout.mjs:27](scripts/lint-fsd-layout.mjs#L27)), which `app/providers/…` does not match; and its test is
  `digest(webPath) === digest(mobilePath)` ([lint-fsd-layout.mjs:125](scripts/lint-fsd-layout.mjs#L125)), which the
  one-token rename defeats even if the path did match. `app/model/reset-user-state.ts` is the same shape (identical apart
  from the `WEB_`/`MOBILE_` prefixes and one platform import) and is _in_ a covered segment, saved from the guard only by
  those renames.
- Why it matters: §3.5 says pure cross-app code is "designed cross-platform up front and placed in `packages/` directly
  — not built web-first and extracted later", and §3.1 says the R4 gate enforces exactly that. Here the gate documents a
  rule it cannot see: a genuinely shared module sits copied, and the copies are already the vehicle for R002 (the mobile
  one lacks a subscriber the web one has). `reset-user-state.ts` is the more dangerous shape — its inventory lists which
  user-scoped stores get cleared on account switch, so a store added to one app's list and not the other's is a
  stale-prior-user-state leak with no gate to catch it.
- Recommendation: promote `locale-bootstrap` into the `@cosimosi/i18n` React seam (it is the package's own concern) and
  the reset inventory into a shared registry each app extends with only its platform leg. Then strengthen R4 so it
  cannot be evaded: extend the path filter to `app/providers`/`app/model`, and compare normalized content (identifiers
  aside) rather than raw bytes, so a rename no longer buys an exemption.
- Suggested job split: job G — promote the duplicated app-layer modules and strengthen R4.

### R009 A failed sign-out after a committed withdrawal strands the user on a withdrawn account

- Priority: P2
- Area: async/lifecycle, web + mobile withdrawal feature
- Evidence: the mutation body is two sequential awaits with one error handler —
  [web WithdrawAccount.tsx:20-26](apps/web/src/features/withdraw-account/ui/WithdrawAccount.tsx#L20-L26) and the
  identical [mobile WithdrawAccount.tsx:22-27](apps/mobile/src/features/withdraw-account/ui/WithdrawAccount.tsx#L22-L27):
  `await withdraw(transport); await signOut()`, with `onError: showError`. There is no rollback and no distinction
  between the two failure points.
- Why it matters: if `withdraw` commits and `signOut` then fails (network blip, adapter error), the user sees a generic
  error toast implying the withdrawal did not happen — while it did. They remain signed in on an account the platform
  gate now rejects: every subsequent RPC returns `PermissionDenied` / `ACCOUNT_WITHDRAWN` from
  [withdrawn_scope.go:45-53](apps/api/internal/platform/withdrawn_scope.go#L45-L53), with `RestoreAccount` the single
  exempt procedure and no restore affordance rendered on the my-page surface they are stuck on. The retry path is also
  wrong: pressing the button again re-calls `withdraw`, which is idempotent server-side but reports the _original_
  `withdrawnAt`, so the toast/skew story does not improve.
- Recommendation: treat the withdrawal as committed once `withdraw` resolves — succeed the mutation, then attempt
  sign-out separately and, if that fails, drop to a local session teardown rather than surfacing the withdrawal as
  failed. Because both apps carry the same body, fix it in one shared place (see R004/R007 for the pattern).
- Suggested job split: job I — withdrawal sign-out failure path.

### R010 Client nickname validation is weaker than the server's, so a valid-looking name 400s

- Priority: P3
- Area: golden-parity between shared client logic and the Go domain
- Evidence: the server trims, measures code points against the generated bounds, **and** rejects control characters and

  [signup.go:91-103](apps/api/internal/account/signup.go#L91-L103): `if unicode.IsControl(r) || unicode.Is(unicode.Zl, r)
|| unicode.Is(unicode.Zp, r) { return "", ErrNicknameInvalid }`. The shared client helper implements only the first two
  checks ([nickname.ts:12-23](packages/auth/src/nickname.ts#L12-L23)).
- Why it matters: a nickname containing a pasted newline or control character passes the client's advisory check, enables
  the submit button, and comes back as `InvalidArgument` / `ACCOUNT_NICKNAME_INVALID` — a dead end during the one flow
  the user cannot skip (signup). The helper's own doc comment correctly says the server stays authoritative, so this is
  a completeness gap rather than a layering mistake.
- Recommendation: mirror the character-class rejection in `validateNickname` so the two predicates agree, and pin the
  agreement with a shared case table (the same fixtures asserted on both sides).
- Suggested job split: job J — cross-cutting Epic K hygiene.

### R011 `ProfileGate`'s `enabled` guard has no reachable false branch, and would deadlock the screen if it did

- Priority: P3
- Area: latent footgun, web + mobile app layer
- Evidence: [profile-gate.tsx:18-29](apps/web/src/app/providers/profile-gate.tsx#L18-L29) sets
  `enabled: userId !== null` and then returns the hold on `profile.isPending`. But the component is rendered only inside
  `status === 'authenticated' || status === 'refreshing'`
  ([route-screens.tsx:60-69](apps/web/src/app/routes/route-screens.tsx#L60-L69)) — both of which preserve a non-null
  `userId` — so the false branch never executes today.
- Why it matters: in TanStack Query v5 a disabled query reports `status: 'pending'` with `fetchStatus: 'idle'`, so
  `isPending` is `true` for as long as it stays disabled. Should a future caller mount `ProfileGate` outside that
  boundary, the guard's effect is a permanent loading screen rather than a passthrough or an error — a silent hang, the
  hardest failure to diagnose. The guard reads as defensive while being the opposite.
- Recommendation: either drop `enabled` (the mount site already guarantees the invariant) or make the disabled case
  explicit — branch on `fetchStatus === 'idle' && isPending` and render a definite state instead of the hold.
- Suggested job split: job J — cross-cutting Epic K hygiene.

### R012 The web app imports the i18n facade two different ways, and Epic K's new files split across both

- Priority: P3
- Area: convention/hygiene, `apps/web`
- Evidence: `apps/web/src/shared/i18n/index.ts` exists specifically to route the app through the React seam — it
  re-exports from `@cosimosi/i18n/react` and adds `moodLabel` from `@cosimosi/emotion/i18n`. Yet 40 files under
  `apps/web/src` import `@cosimosi/i18n` directly while 56 go through the barrel, and the epic's own new files land on
  both sides: `WithdrawAccount.tsx` and `MePage.tsx` use the barrel, while `profile-gate.tsx:8` and
  `locale-bootstrap.tsx:7` import the package directly.
- Why it matters: the barrel is the only thing that makes the `@cosimosi/i18n` vs `@cosimosi/i18n/react` distinction
  visible, and that distinction is precisely what R002 turns on — a reader cannot tell from an import line whether a file
  participates in locale reactivity. No lint enforces either choice, so the split will keep widening.
- Recommendation: pick the barrel as the single app-facing entry (it is the one that carries the React seam), migrate the
  40 direct importers, and add the direct package path to the web app's restricted-imports list so the gate holds the
  line.
- Suggested job split: job J — cross-cutting Epic K hygiene.

### R013 The worker composes the account service with no-op reward granters

- Priority: P3
- Area: seam-without-consumer / production fakes, `apps/api/cmd/worker`
- Evidence: [main.go:155-161](apps/api/cmd/worker/main.go#L155-L161) declares `workerNoInviteGranter` and
  `workerNoSignupBonusGranter`, both returning `nil` unconditionally, and injects them into the real
  `account.NewService` at [main.go:95-107](apps/api/cmd/worker/main.go#L95-L107). They exist only to satisfy
  `NewService`'s non-nil checks ([service.go:45-50](apps/api/internal/account/service.go#L45-L50)); the worker's sole
  account entry point is `SweepWithdrawnAccount`.
- Why it matters: these are silently-conforming fakes running in production. Today nothing calls the settlement path in
  the worker, so they are inert — but if a future job kind ever reaches `SettleSignup`, `errors.Join(settlementErr,
bonusErr)` returns `nil` and the job completes successfully having credited nothing, with no log and no failed job to
  investigate. The composition asserts a capability the process does not have.
- Recommendation: make the absence explicit rather than silent — either return a distinct "not available in this
  process" error from the granters (so a wrong caller fails loudly), or let the worker construct a service variant whose
  type does not carry the settlement surface at all.
- Suggested job split: job J — cross-cutting Epic K hygiene.

### R014 The new `[I1]` hard-delete gate matches only `DELETE FROM`

- Priority: P3
- Area: guard completeness (`scripts/check-persistence-isolation.mjs`)
- Evidence: the check added by this epic scans
  `/\bDELETE\s+FROM\s+(?:(?:"[^"]+"|[A-Za-z0-9_]+)\.)?(?:"([^"]+)"|([A-Za-z0-9_]+))/gi` against the migration-derived
  set of product tables, flagging any hit not in the 33-entry allowlist. `TRUNCATE` is not in the pattern, and the
  probe test added alongside it ([check-persistence-isolation.test.mjs:318-328](scripts/check-persistence-isolation.test.mjs#L318))
  exercises only the `DELETE FROM` form.
- Why it matters: the gate's stated invariant is that product rows are hard-deleted only by the sanctioned retention
  mechanisms, and `TRUNCATE product_table` bypasses it entirely while passing the gate. The allowlist design is right;
  the surface it covers is narrower than the invariant it claims. Low likelihood (nothing in the tree truncates today),
  trivial to close.
- Recommendation: add `TRUNCATE` to the scanned forms and extend the probe to cover it, so the guard's coverage matches
  its wording.
- Suggested job split: job H — guard scope and coverage.

### R015 Deploy health and CORS verification is skipped for every non-`main` deploy

- Priority: P3
- Area: CI/deploy parity, `.github/workflows/deploy-backend.yml`
- Evidence: the verification step added by `89fb5bdd` is guarded by
  `if: ${{ github.ref_name == 'main' }}` and hardcodes the production origins
  (`API_ORIGIN: https://api.cosimosi.haeram.me`, `WEB_ORIGIN: https://cosimosi.haeram.me`). The

- Why it matters: staging exists to catch exactly what this step checks — a container that starts but answers no
  health probe, or a CORS origin list that rejects the web app. A staging deploy currently reports success without

- Recommendation: parameterize the origins per environment (they are already environment-derived elsewhere in the
  workflow) and run the verification for both refs.
- Suggested job split: job K — deploy verification parity.

### R016 A test failure message prints a pointer address instead of the value

- Priority: P3
- Area: test diagnostics, `apps/api/internal/memory/pg`
- Evidence: the R001 failure read `materialized = stage 0 pending 0x36c45ad387b8 ladder <nil>` — the format string at
  [consolidate_convergence_test.go:451](apps/api/internal/memory/pg/consolidate_convergence_test.go#L451) passes

- Why it matters: the one artifact a reader gets from an intermittent failure is its message, and this one omits the

- Recommendation: dereference for the message (or print `nil`/the value explicitly). Worth a quick sweep for the same

### R017 `Withdraw` enqueues the sweep before it knows the account exists

- Priority: P3
- Area: ordering, `apps/api/internal/account`
- Evidence: [withdrawal.go:26-49](apps/api/internal/account/withdrawal.go#L26-L49) calls
  `s.scheduler.Schedule(ctx, scope, …)` first, and only then opens the transaction that can conclude
  `ErrSignupRequired` when no `users` row exists.
- Why it matters: the code comment ("A trigger without a mark is harmless because the worker always re-derives
  due-ness") is correct — `SweepWithdrawnAccount` returns `nil` when `deleted_at` is null
  ([withdrawal.go:124-128](apps/api/internal/account/withdrawal.go#L124-L128)) — so this is not a data-loss path. It
  does mean an authenticated-but-unprovisioned caller can leave a permanent `jobs` row per attempt that the queue
  carries for 30 days and the worker wakes for once. Minor, but it is unbounded by the caller.
- Recommendation: check signup state before scheduling, or schedule inside the same transaction that establishes the
  mark.
- Suggested job split: job J — cross-cutting Epic K hygiene.

## Cross-Cutting Themes

- **Two copies, one contract.** R004 (dedup key in two binaries), R007 (`locale-bootstrap` and `reset-user-state` in two
  apps), R009 (the same withdrawal body in two apps), and R010 (nickname rule in Go and TS) are one root cause: Epic K
  spans two Go binaries and two React apps, and each time a rule needed to exist on both sides it was _copied_ rather
  than published from one owner. The architecture already names the fix in two places — §2.2 "contexts integrate through
  small published behavior" and §3.5 promote-on-reuse — and R007 shows the guard meant to catch it was evaded by a
  rename. Nothing in the gate compares two copies for agreement.
- **Guards narrower than the rules they advertise.** R007 (R4's path filter and byte-identity test), R008 (`.sql` and
  `scripts/` unscanned), R014 (`TRUNCATE` unmatched), and R015 (verification gated to `main`) are all the same shape: an
  executable guard exists, passes, and covers less than its wording claims. This is the specific cluster per-job
  verification cannot see, because each job legitimately runs a green gate.
- **Silent degradation where the neighbour fails closed.** R003 (invite signer degrades; credential directory hard-fails,
  20 lines apart in the same file) and R013 (no-op granters in the worker) show an inconsistent fail-closed policy. The
  common consequence is that a misconfigured production is indistinguishable from an idle one.
- **Tests that assert the mechanism instead of the outcome.** R002's locale test asserts the store value rather than
  rendered copy; R001's queue test asserts _a_ job ran rather than _this_ job. Both pass while the behavior users depend
  on is broken. Both were green in the run that produced this report.

## Questions / Tradeoffs

- **Is the 30-day account-restore window genuinely the same policy number as the diary-release window (R005)?** If
  product intends them to move together, the fix is a shared, renamed scalar with a comment saying so — not two
  independent ones. If they are separate promises, they need separate scalars. This is a product decision, not a
  refactor decision, and it changes the shape of job E.
- **How should the invite capability behave in a misconfigured production (R003)?** Fail closed at boot (safest, but a
  missing optional key takes the whole API down) or degrade loudly (keeps the service up, needs a log/alert seam that
  does not exist yet). Recommendation: fail closed at boot in production, because the invite reward has economic
  consequences and a silent half-working state is worse than a refused deploy — but the call is the owner's.
- **Where does locale reactivity belong (R002)?** Keying the provider's subtree on the locale is the smaller change;
  putting the locale in React context is the more honest model and would make R012's import distinction moot. The second
  is more churn now and less later.
- **`initialAuthProvider` stores the Supabase user id as `provider_user_id`**
  ([signup.go:105-120](apps/api/internal/account/signup.go#L105-L120)), acknowledged in its comment as a deliberate
  narrowing of the directory port. The `(user_id, provider)` primary key makes it collision-free today, so this is not a
  finding — but if a second identity per provider ever matters, the column holds no information the `user_id` does not.
  Worth deciding before `auth_providers` grows a consumer.

**REFUTED candidates** (raised during the sweep, disproved — recorded so they are not re-raised):

- _Repeated `Withdraw` postpones the sweep indefinitely._ Refuted: `EnqueueJob` resolves the dedup conflict with
  `ON CONFLICT (user_id, kind, dedup_key) … DO UPDATE SET dedup_key = jobs.dedup_key`
  ([launch.sql:178-179](apps/api/db/queries/memory/launch.sql#L178)) — a deliberate no-op update that preserves the
  original `next_run_at`. Target re-insert is likewise `ON CONFLICT DO NOTHING`. A second withdrawal cannot move the
  deadline.
- _The pg unique-violation code is wrong._ Refuted: `pgErr.Code == "23505"` at
  [account/pg/store.go:351](apps/api/internal/account/pg/store.go#L351) is Postgres `unique_violation`, correctly paired
  with `ConstraintName == "invites_invitee_unique"`; the `ON CONFLICT (token) DO NOTHING` path is separately handled via
  `pgx.ErrNoRows`.
- _The invite settlement advisory lock leaks on error._ Refuted: `WithInviteSettlementLock` registers
  `defer conn.Release()` _before_ the unlock defer, and Go runs defers LIFO, so the unlock executes on the same
  connection first ([account/pg/store.go:85-100](apps/api/internal/account/pg/store.go#L85-L100)). The unlock also runs
  under `context.WithoutCancel` with its own 5s timeout, so a cancelled request still releases.
- _`loginReturnTarget` is an open-redirect._ Refuted: it rejects non-`/` prefixes, protocol-relative `//host`, `/login`,
  `/signup`, and `/invite/*`, falling back to `/`
  ([auth-gate.ts:30-42](apps/web/src/app/routes/guards/auth-gate.ts#L30-L42)), and the value is consumed as a
  client-side router `to`, never as `location.href`.
- _`SweepWithdrawnAccount` can purge data a user could still restore._ Refuted: the sweep and `RestoreAccount` both run
  under `InWithdrawalTx`, which locks the `users` row (`AccountWithdrawalStatusForUpdate` … `FOR UPDATE`), and the sweep
  refuses before the deadline (`withdrawalNotDueError`) while restore refuses after it (`ErrRestoreWindowExpired`). The
  windows are disjoint and serialized.
- _`packages/ui` tabs diverged between web and native._ Refuted: `tabs.native.tsx` is a legitimate `*.native` sibling
  per §3.5 — the web copy's extra code is DOM-specific ARIA tab keyboard navigation (`aria-controls`, roving `tabIndex`,
  Arrow/Home/End), and the native copy carries the RN equivalents (`accessibilityRole="tab"`, `accessibilityState`). No
  shared logic is duplicated.
- _`ExportDiaries` drops a rejected delivery on mobile._ Refuted: the mobile `deliverDiaryExport` is `async` and is
  correctly `await`ed inside the mutation body
  ([mobile ExportDiaries.tsx:20-24](apps/mobile/src/features/export-diaries/ui/ExportDiaries.tsx#L20)), so a failed
  native share sheet reaches `onError`. The web copy is synchronous and needs no await.

**PLAUSIBLE, not raised as a finding.** The web export builds a detached `<a>`, clicks it, and calls
`URL.revokeObjectURL` on the next synchronous line
([deliver-export.ts](apps/web/src/features/export-diaries/lib/deliver-export.ts)). This is the widely-used pattern and
works in current Chromium and Firefox, but detached-anchor downloads and immediate revocation have historically been
fragile in Safari. Not confirmed against a real browser in this audit — worth a manual check on Safari before trusting
the export path there, rather than a speculative code change.
