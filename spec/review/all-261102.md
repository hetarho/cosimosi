## summary

- 16 proposals: 2 P1, 11 P2, 3 P3. The highest-priority defect is a late mutation response repopulating a new account's client state; resource retention and expensive synchronous paths follow.
- Keep the existing domain-first Go, FSD, unary RPC and shared web/mobile renderer. Refactor ownership, state reconciliation and hot paths incrementally; a framework rewrite or dependency sweep is not justified by this review.
- Inventory covered approximately 1,068 authored Go/TS/TSX/MJS/SQL files and 103k lines; deep inspection followed entrypoints, recently changed modules, large modules and lifecycle/data paths. This is a risk-based review, not a claim that every line or production workload was exercised.

- For a focused change, run only its owning suites plus relevant boundary/proto/SQL checks first. At integration, run the complete `pnpm check` once the migration baseline is repaired, real PostgreSQL integration/concurrency suites, and representative physical-device tests. Add `go test -race` to adopted concurrent backend seams rather than claiming ordinary tests prove race freedom. Timing/allocation benchmarks are separate from deterministic unit tests.
- Regression invariants: immutable Diary bodies; soft-delete/restore and withdrawal boundaries; one debit/receipt per paid operation; monotonic universe time and semantic stages; source-faithful text; graph membership and picking; no cross-user state; deterministic domain math; no emotion input to physical layout; no stored authoritative coordinates. Characterize these before restructuring their owners.
- Rollout: ship session/resource correctness patches first. For higher-risk transaction and protocol changes, retain compatible old reads, compare side-effect-free fixture/shadow computations where useful, then enable by an existing operational switch or release cohort after validation. Never shadow-run a charge, mutation or billable provider call merely to compare implementations.
- Rollback: each package is independently revertible. Any database/proto change is additive first; retain old readers and fields through the compatibility window, and remove them only in a later cleanup. A code rollback must not require deleting retained content or refunding a second debit. Stop rollout on tenant-state contamination, duplicate billing, monotonicity regression, growing retained resources or a material p95 regression against the agreed workload.
