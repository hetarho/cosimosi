# T181 Transactions never borrow a second pooled connection

## goal

No request holds a transaction while acquiring another pooled connection, and both roots size their pools explicitly.

## acceptance

- [x] Twinkle spend and earn paths that run inside a transaction read the user zone through the transaction-bound capability: `internal/twinkle/service_test.go` `TestTransactionalPathsReadZoneFromTransaction` binds a pool-side `UserZone` fake that fails the test when called and drives `CheckAndSpend`, `CheckCanSpend`, `EarnOnWrite` and every `InLedgerTx` earn (signup bonus, admin grant, achievement reward, invite claim)
- [x] Memory launch, recall, whole-diary recall, sync and gist view and store decorate read "today"/zone via `EconomyTx.ZoneFor` inside their transaction; their unit fakes assert the constructor-held `UserZone` is not called inside `In*Tx`
- [x] Invite settlement holds no idle pooled connection and no session advisory lock: `WithInviteSettlementLock` and the `AcquireInviteSettlementLock`/`ReleaseInviteSettlementLock` queries are deleted; the directory email check runs before any transaction; `ClaimInvite` takes a transaction-scoped inviter lock inside its ledger transaction and rechecks the reward cap there (account settlement and twinkle claim tests updated, including two concurrent claims for one inviter at the cap)
- [x] Every hand-written transaction helper defers `Rollback` (admin `inTx`, account pg); `internal/admin/pg/store_integration_test.go` makes `fn` panic and asserts the pool returns to zero acquired connections
- [x] `platform/db.Open` takes `Config{URL, MaxConns, MaxConnLifetimeJitter}`; a `pool_max_conns` in the URL still wins (`internal/platform/db/db_test.go`)
- [x] DB-backed `cmd/api/single_connection_integration_test.go` composes the real services over a pool with `MaxConns = 1` and runs launch, recall, gist view, decorate and invite settlement, each within 10 s
- [x] DEPLOY.md states the connection budget: 2 stacks × (API 4 + worker 3) = 14 session-pooler clients
- [x] `pnpm check:api` passes (gofmt, vet, Go suite, build)

## impl notes

- from review/post-refactor-261102 F1
- The zone is read on the transaction's own connection rather than resolved before BEGIN, so use-case order is unchanged: the cmd capability factories that already bind twinkle's ledger to the open transaction also bind account's zone reader to it (new `accountpg.NewZoneReader(tx dbgen.DBTX)` over `GetUserProfile`), the ARCH-9 shared-transaction shape.
- memory: `EconomyTx` gains `ZoneFor(ctx, scope) (*time.Location, error)`; code inside `In*Tx` (`sync.go` `userToday`, recall, view, launch) calls it; the constructor-held `UserZone` remains only for transaction-less reads (spend signals).
- twinkle: transactional entry points take `twinkle.LedgerTx` (`LedgerStore` plus `ZoneFor`); `twinklepg.Store.WithZoneBinding(func(dbgen.DBTX) twinkle.UserZone)` supplies it inside `InLedgerTx`, bound at both roots; an unbound zone fails closed with `ErrZoneReaderRequired`. store decorate passes the same `LedgerTx`.
- Inviter lock: `pg_advisory_xact_lock(hashtextextended('invite_settlement:' || inviter_user_id, 0))` as the first statement of the claim's ledger transaction.
- Pool budgets are deployment constants at each root (ARCH-33), not values.yaml keys: `cmd/api` `apiDBMaxConns = 4`, `cmd/worker` `workerDBMaxConns = 3`, both `dbConnLifetimeJitter = 10 * time.Minute`. T197 reads `workerDBMaxConns`.
- The `MaxConns = 1` integration test is the proof and runs in the batch tier; record it in result limits for the coordinator.

## result

- outcome: Transactional twinkle earns and spends read the user zone through a reader bound to the same transaction (`twinkle.LedgerTx`, `twinklepg.Store.WithZoneBinding`, `account.NewZoneReader` over the transaction); memory resolves today before opening its launch, sync and recall transactions; invite settlement lost its idle session lock, the reward cap staying enforced inside the claim's ledger transaction; admin `inTx` defers rollback; both roots size their pools (API 4, worker 3, dev worker 2, 10 m lifetime jitter) and DEPLOY.md states the 14-client budget.
