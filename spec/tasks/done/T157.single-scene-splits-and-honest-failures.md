### 12. Change: Single-scene splits and honest failures

> A **change proposal** (a WHAT delta) that modifies the already-shipped behavior of [plan/20.encode-usecase](../../plan/20.encode-usecase.md).
> Filled by /cosimosi:create-change through a user interview — a reviewable doc, not a one-line prompt.
> The STEPS live in the job that /cosimosi:create-change-job creates. Write it in English.

#### As-is

A production 별 쪼개기 press returned `resource_exhausted` (HTTP 429) with
`reason: MEMORY_ENCODE_RETRY_EXHAUSTED` and the message
`memory encode retry budget exhausted: Return between 2 and 5 memories, split on event boundaries …`.
Nothing was over any spend limit. Four separate defects meet in that one response.

##### 1. The count floor is unsatisfiable for a diary that holds one scene

PRD [E2] states the split granularity as **"장면(scene) 단위, 보통 2~5개"** — a target. Plan 20 and
`spec/values.yaml` hardened "보통 2~5" into a rejection floor: `encode.min_memories = 2`, enforced by
`memoryCountInRange` as "a retry/repair condition, not a silent clamp", with **no** acceptance path when the
retries run out.

The extractor's own prompt then forbids the only way out. Rule 1 says "one continuous event stays ONE memory
even if the writer's mood shifts inside it" and rule 4b says the passages must partition the diary — so for a
genuinely single-scene entry a second memory cannot be produced without breaking a rule the same result is
checked against. The model returns 1, the domain refuses 1, the repair loop re-prompts with the identical
instruction `encode.max_revise_retries` (3) times, the model returns 1 each time, and the writer is told the
diary cannot become a star. A one-scene diary is a legitimate entry, and today it has no path to the universe.

`PersistEncoded` enforces the same `[2, 5]` bound at 별 띄우기, and the web/mobile merge affordance
(`canMerge = memories.length > VALUES.encode.minMemories`) is derived from the same floor.

##### 2. The violation message cannot tell the two directions apart

`repairableViolation` emits one string — "Return between 2 and 5 memories …" — for **both** an under-count and
an over-count, and never states what it actually received. The re-prompt therefore does not tell the model what
to do (merge adjacent scenes vs. look again for a boundary), and the operator reading the API log cannot tell
whether the model returned 1 or 8. The incident above could not be diagnosed from the error at all; it had to
be read out of the code.

##### 3. The transport code claims a spend limit, and the message leaks content

- `ErrEncodeRetryExhausted` maps to `connect.CodeResourceExhausted` → **HTTP 429**, and the shared FE seam has
  no reason-specific copy for `MEMORY_ENCODE_RETRY_EXHAUSTED`, so it falls back to the coarse
  `error_resource_exhausted` line — "현재 한도에서는 이 작업을 마칠 수 없어요". A model that could not meet the
  extraction rules is reported to the writer as an allowance they have used up. The reason is registered exactly
  that way in `policy/platform/errors.md` §2 (`ResourceExhausted` · `fallback`), so this is the shipped
  contract, not a slip.
- The **real** allowance error is invisible. `ai.CostLimitError` — the `ai.daily_call_cap` (200) per-user UTC-day
  meter — has no entry in the memory context's `domainError`, so it falls through to `apperr.Internal`: the one
  genuine "you are over the limit" failure reaches the writer as a masked 500 with a request id. The two errors
  are exactly inverted.
- `StructuredErrorInterceptor` reports only `Internal`/`Unknown` to the unexpected-error reporter, so every one
  of these 429s is absent from Sentry. The failure that most needs operator attention is the one nothing
  reports.
- `apperr.Domain` sends the raw Go error as the client-visible message, and the repair instructions embed
  content: a source-text violation quotes the LLM-proposed memory **name** and a **token of the passage**
  (`The source_text for %q contains %q …`). `policy/platform/errors.md` §1 forbids sending raw error text, diary
  or memory content, or generated content to a client. The count violation the incident produced happens to be
  content-free; the source-text ones are not.

##### 4. A result that fails the invariants is cached, so the retry is free and hopeless

`meteredLLMClient` caches by `(userID, the port adapter's input hash)` with no TTL, and its `Validate` hook only
checks that the JSON **parses** (`parseExtractResult`) — the domain invariants run afterwards, in the use case.
A structurally valid but invariant-violating split is therefore stored. Pressing 별 쪼개기 again on the same
body replays `stableHash("split", body, diaryDate, existing)`, hits the cache, re-derives the same violation and
returns the same 429 — with **zero** provider calls and zero metered spend. That is precisely the reported
symptom: 429 repeating while the budget does not move. The FE compounds it by classifying
`ResourceExhausted` as retriable, offering a retry that cannot succeed by construction.

`tech/ai-worker.md` already documents the intended behavior — "a result the port adapter rejects (its `Validate`
hook fails) is **not** cached, so an identical retry can re-sample" — so the seam is not delivering the property
its own as-built doc claims. (The same section's `ai.per_call_token_cap = 1200` is stale; the shipped value is
7000, as `tech/memory-encode.md` §4 states.)

#### To-be

##### 1. A single-scene diary is a valid split (soft floor)

`encode.min_memories` (2) stays the **target**: the extractor prompt keeps asking for 2–5 scenes, and an
under-count still costs a re-prompt. What changes is that the target stops being a wall.

- A new value `encode.min_memories_accepted` (1) is the floor the **domain** enforces. A result below
  `min_memories` but at or above `min_memories_accepted` is a **soft** violation: the loop re-prompts it at most
  `encode.under_count_nudges` (1) time with the under-count instruction, and if the model still returns fewer
  than the target, the count is **accepted** and the split proceeds.
- The soft floor buys nothing else. Every other invariant stays hard and keeps its full share of
  `encode.max_revise_retries`: source-text fidelity and coverage, ≥ `encode.min_semantic_neurons` semantic
  neuron per memory, typed neurons, and the `encode.max_output_tokens` guard are enforced on the accepted-count
  result exactly as before. Accepting one memory never means accepting an unverified passage.
- An over-count (> `encode.max_memories`) stays a hard repairable violation, unchanged: merging adjacent scenes
  is something a re-prompt can actually achieve.
- The count can never be zero — `parseExtractResult` already refuses an empty list, and that stays an
  `ErrEncodeInvalidSplit`-class adapter breach, not a repair condition.

##### 2. Launch and the merge affordance use the same floor

- `PersistEncoded` accepts a confirmed split of `min_memories_accepted`…`max_memories`, so a preview the server
  just returned can always be launched. A preview that 별 쪼개기 accepts and 별 띄우기 refuses is not a state
  this change may leave behind.
- The web and mobile merge affordance bounds at `min_memories_accepted` instead of `min_memories`, so the UI
  offers exactly what launch accepts — no more, no less. A one-memory proposal renders and launches like any
  other.

##### 3. A violation says what it saw, and says it in the model's terms

- The under-count and over-count instructions are **separate strings**, each naming the count actually
  returned: an over-count is told to merge adjacent scenes; an under-count is told that if the entry truly is
  one continuous event it may stay one memory, and otherwise to look again for the event boundary it missed.
- The canonical error stays `ErrEncodeRetryExhausted`, but it carries a **violation kind** — a closed set of
  non-content discriminators (`count_under`, `count_over`, `source_text_novel_token`,
  `source_text_reworded`, `source_text_coverage`, `semantic_neuron_missing`, `output_too_large`) — so the API
  log, the reporter and the client all say which invariant gave up without any of them handling diary,
  passage, or generated text.

##### 4. The failure is reported honestly, and the retry actually re-samples

**4a. `MEMORY_ENCODE_RETRY_EXHAUSTED` stops claiming a spend limit.** Its Connect code becomes `Unavailable`
(retriable — a re-sample can succeed), it gains reason-specific localized copy on the shared FE seam saying the
split did not come together and inviting another try, and its `ErrorInfo.metadata` carries the violation kind
from delta 3. The client-visible **message** no longer carries the raw repair instruction, so no diary token,
passage or proposed name crosses the wire in an error.

**4b. The real allowance error becomes visible as one.** The per-user daily AI call cap surfaces as
`ResourceExhausted` with its own memory-context reason and its own copy — the writer is told they have used
today's split allowance, without promising a local reset time the UTC window does not guarantee. Because
`internal/memory` must not import `internal/ai` (the dependency rule — `ai` implements `memory`'s ports), the
cap is expressed as a **memory-owned port error** that the AI adapter translates `ai.CostLimitError` into as it
crosses the port; the RPC layer maps that canonical error, never a vendor or supporting-context type.

**4c. The unexpected-error reporter sees this failure.** `StructuredErrorInterceptor` reports
`MEMORY_ENCODE_RETRY_EXHAUSTED` to the reporter in addition to `Internal`/`Unknown`, carrying only
reason · method · request id · violation kind. The error is still **not** masked (it keeps its own code, reason
and copy) — reporting and masking are separate decisions, and this one is reported without being masked.

**4d. A violating split is returned to the repair loop but never cached.** The metering seam gains a way for a
port adapter to mark a returned result **non-cacheable**, distinct from `Validate`'s reject-and-fail: the repair
loop must still receive the violating split (it re-prompts _from_ it), while the cache must not keep it. The
extractor adapter marks a split non-cacheable when the domain's repairable-invariant judgment — owned by
`internal/memory`, exported for this purpose, never re-implemented in `internal/ai` — reports a violation.
Consequence: pressing 별 쪼개기 again on the same body re-samples the model instead of replaying a stored
failure, and a same-body retry is a real attempt (it costs metered calls, which is the honest price of a retry).

#### Acceptance Criteria

1. An extractor result of exactly one memory is re-prompted **once** with an under-count instruction; if the
   next result is still one memory, `Encode` returns that one-memory split successfully instead of an error.
2. A one-memory split still fails the way it should when something else is wrong: a passage token absent from
   the diary, coverage below `encode.source_text_min_coverage`, a memory with no semantic neuron, or an
   over-budget estimate each still drive the repair loop and, unrepaired, still end in the canonical error.
3. A result above `encode.max_memories` is still re-prompted with an instruction to merge adjacent scenes, over
   the full `encode.max_revise_retries` budget, and is never accepted out of range.
4. `PersistEncoded` accepts a confirmed split of `encode.min_memories_accepted`…`encode.max_memories`; every
   preview `Encode`/`ReviseSplit` returns can be launched, and web and mobile allow merging down to the same
   floor and no further.
5. The under-count and over-count re-prompts are distinct strings, each stating the count actually returned.
6. `MEMORY_ENCODE_RETRY_EXHAUSTED` is returned as `Unavailable`, carries the violation kind in
   `ErrorInfo.metadata`, and its client-visible message contains no diary token, passage, or proposed memory
   name. Web and mobile show reason-specific copy for it, not the coarse resource-exhausted line.
7. The per-user daily AI call cap is returned as `ResourceExhausted` under its own memory-context reason with
   its own copy, and `internal/memory` still does not import `internal/ai` — the cap crosses the port as a
   memory-owned error.
8. `MEMORY_ENCODE_RETRY_EXHAUSTED` reaches the unexpected-error reporter with reason · method · request id ·
   violation kind and no content attribute, while keeping its own code, reason and copy on the wire (it is
   reported, not masked).
9. Two identical `SplitDiary` calls whose first result violates a repairable invariant issue **two** real
   provider calls — the violating split is handed to the repair loop and is absent from the identical-input
   cache. A result that satisfies every invariant is still cached and still charges nothing on the second call.
10. `encode.min_memories_accepted` and `encode.under_count_nudges` exist only in `spec/values.yaml` and its
    generated surfaces; no count floor is written literally in Go, TS, or a prompt string.
11. No regression in the shipped encode path: an ordinary multi-scene diary still splits into 2–5 memories with
    names, moods, passages and typed neurons; the demo and onboarding walkthroughs read exactly as before.

3. **`detail_` prefixing defeated the sensitive-attribute guard** (`platform/interceptors.go`). `metadata["diary"]`

4. **A panicking reporter could mask the refusal** (`platform/interceptors.go`). Reporting now recovers, so a
