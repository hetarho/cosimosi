## goal

A memory with missing stage text gets at most one active regeneration job, however many advances see it.

## acceptance

- [x] `enqueueSemanticizeRegen` skips when a `pending` or `running` semanticize job already targets the memory at its current `representation_revision`
- [x] `consolidate_test.go` `TestRepairPassEnqueuesOnceWhileActive`: two advances with a stuck job leave one active job; after that job ends (done or dead) with text still missing, the next advance enqueues again
- [x] DB-backed check of the new existence query in `internal/memory/pg` (plan uses `job_targets_user_target_idx`)
- [x] `pnpm check:api` passes (gofmt, vet, Go suite, build)

## impl notes

- from review/post-refactor-261102 F23
- The check is an `EXISTS` over the queue tables keyed by user, kind, target id and expected revision, exposed to consolidation through the existing `ConsolidateTx` port as `HasActiveSemanticizeJob(ctx, scope, memoryID, revision) (bool, error)` and implemented in `memory/pg` over the transaction.
- A plain dedup key is not used: `EnqueueJob`'s conflict path returns the existing terminal row and would suppress a needed retry.
- T195 later batches this path; keep the check per memory set-based-friendly (it may become one query over the id set there).

## result

- outcome: The consolidation repair pass enqueues a semanticize regeneration only when no pending or running semanticize job targets the memory at its current revision; once that job ends with text still missing, the next advance enqueues again. The check is `HasActiveTargetJob` on the shared queue store (one EXISTS over `job_targets_user_target_idx`), reached through `ConsolidateTx` on the same transaction.
- at: -
- verified: `TestRepairPassEnqueuesOnceWhileActive` (fails with the check disabled), the consolidation suite, DB-backed `TestHasActiveTargetJobSeesOnlyUnfinishedWorkAtTheRevision`, `pnpm lint:persistence`, `vibe check --tier task -- pnpm check:api`.
- limits: the check lives in the shared queue store rather than a memory-only query because the queue tables are platform infrastructure (ARCH-9); T195 may fold it into a set-based read when it batches this path.
