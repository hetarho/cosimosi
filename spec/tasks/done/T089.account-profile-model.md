> plan 04 deliberately left open ("no database domain tables except auth-related persistence that Supabase owns
> externally") and leaves the account use-cases to its three siblings.

#### Purpose

Today cosimosi has **no user**. Identity is 100% delegated to Supabase Auth: `platform.AuthInterceptor` →
`SupabaseJWTVerifier` → `platform.UserIdentity{UserID}` → `platform.UserScope`, and every product table carries a bare
`user_id TEXT`. The only `CREATE TABLE .*users` in the repo is `admin_users`, an operator join. That was correct while
the product was one core loop: a scope string is all a per-user query needs. It stops being correct the moment the
product must answer "what is this person called", "what language do they read", "which sign-in methods are linked", and
above all **"when does their day start"** ([U5][U6][U7]).

The day-boundary question is the reason this unit is the Epic K root and lands before Epic L. Three shipped rules each
invented their own answer, and all three are wrong: `twinkle.BasicRemaining(now, resetWindow, spent)` has no zone
parameter and resets on the **UTC** calendar day; `memory/launch.go` widens its future-date rejection by a whole day
with the comment "one day of slack covers the maximum UTC offset (UTC+14)"; and `WritingFlowSheet`'s `todayIso()` reads
the **device** zone, client-side and unpersisted. So a user in Seoul gets a fresh `SMALL` grant at 09:00 local, can
launch a star dated a day in the future, and sees a default diary date that silently disagrees with the server. [U7]
answers all three with one fact — `User.Timezone`, auto-detected, never asked for, editable in `/me` — and this unit is
where that fact becomes storable and readable ([G2][W5][T1]).

The second decision this unit owns is **what a `users` table adds and what stays in Supabase**. Credentials, email and
email-verification stay in Supabase Auth: they are mutable there, and a copy in our database is a second store that
goes stale on the user's next email change — exactly the drift a profile page cannot tolerate ([K6]). `users` therefore
holds only what Supabase has no opinion about: nickname, timezone, locale, the soft-delete marker
[62.withdrawal-usecase](62.withdrawal-usecase.md) needs, and a creation timestamp. Email is read through the same
Supabase Auth Admin adapter the admin console already ships (`admin/directory/directory.go`), promoted here to a
platform package so `account` and `admin` can both bind it without importing one another.

The third is the **`Invite` token model** ([U8]): a link the invitee never types a code from, verifiable without a
cross-user table scan, expiring on its own terms, and single-use — the shape that lets
[61.signup-and-invite-usecase](61.signup-and-invite-usecase.md) build its four-part anti-farming gate on top of
something that cannot be replayed.

#### Design

##### Placement (extend the existing supporting context, split by file not by package)

Everything here lands in `apps/api/internal/account`: the context already exists, already owns per-user rows, and
already has the `{pg,rpc}` seams; `account` is plain product English as PRD §3.1 rule ⑦ demands. The context grows from
one scalar preference to three aggregates, so the **files** split — `doc.go`, `types.go`, `profile.go`, `authprovider.go`,
`invite.go`, `palette.go` (the shipped palette behavior moved verbatim out of `account.go`), `ports.go`, `errors.go`,
`service.go` — while the **package** stays flat. ARCHITECTURE §2.3 makes the `{domain,app}` split a refactor that must
remove noise; three thin aggregates with no import cycle and no mixed IO/domain code do not qualify, and splitting now
would force 61/62 to move their use-cases again. The named trigger for the split: when a use-case in `account` needs an
orchestrator distinct from its pure validation (i.e. when 61's `SignUp` transaction and 62's `Withdraw` transaction both
exist), `internal/account/{app,pg,rpc}` is earned — and no earlier.

The constructor becomes `account.NewService(account.ServiceDeps{Store, Directory, InviteSigner, Now})` (the shipped
`twinkle.ServiceDeps`/`admin.ServiceDeps` form for a >1-dep context); `apps/api/cmd/api/account.go` is
updated in place and remains the single composition-root file for this context.

##### The three tables (migration `00016_account_identity.sql`)

One goose migration with both `-- +goose Up` and `-- +goose Down`, each table preceded by a prose comment naming this
plan and its invariant tags. sqlc reads `db/migrations/*.sql` as its schema, so the tables are visible to codegen
the moment the migration lands.

```sql
-- users — the account profile row ([U1][U6][U7]). The PK is named user_id (not id) so the
-- persistence gate sees an owned scope column, matching mood_colors/admin_users.
-- There is deliberately NO email column: email lives in Supabase Auth and is read through
-- the platform directory adapter, so it cannot go stale here.
CREATE TABLE users (
    user_id    TEXT PRIMARY KEY,                          -- the Supabase Auth subject; per-user isolation [U1]
    nickname   TEXT NOT NULL,                             -- the only thing signup asks for [U6]
    timezone   TEXT NOT NULL,                             -- IANA name; THE day boundary [U7][G2][W5][T1]
    locale     TEXT NOT NULL,                             -- a shipped @cosimosi/i18n locale [K6]
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    deleted_at TIMESTAMPTZ                                -- withdrawal soft-delete marker; written only by plan 62
);

-- auth_providers — which sign-in methods this account has ([U5]); several rows per user.
-- Membership truth stays in Supabase; this row records when WE first saw the linkage.
CREATE TABLE auth_providers (
    user_id          TEXT NOT NULL,
    provider         TEXT NOT NULL,
    provider_user_id TEXT NOT NULL,
    linked_at        TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (user_id, provider),                      -- one row per method per user
    CHECK (provider IN ('GOOGLE', 'PASSWORD'))            -- the closed set, in the schema
);

-- invites — one row per BINDING ([U8][G6]). A row exists only because an invitee arrived
-- through a link, so invitee_user_id and bound_at are NOT NULL: an "unbound invite" is not
-- representable. No FK to users — a withdrawn inviter leaves a null-tolerated dangling
-- reference, never a cascade.
CREATE TABLE invites (
    id              TEXT PRIMARY KEY,
    user_id         TEXT NOT NULL,                        -- the INVITER; the scoping column [U1]
    invitee_user_id TEXT NOT NULL,
    token           TEXT NOT NULL UNIQUE,                 -- the presented capability; UNIQUE = single use
    created_at      TIMESTAMPTZ NOT NULL,                 -- the token's issued-at, recovered from its payload
    bound_at        TIMESTAMPTZ NOT NULL,                 -- when the invitee arrived
    rewarded_at     TIMESTAMPTZ,                          -- settlement, set once by plan 61 [G6]
    CHECK (invitee_user_id <> user_id),                   -- self-invite is unrepresentable
    CHECK (rewarded_at IS NULL OR rewarded_at >= bound_at)
);
CREATE UNIQUE INDEX invites_invitee_unique ON invites (invitee_user_id);
```

`invites` has **no `deleted_at`**. [62.withdrawal-usecase](62.withdrawal-usecase.md) requires invite rows to be
soft-hidden (not deleted) during a withdrawal window so `rewarded_at` survives and a withdraw→restore cannot re-open a
settled invite; that hiding is **derived** from the inviter's `users.deleted_at`, never copied into a second flag — the
same anti-join discipline [68.diary-search-and-filter](68.diary-search-and-filter.md) pins for released diaries, and
the reason restore stays exact.

##### sqlc queries (`apps/api/db/queries/account/`)

Three new files, all static sqlc with nullable args, in the directory named after the context (the gate keys on
`<dir>/<file>#<sqlcName>`): `users.sql`, `auth_providers.sql`, `invites.sql`. This unit owns the reads and the profile
update; 61 owns the profile/provider/invite inserts and 62 owns the `deleted_at` writes, in the same files.

- `GetUserProfile` — `SELECT … FROM users WHERE user_id = $1` (returns `deleted_at` so 62's interceptor and 61's
  inviter-liveness check read one row, not two queries).
- `UpdateUserProfile` — `UPDATE users SET nickname, timezone, locale WHERE user_id = $1 AND deleted_at IS NULL`.
- `ListAuthProviders` — `WHERE user_id = $1 ORDER BY linked_at`.
- `CountRewardedInvitesByInviter` — the per-inviter cap input 61 reads (`WHERE user_id = $1 AND rewarded_at IS NOT NULL`).

Every statement is conjunctively scoped by a `user_id` parameter, so `pnpm lint:persistence` passes with **no** new
`globalQueries` entry. Note the property that makes this safe rather than lucky: the gate is syntactic, so a
lookup of _another_ user's profile by id (61's inviter-liveness read) also passes it. [U1] for `users` is upheld one
layer up — **no request message in `cosimosi.account.v1` has a `user_id` field**, so the only id a caller can name is
their own scope.

##### `Email` stays in Supabase: the promoted directory adapter

`apps/api/internal/admin/directory/directory.go` already talks to the Supabase Auth Admin API (`/auth/v1/admin/users`,
`apikey` + service-role bearer) and already exposes `EmailFor`. It is promoted to
**`apps/api/internal/platform/supabase`** — platform is "shared infrastructure with no business meaning" (§2.2), which
is exactly what a GoTrue HTTP client is, and `platform/supabase_auth.go` (the JWT verifier) is already there. The
promotion is only legal if the adapter stops importing a context: today it returns `[]admin.DirectoryAccount`, so it
would make `platform` depend on `admin`. Therefore:

- the promoted package returns **platform-owned DTOs** — `supabase.Account{UserID, Email, EmailVerifiedAt, SignupAt}` —
  and exposes `EmailFor`, `EmailVerifiedAt`, `Identities`, `ListUsers`; [62.withdrawal-usecase](62.withdrawal-usecase.md) later adds `SetUserBanned`;
- the keyless in-memory `Fake` moves with it (tests, dev, and the production fallback when no service-role key is set);
- **`account` and `admin` each declare their own consumer-owned port** in their own `ports.go` (§2.4). `account`'s
  is narrow — `account.Directory { EmailFor(ctx, userID) (string, error); Identities(ctx, userID) ([]string, error) }` —
  and `admin.AccountDirectory` is unchanged;
- `apps/api/cmd/api/{account,admin}.go` bind the one concrete through small translating adapter structs (the
  composition-root adapter shape every v2 cross-context edge uses). `admin`'s observable behavior does not change; its existing tests are the regression
  guard.

`platform.UserIdentity` keeps carrying **only** `UserID`. No email, nickname, timezone or locale enters the auth
context — the guard is that the struct has no field for them.

##### The profile model, its validation, and the unprovisioned state

`account.Profile{UserID, Nickname, Timezone, Locale, CreatedAt}` — a domain struct with no proto and no sqlc in sight.
Validation lives in the context behavior, not the handler (§2.9 #7):

- **Nickname** — trimmed, non-empty, **rune** length within `account.nickname_min_length … account.nickname_max_length`
  (rune, not byte: a 4-character Korean nickname is 12 bytes). Not unique.
- **Timezone** — an IANA name accepted only if `time.LoadLocation` resolves it; an unknown name is rejected and never
  stored (the palette allow-list pattern). A stored name that later fails to load coerces on **read** to
  `account.DefaultTimezone = "UTC"`, the same fail-safe `DefaultPaletteID` provides — so the boundary always resolves.
  **Operational consequence, stated because it is easy to miss:** the production image is
  `gcr.io/distroless/static-debian12` with `CGO_ENABLED=0` and therefore ships **no zoneinfo database**, so
  `time.LoadLocation` fails for every name but `UTC`/`Local` unless the tz database is embedded. Both binaries
  (`cmd/api`, `cmd/worker`) must `import _ "time/tzdata"`.
- **Locale** — accepted only if it is a shipped `@cosimosi/i18n` locale. The Go set is a two-element mirror kept honest
  by a **byte-identical fixture pair** introduced here — new `packages/i18n/fixtures/locales.json` ↔ new
  `apps/api/internal/account/testdata/locales.json`, asserted from both sides — reusing the shipped
  `palette-ids.json` drift guard verbatim (`packages/emotion/src/registry.test.ts` ↔ `account_test.go`).
  Precedence: server `users.locale` (authoritative once set) > `localStorage["cosimosi.locale"]` / RN device
  locale > `defaultLocale = 'en'`; the single write is 64's `/me` language control. **The two writers differ on
  purpose and this is the whole of it:** `UpdateProfile` (here) _rejects_ an off-set tag, because the user chose it
  from a two-item control and a silent coercion would lie; `SignUp` ([61](61.signup-and-invite-usecase.md)) _coerces_
  an unknown or empty tag to `defaultLocale`, because the tag there is a negotiated guess and a locale is a
  preference, not a boundary. Timezone has no such split — both writers reject.
- **Unprovisioned is a first-class state.** An authenticated user with no `users` row is normal — every account created
  before this migration is in that state, and so is every user between Supabase sign-up and the nickname step.
  Structurally: `GetProfileResponse.profile` is a **message field**, and its absence _is_ "not provisioned". No default
  nickname is ever synthesized, and **no read writes a row** (there is no lazy provisioning; `SignUp` in plan 61 is the
  only writer). 63's gate routes an absent profile to the nickname step. This is also why no data backfill is needed:
  pre-existing Supabase accounts simply walk one nickname step on their next sign-in.

##### The timezone boundary contract (the core of this unit)

**Representation.** The IANA name (a string) is the single representation that crosses every boundary: the column, the
proto field, and the `account` port. A `*time.Location` is a runtime resolution, never a stored or transported value.

**Publication.** `account.Service.ZoneFor(ctx, scope) (string, error)` is the published behavior: it reads the profile,
coerces an unresolvable or missing zone to `UTC`, and returns the name.

**Consumption.** The consumer declares the port and the composition root binds an adapter:

```go
// apps/api/internal/memory/ports.go — consumer-owned, memory's own types only
type UserZone interface {
    ZoneFor(ctx context.Context, scope platform.UserScope) (*time.Location, error)
}
type UTCUserZone struct{} // shipped default: always time.UTC — today's behavior, preserved
```

The adapter in `apps/api/cmd/api/memory.go` calls `account.Service.ZoneFor` and does the `time.LoadLocation`, so **no
domain code ever parses a zone**. The default binding returns `time.UTC`: unlike the achievement recorder port, which
[75.achievement-tracking-usecase](75.achievement-tracking-usecase.md) requires production to fail closed on, a
UTC fallback loses no data and is exactly the shipped behavior, so this port does not fail closed — but a
composition-root integration test asserts the production wiring binds the real reader (the shape of
`TestProductionTwinkleExternalEarnsFailClosedWithoutAdapters`). `account` imports neither `memory` nor `twinkle`;
neither imports `account`. Plan 65 declares the twin port in `twinkle/ports.go` for the `SMALL` reset.

**What the zone is used for, exhaustively.** The zone answers exactly one question — _what is today for this user_ — and
is applied at every site where the **real** clock (`s.now()`) is truncated to a calendar day:

| Site                                          | Today's code                                                            | What it becomes                                    |
| --------------------------------------------- | ----------------------------------------------------------------------- | -------------------------------------------------- |
| `memory/launch.go` future-date rejection      | `utcDate(s.now()).AddDate(0, 0, 1)` — a whole day of slack "for UTC+14" | today in the user's zone, **no slack** ([T1][I10]) |
| `memory/sync.go` `SyncStatus.Today`           | `utcDate(s.now())`                                                      | today in the user's zone ([R1a])                   |
| `memory/sync.go` `syncToToday` consent target | `utcDate(s.now())`                                                      | today in the user's zone                           |
| `memory/spend_signals.go` recall baseline     | `utcDate(s.now())`                                                      | today in the user's zone                           |

**What the zone must NOT touch**, and this is the structural line that keeps [I10] safe: every other `utcDate` call in
`memory` (`forgetting.go`, `semanticization.go`, `clock.go`) truncates a **universe-time DATE**, not a real instant.
Universe time is a per-user date on the diary timeline with no zone — a zone parameter there would make elapsed-days
math depend on a profile edit. So `AdvanceClock` and `CanLaunchAt` keep their signatures unchanged, and the monotonic
comparison stays date-vs-date. The zone decides what "today" is; it never participates in a comparison between two
stored dates.

**The diary default date ([W5])** is the client's only use of the zone: 63/64's compose sheet replaces
`WritingFlowSheet`'s device-zone `todayIso()` with today in the **profile's** zone. It is a _default_ in an editable
field — the server never trusts a client date, and the future-date rejection above is the enforcement. That asymmetry is
deliberate and is why the zone→date conversion needs no golden fixture (see below).

**Anti-farming ([G2]).** A timezone edit writes only `users`. It touches no `twinkle_balances` row, no
`universe_state` row, and no ledger entry — so a profile edit cannot move a grant window, a balance or a clock. Combined
with the anchor's existing monotonic roll-forward (`GREATEST(basic_reset_window, $reset_window)` in
`UpdateTwinkleBalanceDelta`), a user cannot toggle the timezone to mint a second `SMALL` grant. Plan 65 inherits that
guarantee rather than re-deriving it.

##### The `AuthProvider` linkage ([U5])

The closed set is `GOOGLE | PASSWORD`, expressed three times and never widened: a Go constant set, the DB CHECK, and a
proto enum `AuthProviderKind{AUTH_PROVIDER_KIND_UNSPECIFIED|GOOGLE|PASSWORD}` (buf STANDARD's `_UNSPECIFIED = 0` prefix
form — no enum is reused across contexts).

Membership truth stays in Supabase, because that is where a linkage is created: `ListAuthProviders†` reads the identity
list through `account.Directory.Identities` and maps it onto the closed set; the `auth_providers` row supplies the
product-visible `linked_at` when we have one, and is the degraded fallback if the directory is unavailable (never an
empty list). The `auth_providers` write is `account.Service.RecordAuthProvider(ctx, scope, kind, providerUserID)` —
published behavior that plan 61 calls inside its `SignUp` transaction; this unit does not decide _when_. This split is
safe because linkage is **append-only in v2**: there is deliberately **no `UnlinkAuthProvider` RPC and no unlink
message** anywhere in `cosimosi.account.v1`, so the only possible drift is a provider linked out-of-band that appears on the
next `ListAuthProviders` read — self-healing, and never a claim that a linked method is missing.

##### The `Invite` token model ([U8][G6])

`GetInviteLink†` is marked `NO_SIDE_EFFECTS`, so it **cannot mint a row** — a read that inserts is not a read.
The token is therefore a **stateless, HMAC-signed capability**, and this is what removes the one query that would
otherwise have to scan `invites` across users:

```
payload = base64url(inviterUserID) "." base64url(issuedAtUnix) "." base64url(nonce)
token   = payload "." base64url(HMAC-SHA256(key, payload))
```

- **Issuance** (`GetInviteLink†`): after checking that the caller has a live profile, pure derivation over the
  caller's scope, a fresh nonce, and `s.now()`. It never reads or writes `invites`.
- **Verification** (`account.VerifyInviteToken`, called by 61): recompute the MAC in constant time, then check
  `issuedAt + account.invite_link_ttl_days ≥ now`. **The inviter id comes out of the verified payload**, so there is no
  `SELECT … FROM invites WHERE token = $1` — the cross-user lookup that would have needed a `globalQueries` allowlist
  entry does not exist. That is the deciding argument for a signed token over a stored one.
- **Binding** (plan 61): inserts the row above with `created_at` = the payload's `issuedAt` (which is why `created_at`
  and `bound_at` genuinely differ) and the presented token in `token`. `UNIQUE (token)` is
  the **single-use guard** — a second presenter loses the race and is refused; `UNIQUE (invitee_user_id)` means an
  invitee can be bound at most once, ever, by anyone. Both are schema facts, not checks in code.
- **Consequence, accepted deliberately:** a link is one-per-friend. Sharing one copied link with three people binds only
  the first; the inviter taps for a new link per friend. This is the [G6] direction (each rewardable invite costs the
  inviter a deliberate act) and it is why [61.signup-and-invite-usecase](61.signup-and-invite-usecase.md)'s reward cap counts rows rather than links.
- **The signing key is a secret, not a value:** env `INVITE_TOKEN_SIGNING_KEY` (base64-std, ≥32 bytes), documented in
  `.env.example`, following the `LLM_KEY_ENCRYPTION_KEY`/`secretbox` precedent. It is injected as a consumer-owned port
  `account.InviteSigner` whose default is `UnavailableInviteSigner{}` — which **errors** rather than issuing an unsigned
  token (the shipped `twinkle.UnavailableInviteResolver` shape). An unsigned invite token is not representable.

##### The proto contract (`cosimosi.account.v1`, existing file)

Owner split within the `AccountService` inventory, pinned here so no sibling waits on it: **plan 60 owns `GetProfile†`,
`UpdateProfile`, `ListAuthProviders†`, `GetInviteLink†`**; plan 61 owns `SignUp`; plan 62 owns `Withdraw` and
`RestoreAccount`. The shipped color RPCs are untouched here (renaming a message is a `buf breaking use: FILE`
violation).

```proto
message GetProfileRequest {}                          // scope only — no user_id field, ever
message GetProfileResponse { Profile profile = 1; }   // ABSENT = not provisioned; no synthesized default
message Profile {
  string nickname = 1;
  string timezone = 2;                                // IANA name — THE day boundary [U7]
  string locale   = 3;
  string email    = 4;                                // read through Supabase; NOT a column
  string created_at = 5;                              // RFC3339
}
message UpdateProfileRequest {                        // the ENTIRE writable surface [I11]
  string nickname = 1;
  string timezone = 2;
  string locale   = 3;
}
message UpdateProfileResponse { Profile profile = 1; }
message ListAuthProvidersRequest {}
message ListAuthProvidersResponse { repeated LinkedAuthProvider providers = 1; }
message LinkedAuthProvider { AuthProviderKind kind = 1; string linked_at = 2; }
message GetInviteLinkRequest {}
message GetInviteLinkResponse { string token = 1; string expires_at = 2; }
```

`UpdateProfile` replaces all three fields at once (a partial-update mask is not needed for a three-field form and would
add a way to express "clear the timezone"). Client cache classification (§2.7): `GetProfile`, `ListAuthProviders` and
`GetInviteLink` each get **exactly one** `userScopedUnaryReadPolicy` entry in `accountRpcCachePolicies`
(`packages/client-cache/src/http-policy.ts`); `UpdateProfile` is a plain POST and needs none. `assertRpcCachePolicyCoverage`
hard-fails the build on a missing or duplicate entry, so this needs no runtime check.

Error reasons, added on both sides (`account/rpc/reasons.go` + `packages/errors/src/core.ts`, the shipped
`ACCOUNT_UNKNOWN_PALETTE` pattern): `ACCOUNT_NOT_PROVISIONED`, `ACCOUNT_NICKNAME_INVALID`, `ACCOUNT_TIMEZONE_INVALID`,
`ACCOUNT_LOCALE_INVALID`, `ACCOUNT_INVITE_LINK_UNAVAILABLE`. User-facing copy for each lands with 63/64 — this
unit adds no i18n key.

##### Golden-parity stance

**No pure function in this unit is mirrored TS↔Go, and one candidate is deliberately excluded.** This is a headless
unit, shared by construction ([00.overview](00.overview.md) §4). The one function a reader might expect to be mirrored is the zone→calendar-date
conversion, and it is not, for two reasons: (1) it is a _platform tz-database lookup_, not domain math — Go reads
embedded `time/tzdata` and TS reads `Intl.DateTimeFormat`, and a golden fixture would pin one tzdata release and break
on the next; (2) the asymmetry is already load-bearing — the client's local date is only a **default** in an editable
field ([W5]), while every _rule_ (the future-date rejection, the `SMALL` reset, the monotonic check) is decided
server-side, so the two sides do not need to agree bit-for-bit. What the two sides must agree on is the **name**, and
the drift guard for that is the locale/timezone-name contract, not a numeric fixture. The locale set does get a
drift guard, and it is a byte-identical fixture pair (the `palette-ids.json` pattern), not a golden-parity harness.

Consequence for plan 65: `SmallRemaining` gains the zone parameter as an **IANA name resolved by its caller**, and its
golden fixture expresses the zone as a name with cases chosen for tzdata-stable zones — plan 65 owns that fixture; this
unit only pins the representation.
