#### Purpose

v1 shipped Twinkle as a _recall_ currency: two tiers, two spend purposes (회고, 요지 열람), three earn paths (write,
invite, verified payment) — [44.earn-spend-usecase](44.earn-spend-usecase.md). v2 promotes it to the product's **only**
currency ([G2a]): the decoration panel pays for backgrounds, star shaders and palettes in the same unit ([P9]), and
achievements pay _into_ it ([A3]). Two things must happen in one place before either sibling can be built. First, the
spend surface must accept a purpose whose price is **not** a cost curve but a catalog total owned by another context.
Second, the earn surface must grow the two paths v1 never had — achievement reward ([A3]) and signup bonus ([U11]) —
while the one path v1 _did_ have and cannot keep is removed.

That removal is the second half of this unit's reason to exist. PRD §8.3 defers payment (스토어/PG) to v3 and [G3] names
the funding set that replaces it: 매일 지급 · 일기 작성 · 업적 · 친구 초대 · 가입 보너스. Today the payment path is a
guaranteed-fail affordance on both sides — `cmd/api/twinkle.go` binds `twinkle.UnavailablePaymentVerifier{}` in
production and the client's store purchase always throws — so shipping v2 with `Charge` reachable ships a broken button
and an error-recovery flow that points nowhere. v2 retires it, and this plan executes the server half exhaustively:
the RPC, the use-case, the port, the five errors, the four transport reasons and `twinkle.charge_pack` all go away,
while the `payment` `EntryReason` constant and migration `00010`'s uniqueness index stay so historical rows remain
readable and foldable.

Third, [G7] demands that 구매·수령·적립·소모 all be readable chronologically in `/me` ([U9]). The ledger already records
them; nothing exposes them. This unit adds the one read — `GetLedger`† — with a keyset cursor, and pins what a ledger
row is allowed to say on the wire. The daily `SMALL` refill deliberately has **no row**: it stays a derivation,
and the wire enum has no member for it, so no client can mistake the refill for a transaction.

#### Design

##### Placement (domain-first Go, ARCHITECTURE §2.3 — no new context)

Everything lands in the **shipped** `apps/api/internal/twinkle` package: `ledger.go` (the reason set — a domain type),
`service.go` (the use-cases), `ports.go` (consumer-owned ports), `pg/store.go` + `db/queries/twinkle/ledger.sql` (the
page read), `rpc/{server.go,reasons.go}` (thin handlers). No `app/` or `domain/` split is earned (§2.9 #2) and no new
context is created — a purchase debit is twinkle behavior, not store behavior. `twinkle` imports neither `memory`,
`store` nor `achievement`; every cross-context edge stays a composition-root adapter over a consumer-owned port, in
`cmd/api/twinkle.go` (memory) and — bound by their owning plans — `cmd/api/store.go` (72) and
`cmd/api/achievement.go` (75).

##### The `EntryReason` closed set (sole ownership)

`twinkle.EntryReason` is exactly the eleven values enumerated in _Scope / Non-goals_, in one const block in
`ledger.go`. Two properties make the set
enforceable rather than merely documented:

1. **Every writable reason has exactly one named use-case entry point, and the unwritable ones have none.** There is no
   exported `Earn(reason, amount)`; the surface is `EarnOnWrite`, `ClaimInvite`, `EarnSignupBonus`,
   `EarnAchievementReward`, `EarnAdminGrant`, `CheckAndSpend`. `daily_grant` and `payment` therefore have **no caller
   at all** — the guard is the absent method, not a validation branch.
2. **The set is asserted whole.** The shipped `TestEarnReasonsAreAClosedSetWithNoLoginBonus`
   (`internal/twinkle/service_test.go`) is extended to enumerate all eleven, assert each reason's earn/spend
   classification, assert no reason smells of login/attendance ([G3]) and assert `daily_grant`/`payment` are reachable
   from no entry point. A plan that adds a twelfth reason fails this test.

**No PG `CHECK` on the `reason` column and no PG enum.** The shipped DDL comment already declares `kind`/`reason` TEXT
closed sets "owned by the domain (like neuron_type / jobs.kind)". A closed-set CHECK on an append-only ledger costs a
migration per reason and risks failing against historical rows; the domain owns the set, the schema owns the
_arithmetic_ invariants. The one reason-shaped CHECK this unit does add is [P9]'s, because that one guards money.

Classification helpers live with the set: `EntryReason.IsSpend()` and `EntryReason.SmallEligible()` — the latter true
for `recall` and `gist_view` only (the recall family; a `DIARY_RECALL` action writes one `recall` row per member, so
it needs no reason of its own). `SmallEligible` is the single place the eligibility question is answered, and it feeds
`PlanSpend`'s purpose argument.

##### `Spend` grows a third purpose ([G4].3 [P9])

`SpendIntent` becomes an **opaque value with unexported fields**, built by three constructors, so a caller physically
cannot mix a purchase amount with a curve signal:

```go
// internal/twinkle/service.go — fields unexported; these three are the only way to build one.
func RecallSpendIntent(accessibilityCost float64, dedupKey string) SpendIntent   // reason = recall
func GistViewSpendIntent(semanticStage int, dedupKey string) SpendIntent         // reason = gist_view
func PurchaseSpendIntent(amount int, dedupKey string) SpendIntent                // reason = ornament_purchase
```

A recall intent has no field for an amount (so a caller can never set a recall's own price — [CC3] survives) and a
purchase intent has no field for a decay depth or a gist stage (so the curve can never price a purchase). `spendPrice`
gains one arm: `ornament_purchase` → the intent's amount, refused when non-positive (`ErrPurchaseAmountInvalid`). The
ornament price table stays `store` content; twinkle is told the total and never learns what was bought.

`CheckAndSpend(ctx, scope, ledger LedgerStore, intent SpendIntent)` keeps its shape — the `LedgerStore` argument is
still the caller's transaction-bound store, so [72]'s `Decorate` gets the same "one transaction or nothing" guarantee
recall has: `cmd/api/store.go` type-asserts `interface{ DB() dbgen.DBTX }` and binds `twinklepg.NewStore` onto the same
pgx transaction. The tier draw comes from 65's `PlanSpend(smallRemaining, general, cost, purpose)` with
`purpose` derived from `intent.reason.SmallEligible()` — a purchase yields `FromSmall: 0`, and migration `00019`
refuses the row if it ever did not.

**Insufficiency becomes typed.** `CheckAndSpend` returns `*InsufficientTwinkle{Cost, Eligible, Shortfall}` — an error
wrapping the canonical `ErrInsufficientTwinkle`, so every existing `errors.Is` site keeps working — where `Eligible` is
the balance actually usable for this purpose (`general` for a purchase, `small + general` for the recall family) and
`Shortfall = Cost - Eligible`. This replaces `QuoteSpend`'s shipped `shortfall = cost - balance.Basic -
balance.Additional`, which is wrong for any non-recall purpose. The shortfall reaches the client through
`apperr.Domain(code, reason, err, metadata)`'s shipped `map[string]string` detail channel; [72] maps it onto
`STORE_INSUFFICIENT_TWINKLE` with the item name it alone knows, and [67] re-targets `TWINKLE_INSUFFICIENT`'s recovery.

**`QuoteSpend` gains no purchase kind.** `QuoteKind` stays `recall|gist_view|diary_recall` and `QuoteSpendRequest`
gains no ornament field. A purchase is previewed client-side from [71]'s catalog mirror plus `GetBalance`; routing it
through a server quote would publish the price table on a second contract and hand `/demo` a price string ([Z8]).

##### Earn: the five paths of [G3], and the one that leaves

| Reason              | Entry point                | Amount                                      | Dedup key                  | Transaction            |
| ------------------- | -------------------------- | ------------------------------------------- | -------------------------- | ---------------------- |
| `daily_grant`       | **none**                   | `twinkle.small_daily_amount` (65)           | —                          | derived, never written |
| `write_diary`       | `EarnOnWrite` (shipped)    | `twinkle.earn_write`                        | `write_diary:<diaryID>`    | memory's launch tx     |
| `invite`            | `ClaimInvite`, inviter leg | `twinkle.earn_invite_inviter`               | `invite:<signupID>`        | own ledger tx          |
| `invite_signup`     | `ClaimInvite`, invitee leg | `twinkle.earn_invite_invitee`               | `invite_signup:<signupID>` | own ledger tx          |
| `signup_bonus`      | `EarnSignupBonus`          | `twinkle.earn_signup_bonus`                 | `signup_bonus:<userID>`    | own ledger tx          |
| `achievement_claim` | `EarnAchievementReward`    | caller's validated amount (74)              | `achievement:<claimID>`    | own ledger tx          |
| `admin_grant`       | `EarnAdminGrant` (shipped) | operator amount ≤ `twinkle.admin_grant_max` | grant id                   | own ledger tx          |

Every earn credits **`GENERAL`** ([A3][G2] — `SMALL` is the daily reset and is never earned). Every earn is dedup-keyed
and append-first, so a replay skips the balance delta exactly as the shipped `earn` helper already does. `ClaimInvite`
keeps its shipped name, its `InviteResolver` seam and its **own** ledger transaction: running outside the
causing write is precisely what makes [61]'s deferred settlement an idempotent pairing that heals on replay instead of
a cross-context transaction. `EarnAchievementReward` mirrors it for the same reason — `claimed_at` set with the
reward uncredited is recoverable, whereas a shared transaction would make `achievement` the owner of twinkle's tables.

`EarnSignupBonus` and `EarnAchievementReward` are **credit primitives**: they validate scope, amount and key and decide
no eligibility. Whether a signup is valid ([G6] — four-part conjunction, per-inviter cap) is [61]'s; whether an
achievement is achieved is [75]'s.

##### The `SMALL` day boundary is the user's zone ([U7])

65 makes the pure derivation take a zone; this unit supplies it. `twinkle.UserZoneReader` is a new consumer-owned port
in `internal/twinkle/ports.go`:

```go
type UserZoneReader interface {
    ZoneFor(ctx context.Context, scope platform.UserScope) (string, error) // IANA name, e.g. "Asia/Seoul"
}
```

**As built this port is [65]'s, not this unit's** — 65's scope and its acceptance criterion A5 claim the port, the
`ErrZoneReaderRequired` guard and the `cmd/api/twinkle.go` adapter, and 65 lands first, so here it is a verification.
It is bound in `cmd/api/twinkle.go` to an adapter over `account`'s published profile read (60) — an IANA **string**, never a
`*User`, so no account type crosses the boundary. An unknown, empty or unparseable zone resolves to `UTC`, and that
fallback is safe in both directions because the stored anchor is the user's local calendar date and
`UpdateTwinkleBalanceDelta` advances it with `GREATEST` only: a wrong zone can delay a refill by at most a day, never
mint a second one ([I10]). The zone is read once per balance derivation; no cache, and no clock port beyond the shipped
`now` seam.

elapsed real time.

##### `GetLedger`† — the one read [G7] needs

```proto
enum LedgerEntryKind   { LEDGER_ENTRY_KIND_UNSPECIFIED = 0; LEDGER_ENTRY_KIND_EARN = 1; LEDGER_ENTRY_KIND_SPEND = 2; }
enum LedgerEntryReason {
  LEDGER_ENTRY_REASON_UNSPECIFIED = 0; LEDGER_ENTRY_REASON_WRITE_DIARY = 1; LEDGER_ENTRY_REASON_INVITE = 2;
  LEDGER_ENTRY_REASON_INVITE_SIGNUP = 3; LEDGER_ENTRY_REASON_SIGNUP_BONUS = 4;
  LEDGER_ENTRY_REASON_ACHIEVEMENT_CLAIM = 5; LEDGER_ENTRY_REASON_ADMIN_GRANT = 6;
  LEDGER_ENTRY_REASON_RECALL = 7; LEDGER_ENTRY_REASON_GIST_VIEW = 8;
  LEDGER_ENTRY_REASON_ORNAMENT_PURCHASE = 9; LEDGER_ENTRY_REASON_PAYMENT = 10; // historical rows only
}
message GetLedgerRequest  { int32 page_size = 1; string page_token = 2; }   // no user_id — scope is the JWT
message GetLedgerResponse { repeated LedgerEntry entries = 1; string next_page_token = 2; }
message LedgerEntry {
  string id = 1; LedgerEntryKind kind = 2; LedgerEntryReason reason = 3;
  int64 amount = 4; int64 from_small = 5; int64 from_general = 6;
  string occurred_on = 7;  // YYYY-MM-DD, already resolved in User.Timezone
  string occurred_at = 8;  // RFC3339
}
```

**As built, the row carries TWO timestamps, not one `created_at`.** [67]'s design needs a day header, and [U7] makes the
server the day-boundary authority: a device-local grouping would draw headers that disagree with the `SMALL` reset
boundary the same user just watched refill. So `occurred_on` is the entry's date already resolved in the user's zone —
from the same `ResetWindowOf` the refill uses — and `occurred_at` carries the within-day ordering and the time on the
row. 67 explicitly adds no proto field, so a `created_at`-only contract would have forced it to reopen this wire.

Pinned decisions: **no `DAILY_GRANT` member** (the refill is not a row; [67] renders it as a labeled synthetic
day marker from the same derivation); **no `dedup_key` field** (it embeds diary ids, signup ids and claim ids — a leak
with no product use); **no per-reason payload** (an `ornament_id` would put store vocabulary in the twinkle contract;
the reason _is_ the caption and [67] owns the copy); **`from_small`/`from_general` follow 65's domain names** while the
columns stay `from_basic`/`from_additional` (`pg/store.go` is where the two spellings meet); timestamps are
RFC3339 strings, matching the shipped `admin.v1` convention rather than importing `google.protobuf.Timestamp`.

Paging copies the shipped keyset shape, not admin's `LIMIT/OFFSET`: one static sqlc query
`ListTwinkleLedgerPage` in `db/queries/twinkle/ledger.sql` — `WHERE user_id = $1 AND (sqlc.narg(cursor_created_at) IS
NULL OR (created_at, id) < (cursor_created_at, cursor_id)) ORDER BY created_at DESC, id DESC LIMIT $n` — with the
cursor an opaque `base64url("<created_at RFC3339Nano>|<id>")` mirroring `encodeDiaryCursor`
(`internal/memory/diaries.go`). `page_size` clamps to `twinkle.ledger_page_size` as both default and hard cap. Ties on
`created_at` break on the backend-minted id — deterministic, if arbitrary. **As built:** the use-case asks the store for
one row beyond the page, which is how "the history continues" is told apart from "the page ended exactly here" without a
second count query; a fabricated token is refused (`ErrLedgerCursorInvalid`) rather than silently restarting the
history. `GetLedger` is `NO_SIDE_EFFECTS` and is
registered once in `twinkleRpcCachePolicies` (`packages/client-cache/src/http-policy.ts`) with
`userScopedUnaryReadPolicy`; the production transport refuses to start otherwise (§2.7).
