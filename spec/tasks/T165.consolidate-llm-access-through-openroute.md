### 14. Change: Consolidate LLM access through OpenRouter

> A **change proposal** (a WHAT delta) that modifies the already-shipped behavior of [plan/28.ai-provider-abstraction](../plan/28.ai-provider-abstraction.md).
> Filled by /cosimosi:create-change through a user interview — a reviewable doc, not a one-line prompt.
> The STEPS live in the job that /cosimosi:create-change-job creates. Write it in English.

#### As-is

`internal/ai` already keeps product-shaped prompts, JSON Schemas, and memory DTO mapping behind the provider-neutral
`LLMClient` and `EmbeddingClient` capability interfaces. The abstraction above those clients is sound; the concrete LLM
transport below it is where the shipped system is wider than it needs to be.

- The LLM registry names Anthropic, OpenAI, DeepSeek, GLM, Gemini, and Kimi slots. Anthropic and DeepSeek have concrete
  adapters today. Each implemented adapter separately owns authentication, request/response shapes, structured-output
  behavior, model listing, endpoint and error mapping, with its own tests and (for Anthropic) SDK dependency.
- The embedding capability is selected independently and is concretely implemented by the direct Voyage AI adapter.
  Its deliberately curated `voyage-4`-generation catalog guarantees `ai.embedding_dim` and one compatible vector
  space for the existing HNSW/dedup data.
- Plan 58's admin seam stores API keys per provider and a `(provider, model)` selection per capability. LLM operators
  therefore manage vendor-specific credentials and choose a provider before choosing a model. The model dropdown is
  advisory: it comes from the selected vendor's live catalog, retains a manual-ID escape hatch, and `SetAIConfig`
  accepts a model that was not listed.
- Effective config remains DB override -> env -> keyless mock. A provider/model/key change rebuilds the concrete client
  without changing the memory ports, metering wrapper, retry behavior, or worker.

This buys direct-vendor independence, but adding or switching an LLM still carries adapter code and credential
operations even though OpenRouter exposes the required models through one OpenAI-compatible API. The sibling
PostPilot project demonstrates that narrower transport shape with one OpenRouter adapter and model IDs of the form
`vendor/model`.

#### To-be

**OpenRouter becomes the only production LLM provider, while Voyage AI remains the independent direct embedding
provider.** `LLMClient` and `EmbeddingClient` remain separate capability contracts; consolidation happens strictly
below `LLMClient`, not by merging the capabilities.

##### One LLM gateway, one reviewed model catalog

- The implemented LLM registry contains one production provider: `openrouter`. Anthropic and DeepSeek direct adapters
  and the speculative direct-vendor LLM slots are retired after cutover. A future escape from OpenRouter still fits
  behind the unchanged `LLMClient`; it is a new earned change, not a dormant slot maintained now.
- One OpenRouter credential serves every curated LLM model. The existing LLM key env seam is explicitly an OpenRouter
  key after the change, and `COSIMOSI_LLM_PROVIDER` is no longer an operator choice. DB override -> env -> keyless mock,
  encrypted-at-rest key handling, write-only RPC behavior, and rebuild-on-change remain intact.
- Real calls always resolve to an explicit OpenRouter model ID (`vendor/model`). The initial candidates are the
  OpenRouter equivalents of the shipped adapters' models (currently Claude Opus 4.8 and DeepSeek V4 Flash), but a
  candidate enters the production catalog only after passing the evaluation gate below.
- The OpenRouter adapter owns a **curated allowlist** of reviewed models. `ListProviderModels(openrouter, llm)`
  intersects that allowlist with OpenRouter's current model metadata and returns only entries still advertising the
  required structured-output parameter. Neither the FE nor i18n contains a duplicate catalog.
- The LLM admin row shows OpenRouter as fixed provider identity and offers only that returned model list. There is no
  manual model-ID escape hatch for LLM, and the server rejects an empty or non-curated model. A listing outage leaves
  the current selection visible but cannot be bypassed to save an unreviewed model. Embedding administration remains
  the existing Voyage flow.

##### Routing and contract preservation

- Every completion uses OpenRouter's OpenAI-compatible chat-completions shape with the requested JSON Schema. Routing
  requires support for every supplied parameter and denies data-collecting endpoints; request-level ZDR is mandatory.
  Deployment setup also keeps OpenRouter prompt logging opt-in disabled.
- Endpoint fallback is allowed only among eligible endpoints serving the **selected model**. There is no automatic
  fallback to another model, no auto-router model, and no silent substitution: model choice continues to determine
  quality, behavior, and price.
- Native structured output is defense in depth, not the trust boundary. The adapter locally validates every completed
  response against the whole requested JSON Schema before returning it, preserves finish/completion checks, and maps
  OpenRouter and upstream failures into the existing typed error set. Caller cancellation/deadline remains the
  unchanged context error.

##### Evidence-gated cutover

Before the direct LLM adapters are removed, every model admitted to the curated catalog is exercised against a fixed,
reviewable Korean diary corpus covering split, split revision, semantic-stage generation, prediction-error comparison,
and seal suggestion. The evaluation records:

- full JSON-Schema and domain-validator pass/fail results;
- reviewer-scored task fidelity, including source-faithfulness failures;
- token usage and provider-reported cost per scenario, with the OpenRouter platform/credit fee reported separately;
- end-to-end p50 and p95 latency for the direct baseline and OpenRouter candidate.

The job may cut over only after the report is reviewed and the OpenRouter key/model has passed a real smoke call. There
is no claim that a gateway is intrinsically faster or cheaper: at proposal time OpenRouter publishes pass-through
inference pricing plus a credit-purchase fee, and provider fallback can improve availability while making a request
that actually falls back slower. Current official pricing and routing behavior must be rechecked when the job runs.
An existing direct-provider DB selection is never silently reinterpreted with its old key and never silently degraded
to mock; rollout preflight reports the required OpenRouter replacement explicitly.

#### Scope / Non-goals (regression boundary)

**Changes**

- The concrete LLM adapter/registration/dependency set and composition-root wiring.
- LLM runtime configuration and admin presentation: fixed `openrouter` provider, one OpenRouter key, curated model
  selection, and server-side allowlist enforcement.
- OpenRouter-specific structured-output request mapping, ZDR/parameter-capability routing, same-model endpoint fallback,
  response validation, model-catalog reconciliation, and typed error normalization.
- Contract and evaluation fixtures sufficient to prove every curated model before it becomes selectable.
- The plan-58/admin and operations documentation that currently describes arbitrary provider selection and advisory
  manual model entry.

**Must not change**

- `LLMClient`, the memory-owned `Extractor`/`Semanticizer`/`PredictionError`/`SealSuggester` ports, their prompts and
  schemas, DTO mapping, repair loops, job semantics, cache decisions, or the keyless deterministic mock.
- Metering caps and error meanings. OpenRouter credit exhaustion is a terminal provider-operations failure; it must
  not masquerade as the locally raised cost cap or the per-user daily call cap.
- The direct Voyage embedding adapter, provider key, model administration, `voyage-4`-generation allowlist,
  `input_type=document`, `ai.embedding_dim`, stored vectors, HNSW index, or dedup threshold. No embedding request goes
  through OpenRouter and no re-embedding is introduced.
- [I1]-[I13]: the provider remains a pure request/response dependency and receives no authority to write, mutate, or
  delete product state.

**Non-goals**

- No cross-model fallback, auto-router, price auction, A/B routing, per-user model selection, or model marketplace.
- No OpenRouter BYOK fan-out to direct vendor keys; that would reintroduce the credentials this change removes.
- No new spend dashboard, budget model, streaming surface, prompt fork, FE surface outside the existing web-only admin
  console, database schema, or automatic deletion of dormant encrypted legacy provider-key rows. Legacy secrets are an
  explicit operator cleanup after the rollback window, not an irreversible migration side effect.
- No automatic admission of a model merely because OpenRouter lists it or labels it structured-output capable.

#### Acceptance Criteria

1. A production LLM call can be wired only through the `openrouter` adapter; the Anthropic and DeepSeek direct LLM
   adapters, their composition-root imports, vendor-specific SDK dependency, and speculative direct-vendor LLM slots
   are absent. `LLMClient` and every memory-owned AI port remain unchanged.
2. LLM effective configuration remains DB override -> env -> keyless mock, but its real provider identity is fixed to
   OpenRouter: one encrypted/write-only OpenRouter key and one explicit curated `vendor/model` selection rebuild the
   client without redeploy. A legacy direct-provider selection fails preflight with an actionable migration error and
   is never silently treated as OpenRouter or mock.
3. `ListProviderModels(openrouter, llm)` returns the intersection of the adapter-owned reviewed allowlist and models
   currently advertising the required OpenRouter structured-output capability. The admin UI exposes only those models,
   has no LLM manual-entry escape hatch, and `SetAIConfig` rejects empty/unlisted LLM model IDs server-side.
4. Every OpenRouter completion enforces request-level ZDR/data-collection denial and required-parameter routing. It may
   fall back only between eligible endpoints for the selected model; tests prove that no request supplies a second
   model or accepts a response silently substituted from another model.
5. Every successful completion has a terminal completion state and passes local full JSON-Schema validation before it
   crosses `LLMClient`. Malformed/truncated output, 401/403, insufficient OpenRouter credits, 429/overload/upstream 5xx,
   and transport failures map into the existing error/cancellation contract with causes sanitized and preserved as
   appropriate; no OpenRouter response type escapes the adapter.
6. A checked-in evaluation corpus covers split, revision, semanticization, prediction error, and seal suggestion. Each
   curated model has a reviewed result showing schema/domain-validator outcomes, source fidelity, provider-reported
   token cost, the current OpenRouter platform fee separately, and direct-vs-gateway p50/p95 latency. The production
   cutover is recorded only after that evidence and a real OpenRouter smoke call are approved.
7. Metering, cache admission, repair loops, daily/per-call caps, job retry/backoff, runtime rebuild behavior, and the
   keyless mock pass their existing regression suites unchanged above the new adapter.
8. The Voyage embedding path is byte-for-contract unchanged: it remains a separately keyed direct provider, offers only
   the compatible `voyage-4` family, sends document input with `ai.embedding_dim`, and neither rewrites nor mixes any
   stored embedding.
9. The admin and AI-worker SSOT describe the final operational trade-off honestly: one LLM gateway/key and a curated
   catalog reduce adapter/credential work, while OpenRouter becomes the LLM availability/billing dependency and may add
   gateway or fallback latency. No cost or latency improvement is asserted without the evaluation evidence.
10. No `spec/values.yaml` key is added or changed. Provider identity, endpoint, credential, model IDs, catalog rows,
    routing privacy flags, and external prices remain adapter/runtime/operations facts rather than product tuning.

### OpenRouter LLM cutover evaluation

> Evidence record for [change 14](../changes/14.consolidate-llm-access-through-openroute.md). The production registry
> may not admit an OpenRouter model and the direct LLM adapters may not be removed until every gate in §5 is complete

#### 1. Official contract review

- Retrieval date: **2026-08-30 (Asia/Seoul)**.
- Stack: Go 1.26, `net/http`, non-streaming Chat Completions. The existing
  `github.com/santhosh-tekuri/jsonschema/v6` validator remains the local trust boundary. No OpenRouter or OpenAI SDK is
  required by the current HTTP contract, so this cutover adds no SDK dependency.
- Chat endpoint: `POST https://openrouter.ai/api/v1/chat/completions`, Bearer authentication, JSON request/response.
- Model catalog: `GET https://openrouter.ai/api/v1/models`. Each row exposes its request `id`, permanent
  `canonical_slug`, and `supported_parameters`. The reviewed intersection requires both `structured_outputs` and
  `response_format`; `require_parameters` independently filters the eligible provider endpoints for the parameters
  on each completion request.
- Structured output: `response_format.type = "json_schema"`, with `json_schema.strict = true` and the caller's whole
  schema in `json_schema.schema`. Native enforcement is defense in depth; the adapter must still validate the returned
  JSON locally against the whole schema.
- Completion state: the non-streaming success shape carries `model` and `choices[].finish_reason`. The adapter accepts
  exactly one choice with `finish_reason = "stop"`; missing/multiple choices, `length`, `content_filter`, `tool_calls`,
  `error`, empty/unknown states, or an empty body are not terminal successes.
- Routing: one explicit reviewed `vendor/model` is sent in `model`. The request contains no `models`, router/auto model,
  route, preset, plugin, or vendor BYOK credential. `provider.allow_fallbacks = true` permits OpenRouter to retry
  eligible endpoints for that same model; cross-model fallback is opt-in through the absent `models` array.
- Privacy and parameter routing, on every request:
  `provider.zdr = true`, `provider.data_collection = "deny"`, and `provider.require_parameters = true`.
  OpenRouter states that it does not retain prompts unless an account explicitly opts in to prompt logging.
- Prompt-logging account check: **PENDING — an operator with access to the production OpenRouter workspace must
  confirm prompt logging opt-in is disabled before the smoke call or cutover approval.**
- Error contract: the standard envelope is `{"error":{"code":number,"message":string,"metadata":object?}}`.
  401/403 and 402 (`payment_required`, insufficient credits) require operator action; 429, overload/unavailable,
  request timeout, and upstream 5xx/502/503 are retryable. `Retry-After` may be supplied on 429/503 and is accepted only
  as a safe non-negative delta-seconds value. Causes crossing the adapter contain status/category only, never vendor
  messages, response bodies, prompts, or keys.
- Usage/cost: non-streaming responses include usage accounting. Inference prices are provider pass-through prices;
  the current pay-as-you-go platform fee is a **5.5% credit-purchase fee** (the FAQ currently also states a USD 0.80
  minimum), not an inference-price markup. Evaluation therefore records provider-reported inference cost and the
  applicable credit-purchase fee as separate lines.
- Latency: provider fallback can add latency when an earlier endpoint fails. No speed, cost, or availability
  improvement is assumed without the measurements below.

#### 2. Corpus and method

- Checked-in corpus: `apps/api/internal/ai/testdata/llm-evaluation-corpus.json`.
- Opt-in harness: `apps/api/internal/ai/live_evaluation_test.go`.
- The corpus is synthetic Korean diary content and contains no real diary, account identity, or secret.
- The harness calls the shipped `Split`, `ReviseSplit`, `GenerateSemanticStages`, `Differs`, and `Suggest` ports, so it
  reuses the production prompts, JSON Schemas, parsers, local schema validation, source-fidelity check, and domain
  validators. It is skipped unless `COSIMOSI_LIVE_LLM_EVAL=1` and never runs in the hermetic suite.
- Required run inputs: provider, model, API key, warm-up count, and measured sample count. Keys are supplied through
  environment variables and are never printed or written.
- Warm-up samples are excluded. Each measured call uses a distinct synthetic user scope to bypass the identical-input
  cache while retaining the production metering/request path.
- The harness records per-scenario schema/domain outcome, source-fidelity outcome where applicable, elapsed time,
  provider-reported input/output token counts, and provider-reported cost when the response supplies it. A human
  reviewer scores task fidelity and source fidelity from the product-shaped result, then copies only aggregate
  evidence into this file. Raw provider payloads and prompts are not committed.
- Latency is wall-clock end to end around the product port. p50 uses the nearest-rank 50th percentile and p95 uses the
  nearest-rank 95th percentile over measured samples after warm-up.
