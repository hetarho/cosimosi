# 08. Change: Retire the named palette registry

> A **change proposal** (a WHAT delta) that modifies the already-shipped behavior of [plan/51.palette-customization](../../plan/51.palette-customization.md).
> Filled by /cosimosi:create-change through a user interview — a reviewable doc, not a one-line prompt.
> The STEPS live in the job that /cosimosi:create-change-job creates. Write it in English.

## As-is

Two palette models are shipped, and only one of them colors anything.

**The named registry (plan 51, job 62).** `packages/emotion/src/registry.ts` publishes an id → thirteen-color
table map: `cosimosi-default` and `muted-dusk`. The account stores the chosen id as one string —
`palette_preferences (user_id, palette_id, updated_at)` from migration `00009`, read and written through
`AccountService.GetPalettePreference` / `SetPalettePreference`, validated against a Go allow-list
(`account.registryPaletteIDs`) that a fixture (`testdata/palette-ids.json`) pins to the client registry.
On the client the id drives `applyPalette` → `setMoodPalette`, a Zustand mirror
(`usePalettePreferenceStore`), a per-scope write session (`change-palette.ts`), and a display-name lookup.

**The per-mood colors (change 07, job 108).** `mood_colors (user_id, mood, color)` stores at most one row per
user and mood; absence means the authored default. `GetMoodColors` / `SetMoodColor` read and write it, and
`applyMoodColors(rows, fallback)` resolves the rows over a fallback table into the one `setMoodPalette` seam.

The second model landed on top of the first without retiring it, so today:

- **The stored id changes no color.** Both app-layer bootstraps
  (`apps/{web,mobile}/src/app/providers/palette-bootstrap.tsx`) call
  `applyMoodColors(rows, defaultMoodPalette)` with the fallback hardcoded — never `paletteById(resolvedId)`.
  `resolvedId` survives only as the argument to `initializePaletteSession` / `paletteSessionMatches`, i.e. as a
  session-scope bookkeeping value. Selecting `muted-dusk` would repaint nothing.
- **Nothing can select an id.** `PaletteSection` was rewritten into the per-mood editor, so the id picker no
  longer exists on any surface. `palette_preferences` is empty in practice and `muted-dusk` is unreachable as a
  choice.
- **The id machinery has no consumer.** `applyPalette`, `applyConfirmedPalette`, `changePalette`,
  `useChangePalette`, `PaletteSessionChangedError`, `readPalettePreference`, `paletteDisplayName` and
  `usePalettePreferenceStore` are re-exported by the `features/change-palette` barrels on both apps and imported
  by no caller but their own tests.
- **The registry survives for one unrelated reason.** `completeMoodColorRecommendations` reads
  `PALETTES['muted-dusk'].colors[mood]` as the second of three offline recommendation colors when the anonymous
  bucket statistic is short — a color source, not a selectable set.
- **Two live consumers do depend on the palette module, but not on ids.** `usePaletteVersion` (both
  `UniverseCanvasWidget`s) remounts instanced buffers on a palette change, and the `palette` leg of
  `packages/auth`'s user-state reset registry clears the previous account's colors on a scope transition — today
  by way of `resetPaletteSession` + the store's `reset()`.

The registry was never asked for. PRD [P1] requires that the user can change the **mood↔color mapping** and
ships "a good default plus the ability to change it"; a catalog of named alternative tables is an
implementation-level invention of plan 51 that change 07 then superseded with a strictly more expressive
per-mood editor.

## To-be

**One palette model: the authored default table, overridden per mood by what the user chose.** The named
registry, the stored palette id, and every surface that carried it are gone.

- **The only stored color preference is `mood_colors`.** A mood the user chose has a row; a mood they never
  chose has none and renders the authored default color. There is no second stored preference of any kind.
- **`palette_preferences` no longer exists** — the table, its sqlc queries, and its leg of the withdrawal purge
  are removed (the down migration recreates the table, empty).
- **`AccountService` carries no palette-id RPC.** `GetPalettePreference` and `SetPalettePreference`, their
  request/response messages, the `account.DefaultPaletteID` contract constant, the `registryPaletteIDs`
  allow-list, `RegistryPaletteIDs()`, `ErrUnknownPaletteID` and the `palette-ids.json` fixture guard are all
  removed. `GetMoodColors` / `SetMoodColor` / `GetMoodColorStats` are untouched.
- **`packages/emotion` publishes no id vocabulary.** `registry.ts` is deleted along with `PALETTES`,
  `DEFAULT_PALETTE_ID`, `resolvePaletteById`, `paletteById`, `listPalettes`, `paletteIds` and
  `ResolvedMoodPalette`; so are `apply-palette.ts`, `change-palette.ts`, `palette-preference-store.ts`,
  `read-palette-preference.ts` and `palette-display-name.ts`. `defaultMoodPalette`, `setMoodPalette`,
  `resetMoodPalette`, `moodColor`, `paletteVersion`, `subscribeMoodPalette`, `usePaletteVersion`,
  `resolveMoodColors` and the mood-color editor remain — the seam and the per-mood layer are the whole model.
- **`muted-dusk`'s thirteen colors survive only as what they are actually used for.** They become an authored
  table of alternative recommendation colors consumed by `completeMoodColorRecommendations`, carrying no id and
  registered nowhere. Recommendation behavior on screen is unchanged.
- **The scope-transition reset keeps working without an id.** The `palette` leg of the user-state reset registry
  clears the previous account's colors through `resetMoodPalette()`; the bootstraps gate on the authenticated
  user and the resolved colors, which they already compare, so no scope-key bookkeeping is needed to know a
  palette is applied.
- **The bootstraps read one query.** `GetMoodColors` alone decides when palette-dependent children are
  released; the `GetPalettePreference` query, its query-key/options factories and the `setPalettePreference`
  client helper are removed from `packages/api-client`.
- **`features/change-palette` is renamed to what it now contains.** The slice becomes
  `features/change-mood-colors` on web and mobile, exporting the per-mood editor (renamed `MoodColorSection`)
  and the per-mood hooks — no `palette-id` re-exports. `/me` mounts it exactly where `PaletteSection` was.

## Scope / Non-goals (regression boundary)

**In scope** — deleting the id model end to end (schema · sqlc · Go service/port/adapter/rpc/errors · proto +
regenerated clients · `packages/emotion` id modules · `packages/api-client` helpers · both bootstraps · the
`features/change-palette` slice on both apps · the user-state reset leg · the retired i18n keys · the affected
`spec/tech` and `spec/policy` text), and moving `muted-dusk`'s colors to the recommendation source that already
uses them.

**Must not change:**

- **The per-mood model shipped by change 07** — storage shape, the `SetMoodColor` lightness snap onto the
  emotion steps, the anonymous hue-bucket statistic and its sample floor, the warn-only near-duplicate notice,
  the first-sign-in thirteen-star screen and its "proceed with recommendations" exit, and the `/me` editor's
  behavior. Only the slice's name and the editor component's name move.
- **The one render seam** — all live color still passes through `setMoodPalette` / `moodColor`
  ([P2], plan 17 [M6]); rendering stays palette-agnostic and no rendering package is edited.
- **The meaning layer** ([I3][I11]) — no star's position, emotion, strength, brightness or seed is read or
  written. Color remains downstream and never writes back.
- **The axis-consistency guardrail** ([P3]) stays warn-only, and `checkPaletteAxisConsistency` keeps its
  signature (it takes a table, not an id).
- **Withdrawal and restore** ([U10][X2]) — removing the `palette_preferences` purge leg must not change what
  else the sweep deletes, and `mood_colors` keeps being purged with the other account dependents.
- **Everything else on `AccountService`** — profile, auth providers, invites, withdrawal, restore, and the
  three mood-color RPCs keep their contracts, so no other client changes.
- **The universe canvas remount path** — `usePaletteVersion` and its `UniverseCanvasWidget` usage are untouched
  on both apps.
- **Demo isolation is not built here.** Plan 79's import-ban list names `changePalette`, `useChangePalette` and
  `readPalettePreference`; those names simply cease to exist, which satisfies the ban rather than replacing it.

**Non-goals:**

- **No new palette feature.** No preset picker, no free color-wheel editor, no import/export of color sets.
  The user picks per mood, exactly as change 07 ships it.
- **No decision about `OrnamentKind.PALETTE`.** [P10] integrates the [P1] color change into the decoration
  panel for free, and plans 71–74 currently describe that as selecting a registry id. Re-deriving what a
  `PALETTE` ornament means against the per-mood model is left to plan-71/72/73/74 authoring — this change only
  removes the shipped code so that authoring reads the as-built truth. It records the plans to revisit; it does
  not edit their design.
- **No PRD amendment.** [P1]–[P3] and [P10] are satisfied by the per-mood model; only plan 51's implementation
  choice is retired.

## Acceptance Criteria

1. A user's only stored color preference is `mood_colors`; `palette_preferences` does not exist in the schema,
   and a fresh `pnpm db:migrate` produces no such table.
2. `AccountService` exposes no palette-id RPC — `GetPalettePreference` and `SetPalettePreference`, their
   messages, and the generated Go/TS clients for them are gone; the three mood-color RPCs behave exactly as
   before.
3. `packages/emotion` exports no palette id, no palette registry, and no id-keyed lookup; a repository-wide
   search for `DEFAULT_PALETTE_ID`, `PALETTES`, `paletteById`, `paletteIds`, `resolvePaletteById`,
   `applyPalette`, `changePalette`, `readPalettePreference`, `paletteDisplayName` and
   `usePalettePreferenceStore` returns no hit in shipped code.
4. Signing in resolves the palette from `GetMoodColors` alone: the bootstrap issues no palette-preference
   request, still holds palette-dependent children until the colors are applied, and still falls back to the
   authored default when the read fails.
5. A mood with no stored row renders the authored default color, and a mood with a row renders that row's
   color — on web and mobile, unchanged from change 07.
6. Each mood still offers three recommendations with the same colors and the same ratio-or-silence rule as
   before this change; the alternative colors come from an authored table that no longer carries an id.
7. Signing out and into another account leaves no color from the previous account applied, with the reset
   driven by `resetMoodPalette()` rather than a palette-id session.
8. The per-mood editor is reachable from `/me` on web and mobile, from a slice named for what it does
   (`features/change-mood-colors`), and editing still applies live through the unchanged `setMoodPalette` seam
   with no `GetUniverse` refetch.
9. Withdrawal still purges `mood_colors` with the other account dependents, and the sweep's other deletions are
   unchanged.
10. No regression in the constitution: rendering remains palette-agnostic, the meaning layer and the brightness
    channel are untouched, the axis check remains warn-only, and the first-sign-in color screen and plan 80's
    take-once tour trigger keep their shape.
11. No orphan text: `spec/tech/emotion-model.md`, `spec/tech/account.md`, `spec/policy/ux/emotion-palette.md`
    and `spec/policy/ux/my-page.md` describe the per-mood-only model, the retired i18n keys
    (`settings_palette_selected`, `palette_name_cosimosi_default`, `palette_name_muted_dusk`) are removed from
    both locales, and plan 51 is updated to the as-built shape.
12. The gates are green: `pnpm gen` / `pnpm check:gen` clean after the proto change, Go build · vet · test pass,
    web build · lint pass, and the mobile source gate (typecheck · lint) passes.
