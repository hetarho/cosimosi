# 71. ornament catalog model

> Ornament catalog model — Epic N's root: a NEW `internal/store` context owning `Ornament`, `OrnamentKind`
> (`BACKGROUND`/`STAR_SHADER`/`PALETTE`), `OrnamentOwnership` and `OrnamentSelection` (one row per kind), the in-code
> catalog whose rows name a **price tier** and never a number, the two tables, and the `store.v1` read contract. The
> invariant that shapes everything: an ornament sells a **render-parameter id and nothing else** — no row, struct or
> proto message has a field for a color, size, brightness or seed, so [V10]/[I11] hold structurally. It leaves
> `Decorate` (the write) and every pixel of UI to siblings. Scope: FS | Status: planning
>
> Layer D. Home: `apps/api/internal/store/{doc.go,types.go,catalog.go,service.go,ports.go,errors.go}` + `store/pg` +
> `store/rpc`, `proto/cosimosi/store/v1/store.proto`, migration `00020_store_ornaments.sql`, plus the two renderer-side
> id registries the catalog addresses (`packages/3d-renderer/src/assets/{backgrounds,bodies}`). It fills the
> "no user preference for the skin" seam [14.rendering-foundation](14.rendering-foundation.md) left open and leaves the
> palette-storage cutover and the purchase transaction to [72](72.decorate-usecase.md), the panel to [73](73.decoration-panel.md).

## Purpose

cosimosi's universe is the user's own; [P4] promises they may dress it, and [P5]–[P11] make that promise concrete in v2
as 우주 꾸미기. But the product has nowhere to put an ornament today. The shipped renderer has a **skin** seam
(`UNIVERSE_SKINS`, `SkinProvider`, `setSkinKey`) whose active value is a build-time constant
(`spec/values.yaml → rendering.active_skin`) with **zero production callers** of the runtime setter, and a **palette**
registry (`packages/emotion/src/registry.ts` `PALETTES`) whose per-user choice lives in `account`'s
`palette_preferences`. Neither is a catalog, neither knows what a purchase is, and there is no notion of owning
anything. This unit is the domain that closes that gap: what an ornament **is**, which ones exist, what a user **owns**,
and what is **applied right now**.

The unit exists to make one thing impossible rather than discouraged. [I11] says money and achievement cannot buy
meaning: no purchase may move a star, change its brightness, recolor its emotion, or reshape its seed. [V10] says the
decoration layer is _render parameters only_. The weakest way to honor that is a review rule over a `params JSONB`
column. The way taken here is that **the catalog row, the DB row, and the proto message have no field in which a render
parameter's _value_ could be written** — they carry an opaque id, a kind, an acquisition path and a tier ordinal. The
color table, the shader graph and the sky node stay where they already are, in the rendering layer behind the plan-17
`moodColor` seam and the plan-14 asset sources ([ARCHITECTURE.md](../ARCHITECTURE.md) §3.4). The server never learns what
an ornament looks like.

The second shaping requirement is [P7]: 보관함·인벤토리·장착 must not exist as a user concept. That is enforced here as
absence — the contract has no `ListInventory` message and no `Equip` method, and `GetCatalog` answers with
per-item `owned`/`selected` booleans so the panel can render one list of everything ([P6]) and reveal ownership through
price alone ([P7]).

Finally, the catalog is deliberately **a wrapper, not a parallel asset library** — with one honest exception. `PALETTE`
wraps the shipped `PALETTES` registry; `BACKGROUND` wraps the 12 shipped TSL sky effects plus the 4 nebula/gradient
specs already authored in `UNIVERSE_SKINS`, of which only `grainient` is reachable in production today.
`STAR_SHADER` has **nothing to wrap** — `createStarBodySource()` takes no arguments and `StarLayer` calls it in a bare
`useMemo` — so this unit creates that registry, which is why the scope line is FS rather than BE.

## Design

### Placement — a NEW `internal/store` supporting context (ARCHITECTURE §2.2/§2.3)

Ornaments have their own aggregate (`OrnamentSelection` per user, with `OrnamentOwnership` as its permanent history),
their own lifecycle (acquire once, select any time) and their own tables. Folding them into `memory` would put
product-store vocabulary inside the one neuroscience core context; folding them into `account` would make the palette a
preference again and make [P8]'s one transaction across all three kinds impossible (§2.2 forbids `store` reaching into
`account`'s table, and spanning both would make one context the transaction owner of the other's tables). So: a peer
supporting context, following the observed `twinkle`/`admin` recipe exactly —

```
apps/api/internal/store/{doc.go, types.go, catalog.go, service.go, ports.go, errors.go}
apps/api/internal/store/pg/store.go            the only package importing dbgen (§2.6)
apps/api/internal/store/rpc/{server.go, reasons.go}
apps/api/cmd/api/store.go                      storeServiceOption(...) → platform.WithRPCService
apps/api/db/queries/store/ornaments.sql        directory name == context name (the isolation gate keys on it)
```

`store.NewService(store.ServiceDeps{Ownerships: …, Selections: …})` — the `twinkle.ServiceDeps` form, since there is
more than one dep. No empty `domain/`/`app/` directories (§2.9 #2). `store` imports **no** other `internal/` context;
the only sanctioned internal→internal import in the repo stays `ai → memory`.

### The catalog — code, not a table; a row names a tier, never a number

The catalog is a package-level Go table in `store/catalog.go`: `map[OrnamentID]Ornament`. Prices, kinds and acquisition
paths are **content**, so they are code; the tier's _number_ is tuning, so it is `values.yaml`. PRD §5.9/§5.10's
"오너먼트 가격 → values.yaml" is amended by this unit to that split.

```go
type OrnamentID string            // opaque to the server: "<kind-slug>.<registry-key>"
type OrnamentKind uint8           // BACKGROUND | STAR_SHADER | PALETTE
type OrnamentAcquisition uint8    // FREE | PURCHASE | ACHIEVEMENT
type PriceTier uint8              // 0 = not purchasable; 1..3 → values.StorePriceTierN

type Ornament struct {
    ID          OrnamentID
    Kind        OrnamentKind
    Acquisition OrnamentAcquisition
    Tier        PriceTier
}
```

Four fields, all discrete. **There is no `Price int` field** — a per-row literal price is unrepresentable, which is how
the tier rule becomes structural rather than a review note. **There is no `Label`, `Blurb`, `PreviewURL`, `Color`,
`Size`, `Brightness`, `Seed` or `Params` field** — the server cannot describe an ornament, only name one. Display names
are `store_*` i18n keys keyed by ornament id (plan 73); the renderer registries keep their own developer-facing labels
alongside the shipped `SKY_EFFECTS` `label`/`blurb` fields.

`OrnamentID` values are literal strings of the form `<lower(kind)>.<registry key>` — `background.grainient`,
`star_shader.classic`, `palette.cosimosi-default`. Two consequences are load-bearing: a duplicate id is a **compile
error** (a duplicate constant key in a Go map literal), and cross-kind uniqueness — which `ornament_ownerships`' primary
key `(user_id, ornament_id)` depends on — follows from the prefix rather than from a test. The Go side never parses the
id; the FE mirror splits on the first `.` to pick the registry.

**Catalog membership (22 rows), decided here:**

| Kind          | Rows                                                                                   | Free default                                            | Purchasable                                                                         | Achievement-only             |
| ------------- | -------------------------------------------------------------------------------------- | ------------------------------------------------------- | ----------------------------------------------------------------------------------- | ---------------------------- |
| `BACKGROUND`  | 16 = the 12 shipped `SKY_EFFECTS` + the 4 `UNIVERSE_SKINS` nebula/gradient backgrounds | `background.grainient` (today's production sky)         | 13 — tier 1 for the 4 nebula/gradient specs, tier 2 for the 9 remaining sky effects | `background.prismatic-burst` |
| `STAR_SHADER` | 4 (this unit creates the registry)                                                     | `star_shader.classic` (today's shipped star, unchanged) | 2 at tier 3 — the scarcest kind, because it touches the star itself                 | `star_shader.nova`           |
| `PALETTE`     | 2 — whatever `packages/emotion` `PALETTES` publishes                                   | `palette.cosimosi-default` (free forever, [P10])        | `palette.muted-dusk` at tier 1                                                      | —                            |

Exactly two achievement-only rows keeps [P11]'s "아주 가끔" honest. The per-row tier assignment is catalog content; the
**tiering rule** above is the decision. The rows' aesthetics are reviewed under plan 57.

**Cross-catalog direction is one-way:** `achievement` (plan 74) names an ornament id as a reward; `store` **never names
an achievement**. `Ornament` therefore has no `AchievementID` field and the proto has no `achievement_id`, so there is no
id to drift. The panel joins an `ACHIEVEMENT` item to its condition text through `ListAchievements`, which the `/me`
achievements tab already reads. Plan 74 lands the pairing test (`apps/api/cmd/api/catalog_consistency_test.go` —
`cmd/api` is the one package that legitimately sees both catalogs, §2.4), asserting every `ACHIEVEMENT` row is the
reward of exactly one achievement.

### The two tables (migration `00020_store_ornaments.sql`, goose up + down)

Migration numbers are claimed in plan order from `00016` ([00.overview](00.overview.md) §5.6): 60 → `00016`, 62 → `00017`, 66 → `00018`,
68 → `00019`, **71 → `00020`**, 72 → `00021`, 74 → `00022`.

```sql
-- Plan 71 ([P7][P9][I11][U1]). Permanent ownership history: purchase or achievement grant, never
-- expiring, never revoked, never UPDATEd by the system. The insert is ON CONFLICT DO NOTHING,
-- which is also the idempotency guard for the achievement reward leg (plan 75). No `kind` column —
-- kind is derivable from the id prefix and is not stored (ARCHITECTURE §2.9 #3).
CREATE TABLE ornament_ownerships (
    user_id      TEXT NOT NULL,
    ornament_id  TEXT NOT NULL,
    acquired_via TEXT NOT NULL,   -- 'purchase' | 'achievement' — the [P9]/[P11] audit trail
    acquired_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (user_id, ornament_id),
    CHECK (acquired_via IN ('purchase', 'achievement'))
);

-- Plan 71 ([P8][P10][I11]). The single source of truth for what the universe wears right now —
-- one row per kind, which is what makes "exactly one applied ornament per kind" structural.
-- PALETTE rows supersede account.palette_preferences (plan 72 migrates and drops it).
-- ABSENCE = the kind's free default; no row is ever written for a default.
CREATE TABLE ornament_selections (
    user_id     TEXT NOT NULL,
    kind        TEXT NOT NULL,   -- 'BACKGROUND' | 'STAR_SHADER' | 'PALETTE'
    ornament_id TEXT NOT NULL,
    selected_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (user_id, kind),
    CHECK (kind IN ('BACKGROUND', 'STAR_SHADER', 'PALETTE')),
    -- The id prefix must equal the kind: a PALETTE row can never hold a background id.
    CHECK (ornament_id LIKE lower(kind) || '.%')
);
```

Notes. **No foreign key to `users`**, consistent with every existing product table, so a withdrawn user leaves no
cascade. **No `deleted_at`**: a withdrawn scope is rejected by the `platform` interceptor _before any context
read_ (plan 62), so "hidden during the 30-day window" needs no per-query filter and `store` has no knowledge of
withdrawal at all. **No `params`/`config`/`overrides` column** — that absence is the schema-level half of the [I11]
guard. The `LIKE lower(kind) || '.%'` CHECK is the reason the id prefix is not decoration: it turns "the selection
belongs to its kind" into a schema fact.

### sqlc surface (`db/queries/store/ornaments.sql`, static sqlc only)

- `ListOrnamentOwnerships` — `SELECT ornament_id, acquired_via, acquired_at … WHERE user_id = $1`.
- `ListOrnamentSelections` — `SELECT kind, ornament_id … WHERE user_id = $1`.
- `InsertOrnamentOwnership` — `INSERT … ON CONFLICT (user_id, ornament_id) DO NOTHING`. Plan 72's purchase leg and plan
  75's `OrnamentGranter` both call it; the primary key is the dedup key, so a replayed claim never double-grants.
- `UpsertOrnamentSelection` — `INSERT … ON CONFLICT (user_id, kind) DO UPDATE SET ornament_id = …, selected_at = now()`.
  Plan 72 calls it once per kind inside one transaction ([P8]).
- `DeleteOrnamentOwnershipsForUser` / `DeleteOrnamentSelectionsForUser` — the withdrawal sweep's purge (plan 62).

Every statement is plain sqlc with a conjunctive `user_id` scope; no hand-built dynamic pgx string, because such a query
escapes the [U1] gate entirely (the gate scans only `db/queries/**/*.sql`). `store/pg` maps rows to domain and is
the only importer of `dbgen`.

### Read behavior and the RPC contract (`cosimosi.store.v1`, Connect, unary — §2.7)

```proto
service StoreService {
  rpc GetCatalog(GetCatalogRequest) returns (GetCatalogResponse) { option idempotency_level = NO_SIDE_EFFECTS; }
  rpc GetSelection(GetSelectionRequest) returns (GetSelectionResponse) { option idempotency_level = NO_SIDE_EFFECTS; }
  // rpc Decorate — appended to this same file by plan 72.
}

enum OrnamentKind { ORNAMENT_KIND_UNSPECIFIED = 0; ORNAMENT_KIND_BACKGROUND = 1;
                   ORNAMENT_KIND_STAR_SHADER = 2; ORNAMENT_KIND_PALETTE = 3; }
enum OrnamentAcquisition { ORNAMENT_ACQUISITION_UNSPECIFIED = 0; ORNAMENT_ACQUISITION_FREE = 1;
                           ORNAMENT_ACQUISITION_PURCHASE = 2; ORNAMENT_ACQUISITION_ACHIEVEMENT = 3; }

message GetCatalogRequest {}                    // scope comes from platform.UserScope — never the wire
message Ornament {
  string ornament_id = 1;
  OrnamentKind kind = 2;
  OrnamentAcquisition acquisition = 3;
  int64 price = 4;      // server-resolved from the tier; 0 for FREE and ACHIEVEMENT
  bool owned = 5;
  bool selected = 6;
}
message GetCatalogResponse { repeated Ornament ornaments = 1; }

message GetSelectionRequest {}
message OrnamentSelection { OrnamentKind kind = 1; string ornament_id = 2; }
message GetSelectionResponse { repeated OrnamentSelection selections = 1; }
```

- **No `user_id` field anywhere** — scope comes from `platform.UserScope`. **No `ListInventory`-shaped message and no
  `Equip` method** ([P7]). No label, blurb, asset URL, color, or numeric render parameter — the wire cannot describe an ornament.
- `owned = acquisition == FREE || an ownership row exists`. A `FREE` row is owned by everyone with **no row ever
  written**, which is how [P10]'s free default needs neither a signup grant nor a user backfill.
- `price` is resolved server-side from `PriceTier` → `values.StorePriceTier{1,2,3}`. The FE never holds the price table,
  which is also what keeps [Z8] true for the demo taster by construction.
- **`GetSelection` always returns exactly three entries, one per kind**, with absence and any unknown/retired id coerced
  to that kind's default. This reproduces `GetPalettePreference`'s shipped contract ("the default id when unset; a
  retired id coerces to the default"), makes the FE boot deterministic, and is what plan 72's
  `account.GetPalettePreference` read-through delegates to.
- Both methods are classified exactly once in `packages/client-cache/src/http-policy.ts` as user-scoped GET with
  `sharedCdn: false`. The production transport hard-fails on a missing, duplicate, or proto-incompatible classification
  before I/O — the structural guard; no runtime check is written (§2.7).
- `store/rpc/server.go` stays thin (map + call, §2.9 #7). `errors.go` declares `ErrScopeRequired`, `ErrStoreRequired`,
  `ErrUnknownOrnamentID` and `ErrOrnamentNotPurchasable` — the last two are the catalog's judgements that plan 72's
  `Decorate` surfaces ([P11]). No new client-facing error reason is added here: the two reads take no input.

### Default ids are contract constants, not values (ARCHITECTURE §4)

`store` declares `DefaultBackgroundOrnamentID`, `DefaultStarShaderOrnamentID` and `DefaultPaletteOrnamentID` as contract
constants, following `account.DefaultPaletteID`'s shipped rationale verbatim ("a contract constant, not a tuning
value"). `spec/values.yaml → rendering.active_skin` **narrows** to the two jobs it keeps: it selects the skin whose
bloom/camera the scene wears (never sellable), and it must agree with the default background.
`resolveActiveSkin`'s fallback moves from the wrong `'aurora'` to a named `DEFAULT_SKIN_KEY` equal to the product
default, matching `resolvePaletteById`.

The drift guard is the generalized fixture: `apps/api/internal/store/testdata/ornament-ids.json` and its byte-identical
FE twin list all 22 ids plus the three defaults, each side asserting the file matches its own registry, and the FE side
additionally asserting `UNIVERSE_SKINS[VALUES.rendering.activeSkin].background` resolves to
`DefaultBackgroundOrnamentID`. Plan 72 deletes `account`'s `registryPaletteIDs` + `palette-ids.json` when it removes the
palette write path; until then both fixtures compare against the same FE source, so neither can drift.

### The renderer registries (ARCHITECTURE §3.4)

**`BACKGROUND`.** `effect` stops being a prop buried in `UNIVERSE_SKINS.emotion.background.props` and becomes a
selectable `BackgroundSpec` id: 16 ids resolving through `assets/backgrounds/registry.ts`'s existing discriminated union
— 12 to `{type:'sky', props:{effect}}`, 4 to the shipped nebula/gradient specs. The `SkinKey` union does **not** grow to
17 arms. `setSkinKey` (zero production callers today) becomes reachable; the two app-boundary sites are
`apps/web/src/widgets/universe-canvas/ui/UniverseCanvasWidget.tsx` and its mobile twin.

**`STAR_SHADER`.** New `packages/3d-renderer/src/assets/bodies/star-variants.ts`: a `StarVariantKey` union and a
`STAR_VARIANTS: Record<StarVariantKey, StarVariant>` record shaped like `UNIVERSE_SKINS`. `createStarBodySource(variant)`
is plumbed through `packages/universe-render/src/StarLayer.tsx`, and a variant change remounts the layer through the
existing `key={\`star-${…}\`}` pattern (`InstancedNodeLayer` owns and disposes the material). The universe itself stays
mounted — plan 14's no-renderer-remount rule holds.

A `StarVariant` may vary **only**: form frequency, relief amount, the relief noise family
(`ridged`/`fbm`/`worley`/`gnoise`, or `pattern.ts`'s `cellEdge`/`contourSteps`/`isoLine`), a **luminance-neutral**
surface finish (`shader-art/finish.ts` `fresnel`/`iridescent`), geometry topology within
`rendering.instance_bucket_size`, and an optional host-timed surface drift that must honor `SkySphere`'s existing
`reducedMotion` freeze. The type has **no field** for tint, brightness, seed or scale: those three instance attributes
and the layer-applied scale are inputs the builder may only pass through. `EMISSIVE_GAIN` is **not** a variant field —
raising it lifts a decayed star back over the bloom threshold, visually undoing forgetting ([V2][F1]).
`SURFACE_CONTRAST` is a variant field only if renormalized to be luminance-neutral; unrenormalized (today's
`tint.mul(1 + shimmer)`, up to +35% luminance) it is excluded.

`StarVariantKey`/`StarVariant` are **rendering vocabulary** (UL §4) and never appear in Go, DB or proto — the server
holds only the opaque `star_shader.*` id, so the render vocabulary cannot flow backward across the §3.4 boundary.

### Golden-parity stance

**No pure function in this unit mirrors TS↔Go, and none should.** There is no formula: a price is a tier→constant lookup
performed once, server-side, and `owned`/`selected` are set membership over rows the server alone holds. The duplicated
artifact is _data_ — the id vocabulary, which must exist in Go (authority, pricing, validation) and in the renderer
(resolution to a node builder). Data cannot drift silently under a byte-identical fixture pair, so the guard is the
generalized `ornament-ids.json` pair rather than a golden math fixture, no `packages/*-logic` mirror is created, and no
price constant needs mirroring at all because the price never crosses into the client.

## Acceptance Criteria

1. A goose migration `00020_store_ornaments.sql` creates `ornament_ownerships (user_id, ornament_id, acquired_via,
acquired_at, PRIMARY KEY (user_id, ornament_id), CHECK (acquired_via IN ('purchase','achievement')))` and
   `ornament_selections (user_id, kind, ornament_id, selected_at, PRIMARY KEY (user_id, kind), CHECK (kind IN
('BACKGROUND','STAR_SHADER','PALETTE')), CHECK (ornament_id LIKE lower(kind) || '.%'))`; `pnpm db:migrate` applies and
   `pnpm db:down` reverses cleanly ([P8][P9][U1]).
2. Neither table has any column for a color, size, brightness, seed, position, or free-form parameter payload (no
   JSON/JSONB column), and neither has a `deleted_at`, expiry, quantity, or revocation column ([V10][I11][P9]).
3. A `PALETTE` selection row cannot hold a background or star-shader id, and a user cannot hold two selections of one
   kind — both refused by the schema, not by application code ([P8][I11]).
4. Every `db/queries/store/*.sql` statement scopes by an owned `user_id`; `pnpm lint:persistence` passes with **no** new
   `platformTables` or `globalQueries` entry ([U1]).
5. `internal/store` follows the context recipe (`{doc.go,types.go,catalog.go,service.go,ports.go,errors.go}` + `pg/` +
   `rpc/`, no empty `domain/`/`app/`), imports no other `internal/` context, and only `store/pg` imports `dbgen`
   (ARCHITECTURE §2.2/§2.3/§2.6).
6. The catalog is an in-code Go table of 22 rows across the three kinds; `Ornament` has exactly the fields
   `{ID, Kind, Acquisition, Tier}`, so **no per-row price number and no visual attribute is representable**, and a
   duplicate `OrnamentID` fails to compile ([P9][V10][I11]). `OrnamentKind` is closed at exactly
   `BACKGROUND | STAR_SHADER | PALETTE` — the three staging-layer surfaces [P4] opens to customization — so a fourth
   kind cannot appear without amending the Go enum, the DDL `CHECK` and the proto in one reviewed change, and nothing
   meaning-bearing (position, strength, emotion, forgetting, gist) is expressible as a kind at all ([P4][V10][I11]).
7. Exactly one row per kind is `FREE` and each is that kind's default; a free default is served as `owned = true` with
   **no** `ornament_ownerships` row ever written for it, and no signup-time grant or user backfill exists ([P10]).
8. `ACHIEVEMENT` rows carry no price tier and report `price = 0`; the catalog exposes them as unbuyable via
   `ErrOrnamentNotPurchasable`, and no Go field or proto field names an achievement ([P11]).
9. `proto/cosimosi/store/v1/store.proto` declares `GetCatalog`† and `GetSelection`† with the `ORNAMENT_KIND_*` /
   `ORNAMENT_ACQUISITION_*` enum spellings, contains **no `user_id` field**, **no `ListInventory`-shaped message** and
   **no `Equip` method**, and passes `buf lint` STANDARD and `buf breaking` ([P6][P7]).
10. `GetCatalog` returns **every** catalog row — owned and unowned alike — each with `owned`, `selected` and a
    server-resolved `price` read from `values.StorePriceTier{1,2,3}`; no price table, label, blurb, or color reaches the
    client ([P6][P7][P9], [Z8]-safe).
11. `GetSelection` returns exactly three entries, one per kind; an absent row and an unknown/retired stored id both
    resolve to that kind's default contract constant ([P10]).
12. Both new `NO_SIDE_EFFECTS` methods are classified exactly once in `packages/client-cache/src/http-policy.ts` as
    user-scoped GET with `sharedCdn: false`, and the transport fails before I/O on a missing or duplicate classification
    (ARCHITECTURE §2.7).
13. `createStarBodySource(variant)` accepts a `StarVariant` that has **no writable handle** to `aStarTint`,
    `aStarBrightness`, `aStarSeed` or the layer-applied scale and no field for `EMISSIVE_GAIN`; `star_shader.classic`
    renders identically to the shipped star; a variant change remounts only the star layer, never the renderer
    ([V2][V3][V5][V10][I11]).
14. `BACKGROUND` ids resolve through the existing `BackgroundSpec` union (12 sky effects + 4 nebula/gradient specs); no
    ornament id resolves to a `BloomParams` or any camera field, and the `SkinKey` union does not grow
    ([V10][I11]).
15. `resolveActiveSkin` falls back to the product default skin rather than `'aurora'`, and a test asserts
    `UNIVERSE_SKINS[VALUES.rendering.activeSkin].background` resolves to `DefaultBackgroundOrnamentID`.
16. `apps/api/internal/store/testdata/ornament-ids.json` and its FE twin are byte-identical, list all 22 ids plus the
    three defaults, and are asserted from **both** sides — a renamed or dropped registry key fails a test on both
    runtimes.
17. `store.Service.PurgeUser` hard-deletes only the calling user's ownership and selection rows, and `store` contains no
    other delete path ([I1][U1]).
18. `spec/values.yaml` gains exactly `store.price_tier_1|2|3`; no ornament id, default id, catalog row, tier assignment,
    row count, or shader constant appears in values, and no price literal appears in Go, TS, DDL, or proto.
19. `ubiquitous-language.md` registers `StarVariant` in §4 (renderer-only), and the `(ornaments)` table name is struck
    from UL §1.1 and PRD §3.2's `Ornament` row — the catalog has no table.
