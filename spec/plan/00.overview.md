## 1. How we build — epics, delivered as sprints, layered within

### 1.1 The roadmap is organized by **product epic**

Forward work is grouped into **epics** — product capability areas drawn from the PRD requirement prefixes
([W] writing, [R] recall, [F] forgetting, …). Epics are sequenced into **sprints** (delivery increments, §2.2). This
is the top-level structure: we ship a capability, not a layer.

### 1.2 Within an epic, units flow through the clean-architecture layers

Each epic's backlog units are ordered by the **product's clean-architecture layers** — **domain → use-case →
presentation** — which is _orthogonal_ to the code architecture (FSD on the frontend, domain-first Go on the backend):

- A unit's **layer** decides _when within its epic_ it is built; the **architecture** decides _where its code lives_
  (which context / slice / segment). A domain unit is the pure model wherever ARCHITECTURE puts it (the `entities/<noun>/model`
  segment, the Go `<context>` package) — **even while its rendering segment stays empty**. _How a thing is shown_ is a
  presentation concern.
- **Domain & use-case units are headless.** Pure domain (types + deterministic functions, FE↔BE golden-parity) and
  use-cases (orchestration behind ports, mock fallback) carry no pixels — verified by golden-parity tests and the
  temporary **`/test` page** (Foundation · plan 12). They parallelize in dependency waves.
- **Presentation units are vertical and sequential.** Each is one user-facing flow taken end-to-end through rendering
  - UI and confirmed on screen, built one slice at a time — **each slice ships web (open beta) + mobile (MVP) together**.
    The rendering layer owns the visual vocabulary and is the one place domain and visual words meet (ARCHITECTURE §3.4).

### 1.3 Shared substrate

Some domain units (the memory aggregate & schema, emotion model, synapse plasticity, the force-sim layout, the
universe clock) are the **engine substrate** that many epics build on. They are first _needed_ by — and therefore built
_inside_ — the earliest epic, then reused. Reuse promotes **down** a layer (to `packages/`), never copied sideways.
On the presentation side, the **rendering substrate** (plan [14](14.rendering-foundation.md), `rendering-foundation`) —
the renderer boundary, the TSL shader toolkit, and the skinnable background — is the seam every Epic-A render unit
mounts.

### 1.4 Numbering

Plans are a **fresh, stable, contiguous series** — never reused or renumbered once authored. The Foundation is
`spec/plan/01`–`13`, plus the pre-Epic-A substrates `14` (rendering) and `15` (web routing); Epics A–J and the
cross-cutting substrates run `16`–`59`, so the next plan `/create-plan` scaffolds is `60`. **Backlog units below are
listed by title in dependency order, without a number** — the number is assigned when `/create-plan` scaffolds the unit.

## 2a. v2 epics (PRD v2 — §8.2)

> **v1 is complete; these are the v2 capability areas.** The v2 PRD promotes Twinkle from a recall-only currency to the
> product's **single currency** (`SMALL` recall-only daily-reset · `GENERAL` universal permanent) and builds the surfaces
> that ride on it: the finished account path, a real diary archive, universe decoration, achievements, and the public
> funnel (landing · blog · demo · onboarding). Payment is **not** v2 — it moves to v3 (PRD §8.3), so achievements and the
> daily grant carry the supply.
>
> **All 23 units below are now authored as plans `60`–`82`** (§1.4; the per-unit number is in the plan index, §5.1).
> Two PRD rules shape every unit here: the naming exception (§3.1 rule ⑦ — `account` · `store` · `achievement` ·
> `demo` are supporting contexts in plain product English, _not_ neuroscience terms) and the meaning-layer guarantee
> ([I11] extended, [V10] — decoration and achievements change render parameters only; no purchase or unlock moves a
> star's position, emotion, strength, forgetting, or gist).
>
> Their cross-plan questions — context placement, the currency redefinition and its migration, the single source of
> truth for the chosen palette, demo isolation, the parity matrix, the values groups, and one structural guard per
> at-risk invariant — were settled **before** the plans were written, the same way CC1–CC12 preceded Epics C–J. Each
> answer now lives in the doc that owns it: the risk register in §3, the values-group and parity rules in §4, build
> order and single-owner DDL in §5.6, and everything unit-specific inside the owning plan.

## 4. Cross-cutting decisions

- **App roots:** `apps/api` · `apps/web` · `apps/mobile`, plus `apps/blog`. Shared pure code lives in `packages/`.
- **Mobile = React Native — first-class MVP target, built alongside web (not deferred).** Release targets: **web =
  open beta, mobile = MVP**. RN reuses the one shared stack (no parallel state/i18n lib); the RN WebGPU renderer is in
  scope (pre-1.0 `react-native-webgpu`, early-adopter caveats). Rationale: [ARCHITECTURE.md](../ARCHITECTURE.md) §3.5.
- **Deployment is live**, and [DEPLOY.md](../../DEPLOY.md) is its SSOT: a Cloudflare Worker on `cosimosi.haeram.me`, a
  Lightsail Seoul VPS behind Caddy for `api.cosimosi.haeram.me`, a live Supabase project, and Workers Builds promoting
  `main`. Read it there rather than restating it here.
- **Config is build-time.** Every tuning number a plan introduces goes in `spec/values.yaml` → `pnpm gen:values` →
  FE(TS)/BE(Go) constants; never hardcoded.
- **Numbering.** Fresh contiguous series (01+); stable IDs — never reused or renumbered once authored.
- **Docs.** The PRD, concept stay Korean (the vision source); the glossary is bilingual; plan / job / tech /
  ARCHITECTURE / principle docs are English.
- **tech/ & policy/** docs are added incrementally as units land — the as-built rules each one needs.
- **Values groups are closed; keys inside a group are not.** A plan may add a tuning number to a group it owns; it may
  **not** create a group, and a **catalog row is never a value**. Ornament definitions/prices and achievement
  conditions/rewards are content and live as Go tables in their context — a catalog row names a _tier_, and
  `spec/values.yaml` holds that tier's number. (`values.yaml`'s own precedent draws the line: the retired
  `twinkle.charge_pack` comment reads "a multi-pack table is content, not a scalar".) v2 adds the groups `account`,
  `store`, `achievement`, `sequence`, `demo` and extends `twinkle`, `diary_reader`, `release`, `rendering`. This
  amends PRD §5.9/§5.10, which promised ornament prices and achievement numbers wholesale to `values.yaml`.
- **`/me` carries five tabs, and 감정 색 is one of them while 계정 is not.** [U9] enumerates the page's concerns, and
  the tab set is not a one-to-one reading of that list. **감정 색** earns a surface of its own between 프로필 and
  별가루 rather than a row inside 프로필: it is plan 51's per-mood editor, and it does not widen [U9]'s exclusion —
  감정 색 is emotion _vocabulary_, free and reaching no meaning field ([P10][I11]), which is exactly why "우주
  꾸미기는 여기 두지 않는다" still holds. **계정** goes the other way and is _not_ a tab: the identity, the linked ways
  in, sign-out and withdrawal are facts about the same person 프로필 is about, so they sit at the foot of it, behind a
  separating rule, where a stray press cannot reach them. Both amend PRD §5.1 [U9]'s tab list, which is now written
  that way. Owners: [51] the editor, [64] the page.
- **web↔mobile parity is per-surface, and a waiver must be written down.** Parity means _shared package + forked
  `ui`_ (ARCHITECTURE §3.5): everything under `model`/`api` and all of `packages/` is shared verbatim, and a
  normalized-equivalent pure module present in both apps is a **lint failure** until it is promoted to its package —
  identifier-only renames do not turn copying into parity. `scripts/lint-fsd-layout.mjs` does not enforce web↔mobile page peering, so an _unstated_ waiver is
  silently broken rather than caught; each waiver cites the admin-console precedent (`spec/policy/ops/admin.md` §6).
