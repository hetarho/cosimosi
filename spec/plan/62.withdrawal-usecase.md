# 62. withdrawal usecase

> Withdrawal use-case — account-scoped soft delete that reuses the shipped [X2] 30-day contract: `Withdraw` stamps
> `users.deleted_at`, a `platform` interceptor makes every withdrawn scope unreadable before any context read,
> `RestoreAccount` undoes it inside the window, and one scheduled sweep job hard-deletes every per-user row afterwards —
> across `memory`, `twinkle`, `account` and (later) `store`/`achievement`. The sweep is the **same** mechanism, the
> **same** retention key and the **same** worker loop as the diary retention sweep, so the product still has exactly one
> hard-delete mechanism and it is still user-origin only ([I1]).
> Scope: BE | Status: built ([job 91](../jobs/archive/91.withdrawal-usecase.md))
>
> Layer U. Home: the supporting context `apps/api/internal/account` — use-cases `Withdraw` / `RestoreAccount` /
> `SweepWithdrawnAccount`, plus the `platform` admission interceptor and one narrow purge port per context that owns
> per-user rows. It fills the withdrawal seam [U10] left open and leaves the confirm/restore screens, the export button
> and the `withdraw_*` copy to [64.my-page](64.my-page.md).

## As-built decisions

- `users.deleted_at` is the only withdrawal and deadline authority. `Withdraw` enqueues the identity-only
  `withdrawal_sweep` job before marking the row; an orphan job therefore no-ops, while an early job retries at the
  deadline derived from the shared `release.soft_delete_retention_days`.
- The admission interceptor is mounted directly after authentication. It permits only `RestoreAccount`, treats an
  absent profile as live/unprovisioned, and returns `PLATFORM_ACCOUNT_WITHDRAWN` with both window timestamps before a
  context handler can read.
- The worker holds the `users` row lock while replay-safe, per-context purge transactions run in the order memory →
  twinkle → account dependents → credential ban/delete → `users`. The in-flight queue row is the only temporary
  survivor.
- `00017_withdrawal_sweep.sql` adds the revisionless `user` job target and records account withdrawal as the sole
  exception to Twinkle's system append-only rule. No second retention value, cron, withdrawal ledger, or direct purge
  RPC exists.
- Production API and worker composition reject a keyless credential directory. Development may use the in-memory
  fake, but a production sweep cannot delete product rows without a configured Supabase Admin API.
- The persistence gate now allowlists every product hard-delete statement by exact sqlc name. The integration test
  derives `user_id` tables from the migrations, cross-checks them against the migrated schema, seeds every table, and
  proves only the running sweep job remains for the withdrawn user.

## Purpose

A person who wants to leave must be able to leave, and a person who leaves in a hard moment must be able to come back.
[U10] fixes both halves at once: withdrawal is reachable from `/me` → account, and it **reuses [X2]'s 30-day
soft-delete contract at the account scope** — restorable for 30 days, hard-deleted after. The same paragraph makes the
Export offer mandatory at the confirm step ("지금 CSV·MD로 내보내시겠어요?", [W6]), because the honest version of
"everything will be gone" is "take it with you first".

Nothing of this exists today. There is no `users` table (plan [60.account-profile-model](60.account-profile-model.md)
creates it), no withdrawal RPC, and — the part that makes a naive implementation a privacy defect — **credentials do not
live in our database**. Identity is Supabase end to end (`platform.AuthInterceptor` → `SupabaseJWTVerifier` →
`UserIdentity{UserID}`), so a withdrawal that only stamps `users.deleted_at` is cosmetic: the JWT still verifies,
`platform.UserScope` still resolves, and every `WHERE user_id = $1` still returns the user's diaries. This unit is
therefore three things, not one — a soft-delete write, an **admission gate** in `platform` that refuses a withdrawn
scope before any context is entered, and a **scheduled purge** that reaches every table holding that user's rows.

The purge is where [I1] is most at risk. The constitution says the system never deletes; the single exception is the
user's own explicit deletion, executed after the grace period by the retention sweep — today
`memory.RetentionSweeper`, documented in code as "the ONLY hard delete of user data". Withdrawal adds a second **call
site** of that promise, and this plan's job is to make sure it does not become a second _mechanism_: same retention key
(`release.soft_delete_retention_days`), same `jobs` queue, same worker loop, same "a user who never returns is still
swept" guarantee, same refusal to touch any row the user did not choose to remove. Everything else about the account —
the twinkle ledger, ornament ownership, achievement progress, an invite whose inviter withdrew — is enumerated here
once, so five later plans do not each guess.

## Scope / Non-goals

**In scope**

- **`account.Withdraw(ctx, scope)`** ([U10][X2]) — idempotently stamps `users.deleted_at` (real-clock UTC), pairs with
  one scheduled sweep job at `deleted_at + release.soft_delete_retention_days`, and returns `withdrawn_at` +
  `restore_deadline_at`. No new table, no per-effect ledger.
- **`account.RestoreAccount(ctx, scope)`** ([U10][X2]) — clears `deleted_at` inside the window and cancels the
  scheduled sweep; refuses outside it. The **only** procedure a withdrawn scope may call.
- **The withdrawn-scope admission interceptor** in `platform` ([U1]) — rejects every other procedure for a
  withdrawn scope with a dedicated reason **before any context read**, carrying `withdrawn_at` /
  `restore_deadline_at` as error metadata so [64.my-page](64.my-page.md) can render the restore screen.
- **`account.SweepWithdrawnAccount(ctx, scope, now)`** ([I1][X2]) — the scheduled hard delete: a named purge leg per
  context that owns per-user rows, then `account`'s own rows, then the credential deletion, then the `users` row as the
  completion marker. Idempotent and replay-safe at every step.
- **The purge legs this plan writes**: `memory.PurgeUser` (the whole memory aggregate + queue rows + `universe_state` +
  provenance + paid-action receipts + release ledger), `twinkle.PurgeUser` (balance + ledger entries), and `account`'s
  own (`auth_providers`, `invites` as inviter, `palette_preferences` while it exists, `users`).
- **The credential seam** — a `CredentialDirectory` port over the Supabase Auth adapter
  [60.account-profile-model](60.account-profile-model.md) promotes: `SetUserBanned` and `DeleteUser`, with the
  ban/delete **timing** pinned below so a self-service restore stays possible.
- **The queue seam** — `jobs.kind = 'withdrawal_sweep'` with a `job_targets.target_kind = 'user'` identity target,
  scheduled and cancelled through a consumer-owned port; migration `00017_withdrawal_sweep.sql`.
- **The proto contract** on the existing `cosimosi.account.v1.AccountService`: `Withdraw`, `RestoreAccount` — no
  fourth transport shape, no `user_id` on the wire.
- **Two structural [I1] guards**: a hard-delete allowlist in `scripts/check-persistence-isolation.mjs`, and an
  integration test that enumerates every per-user table from the migrations and asserts the sweep leaves zero rows.
- The amendments this unit owns: the `twinkle_ledger_entries` / `twinkle_balances` "never
  DELETEd by the system" comment, `memory/release.go`'s "the ONLY hard delete", and the UL row for `RestoreAccount`.

**Non-goals**

- **No withdraw / restore UI, confirm step, or copy.** The account tab, the confirmation, the Export offer's button and
  every `withdraw_*` i18n key belong to [64.my-page](64.my-page.md).
- **No `users` / `auth_providers` / `invites` DDL.** Plan [60.account-profile-model](60.account-profile-model.md) is
  their sole owner ([00.overview](00.overview.md) §5.6); this unit only reads and deletes through new query files.
- **No export implementation.** `memory.Export` (CSV/MD) ships in [46.provenance-export](46.provenance-export.md); the
  confirm step calls it unchanged.
- **No diary-level deletion behavior.** `Release` / `Restore` / `LetGo`, the sealing rules and the release-effect
  ledger belong to [49.release-usecase](49.release-usecase.md) / [48.deletion-rules](48.deletion-rules.md). This unit
  does not change them and does not reuse their ledger _shape_.
- **No invite settlement logic.** "The inviter is not withdrawn" is one arm of plan
  [61.signup-and-invite-usecase](61.signup-and-invite-usecase.md)'s valid-signup conjunction; this unit supplies the
  withdrawn fact and the row disposition, not the gate.
- **No `store` / `achievement` purge legs.** Those contexts do not exist yet (the sprint order in
  [00.overview](00.overview.md) §5.6); plans [71.ornament-catalog-model](71.ornament-catalog-model.md) and
  [74.achievement-catalog-model](74.achievement-catalog-model.md) register theirs against the port declared here, and
  the enumerating test fails until they do.
- **No operator-facing withdrawal tooling.** The admin console ([58.admin-console](58.admin-console.md)) gains no
  withdraw/restore action, and `admin_*` tables are deliberately not swept (below).
- **No queue promotion refactor.** `jobs` / `job_targets` stay `memory`-owned; the debt is named, not paid, here.
- **No new tuning number.** The retention window is the shipped one.

## Design

### Placement (domain-first Go, ARCHITECTURE §2.2/§2.3/§2.4)

`Withdraw`, `RestoreAccount` and `SweepWithdrawnAccount` are application use-cases of the supporting context
`apps/api/internal/account` — the context that owns `User`. They keep the earned layout
plan 60 establishes: behavior in the context package, ports in `internal/account/ports.go` (this plan creates that file
if plan 60 has not), sqlc + pgx in `internal/account/pg`, the thin Connect handler in `internal/account/rpc`. New query
file `apps/api/db/queries/account/withdrawal.sql` (directory name = context name, required by
`scripts/check-persistence-isolation.mjs`'s `<dir>/<file>#<sqlcName>` keys). The counterpart purge queries live with
their owning contexts: `db/queries/memory/purge_user.sql`, `db/queries/twinkle/purge_user.sql`.

`account` imports no other context. Every cross-context edge is a consumer-owned interface declared in
`account/ports.go` and bound by an adapter in `apps/api/cmd/api/account.go`:

```go
// apps/api/internal/account/ports.go — consumer-owned (§2.4); concretes injected at cmd/api.
type WithdrawalStore interface { /* users.deleted_at read/lock/mark/clear + account-owned row purges */ }

// One leg of the sweep per context that owns per-user rows. Name is for logs and the boot audit.
type UserDataPurger interface {
    PurgeName() string
    PurgeUser(ctx context.Context, scope platform.UserScope) error
}

// The queue seam. jobs/ job_targets stay memory-owned; account never sees them.
type WithdrawalSweepScheduler interface {
    Schedule(ctx context.Context, scope platform.UserScope, dueAt time.Time) error
    Cancel(ctx context.Context, scope platform.UserScope) error
}

// The Supabase Auth admin adapter promoted by plan 60. No email, nickname or profile field.
type CredentialDirectory interface {
    SetUserBanned(ctx context.Context, userID string, banned bool) error
    DeleteUser(ctx context.Context, userID string) error // absent user = success (idempotent)
}
```

`AccountServiceDeps{Store, Purgers []UserDataPurger, Scheduler, Directory, Now}` follows the shipped
`twinkle.ServiceDeps` / `admin.ServiceDeps` form. **Production fails to boot** if `Scheduler`, `Directory` or an empty
`Purgers` slice is missing — the no-op is a test-only construct, mirroring
`TestProductionTwinkleExternalEarnsFailClosedWithoutAdapters`. Silently withdrawing without a sweep is worse than
refusing to start.

### `Withdraw` — an idempotent pairing, and `users.deleted_at` is the only source of truth

`Withdraw(ctx, scope)` spans two contexts (the account row, the queue row) and therefore uses an
**idempotent pairing**, never a shared transaction — `account` may not own `memory`'s
tables. The order is **enqueue first, mark second**, and the healing rule is that the job row is only a _trigger_:

1. `Scheduler.Schedule(scope, now + release.soft_delete_retention_days)` — one `jobs` row, dedup key
   `withdrawal:<userID>`, made exactly-once by the shipped `jobs_user_kind_dedup_key_unique` index.
2. `UPDATE users SET deleted_at = now() WHERE user_id = $1 AND deleted_at IS NULL RETURNING deleted_at` in `account`'s
   own transaction. Zero rows = already withdrawn: the use-case reads the existing timestamp and returns it, so a
   retried confirm is idempotent and **never extends or shortens** an in-flight window.
3. Return `withdrawn_at` and the derived `restore_deadline_at`.

A crash between 1 and 2 leaves a scheduled job for an account that is not withdrawn. That is harmless because
`SweepWithdrawnAccount` **re-derives due-ness from `users.deleted_at`**: no `deleted_at` → complete as a no-op
(exactly how the shipped sweep treats a group retired by `Restore`); `now` before `deleted_at + retention` → return a
`RetryAt(deadline)` error, which the shipped `jobqueue` runner honors via its `retryAtError` interface. So a stale or
early job can never purge early, and no reconciliation scan across users is needed (no `globalQueries` allowlist
entry — v2 adds none).

**Decided:** the timestamp is real-clock UTC, not universe-time — "30 days to change your mind" is a human-time
promise, identical to [49.release-usecase](49.release-usecase.md)'s reasoning. **Decided:** `Withdraw` does **not**
cancel the user's pending `embed`/`semanticize`/`consolidate` jobs. Restore must return the account _intact_ ([X2]),
and cancelling in-flight enrichment would restore a star that can never link; the cost is bounded by work the user
already caused and the rows vanish at sweep anyway.

### The withdrawn-scope admission gate ([U1], the Epic K structural guard this plan owns)

A new `platform` interceptor, mounted immediately after `AuthInterceptor` in `platform.NewHandler`'s chain, so it runs
**before any context handler** and therefore before any `WHERE user_id = $1`:

```go
// apps/api/internal/platform/withdrawn_scope.go — platform declares what it consumes (§2.4).
type AccountStatusReader interface {
    WithdrawnAt(ctx context.Context, userID string) (withdrawnAt time.Time, withdrawn bool, err error)
}
func WithdrawnScopeInterceptor(reader AccountStatusReader, exempt []string) connect.UnaryInterceptorFunc
```

- `platform` gains **no** account import: the concrete reader and the exempt procedure list are supplied by
  `cmd/api/account.go` through `WithAccountStatusReader(...)` / `WithWithdrawnScopeExemptProcedures(...)`, the way
  `WithPublicProcedures` already works. The exempt list is exactly one entry —
  `accountv1connect.AccountServiceRestoreAccountProcedure`.
- Rejection is `connect.CodePermissionDenied` with `apperr.ReasonPlatformAccountWithdrawn` and metadata
  `withdrawn_at` / `restore_deadline_at`. **Not** `Unauthenticated` — that code drives the shipped session-refresh /
  sign-out path and would hide the restore affordance.
- **No status RPC exists.** The withdrawn state is delivered _as the error_, so there is no "read my withdrawn account"
  surface to leak from, and the account RPC inventory stays exhaustive.
- **Fail closed**: a lookup error, or a nil reader in a build that registered services, refuses the request. An absent
  `users` row means _not withdrawn_ (a first-time caller has no row until `SignUp` writes one) — and because the
  predicate is "row exists AND `deleted_at IS NOT NULL`", a withdrawn user calling `SignUp` is refused, so re-signing
  up to escape the window (and re-claiming the [U11] bonus) is impossible without restoring.
- **No caching.** A withdrawn user must lose access on the next request, and the lookup is one primary-key read on the
  same pool; a TTL cache would buy microseconds and sell the guarantee. Explicitly rejected, no values key.

### `RestoreAccount` — reachable, which is what fixes the credential ordering

`RestoreAccount(ctx, scope)` locks the `users` row, refuses when `deleted_at IS NULL`
(`ACCOUNT_NOT_WITHDRAWN`) or when `now >= deleted_at + retention` (`ACCOUNT_RESTORE_WINDOW_EXPIRED`), otherwise clears
`deleted_at` and calls `Scheduler.Cancel(scope)`. A failed cancel is safe: the orphaned job re-reads `deleted_at`, finds
it null, and completes as a no-op. After restore the account is whole with **zero special handling** — the twinkle
ledger was never touched, so the balance folds back correctly; the `SMALL` reset anchor is simply stale, so
`SmallRemaining` derives a fresh full grant (unspent prior `SMALL` is discarded — no carry, and deliberately no
special handling); ornament ownership, selections and `achievement_progress.claimed_at` are **restored, never re-granted**, so
no claimed reward can be paid twice.

**Decided — the credential timing.** The rule the withdrawal contract fixes is **ban, not delete** — a delete would
make [X2]-style restore impossible. Both mechanisms are kept and the _order_ is pinned here, because Supabase refuses
sign-in for a banned user: a user banned at withdrawal could never obtain a session, and therefore could never call
`RestoreAccount` — the ban would silently delete the [U10] restore promise. So:

- **At `Withdraw`:** `users.deleted_at` only. Sign-in still works; the admission gate makes every product procedure
  unreachable, so a valid JWT reads nothing. This is precisely the protection the admission gate exists to provide,
  and it is what makes the restore screen reachable.
- **At the sweep:** `SetUserBanned(userID, true)` first (no new session can be minted while the purge runs), then
  `DeleteUser(userID)` as the last credential step. Deleting is required, not optional: it removes the last copy of the
  user's email (which we deliberately never stored), frees the address for a genuinely new
  signup, and — because a Supabase user id can then never recur — makes a _swept_ account's `signup_bonus:<userID>` /
  `invite:<signupID>` dedup keys structurally unreachable even though their ledger rows are gone.
- Restore inside the window needs no un-ban call at all; `SetUserBanned(false)` exists for the operator-recoverable
  case where a sweep failed after banning.

### `SweepWithdrawnAccount` — the second call site of the one hard-delete mechanism

Triggered only by the scheduled `withdrawal_sweep` job. After the due-ness re-derivation above, the legs run **in this
order**, each in its own transaction (§2.3 — one context per transaction), each an idempotent `DELETE … WHERE
user_id = $1`:

1. **Registered `UserDataPurger` legs**, dependents first: `memory` → `twinkle` → (`store`, `achievement` once plans
   71/74 register theirs).
2. **`account`'s own dependents**: `auth_providers`, `invites` **where `user_id` = the withdrawn user** (the inviter's
   own rows), `palette_preferences` while that table exists.
3. **Credentials**: ban, then delete the Supabase user (absent = success).
4. **`users`** — deleted last, so the row's existence is the "sweep incomplete" marker and any crash simply replays.

`memory.PurgeUser(ctx, scope, keepJobID string)` deletes the user's entire memory footprint — `diaries`,
`episodic_memories`, `neurons`, `neuron_activations`, `synapses`, `embeddings`, `memory_provenance`,
`memory_paid_action_receipts`, `universe_state`, the `release_*` group + effect rows, and the user's `jobs` /
`job_targets` rows — **retaining only the in-flight sweep job row**, whose own completion the runner still needs to
record and which the shipped terminal-job cleaner removes afterwards. That row is identity-only (empty payload, one
`(user, <userID>)` target), so no product content survives it; the residue is queue bookkeeping and it is stated here
rather than discovered later. `twinkle.PurgeUser` deletes `twinkle_balances` + `twinkle_ledger_entries`.

**`admin_*` tables are deliberately not swept.** `admin_users`, `admin_stardust_grants` and `admin_audit_log` are
operator state, not per-user product data (the `platformTables` category in `check-persistence-isolation.mjs`), and
operator accountability
requires the audit trail to outlive the accounts it describes. A stale promotion row is unusable because the
credentials are gone.

**Row disposition, restated at query precision** — this unit owns the enumeration, and these are the clauses that
implement it:

| Rows                                                                | During the window                                                                                                                             | At sweep                                                                                                  |
| ------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| `diaries` + the whole memory aggregate + `release_*`                | untouched (reads unreachable via the gate)                                                                                                    | hard-deleted, memory rows before the diary row, reusing the shipped ordering                              |
| `twinkle_balances`, `twinkle_ledger_entries`                        | untouched — which is why restore needs no balance repair                                                                                      | hard-deleted                                                                                              |
| `ornament_ownerships`, `ornament_selections` (plan 71)              | unreachable, never re-granted                                                                                                                 | hard-deleted                                                                                              |
| `achievement_progress` (plan 74)                                    | unreachable, `claimed_at` preserved                                                                                                           | hard-deleted                                                                                              |
| `invites` where the withdrawn user is the **inviter**               | not deleted, so `rewarded_at` survives and a withdraw→restore cannot re-open a settled invite; the link is inert (checked by plan 61)         | hard-deleted                                                                                              |
| `invites` where the withdrawn user is the **invitee**               | **another user's row — never touched.** `invitee_user_id` becomes a dangling reference read null-tolerantly (no FK to `users`, so no cascade) | untouched                                                                                                 |
| already-credited ledger rows on **either** side of a settled invite | untouched                                                                                                                                     | the withdrawing side's are deleted with its ledger; the other side's stay. **No reward is ever reversed** |
| `palette_preferences`                                               | unreachable                                                                                                                                   | hard-deleted while the table exists; plan 72's drop of that table retires this clause                     |
| `admin_*`                                                           | untouched                                                                                                                                     | untouched (operator state)                                                                                |

A diary release whose own 30-day window expires _during_ the account window is swept normally by its own job — the
worker is not gated by the RPC interceptor, and honoring the user's earlier deletion is correct. Such a diary is
consequently not restorable by `RestoreAccount`; its window ended on its own terms.

### The queue seam and migration `00017_withdrawal_sweep.sql`

The sweep must fire for a user who never comes back, so it needs the durable trigger [49.release-usecase](49.release-usecase.md)
already established: a `jobs` row and the normal worker loop, no cron (§2.8). `jobs` / `job_targets` are `memory`-owned
today, so `memory` publishes the narrowest possible scheduling behavior and **keeps** ownership:

- `memory.Service.ScheduleUserJob(ctx, scope, UserJobSpec{Kind, DedupKey, DueAt})` and
  `CancelUserJob(ctx, scope, kind, dedupKey)`. `UserJobSpec` has **no payload field and no target field**: the payload
  is always empty and the target is always `(user, scope.UserID())`. A caller therefore cannot forge a memory job
  through it — every memory handler validates a memory target kind and would reject one. Containment by contract
  shape, not by review.
- Migration `00017_withdrawal_sweep.sql` (migration numbers are claimed in plan order from `00016` —
  [00.overview](00.overview.md) §5.6; plan 60 holds `00016`) extends the shipped
  `job_targets_kind_revision_check` with `target_kind = 'user'` / `expected_revision IS NULL`, and carries the
  ledger comment amendment as `COMMENT ON TABLE` on
  `twinkle_ledger_entries` and `twinkle_balances`: append-only against the _system_, with the user's own withdrawal
  purge named as [I1]'s stated exception. Putting the amendment in the live schema rather than editing an immutable
  older migration keeps the authority where a reader will look.
- `memory.NewJobRunner` / `NewDefaultJobRunner` accept extra handlers keyed by job kind (duplicate kind = boot error),
  and **both** composition roots (`cmd/worker/main.go`, `cmd/api/worker.go`) register
  `"withdrawal_sweep"` → a closure over `account.Service.SweepWithdrawnAccount`. The adapter lives in the composition
  root, which is the one place allowed to see both contexts; `account` never imports `memory` and `memory` never
  imports `account`.
- **Named debt:** the `jobs` table is a platform queue living in a context package. If a third context needs it, the
  right move is promoting `jobs`/`job_targets` to `platform`. That refactor is deliberately out of scope; no v2
  decision authorizes it and this unit needs only a scheduling call.

### RPC contract (`cosimosi.account.v1.AccountService`, Connect, unary — §2.7)

Both are mutations: POST, **not** `NO_SIDE_EFFECTS`, therefore no entry in
`packages/client-cache/src/http-policy.ts` (which accepts only unary `NO_SIDE_EFFECTS` reads). Handlers in
`account/rpc` map proto↔domain and call the use-case; the window guard, the pairing and the purge order live in the
use-case (§2.9 #7).

```proto
// Withdraw — account-scoped soft delete; restorable for release.soft_delete_retention_days ([U10][X2]).
rpc Withdraw(WithdrawRequest) returns (WithdrawResponse);
// RestoreAccount — undo inside the window ([U10][X2]). The one procedure a withdrawn scope may call.
rpc RestoreAccount(RestoreAccountRequest) returns (RestoreAccountResponse);

message WithdrawRequest {}          // scope comes from platform.UserScope, never the wire
message WithdrawResponse  { string withdrawn_at = 1; string restore_deadline_at = 2; } // RFC3339 UTC
message RestoreAccountRequest {}
message RestoreAccountResponse { string restored_at = 1; }
// NOTE: no user_id, no "purge_now"/"skip_window"/"immediate" field, no reason/exit-survey text, and no
// PurgeAccount method anywhere in this file. The 30-day window and the sweep-only hard delete are
// unrepresentable to bypass from a client ([I1][X2]) — that absence is the guarantee.
```

New taxonomy reasons, mirrored in `packages/errors/src/core.ts` (one concept, both sides —
[59.error-taxonomy-and-handling](59.error-taxonomy-and-handling.md)): `PLATFORM_ACCOUNT_WITHDRAWN` (in `apperr`, since
`platform` raises it), `ACCOUNT_NOT_WITHDRAWN`, `ACCOUNT_RESTORE_WINDOW_EXPIRED` (in `account/rpc/reasons.go`).

### The two [I1] gates

1. **Hard-delete allowlist.** `scripts/check-persistence-isolation.mjs` gains a set keyed like the existing
   `globalQueries` (`<dir>/<file>#<sqlcName>`): a `DELETE` whose target table declares `user_id` and is not a
   `platformTables` entry must appear in it. The initial contents are exactly the shipped release-sweep and
   queue-maintenance statements plus this plan's purge statements. Any future plan that deletes user product data from
   anywhere else fails `pnpm lint:persistence` — [I1] becomes a gate instead of a habit.
2. **Completeness test.** An integration test enumerates every table in `db/migrations/*.sql` that declares a
   `user_id` column, minus `platformTables`, seeds one row per table for a user, runs the sweep, and asserts zero
   remaining rows (with the in-flight job row as the single declared exception). A per-user table added by plan 71 or
   74 **fails this test until its purge leg is registered**, which is how the two missing legs are guaranteed to
   arrive.

### Golden-parity stance

No pure function is mirrored TS↔Go by this unit. It is transactional writes, an admission decision and scheduled
deletes; the only shared number is `release.soft_delete_retention_days`, already generated to both sides by
`pnpm gen:values`, and the restore deadline is derived from it server-side and sent as a timestamp so no client
recomputes it. [00.overview](00.overview.md) §4 classifies this unit as headless and shared by construction, so there
is no web↔mobile parity obligation either.

## Acceptance Criteria

1. `Withdraw` stamps `users.deleted_at` with real-clock UTC and pairs it with exactly one scheduled sweep job due at
   `deleted_at + release.soft_delete_retention_days`; it creates **no** withdrawal ledger, group table, or per-effect
   rows. ([U10][X2])
2. `Withdraw` is idempotent: a second call inside the window returns the original `withdrawn_at` /
   `restore_deadline_at` and neither extends nor shortens the window, and the dedup key yields exactly one queued
   sweep. ([U10])
3. Every authenticated procedure except `RestoreAccount` is refused for a withdrawn scope **before any context read**,
   with `PLATFORM_ACCOUNT_WITHDRAWN` and `withdrawn_at` / `restore_deadline_at` metadata; the interceptor fails closed
   on lookup error or an unbound reader, and an absent `users` row is treated as not withdrawn. ([U1][U10])
4. A withdrawn user cannot obtain a new account without restoring: `SignUp` is refused for a scope whose `users` row
   carries `deleted_at`, so the [U11] signup bonus cannot be re-claimed by withdrawing. ([U11][G6])
5. `RestoreAccount` clears `deleted_at` and cancels the scheduled sweep inside the window, and refuses with
   `ACCOUNT_NOT_WITHDRAWN` or `ACCOUNT_RESTORE_WINDOW_EXPIRED` outside it; a failed cancellation cannot cause a purge,
   because the sweep re-derives due-ness from `users.deleted_at`. ([U10][X2])
6. After `RestoreAccount` the account is whole with no compensating writes: twinkle balance and ledger are unchanged, a
   stale `SMALL` anchor derives a fresh full grant with no carry, and ornament ownership/selection plus
   `achievement_progress.claimed_at` are restored rather than re-granted (no reward is paid twice). ([U10][G2])
7. The hard delete has **no client-reachable trigger**: no `PurgeAccount` RPC exists, `WithdrawRequest` carries no
   immediate-delete / window-skipping field, and no per-user request in `cosimosi.account.v1` carries a `user_id`.
   ([I1][U1])
8. The sweep runs only from the scheduled `withdrawal_sweep` job, reuses `release.soft_delete_retention_days` and the
   shipped `jobs` worker loop (no cron, no second retention key), fires for a user who never returns, no-ops when
   `deleted_at` is null, and retries at the true deadline when claimed early. ([I1][X2])
9. The sweep hard-deletes every per-user row of the withdrawn account across all registered contexts — memory
   aggregate + diaries + provenance + receipts + `universe_state` + `release_*`, twinkle balance + ledger,
   `auth_providers`, the user's own `invites`, `palette_preferences` while it exists — then the Supabase credential,
   then the `users` row; each leg is per-context, per-user-scoped, and idempotent under replay. ([I1][U1][X2])
10. The sweep never deletes another user's or the operator's rows: `invites` are purged only by `invites.user_id`
    (never `invitee_user_id`), an invite naming the withdrawn user as invitee survives as a null-tolerated dangling
    reference, already-credited counterpart ledger rows are untouched, and no `admin_*` row is touched. ([U1][I1])
11. Restore and sweep are mutually exclusive and crash-safe in either order: `users.deleted_at` is the single source of
    truth for both withdrawn-ness and due-ness, and the `users` row is deleted last as the completion marker.
    ([X2][I1])
12. `pnpm lint:persistence` passes, and its new hard-delete allowlist fails any `DELETE` on a `user_id`-bearing product
    table outside the release sweep and this unit's purge statements. ([I1][U1])
13. An integration test enumerates every `user_id`-bearing table from the migrations (minus operator tables) and
    asserts the sweep leaves zero rows for the swept user, with the in-flight job row as the only declared exception —
    so a later plan's new per-user table fails until its purge leg is registered. ([I1][U1])
14. Production refuses to boot when the scheduler, the credential directory, or the purge-leg set is unbound, and both
    worker composition roots handle `withdrawal_sweep` (a dead-lettered withdrawal job is a failing test, not a silent
    retention leak). ([I1])
15. `Withdraw` / `RestoreAccount` are POST mutations with no `NO_SIDE_EFFECTS` option and no
    `packages/client-cache/src/http-policy.ts` entry; handlers stay thin (map + call) and no proto or sqlc type reaches
    the use-case. (§2.7/§2.9 #4/#7)
16. `Export` is unchanged and callable up to the moment of withdrawal, and the withdrawn account's diaries stay intact
    and exportable for the whole window — no `Diary` body is ever updated by this unit. ([W6][I2])
