# 74. achievement catalog model

> Achievement catalog model — the domain foundation of Epic O: a NEW `internal/achievement` supporting context that owns
> the **catalog** (`Achievement` = one condition + one reward, a Go table in code), the **counter store** every condition
> is evaluated against, and `AchievementProgress` (achieved-at · claimed-at · claim id). The hard decision is [A1a]: the
> service receives **no clock**, a `Condition` has **no time-typed field**, and the store keeps **no per-event row** — so a
> streak or a consecutive-login condition is unrepresentable, not merely forbidden. It ships the read (`ListAchievements`†)
> and leaves every write to a sibling. Scope: BE | Status: **built** (job 113)
>
> Layer D. Home: `apps/api/internal/achievement` (+ `achievement/pg`, `achievement/rpc`), `proto/cosimosi/achievement/v1/`,
> `apps/api/db/queries/achievement/`, migration **`00025`** (`00023`/`00024` were taken by the time this landed —
> reserved from the tree, §5.6). It fills the Epic O model seam and deliberately leaves open the
> progress-recording seam ([75.achievement-tracking-usecase](75.achievement-tracking-usecase.md)) and the whole
> presentation seam ([76.achievement-ui](76.achievement-ui.md)). As-built rules:
> [tech/achievements.md](../tech/achievements.md); domain policy: [policy/domain/achievements.md](../policy/domain/achievements.md).

## Purpose

v2 runs an **unmonetized** economy: payment moves to v3 ([G3]), so the only things that fund a user's `GENERAL`
Twinkle are the write-diary earn, the invite settlement, and **achievements** ([A3]). Achievements are therefore not a
decoration on the product — they are one of three supply lines for the currency that buys ornaments ([P9]) — and they are
promised to be reachable _by using the product normally_ ([A1]). Nothing in the shipped system models them: there is no
`internal/achievement`, no `achievement_progress` table, no `cosimosi.achievement.v1` package. This unit creates that
model.

The interesting problem is what an achievement is **allowed to measure**. cosimosi has one clock and it is universe time
([T3][T5]); the only sanctioned crossing into real time is the daily `SMALL` refill, which _paces a grant_ and is isolated
to `internal/twinkle` ([65.twinkle-kind-redefinition](65.twinkle-kind-redefinition.md)). A streak achievement would
create a second clock the user competes against — so [A1a]
bans real-world-time conditions outright, and [A1] bans conditions that reward abnormal behavior. Prose bans drift. This
unit therefore spends its structural budget on making the banned thing **unsayable**: a condition is a pair
`(counter key, integer target)` with no third field; the service has no `Now` and no clock port in its deps; the two
timestamp columns are written by PostgreSQL `now()` inside the SQL, so no Go call site in the context can read a clock at
all; and the store holds **aggregates, never events**, so "how many days in a row" has no query that could answer it.

The second problem is scope creep into the meaning layer. [A6] extends [I11]: an achievement must not move a star's
position, strength, emotion, forgetting, or gist stage. The guard is the same shape — the context's only tables are its
own two, it holds no read port into `memory`, and the recorded progress payload is `(scope, counterKey, delta)` with no
field for a memory id, a strength, or any text. An achievement literally cannot name a star. Finally, [I4]: a
constellation is emergent and has no type or table, so **cluster size is not a condition** — [A2] already carries that
correction, and this unit's counter vocabulary counts `NeuronActivation` rows on one neuron, a stored fact, instead.

## Design

### Placement (ARCHITECTURE §2.2/§2.3 + the context recipe)

Achievement progress has its own aggregate (`AchievementProgress`), its own lifecycle (counter accumulation → achieved →
claimed), and its own tables — so by §2.2 it is a **supporting context**, `apps/api/internal/achievement`, exactly as
plan 43 argued for `twinkle`. Files: `doc.go` (the charter, naming both guards), `types.go`, `catalog.go`, `service.go`,
`ports.go`, `errors.go`, `achievement/pg/store.go`, `achievement/rpc/{server.go,reasons.go}`. Constructor
`achievement.NewService(AchievementServiceDeps{...}) (*achievement.Service, error)`. Composition root
`apps/api/cmd/api/achievement.go` exposing `achievementServiceOption(...) (platform.HandlerOption, error)` and
registering via `platform.WithRPCService` + `achievementv1connect.NewAchievementServiceHandler`. Queries live in
`apps/api/db/queries/achievement/` — the directory name **must** equal the context name because
`scripts/check-persistence-isolation.mjs` keys on `<dir>/<file>#<sqlcName>`. `achievement` imports no other context; the
context is not importable _from_ one either, since every edge is a composition-root adapter.

### Catalog in code, progress in the DB, progress-value derived

Three artifacts, deliberately in three places:

1. **The catalog is a Go table** (`catalog.go`): `[]Achievement` with `ID` (a stable snake_case string, e.g.
   `first_diary`, `diary_50`), `Axis`, `Condition`, `Reward`. Content, not values — the amounts a reward _tier_
   resolves to are the only numbers in `values.yaml`. There is **no `achievements` table**; PRD §3.2 and UL §1.1
   are amended to drop the `(achievements)` parenthetical.
2. **The counters are stored facts** (`achievement_counters`): one row per `(user_id, counter_key)`.
3. **Progress is derived, never stored** (§2.5, §2.9 #3): `Progress = min(counter, target)` computed at read.
   `achievement_progress` stores only what cannot be derived — _when_ the condition was first met and _when_ the reward
   was received. A user who has never achieved anything has zero rows in it.

**As-built: the read's statement order is load-bearing.** The read is two statements, and **progress is read first**. A
recorder committing between them is visible to one and not the other; reading progress first makes the counter read a
strictly later snapshot, and counters are monotonic — so any achievement whose row already exists must also satisfy
`counter >= target` in that later read. The contradiction "achieved, 0/5" is therefore unrepresentable, with no read
transaction and no isolation-level dependency (the same ordering argument `store.Catalog` already uses). The worst a race
produces is a just-achieved row whose `achieved_at` arrives on the next read.

### The counter vocabulary (closed set, two accumulation modes)

Every condition reads exactly one counter. The producing contexts push deltas through the counter-only recorder port —
`RecordProgress(ctx, scope, tx, counterKey string, delta int)` — so the caller declares no semantics beyond a key and a
number. The **mode** belongs to the counter definition in `achievement`, never to the call site: for
`accumulate` keys the value is added; for `reach` keys the stored value becomes `GREATEST(value, delta)` — a high-water
mark, which is how "단계 도달" ([A1a]) is expressed without a rate or a window. Because the caller has no field in which
to declare a mode, a producer cannot invent a third accumulation semantics.

**Two derived counters, maintained by `achievement` itself**, are the closed exception to "producers push everything":
`mood_variety` and `ornament_kind_variety`. Distinctness is a property `achievement` can prove because it owns the table:
the counter write is `INSERT … VALUES (user_id, key, 0) ON CONFLICT DO NOTHING` (`:execrows`) followed by the add/raise,
so a `1` from the insert **is** first touch, and the same transaction bumps the family's variety counter by one. No
`xmax`, no dynamic SQL, no second condition kind — every condition stays a single-counter integer comparison.
`mood_variety`'s ceiling is 13, the `MOODS` length in `packages/emotion/src/mood.ts` ([M2]); `ornament_kind_variety`'s is
**2**, the `OrnamentKind` arity after change 08 retired `PALETTE`. Each ceiling is asserted against its family's length,
never written as a literal.

The key set is **closed**. `achievement` exports the set (and family membership) so a composition-root test can assert
that every producer's local key constant is a member — the drift guard, since a producing context cannot import
`achievement`'s constants. At runtime an unknown key is a wiring fault (`ErrUnknownCounterKey`) that fails its
transaction, which is safe precisely because the membership test makes the typo a test failure first.

### `Condition` and `Reward` — the two shapes that make the bans unsayable

```go
type Condition struct {          // exactly two fields, forever
    Counter CounterKey           // one of the closed set above
    Target  int                  // "누적 N" or "단계 N 도달"
}

type Reward struct {             // exactly one of the two is set
    Tier       RewardTier        // RewardTierNone | RewardTier1 | RewardTier2 | RewardTier3
    OrnamentID string            // an opaque plan-71 achievement-only id; "" for a stardust reward
}
```

- **No time type, no duration, no window, no second counter, no comparison operator** on `Condition`. A streak, "N per
  day", "consecutive logins", "within 7 days" and "counter A while counter B" have nowhere to live ([A1a][A1]). The
  comparison is fixed at `counter >= target`; there is no operator field to invert it.
- **No `TwinkleKind` field** on `Reward`. [A3]'s "`SMALL` 별가루를 보상으로 주지 않는다" is unexpressible, not validated:
  the reward names a tier, and plan 75's payout port is `EarnAchievementReward`, which credits the permanent tier by
  construction ([75.achievement-tracking-usecase](75.achievement-tracking-usecase.md)). The **amount** never appears
  in the catalog — `Tier` resolves through `achievement.reward_tier_{1,2,3}`, so re-balancing rewards is a values
  edit, not a code edit.
- **Exactly one leg per reward.** `Tier == RewardTierNone` iff `OrnamentID != ""`, asserted by a catalog self-test that
  also asserts: unique ids, non-empty axis, `Target >= 1`, every `Counter` in the closed set, and — at the composition
  root, where both catalogs are visible without a context import — that every `OrnamentID` resolves to an ornament plan
  71 marks achievement-only ([P11]).
- **`AchievementServiceDeps` is `{Repo}`** — a store and nothing else. No `Now`, no clock, no id minter for the read
  path. Compare `twinkle.ServiceDeps`, which _does_ carry `Now` because a daily reset window needs one; achievement has
  no legitimate use for a clock, so it is not given one.

### Tables (goose migration `00025_achievement_progress.sql`)

Migration numbers are reserved **from the tree** ([00.overview](00.overview.md) §5.6). At implement time `00023` was
the palette-preferences drop and `00024` the store ornaments, so this unit took the next free number, **`00025`**. Both
`-- +goose Up` and `-- +goose Down`, each table preceded by a comment naming its invariant tags.

```sql
-- achievement_counters — the cumulative facts every Achievement condition is evaluated against
-- (plan 74, [A1a][A2][U1]). One row per (user, counter_key). `value` is a monotonic sum for
-- accumulate-mode keys and a high-water mark for reach-mode keys; the mode lives in the in-code
-- catalog, not here. There is deliberately NO per-event row and no event timestamp: an aggregate
-- cannot answer "how many days in a row", so a streak condition is unanswerable from this schema.
CREATE TABLE achievement_counters (
    user_id     TEXT        NOT NULL,
    counter_key TEXT        NOT NULL,
    value       BIGINT      NOT NULL DEFAULT 0,
    updated_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (user_id, counter_key),
    CHECK (value >= 0)
);

-- achievement_progress — the two non-derivable per-achievement facts ([A4][U1]): when the condition
-- was first met, and when the reward was received. Progress itself is NOT stored — it is derived at
-- read from achievement_counters against the in-code target (ARCHITECTURE §2.9 #3). The PK is the
-- double-payout guard; claim_id is the dedup key both reward legs carry. Rows are never
-- deleted except by the withdrawal sweep (plan 62), and achieved_at is never cleared ([I1]).
CREATE TABLE achievement_progress (
    user_id        TEXT        NOT NULL,
    achievement_id TEXT        NOT NULL,
    achieved_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    claimed_at     TIMESTAMPTZ,
    claim_id       TEXT,
    PRIMARY KEY (user_id, achievement_id),
    CHECK ((claimed_at IS NULL) = (claim_id IS NULL))
);
```

`achieved_at` and `claimed_at` are stamped by **`now()` in SQL** — the DDL default on insert, `SET claimed_at = now()` on
claim. This is not a stylistic choice: it is what lets the Go context own no clock ([A1a]). No index beyond the two
primary keys is needed — every read is `WHERE user_id = $1`, which the PK prefix serves.

### sqlc queries (this plan owns all of them)

`apps/api/db/queries/achievement/achievement.sql`, plain static sqlc with no dynamic pgx (the isolation gate
scans only `db/queries/**/*.sql`, so a hand-built string would escape [U1] entirely):

| query                                                           | kind        | purpose                                                                                                                   |
| --------------------------------------------------------------- | ----------- | ------------------------------------------------------------------------------------------------------------------------- |
| `ListAchievementCounters`                                       | `:many`     | every counter for the caller — the read path's single counter fetch                                                       |
| `ListAchievementProgress`                                       | `:many`     | every progress row for the caller                                                                                         |
| `GetAchievementProgress`                                        | `:one`      | one row (plan 75's claim precondition)                                                                                    |
| `CreateAchievementCounter`                                      | `:execrows` | `INSERT … VALUES ($1,$2,0) ON CONFLICT (user_id, counter_key) DO NOTHING` — the first-touch signal                        |
| `AddAchievementCounter`                                         | `:one`      | `SET value = value + $3` for accumulate keys, `RETURNING value`                                                           |
| `RaiseAchievementCounter`                                       | `:one`      | `SET value = GREATEST(value, $3)` for reach keys, `RETURNING value`                                                       |
| `MarkAchievementAchieved`                                       | `:execrows` | `INSERT INTO achievement_progress (user_id, achievement_id) … ON CONFLICT DO NOTHING`                                     |
| `ClaimAchievementReward`                                        | `:execrows` | `SET claimed_at = now(), claim_id = $3 WHERE … AND claimed_at IS NULL` — a second claim affects 0 rows, before any credit |
| `PurgeUserAchievementCounters` / `PurgeUserAchievementProgress` | `:exec`     | the withdrawal sweep's purge (plan 62) — see below                                                                        |

Every statement scopes `user_id` conjunctively; the two upserts use `ON CONFLICT … DO NOTHING` (never `DO UPDATE`), so the
isolation gate's conflict-target rule is satisfied by the PK itself. `pnpm lint:persistence` passes with **no**
`globalQueries` and no `platformTables` entry; the two purge deletes are registered in the gate's `hardDeleteQueries`
allowlist, the same leg the store purges sit in.

### Ports (consumer-owned, §2.4/§2.9 #6)

```go
// Store is achievement/pg's surface, bindable to a caller's transaction so a counter write
// commits or rolls back with the launch/recall/decorate that caused it (the shared-tx recorder port).
type Store interface {
    ListCounters(ctx, scope) (map[CounterKey]int64, error)
    ListProgress(ctx, scope) ([]ProgressRecord, error)
    GetProgress(ctx, scope, achievementID string) (*ProgressRecord, error)
    TouchCounter(ctx, scope, key CounterKey) (created bool, err error)
    AddCounter(ctx, scope, key CounterKey, delta int) (int64, error)
    RaiseCounter(ctx, scope, key CounterKey, level int) (int64, error)
    MarkAchieved(ctx, scope, achievementID string) (marked bool, err error)
    MarkClaimed(ctx, scope, achievementID string, claimID string) (claimed bool, err error)
    PurgeUser(ctx, scope) error   // both tables, this user only — the withdrawal sweep's leg (plan 62)
}

// Repo adds the own-transaction runner the RPC-driven paths use.
type Repo interface {
    Store
    InAchievementTx(ctx context.Context, fn func(tx Store) error) error
}
```

`achievementpg.NewStore(db dbgen.DBTX) Store` mirrors `twinklepg.NewStore` verbatim, so the composition root can bind it
onto a producer's transaction through the `interface{ DB() dbgen.DBTX }` assertion plan 75 uses. The write methods
ship here (this plan owns the SQL) and are **called** first by plan 75 — the 43→44 precedent, where the table's owner
provided the primitives and the use-case composed the transaction.

**As-built: three write rules live in the domain, not in the adapter**, so the store cannot be the place they are
relaxed and plan 75's composition reuses them verbatim:

- `RequireForwardDelta(delta)` — monotonicity ([I1]).
- `RequireCounterMode(key, mode)` — a statement is **bound to its key's declared mode**. Without this the mode would be
  the caller's choice after all: `AddCounter(semantic_stage_depth, 1)` four times would unlock the stage-4 row without
  the user ever reaching stage 4. `AddCounter` accepts only accumulate keys, `RaiseCounter` only reach keys.
- `RequireCatalogID(id)` — a progress write for an unpublished id is refused, so a typo cannot leave a durable row no
  read will ever answer for and a later claim could still mark paid.

`MarkClaimed` additionally refuses an **empty claim id**: the DDL `CHECK` only pairs `claimed_at` with `claim_id`, and an
empty string satisfies it while collapsing every claim into one dedup identity. `DerivedCounterKey(key)` is exported for
plan 75's recorder to refuse a producer pushing `mood_variety`/`ornament_kind_variety` directly — distinctness those
callers cannot prove.

### Proto contract (`cosimosi.achievement.v1`)

New file `proto/cosimosi/achievement/v1/achievement.proto`, `buf lint STANDARD`, unary only:

```proto
service AchievementService {
  // The whole catalog with this caller's progress. Free, read-only, no clock advance.
  rpc ListAchievements(ListAchievementsRequest) returns (ListAchievementsResponse) {
    option idempotency_level = NO_SIDE_EFFECTS;
  }
}

message ListAchievementsRequest {}   // empty by design — scope comes from platform.UserScope, never the wire

message ListAchievementsResponse { repeated AchievementEntry entries = 1; }

message AchievementEntry {
  string achievement_id      = 1;  // stable catalog id; the FE resolves all copy from it
  AchievementAxis axis       = 2;  // the UI's grouping key — no group label crosses the wire
  int64  target              = 3;
  int64  progress            = 4;  // min(counter, target) — derived server-side, never stored
  int32  reward_twinkle      = 5;  // GENERAL amount resolved from values; 0 for an ornament reward
  string reward_ornament_id  = 6;  // empty for a stardust reward
  bool   achieved            = 7;
  bool   claimed             = 8;
  string achieved_at         = 9;  // RFC3339 UTC, empty when unachieved (the memory.v1 string-time convention)
}
```

- **No `user_id` field anywhere** — a per-user achievement request with a user id would be a review-blocking
  defect, and the message has no such field to misuse.
- **No `TwinkleKind` field** — the wire cannot express a `SMALL` reward ([A3]).
- **No copy.** Titles, descriptions and axis labels are FE-side, resolved from `achievement_id` / the axis enum, following
  the shipped `mood_<value>` + `moodLabel` projection precedent (`packages/emotion/src/mood-label.ts`). The i18n key
  family `achievement_<id>_title|_body` is plan 76's deliverable.
- `AchievementAxis` is achievement-owned with the `ACHIEVEMENT_AXIS_UNSPECIFIED = 0` prefix form; no enum is reused across
  contexts.
- Entries are returned in a **server-fixed order** (axis order, then target ascending), so no client sorts the catalog.
- `ListAchievements` is classified **exactly once** in `packages/client-cache/src/http-policy.ts` as an authenticated,
  user-scoped, non-shared-CDN GET; the production transport hard-fails on a missing/duplicate classification before I/O
  (ARCHITECTURE §2.7) — that is the guard, no runtime check is added.
- Refusals: `ACHIEVEMENT_SCOPE_REQUIRED` only (`achievement/rpc/reasons.go` + one entry in
  `packages/errors/src/core.ts`, following the `TWINKLE_SCOPE_REQUIRED` shape). The read has no other failure mode: an
  unknown catalog id cannot be requested because nothing is requested.

### What plan 75 extends, stated so the seam is not re-litigated

`cmd/api/achievement.go` ships here with the read wiring only. Plan 75 adds: the producer-side `AchievementRecorder`
ports in `memory`/`store`/`account`, the composition-root adapters, `Service.RecordProgress` (which composes
`TouchCounter` → `Add|RaiseCounter` → the variety bump → `MarkAchieved` for every catalog row on that counter),
`ClaimAchievement` + its two reward ports, the `ACHIEVEMENT_*` claim refusals, and the fail-closed boot gate.
This plan adds no producer port and no `RecordProgress`, so nothing here can record progress by accident.

### Golden-parity stance

**No pure function in this unit is mirrored TS↔Go, and no golden fixture is added.** The two pure functions
(`Achieved(counter, target) = counter >= target` and `Progress = min(counter, target)`) read **no tuned coefficient and no
formula** — unlike plan 43's price curves, which the FE must recompute pre-spend to price a recall without a round-trip.
Here the server is the only evaluator and it sends `progress`/`achieved`/`reward_twinkle` already resolved, so a TS mirror
would duplicate the whole catalog's content with nothing to gain and a drift surface to police. `@cosimosi/achievement`
(plan 76) therefore carries DTO mirrors and display formatting only — **no condition table, no target, no
evaluation**. This unit is headless and shared by construction, so the parity matrix in
[00.overview](00.overview.md) §4 does not apply to it.

## Acceptance Criteria

1. A new supporting context `apps/api/internal/achievement` exists with `doc.go`, `types.go`, `catalog.go`, `service.go`,
   `ports.go`, `errors.go`, `pg/`, `rpc/` and **no** empty `domain/`/`app/` directory; it imports no other `internal/`
   context, and only `achievement/pg` imports `dbgen` (ARCHITECTURE §2.3/§2.4/§2.9 #2).
2. `AchievementServiceDeps` contains **no clock, no `Now` func and no time-typed field**, and no file under
   `internal/achievement` calls `time.Now`; `achieved_at`/`claimed_at` are written by SQL `now()` ([A1a]).
3. `Condition` has exactly two fields — a counter key and an integer target — with **no** time, duration, window,
   operator or second-counter field, so a streak / consecutive-login / per-day condition cannot be constructed ([A1a][A1]).
4. `Reward` has **no `TwinkleKind` field**; a stardust reward names a tier resolved from `achievement.reward_tier_{1,2,3}`
   and carries no literal amount, and exactly one of tier / ornament id is set per row (catalog self-test) ([A3]).
5. Goose migration `00023_achievement_progress.sql` (number reserved from the tree, §5.6) creates `achievement_counters (user_id, counter_key, value BIGINT,
updated_at, PK (user_id, counter_key), CHECK (value >= 0))` and `achievement_progress (user_id, achievement_id,
achieved_at, claimed_at, claim_id, PK (user_id, achievement_id), CHECK ((claimed_at IS NULL) = (claim_id IS NULL)))`;
   `pnpm db:migrate` applies and `pnpm db:down` reverses cleanly ([A4][U1]).
6. Neither table stores a per-event row or an event timestamp, and **no query in
   `db/queries/achievement/` performs date arithmetic** on any column ([A1a]).
7. `user_id` is part of both primary keys, every statement in `db/queries/achievement/achievement.sql` is conjunctively
   user-scoped, and `pnpm lint:persistence` passes with **no** new `platformTables` or `globalQueries` entry ([U1]).
8. There is **no `achievements` table**: the catalog is a Go table in `catalog.go`, and PRD §3.2 + UL §1.1 are amended to
   drop the `(achievements)` parenthetical ([A2]).
9. The counter-key set is **closed**, every key is reachable (read by a condition, or a family member feeding a variety
   counter — no orphan key), and each key has **exactly one** mode: accumulate (`value + delta`) or reach
   (`GREATEST(value, delta)`), enforced per statement so a reach key cannot be accumulated into. An unknown key is
   refused as a wiring fault, and a composition-root test asserts every producer key constant is a member ([A2][A1a]).
   _(As-built correction: "every key maps to exactly one [A2] axis" is **not** what the design guarantees and never was
   — the plan's own catalog puts `diary_written` under both `FIRST_EXPERIENCE` (target 1) and `DIARY_TOTAL`
   (5/20/50/200), and the vocabulary table above says so ("일기 누적 · 첫 경험"). What is guaranteed is one **mode** per
   key and no orphan key; a "first" row and a totals row legitimately share a counter.)_
10. `mood_variety` and `ornament_kind_variety` are maintained **inside `achievement`** by first-touch detection on their
    key families (`ON CONFLICT DO NOTHING` `:execrows`), so every condition remains a single-counter integer comparison;
    `mood_variety` cannot exceed 13, the `MOODS` length ([M2][A2]). _(As-built: `ornament_kind_variety`'s ceiling is **2**,
    not 3 — `OrnamentKind` closed at `BACKGROUND`/`STAR_SHADER` when change 08 retired `PALETTE` before it shipped, so the
    `DECORATION` axis's variety row is `ornament_kind_2`. Both ceilings are asserted against their family's length rather
    than written as literals, so the arity moves the capstone.)_
11. Counters are **monotonic** (no decrement path exists; the domain refuses `delta <= 0`) and `achieved_at` is never
    cleared — letting go, releasing a diary, or un-selecting an ornament never revokes an achievement or lowers a counter
    ([I1][A1]).
12. **No counter counts a constellation, a cluster, or a connected component.** The 별자리-규모 axis reads
    `neuron_share_depth` — activations on one `Neuron` — and no condition references an emergent structure ([I4], [A2]'s
    own correction).
13. `achievement` declares **no port into `memory`/`twinkle`/`store`/`account`** and queries only its own two tables; no
    type in the context carries a memory id, star, strength, mood, position or text field ([A6][I11]).
14. `proto/cosimosi/achievement/v1/achievement.proto` defines `AchievementService.ListAchievements` with
    `idempotency_level = NO_SIDE_EFFECTS`, an **empty** request message, no `user_id` field on any message, no
    `TwinkleKind` field, and no user-facing string field; `buf lint` passes and the method is classified **exactly once**
    in `packages/client-cache/src/http-policy.ts` as a user-scoped, non-shared-CDN GET ([U1][U9], ARCHITECTURE §2.7).
15. `ListAchievements` returns every catalog row with `progress = min(counter, target)` computed at read (no `progress`
    column exists), `achieved`/`claimed` flags, the resolved `reward_twinkle`, and a **server-fixed order**; a user with
    no rows in either table gets the full catalog at zero progress ([A4][U9], ARCHITECTURE §2.9 #3).
16. `ClaimAchievementReward` sets `claimed_at`/`claim_id` only when `claimed_at IS NULL`, so a second claim affects zero
    rows before any credit; the `PRIMARY KEY (user_id, achievement_id)` is the double-payout guard ([A4]).
17. The RPC handler is thin (map + call), carries no catalog logic, and its only refusal reason is
    `ACHIEVEMENT_SCOPE_REQUIRED` (ARCHITECTURE §2.9 #7).
18. No TS mirror of the catalog, the condition targets, or the evaluation exists, and no golden fixture is added — the
    server is the only evaluator (contrast [43.stardust-ledger](43.stardust-ledger.md)'s mirrored price curves).
