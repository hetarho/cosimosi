## Purpose

The archive shipped as a proof that the record survives: a reverse-chronological list whose closed row shows a date and
a CSS-clamped body, a 더 보기 button, and — only once opened — the mood chips of the memories the diary launched
([47.diary-reader-page](47.diary-reader-page.md), job 58). That is enough for [D2]'s "완전한 보조 역할" and nothing more.
[D6] asks for a row that can actually be scanned: the date, a preview whose length is a tuned number, the **count** of
stars born from the entry, and its **mood color dots** — the three facts that let a diarist recognise an entry without a
title. The product refuses a title field on purpose ([D6]: 작성 마찰 최소화, and `Diary` gets no `title` column), so the
row itself has to carry the recognition load.

Two more basics are missing. [D7] wants a newest/oldest toggle and pagination that holds up "대량 기록에서도" — the
shipped list has one direction and a manual button, a fine v1 answer and a poor archive. [D8]/[D9]'s search and filter
controls, whose reads land in [68.diary-search-and-filter](68.diary-search-and-filter.md), need a surface that composes
them without promoting the reader into a second main page.

The last job is the one easiest to lose. [D11] demands that the boundary between the free archive and the single paid
action be **visible**, not merely true: listing, previewing, searching, filtering and reading the original are free and
advance no universe time ([G4][T3]), while the [D3] jump spends 별가루 and syncs the clock. Today both sit in the same
row with the same visual weight. This unit gives the one paid door its own marking and makes the free surfaces
structurally incapable of pricing anything.

This is a completion, not a rebuild. The `GetDiaries` read, the DTO→domain mapper, the opened-entry verbatim body, the
split chips, the star-detail deep-link, the jump machine and its quote→consent→recall sequencing are shipped and stay
shipped.

## Scope / Non-goals

**In scope**

- **The [D6] row** — `features/read-diary-list` (both apps) renders, for a closed row: the `diary_date`, a body preview
  bounded by `diary_reader.body_preview_length`, the count of live stars born from the entry, and its mood color dots.
  No title, anywhere ([D6]).
- **`diaryPreview(body, length)`** — one pure, shared preview function in `packages/memory` beside `diariesFromDtos`:
  code-point safe, whitespace-collapsing, ellipsis-appending, client-side only ([D6]).

  primitive pair `segmented-control.tsx` / `segmented-control.native.tsx` — promoting the design system's **reserved
  deferred name** `SegmentedControl` (`spec/tech/design-system.md`'s promote-on-use list; inventing a `toggle-group`
  name would bypass that reservation).
- **The [D7] infinite scroll** — the 더 보기 button is removed; web loads the next keyset page from an
  `IntersectionObserver` sentinel, mobile from `FlatList onEndReached`. Web windows its rows with
  `@tanstack/react-virtual` (job 143), mirroring what `FlatList` already does on mobile.
- **The search + filter controls themselves** ([D8][D9]) — a NEW `features/search-diary` slice (both apps): the
  keyword field (debounced), the 13-mood chips behind their fold, and the `(diaryBody, query)` **highlighter**
  the rows render — the FE half [68](68.diary-search-and-filter.md) deliberately excludes ("No UI… are [69]").
  `widgets/diary-reader` mounts it above the list, binds it to one archive query, and owns the **no-results** state
  (distinct from an empty archive) with a clear-conditions action.
- **The web `/diary` search-param schema** — `validateSearch` carrying `{q, moods, from, to, sort}`, injected into the
  page as props by `route-screens.tsx`; mobile holds the same shared value in screen-local state.
- **The visual free-vs-paid boundary** ([D11][D3][D2]) — one restrained header line stating that reading and searching
  cost nothing and the universe clock stays still here, a paid marker on the single jump affordance, and the structural
  guarantee that no price/balance/spend can reach the free surfaces.
- **Copy + parity** — every new string through the i18n seam under the existing `diary_reader_*` prefix; the same
  page/widget/feature on web **and** mobile (`FlatList onEndReached` is the mobile answer).

- **No `title` column, no title UI, no server-side preview** ([D6]).
- **No new page, route, or slice.** `/diary`, `pages/diary-reader`, `widgets/diary-reader` and

### The [D6] row

Closed row, in reading order: `diary_date` as a `<time>` element — the row's primary line, so **there is no slot a title
could occupy** — then the preview, then a footer line carrying the star count and the mood dots.

- **Preview.** `diaryPreview(body, VALUES.diaryReader.bodyPreviewLength)`: collapse every run of whitespace/newlines to a
  single space, take the first N **code points** (`Array.from`, so a surrogate pair is never split), append `…` only when
  the body was longer; the ellipsis is not counted in N. CSS clamping / `numberOfLines` stays as a second, purely visual
  guard for narrow viewports — the length bound is the contract. Truncation is **client-side**: the wire already carries
  the verbatim body because the opened entry needs it ([I2][D4]).
- **Star count** = `diary.memories.length`, the live stars born from the entry. `0` for a never-launched past-dated diary
  ([T1]) or an all-let-go one ([X4]) — and the row still lists ([I1]).
- **Mood dots** = the **distinct** moods present in `diary.memories`, ordered by `MOODS` declaration order from
  `packages/emotion` (a deterministic client-side order that does not depend on the server's row order), each colored by
  `moodColor(mood)`. Capped at `diary_reader.row_mood_dot_max`, with the remainder collapsed into a `+N` marker.
  Deduplication is deliberate: a four-memory diary that is three-quarters 기쁨 should read as "two feelings, four stars",
  not as a wall of identical dots. Zero live memories ⇒ zero dots, and **never** `NEUTRAL`'s color, which would assert an
  emotion the user never recorded.
- **Accessibility.** Dots are decorative to assistive tech; a visually-hidden sibling names them through
  `packages/emotion`'s `moodLabel` (reuse the projection, add no `mood_*` keys). The star count is a translated
  string with a `{count}` placeholder, not a bare numeral.
- **The row opens the entry; it does not expand.** A press opens that diary as a modal the composing widget mounts over
  the archive — announced as such (`aria-haspopup="dialog"` on web, an `accessibilityHint` on mobile). An expanding row
  would push every row beneath it down and land the reader somewhere else in a long archive when it folded back, and on
  a windowed list its measured height would change under the virtualizer; the modal leaves the list where it stands, and
  dismissing it lands on the row that opened it. `openedDiaryId` therefore stays a prop of the list, but only as the
  index the web window virtualizer scrolls to, so a deep-linked entry sits under its own modal — no row renders a body.
- **The opened entry is one shared presentational component**, `DiaryEntry`: the verbatim body ([D4][I2]), the 2–5
  mood-named split chips ([D3]) or the quiet all-let-go note in their place ([I1]), and one action slot the composing
  widget fills. It is what **both** surfaces that open a diary render — this unit's per-diary modal and
  [70](70.diary-calendar-view.md)'s day modal — so a diary reads identically wherever it is reached from, and the
  entry's own props stay as free of cost, quote and spend as the list's.

### The [D7] sort toggle and infinite scroll

- **Sort** is a two-option `ToggleGroup` (`최신순` / `오래된순`) bound to the archive query's `sort` field. It sets a
  direction, and the direction selects one of [68](68.diary-search-and-filter.md)'s two static sqlc queries — the client
  never composes an `ORDER BY`. Changing it yields a new query key, hence a fresh keyset page 1; the list scrolls
  to top and any opened entry closes, because that entry may not be in the new result set.
- **Infinite scroll** replaces the button. Web: a zero-height sentinel after the last row, observed with
  `rootMargin = diary_reader.infinite_scroll_root_margin_px`, calling `loadMore()` while `hasMore && !isLoadingMore`.
  Mobile: `FlatList onEndReached` with `onEndReachedThreshold = diary_reader.infinite_scroll_end_threshold`. Both are
  idempotent against an in-flight fetch — the guard is the archive hook's already-exposed `isLoadingMore`.
- **Three terminal states, kept distinct:** loading-more (a polite live region on web, `ListFooterComponent` on mobile),
  end-of-archive (one quiet, **direction-neutral** line — "the end" is the oldest entry under 최신순 and the newest under
  오래된순), and **no results** (conditions are active and matched nothing) with a clear-conditions action. The shipped
  "아직 담아 둔 일기가 없어요" stays reserved for a genuinely empty archive; conflating the two is the bug this
  distinction exists to prevent.
- **Performance ([D7]).** Keyset pagination (never `OFFSET`), a length-bounded preview instead of a whole body in every
  closed row, and windowing on both apps: `FlatList` on mobile, `@tanstack/react-virtual`'s `useWindowVirtualizer` on
  web (job 143). `diary_reader.page_size` (= 20) stays both the default and the hard cap.
  - The web list is **window-scrolled** — the page scrolls, not a box inside it — so the virtualizer is the window one
    and the rows' document offset is measured from the list element and re-read whenever the document's box changes.
    Rows are absolutely positioned inside a `<ul>` that carries the full scroll height, with the row gap supplied by
    the virtualizer rather than a flex `gap`. The keyset sentinel keeps its place after that height, so it is still the
    true end of the archive that triggers the next page.
  - **As-built amendment (after this unit shipped):** the web list is a **grid** whose column count is the measured width
    divided by `diary_reader.row_min_width_px`, handed to the virtualizer as its **lane** count — so a wide desktop mounts
    a windowed row per lane rather than a multiple of the DOM, and the archive gains a column whenever the window has room
    for one instead of at a named breakpoint. A card's width and offset are percentages of the list, so a resize re-lays
    the grid without waiting for a measurement pass; a lane-count change re-measures, because the offsets taken under the
    previous count describe a layout that no longer exists. The overscan is scaled by the column count, so the same number
    of windowed ROWS stays mounted beyond each edge at every width. Mobile stays one column.
  - The row a reader has focused stays mounted after it scrolls out of the window; otherwise keyboard focus would fall
    to the document body mid-scroll. Rows outside the window are absent from the DOM and therefore from tab order —
    the one behavior windowing changes, and the reason the focused row is pinned.
  - `TwinkleLedgerList` and `AchievementList` are deliberately **not** windowed. The achievement list is the server's
    fixed 39-row catalog with no paging — it cannot grow with use. The ledger is paged and unbounded, but its rows are
    cut into day sections, so windowing it means first flattening headers and entries into one index space; window it
    when a real account's ledger reaches the low thousands.

### The archive query, and where its state lives

One list, **one** infinite query. `useDiaryArchive` is extended by [68](68.diary-search-and-filter.md) to take the
the request input (`{q, moods, from, to, sort}` — the generated `GetDiariesRequest` shape, no hand-written mirror
type); this unit consumes that single hook and must not mount a second infinite list
beside it — two caches over one visible list is how a filter and a sort silently disagree. It is also the read that
owns the shared diary mirror, so any other archive read on the screen (the calendar's day modal, [70]) reads without
writing it.

- **Web:** the query is URL-backed. `validateSearch` on the `/diary` route parses and defaults `{q, moods, from, to,
sort}`; `route-screens.tsx` injects the parsed value plus a setter into `DiaryReaderPage` as props. Pages and widgets
  never import the router — the callback-prop seam job 58 established. A filtered archive is therefore a shareable
  URL, and Back restores the previous conditions.
- **Mobile:** the same value in screen-local state. Only the holder differs; the _shape_ is shared, because both feed
  the same generated `GetDiariesRequest` input (no hand-written mirror type exists).
- **Schema ownership:** this unit owns the `/diary` search-param schema, because `sort` is its field and one route can
  only have one schema. [70.diary-calendar-view](70.diary-calendar-view.md) **extends** it with `view` and `month`; this unit does not
  pre-add that field.
- **No XState** (§3.2). Sort, filters, query text and pages are data (Query + URL/screen state); `diaryReaderMachine`
  keeps owning exactly the jump phases (`browsing → confirming → recalling → flying`).
- **Invalidation:** the two client helpers [68](68.diary-search-and-filter.md) owns move in opposite directions —
  `createGetDiariesInfiniteQueryOptions(transport, input)` gains the filter/sort input (the key embeds it), while the
  invalidation helper `createGetDiariesInfiniteQueryKey(transport)` **drops** `pageSize` and takes no input, so it
  renders as a partial key matching every filter/sort variant. This unit's only obligation is that the list re-derives from the hook, so
  an existing release/restore invalidation ([50.deletion-ui](50.deletion-ui.md)) makes a released row disappear and a
  restored row reappear with no local bookkeeping.

### The visible free-vs-paid boundary ([D11])

Three moves, one of them structural:

1. **One header line** under the reader title states the boundary plainly: reading and searching cost nothing, and the
   universe's time does not move here. Restrained, one sentence, not a banner.
2. **The one paid door is marked.** `RecallDiaryStarsAction` — the [D3] jump — carries a 별가루 marker beside the
   control, and that marker alone is what says this one costs; the copy stays one sentence and repeats nothing. It shows
   **no price** (the server quote is fetched once, in the jump dialog, per job 58) and performs no spend itself. Both it
   and the destructive delete live in the **opened entry**, never in a row: the paid door under the body it would act on,
   the delete as a danger-colored trash glyph in the entry's top-right corner, so **distance and form** are what keep the
   two apart — destructive is not the same as paid. That corner is the entry's own, not the modal's header: below `md`
   the header is the sheet's drag surface, and a press there that became a downward drag would be ambiguous between
   deleting the diary and dismissing it. The glyph is silent to the eye and named to assistive tech — its accessible
   name is the full 이 일기 지우기 action, and on web a tooltip says the same thing.
3. **The free surfaces cannot price anything, by shape.** `DiaryListProps` carries no cost, balance, quote or spend
   field, and `features/read-diary-list` imports no economy or clock module. The list has **no action slot at all**: a
   row is one press that opens an entry, and a paid or destructive affordance can only be mounted in the modal the widget
   opens over it. A contributor cannot put a price in a row without first adding a field that does not exist — which is
   the review-visible event ([D11]).

### Golden-parity stance

**No golden parity, deliberately.** `diaryPreview` is a presentation truncation with **no Go counterpart** and must never
acquire one: a server-side preview would put a second, derived rendering of the body on the wire — precisely the opening
[D10] closes, and a breach of [I2]'s "the wire carries the verbatim body and nothing derived from it". The dot
ordering (`MOODS` order) and the dedup rule are client-only and read no server value. The only cross-language contract
this unit touches is `spec/values.yaml` → `packages/config`, already guarded by `pnpm gen:values` + `pnpm check:gen`.

## Acceptance Criteria

1. A closed list row shows, and shows only: the `diary_date`, a body preview, the count of live stars born from the
   diary, and its mood dots. There is **no** title field, no title UI, and no `title` column on `Diary` ([D6]).
2. The preview is `diaryPreview(diary.body, VALUES.diaryReader.bodyPreviewLength)` — a whitespace-collapsed,
   code-point-bounded prefix of the **verbatim** body with a trailing `…` only when truncated. It is computed on the
   client; no `preview`/derived-text field exists on `DiaryDto`, and `CurrentText`/`DecayStages` are never read
   ([D6][I2][D4]).
3. `diaryPreview` lives in `packages/memory` and is imported verbatim by both apps; `segmented-control.tsx` /
   `segmented-control.native.tsx` (the design system's reserved `SegmentedControl`, promoted on use) live in
   `packages/ui/src/primitives/`. No byte-identical pure module is duplicated under
   `apps/*` — `pnpm lint:fsd:layout` R4 passes (§3.1/§3.5).
4. Mood dots are the **distinct** moods of `diary.memories`, ordered by `MOODS` declaration order, colored by
   `moodColor`, capped at `diary_reader.row_mood_dot_max` with a `+N` remainder marker; a diary with zero live memories
   shows a count of `0`, no dots and **no** `NEUTRAL` color, and still appears in the list ([D6][I1]).
5. Dots are decorative to assistive tech and are accompanied by a visually-hidden mood list built from
   `packages/emotion`'s `moodLabel`; no `mood_*` i18n key is added.
6. A newest/oldest toggle sets the archive query's `sort`; changing it starts a fresh keyset page, scrolls to the top and
   closes the opened entry. The client never composes an `ORDER BY` — the direction selects one of two static server
   queries ([D7]).
7. There is no 더 보기 button. Web loads the next page from an `IntersectionObserver` sentinel with
   `rootMargin = diary_reader.infinite_scroll_root_margin_px`; mobile from `FlatList onEndReached` with
   `onEndReachedThreshold = diary_reader.infinite_scroll_end_threshold`. Neither issues a second fetch while one is in
   flight, and both apps window their rows so the mounted count stays a viewport's worth however many pages are in
   hand ([D7]).
8. Loading-more, end-of-archive and **no-results** are three distinct, translated states; no-results (conditions active,
   zero matches) offers a clear-conditions action and is never shown for a genuinely empty archive ([D7][D8][D9]).
9. The list runs on **one** infinite archive query — `useDiaryArchive(input)` over `{q, moods, from, to, sort}` — and
   **this unit's** `features/search-diary` controls (the keyword field and the folded mood chips, with the
   `(diaryBody, query)` highlighter in the rows) are composed by `widgets/diary-reader` above it ([D8][D9]).
10. On web the query is URL-backed: `validateSearch` on `/diary` parses `{q, moods, from, to, sort}` and
    `route-screens.tsx` injects the value + setter as props; neither `pages/*` nor `widgets/*` imports the router. On
    mobile the same generated request shape lives in screen-local state.
11. This unit adds **no XState machine**: sort, filters, query text and pagination are Query/URL/screen data, and
    `diaryReaderMachine` still holds only the jump phases (§3.2).
12. The reader states its free, time-frozen nature in one restrained header line, and the [D3] jump is the only control
    carrying a paid marker — with no price rendered in any row (the quote appears only in the jump dialog)
    ([D11][D3][G4]).
13. `DiaryListProps` has **no** cost, balance, quote, spend or `query` field **and no action slot**, and
    `features/read-diary-list` imports neither `@cosimosi/twinkle` nor any quote/sync module. A row is one press that
    opens the entry (`aria-haspopup="dialog"` on web, an `accessibilityHint` on mobile) and carries no control of its
    own; the paid jump and the delete reach the reader only through the modal the composing widget opens over the list,
    where the shared `DiaryEntry` renders the verbatim body, its split chips and one action slot ([D11][T3][D10][D4]).
14. Listing, previewing, sorting, filtering, searching and opening an entry spend **no** 별가루 and advance **no**
    universe time; `GetDiaries` stays unary, GET-eligible and `NO_SIDE_EFFECTS` ([D11][G4][T3], §2.7).
15. A released diary is absent from the list and reappears after Restore with **no** local bookkeeping in this unit — the
    exclusion is [68](68.diary-search-and-filter.md)'s anti-join and the reappearance rides existing invalidation.
16. Every new string resolves through the i18n seam in both locales (`pnpm lint:raw-strings` and `pnpm check:gen` pass),
    `diary_reader_load_more` is removed, and the identical row, toggle, scroll behavior and copy ship on **web and
    mobile**.

## As built (job 106)

Four shapes the surface settles on, each deliberate:

- **The date range has no control of its own.** It stays a field of the read and of the `/diary` address (`from`/`to`),
  and `hasConditions` counts it, so a link carrying `?from=`/`?to=` filters the archive and still offers 조건 지우기 as
  the way out — but no form field on either platform writes it. A pair of typed ISO fields is heavy furniture on a page
  whose job is reading, and the archive's own way to a single day is the calendar ([70]).
- **The thirteen mood chips fold; the keyword and the way out do not.** The chips are two rows of colour most readings
  never touch, so they sit behind a toggle (`diary_search_mood_toggle`, reading plain 감정) while the keyword field
  stands in the open. The toggle is the panel's only name — on web the unfolded panel is a `role="group"` labelled by
  that same word, so no legend repeats it — the number chosen shows beside it (`diary_search_mood_selected`), and the way out of
  the conditions stays **outside** the fold, so a closed panel can neither hide an active filter nor take away the way
  out of one. That way out is a reset glyph (`ResetIcon`) carrying 조건 지우기 as its accessible name and, on web, as a
  tooltip: a correction beside the controls it undoes rather than a third labelled button on the line.
- **A chosen chip is lit in its own mood's colour** — that hue on the rim, a halo around it (a rim alone on RN, which
  has no glow), and the dot at full strength — while an unchosen one is a quiet outline holding a 40%-opacity dot.
  Choosing nothing is what shows everything, so the resting state has to read as **off**: thirteen fully-lit dots read
  as thirteen switches already thrown over an archive that is in fact unfiltered.
- **The highlighting seam is `renderBodyText`, not `renderPreview`,** and it renders the opened entry's verbatim body as
  well as the closed row's preview. Both are `diary.body`, so [D10] is unaffected; the wider name says what it does.

Three things the Design left implicit and the build had to settle:

- **The conditions commit through an update function**, not an object patch. The web host's conditions live in the URL
  and land a navigation later, so a patch built from a captured `value` let a mood chip erase a keyword that was still
  on its way in. `useDiaryConditions` in `@cosimosi/universe/react` owns the drafts and the commit rules for both
  platforms; the pure rules (`isKeywordSearchable` · `shouldAdoptCommitted`) live in `@cosimosi/memory` and are
  unit-tested without a DOM.
- **A refused condition is never committed.** A keyword below the minimum holds at the draft, so a half-typed word
  never replaces the archive with an error mid-keystroke. `parseDiarySearch` applies the same minimum and drops a
  non-ISO `from`/`to`, so a hand-shortened `?q=a` link still shows the archive.
- **A deep link lifts the conditions first.** `useDiaryArchive` fills the shared diary read-model, so a filtered archive
  narrows it; the star-detail 원본 일기 jump therefore clears the conditions before searching rather than paging a
  filtered archive until it runs out.
