# 75. achievement tracking usecase

> Achievement tracking use-case — the half of Epic O that actually observes the product: every producing context
> pushes a **counter-only** progress fact into `achievement` from inside the transaction that caused it, and
> `ClaimAchievement` pays the reward as an explicit user act, never an auto-grant. Progress evaluation is a threshold
> over a cumulative counter; the reward is `GENERAL` Twinkle plus, rarely, an ornament. It leaves the `Achievement` /
> `AchievementProgress` model, the catalog rows and the `ListAchievements` read to [74.achievement-catalog-model](74.achievement-catalog-model.md),
> and every pixel to [76.achievement-ui](76.achievement-ui.md). Scope: BE | Status: **built** (job 114)
>
> Layer U. Home: `apps/api/internal/achievement` (`RecordProgress`, `ClaimAchievement`, `ports.go`, `pg/`, `rpc/`) plus
> the recorder call sites in `internal/{memory,store,account}` and the adapters in `apps/api/cmd/api/achievement.go`.
> It fills the "how does one context observe another's events" seam — with a push port whose payload has no field for
> a meaning-layer write — and opens none. As-built rules: [tech/achievements.md](../tech/achievements.md) §9–§10; domain
> policy: [policy/domain/achievements.md](../policy/domain/achievements.md) §"Who reports what, and when".

## Purpose

Achievements are the promise that using cosimosi well accumulates Twinkle ([A-preamble], [G3]). v2 ships no payment
(PRD §8.3), so the daily `SMALL` grant, writing, invites and **achievements** are the entire money supply — an
achievement that never notices what the user did is a broken economy, not a missing badge. This unit is the noticing.

The product problem is that every fact an achievement counts already happens somewhere else and is owned by someone
else: a diary is written and stars are launched in `memory`'s launch transaction ([20.encode-usecase](20.encode-usecase.md)),
a 회고 in [33.recall-usecase](33.recall-usecase.md), a 요지 read in [34.view-semantic-usecase](34.view-semantic-usecase.md),
a 놓아주기 in [49.release-usecase](49.release-usecase.md), a save in `store.Decorate`
([72.decorate-usecase](72.decorate-usecase.md)), an invite settlement in `account`
([61.signup-and-invite-usecase](61.signup-and-invite-usecase.md)). There is no event bus in this repo and v2 does not
add one. So the design problem this plan must solve cleanly is **observation without coupling**: `achievement`
must learn that something happened without importing `memory`'s internals, reading its tables, or acquiring the
vocabulary of stars, strengths, moods and decay depths.

The answer is a consumer-owned **recorder port** whose entire payload is `(scope, counterKey, delta)`. The
producer reduces every meaning-layer measurement to a count _before_ the port; `achievement` receives a number and a
name and can express nothing else. That is what makes [A6]/[I11] — "an achievement changes no star's position,
strength, emotion, forgetting or gist" — unrepresentable rather than merely forbidden.

The second half is `ClaimAchievement`. [A4] is explicit: a met condition **arms a button**, it does not pay. The user
presses it and _sees_ what they earned. Because the payout crosses into two other contexts (`twinkle`'s ledger,
`store`'s ownership rows), it is an idempotent pairing keyed by a claim id — so the failure mode is "the reward
arrives on replay", never "the reward arrives twice" ([G7], and the double-payout row of the risk register in
[00.overview](00.overview.md) §3).

## Scope / Non-goals

**In scope**

- **The `AchievementRecorder` port and its twin in every producing context** — `internal/memory/ports.go`,
  `internal/store/ports.go`, `internal/account/ports.go`, each declared by the producer, each with the payload
  `(scope, tx, counterKey, delta)` and nothing else, each defaulting to the shipped no-op for tests ([A6][I11]).
- **The exhaustive call-site list** — `memory.PersistEncoded`, `memory.Recall`, `memory.RecallDiaryStars`,
  `memory.ViewSemantic`, `memory.Release`, `store.Decorate`, `account`'s invite settlement. Each call runs
  inside the transaction that produced the fact.
- **The producer half of the closed counter-key vocabulary** — the vocabulary itself (12 producer-pushed keys, 2 key
  families and 2 achievement-derived variety counters, and each key's accumulate/reach mode) is **owned by
  [74.achievement-catalog-model](74.achievement-catalog-model.md)**; this unit declares each emitted key as an exported
  constant in its producing context and reconciles the emitted set against the catalog at boot ([A1][A1a][A2]).
- **`achievement.Service.RecordProgress`** — increment, threshold, and `achieved_at` stamp, in one idempotent SQL
  statement per candidate achievement, on the caller's transaction ([A2]).
- **`achievement.Service.ClaimAchievement` + `rpc ClaimAchievement`** — the explicit claim ([A4]): mark claimed in
  `achievement`'s own transaction, then pay through two consumer-owned granter ports keyed by the claim id ([A3][G3][G7]).
- **Reward payout semantics** — `GENERAL` Twinkle always, an ornament rarely, `SMALL` never ([A3]); a repeat claim is
  an idempotent replay of the same reward, never a second credit.
- **Fail-closed wiring** — `apps/api/cmd/api/achievement.go`: the three recorder adapters, the two granter adapters,
  the boot-time counter-key and reward-ornament reconciliation, and a production boot that refuses an unbound
  recorder.

**Non-goals**

- **The model, the catalog and the read.** `Achievement`, `AchievementProgress`, the condition/reward types, the
  catalog rows and their tiers, the `achievement_progress` DDL and migration, and `ListAchievements`† belong to
  [74.achievement-catalog-model](74.achievement-catalog-model.md). **This unit claims no migration
  number and writes no DDL.**
- **Every pixel and every string.** The `/me` achievements tab, the claim button, the reward reveal and the [A5]
  unlock toast are [76.achievement-ui](76.achievement-ui.md); `achievement_*` i18n keys are its deliverable.
- **The earn path itself.** `twinkle.EntryReason.achievement_claim`, `twinkle.Service.EarnAchievementReward` and every
  `twinkle_ledger_entries` DDL change are [66.earn-and-purchase-spend](66.earn-and-purchase-spend.md)'s — **already
  shipped** (job 101), so this unit binds to existing behavior through a port and adds no reason of its own.
- **The ornament grant.** `store`'s published grant and the `ornament_ownerships` insert query are
  [71.ornament-catalog-model](71.ornament-catalog-model.md)'s; the catalog's `achievement-only` unbuyable rule
  is [72.decorate-usecase](72.decorate-usecase.md)'s ([P11]).
- **No recompute, no backfill, no cron.** Progress is never derived by querying another context's tables,
  and there is no scheduled evaluator — the only clock-driven job in the repo stays the retention sweep.
- **No decrementing and no reversal.** Letting go, releasing a diary, restoring one, or a withdrawal/restore cycle
  never lowers a counter and never un-achieves an achievement ([I1] — nothing is taken back).
- **No FE mirror math.** `@cosimosi/achievement` mirrors types and formats labels; it evaluates nothing.
- **No streak, no login bonus, no real-time condition** ([A1a][G3]).

## Grounding

  - **[I11]/[A6]** — an achievement must not touch the meaning layer. Guard: the recorder port's payload is
    `(scope, counterKey, delta)` — there is no memory id, no star, no strength, no text field to write — **and its

    Both directions are closed by the signature.
  - **[I1]** — the system deletes nothing. Guard: `achievement`'s only statements are an upsert-increment and two
    conditional `UPDATE`s over its own table; no query in this unit deletes a row anywhere.

    `achieved_at`/`claimed_at` are stamped by Postgres `now()` inside the statement, `AchievementServiceDeps` has no
    `Now` field, and no counter key or port parameter carries a date, so a streak cannot be written.

## Design

### Placement (domain-first Go, the context recipe)

`RecordProgress` and `ClaimAchievement` are use-cases on `achievement.Service` in **`apps/api/internal/achievement`**,
which [74.achievement-catalog-model](74.achievement-catalog-model.md) creates with the observed recipe: `doc.go`,
`types.go`, `service.go`, `ports.go`, `errors.go`, `pg/store.go`, `rpc/{server.go,reasons.go}` — no empty `domain/` or
`app/` (§2.3, §2.9#2). This unit adds to `ports.go` (two granter ports), `service.go` (two use-cases that **compose
the write primitives 74's store already ships** — `TouchCounter` / `AddCounter` / `RaiseCounter` / `MarkAchieved` /
`MarkClaimed`, the 43→44 precedent), `rpc/` (one method), and one composition-root file
`apps/api/cmd/api/achievement.go`. **It adds no SQL file**: every statement lives in plan 74's
`apps/api/db/queries/achievement/achievement.sql` (74 is the single owner of every `achievement` statement,
[00.overview](00.overview.md) §5.6).

`achievement` imports no other context, and no other context imports `achievement`. It queries only its own two
tables (`achievement_counters` · `achievement_progress`), through 74's store. **This unit claims no migration
number** — every table it touches is owned elsewhere: the two achievement tables by 74, `twinkle_ledger_entries` by
66, `ornament_ownerships` by 71.

### The recorder port — push, counter-only ([A6][I11])

Each producing context declares its own port. `memory`'s (the twin in `store` is identical with `store.EconomyTx`;
`account`'s takes the tx as bare `any`, since this unit introduces no new exported type name in `account` — the
shipped `memory.EconomyTx` is itself `any`):

```go
// apps/api/internal/memory/ports.go
type AchievementRecorder interface {
    RecordProgress(ctx context.Context, scope platform.UserScope, tx EconomyTx,
        counterKey string, delta int) error
}
type NoAchievementRecorder struct{} // shipped no-op: tests and economy-less builds
```

Four properties, all structural:

1. **The payload cannot describe a memory.** No id, no name, no mood, no strength, no stage, no text, no date. A
   producer that wanted to let an achievement rewrite a star would have nowhere to put the star.
2. **The return carries no value.** `error` only — an achievement outcome cannot influence the transaction that
   produced the fact. This is what makes [A5]'s unlock notice a _read_: nothing is pushed back, so
   [76.achievement-ui](76.achievement-ui.md) detects newly-achieved rows by diffing `ListAchievements` after the
   invalidation the action already triggers (§2.8's "results surface on the next read — no polling, no streaming").
3. **The producer reduces before it reports.** Every meaning-layer measurement — decay depth, gist stage, mood, the
   distinct-kind count — is compared against its threshold _inside the producing context_ and crosses the port as a
   count. `achievement` never receives a measurement, so it needs no vocabulary for one (§3.1 rule ⑦).
4. **A recorder error aborts the causing transaction**, exactly as the write-earn grant does today. Deliberate: there
   is no recompute path (the pre-recall decay depth is unrecoverable afterwards), so a counter that can
   silently diverge from the facts is unfixable later. Loud failure beats silent loss; `memory.NoEarnOnWrite`'s
   silent-nothing behavior is not copied into production.

### The counter keys this unit emits — the vocabulary is owned by [74](74.achievement-catalog-model.md)

The key set, its family members and each key's **mode** (`accumulate` adds the delta, `reach` stores
`GREATEST(value, delta)`) are catalog facts owned by
[74.achievement-catalog-model](74.achievement-catalog-model.md): 12 producer-pushed keys + 2 key families + 2
variety counters `achievement` derives for itself, **16 counters, closed** (29 with both families expanded). One key per observable fact; **many
achievements per key** — the tiers of an axis are catalog rows, never new keys. Keys are snake_case canonical UL
nouns; **no rendering word** (`star`, `constellation`, `nebula`) may appear in one (UL §4), which is why the launch
counter is `episodic_memory_launched`.

The producers this unit wires, and what each pushes:

family member inside the same transaction (74). A producer therefore never computes a distinct-set size.

Decisions embedded in that table:

- **A past-dated diary advances nothing.** `diary_written` and its siblings are emitted _after_ the monotonic launch
  guard, at the same point as the shipped `EarnPort.OnDiaryLaunched` call — a diary that launches no memory is saved
  ([I10][T1]) but grants and counts nothing. Anything else is the [G6] farm with a different name.
- **`RecallDiaryStars` counts per member**, matching [G4]'s "the diary cost is the sum of its per-memory recalls" and
  the as-built one-`recall`-row-per-member ledger.
- **No counter is decrementable and no producer computes a set size.** A _set_ axis (distinct moods, distinct
  ornament kinds) is expressed as a **key family** — the producer pushes `mood_recorded:<MOOD>` /
  `ornament_kind_decorated:<KIND>` and `achievement` raises the matching variety counter on first touch, because
  distinctness is a property only the counter table's owner can prove (74). A family member is a constant string
  built from a closed enum in the producing context, never from user data.
- **`decay_recovered` is captured at the recall moment** from the same anchor snapshot the spend is already priced from
  (the pre-recall decay stage, before the reinforce resets it) — one computation, no extra read. This is the single
  reason a pull/recompute design was rejected outright.
- **[A2]'s "요지화 도달" axis is amended** to be observed at the view moment: `ViewSemantic` pushes the stage it just
  served and 74's **reach** mode keeps the high-water mark, because the call-site list above is exhaustive and
  contains no worker-side site where the risen stage changes. The amendment lands in
  `spec/policy/domain/achievements.md`.
- **The inviter's counter is recorded under a scope minted from the resolved inviter id** via `platform.NewUserScope`
  — the shipped `twinkle.ClaimInvite` precedent for crediting a beneficiary who is not the caller. The invitee gets no
  invite counter: [A2]'s axis is "친구 초대 성공", an inviter fact. **As-built: account's settlement is a locked sequence
  of statements rather than one transaction**, so it passes no tx handle and its report is written over the pool. The
  report therefore lands **before** `rewarded_at` is stamped: a failure then leaves the invite settleable and the next
  settlement heals it (the credit is dedup-keyed), whereas stamping first would make a failed report unrecoverable. The
  only row reading this counter has a target of one, so a healing retry counting twice costs nothing.

**Drift guard (structural).** Each producing context exports its emitted key set (`memory.AchievementCounterKeys`,
`store.AchievementCounterKeys`, `account.AchievementCounterKeys`); the catalog exposes the keys its rows read
(`achievement.CatalogCounterKeys`). At wiring time `cmd/api/achievement.go` — the one place that sees every context
(§2.4) — asserts **set equality in both directions** and returns an error otherwise. **As-built: the comparison has two
sanctioned exemptions**, each for a key that is legitimately on one side only — a family member is emitted but read by no
condition (it feeds a variety counter, so it is admitted when `KnownCounterKey` says the vocabulary defines it), and a
derived counter is read but emitted by nobody (`DerivedCounterKey`). Without them the guard would refuse the shipped,
correct wiring. A renamed key, an orphan key, or a catalog row reading a key nobody emits
**cannot start the server**. No shared fixture, no import edge, no review habit. (This is the boot-time half of the
drift guard; the composition-root **membership test** remains 74's, and the two together are complementary, not
duplicates.)

### Progress evaluation — one statement, no clock ([A1][A1a][A2])

`achievement.Service.RecordProgress(ctx, scope, store Store, counterKey string, delta int) error` — `Store` is 74's
port, arriving already bound to the caller's transaction (the `twinkle.Service.CheckAndSpend(…, ledger LedgerStore,
…)` shape):

1. Refuse `delta <= 0` with `ErrProgressDeltaInvalid` — a wiring fault, not a user error. No axis in the vocabulary is
   decrementable, so a non-positive delta can only be a bug. **As-built: it also refuses a DERIVED key** — a producer
   pushing `mood_variety`/`ornament_kind_variety` directly would be claiming distinctness it cannot prove, so thirteen
   JOY entries would read as thirteen moods. And the write is **dispatched on the key's declared mode**, never on
   anything the caller passed, so an accumulate statement can never land on a reach key.
2. Write the counter through 74's primitives: `TouchCounter` (`INSERT … ON CONFLICT DO NOTHING`, whose `created`
   return is the first-touch signal that bumps the family's variety counter inside the same transaction), then
   `AddCounter` for accumulate keys or `RaiseCounter` (`GREATEST(value, delta)`) for reach keys, each `RETURNING` the
   new value. **Progress is never stored** — it is derived at read as `min(counter, target)` (74, ARCHITECTURE §2.9
   #3); there is no `progress` column anywhere to update.
3. Resolve the candidate achievement ids from the in-code catalog (`counterKey → []Achievement`, a Go map — an empty
   set is a no-op; the boot check makes that branch dead in a correct build) and, for each whose target the returned
   counter value now meets, call 74's `MarkAchieved` — `INSERT INTO achievement_progress … ON CONFLICT DO NOTHING`,
   so `achieved_at` is stamped by Postgres `now()` exactly once and never overwritten; re-crossing the threshold
   changes nothing. The service needs no clock and `AchievementServiceDeps` has no `Now` field: a real-time condition
   is unexpressible ([A1a]). Evaluation is `counter >= target` over two ints; **the condition has no time input**.
4. A per-candidate loop rather than an array-driven batch: the candidate set is one axis's tiers (a handful), every
   statement is 74's plain sqlc inside the isolation gate's supported grammar, and every statement carries `user_id`
   as an inserted parameter ([U1]).

### `ClaimAchievement` — explicit, once, idempotent ([A3][A4][G3][G7])

`achievement.Service.ClaimAchievement(ctx, scope, achievementID) (ClaimResult, error)`:

1. Resolve the catalog row; an unknown id is `ErrAchievementNotFound`.
2. In `achievement`'s **own** transaction, one conditional update — the row is the lock — through 74's
   `MarkClaimed(ctx, scope, achievementID, claimID)`: `UPDATE achievement_progress SET claimed_at = now(),
claim_id = @claim_id WHERE user_id = @user_id AND achievement_id = @achievement_id AND claimed_at IS NULL` (74's
   statement — row **existence** is achievement, so no `achieved_at IS NOT NULL` predicate exists, and the
   `CHECK ((claimed_at IS NULL) = (claim_id IS NULL))` is satisfied by writing both together). Concurrent claims
   serialize on the row and exactly one of them updates it. Zero rows updated → read the row: absent →
   `ErrAchievementNotAchieved` (nothing is credited, [A4] — a met condition is a _precondition_, never a payout);
   present and already claimed → fall through as a **replay**.
3. Still inside that transaction, arm the drain through the consumer-owned `SettlementScheduler` — bound at the
   composition root over `memory`'s user-job seam onto the claim's own handle. A rolled-back claim schedules nothing; a
   committed one leaves a job even if the process dies before the payout.
4. Commit, then pay through the two consumer-owned granter ports (an idempotent pairing — not one cross-context
   transaction, which would make `achievement` the transaction owner of another context's tables, §2.3):
   - `TwinkleGranter.EarnAchievementReward(ctx, scope, claimID, amount) (generalTotal int, err error)` — bound over
     the **shipped** `twinkle.Service.EarnAchievementReward` ([66.earn-and-purchase-spend](66.earn-and-purchase-spend.md),
     built in job 101; it returns a `twinkle.Balance` the adapter narrows to the `GENERAL` total), dedup key
     `achievement:<claimID>` (the `write_diary:<diaryID>` / `invite:<signupID>` form). The credit lands as an ordinary
     append-only `achievement_claim` earn row, so the `/me` stardust history shows it like everything else ([G7]).
   - `OrnamentGranter.Grant(ctx, scope, claimID, ornamentID)` for the rare ornament reward — bound over
     [71.ornament-catalog-model](71.ornament-catalog-model.md)'s ownership insert, `ON CONFLICT DO NOTHING` on
     `(user_id, ornament_id)`.
5. On a successful leg, stamp `paid_at` through `SettleClaim`. A settle failure here is **not** reported: the reward
   arrived and only the stamp is missing, so the claim returns success and the drain re-runs an idempotent leg and
   re-stamps.
6. Return `ClaimResult{TwinkleAmount, OrnamentID, TwinkleTotal}` — **exactly one** of `TwinkleAmount`/`OrnamentID` is
   set, mirroring 74's XOR `Reward`.

**Double payout is structurally impossible** and **a reward is never lost**: the `(user_id, achievement_id)` primary
key admits one progress row per achievement, `claimed_at` is set before any credit, and both legs are idempotent on
the claim id — so `claimed_at` set with the reward uncredited is a _recoverable_ state. It recovers two ways, neither of
which needs the user to notice: the read reports it distinctly (`Entry.RewardSettled` → the wire's `reward_settled`), so
the surface keeps a retry affordance instead of rendering the row as received; and `SettleClaims` drains it from the
worker. A repeat claim is therefore an **idempotent replay returning the same reward**, not an error; there is no
`ALREADY_CLAIMED` refusal, because refusing would strand the reward in exactly the crash window this pairing exists
to heal.

### `SettleClaims` — the drain ([A4])

`achievement.Service.SettleClaims(ctx, scope)` lists this user's progress rows, keeps those that are claimed and not
settled, and replays `payReward` for each. It runs from a `memory` user job of kind `achievement_settle`, enqueued
inside the claim transaction and deduped per **claim** (`achievement_settle:<user>:<achievement>`) — a per-user key
would let one finished drain swallow the next claim's, because the enqueue dedups against terminal rows too.

It is user-scoped by construction (the job names one user; every statement under it is conjunctively scoped), so **no
`globalQueries` exemption is added** — the queue's own `ClaimDueJob` stays the single sanctioned global scan. It has
**no attempt cap and never dead-letters**: the composition root refuses to boot on a catalog row with no payable leg,
with both legs, or with an unpublished ornament, so a permanently unpayable claim cannot reach the handler and every
failure it retries is transient. Both worker roots register the handler.
On a replay the response reports the catalog's current tier while the ledger row remains the authoritative record of
what was credited ([G7]).

**The claim id is derived, not minted:** `claimID = achievementID`, unique per user because the ledger's dedup index
is `UNIQUE (user_id, dedup_key)` and the progress key is `(user_id, achievement_id)`. 74's `claim_id` column records
it (written together with `claimed_at`, per the CHECK), and a derived id makes every replay recompute the identical
dedup key — a random id would buy no uniqueness the pair does not already have.

**`SMALL` is unrepresentable as a reward** ([A3]): the reward type is `{TwinkleAmount int; OrnamentID string}` with no
`TwinkleKind` field, `TwinkleGranter` has no kind parameter, and twinkle's earn path credits `general` unconditionally
(as-built `earn()` → `ApplyBalanceDelta(…, amount, 0)`; `SMALL` is a daily derivation and is never earned —
[65.twinkle-kind-redefinition](65.twinkle-kind-redefinition.md) ·
[66.earn-and-purchase-spend](66.earn-and-purchase-spend.md)). Every reward is **exactly one leg** — a positive
`GENERAL` tier **or** an ornament, never both (74's XOR `Reward` and its catalog self-test; 76 renders the same XOR).

### Wiring and fail-closed boot (`apps/api/cmd/api/achievement.go`, §2.4)

One composition-root file exposing `achievementServiceOption(...) (platform.HandlerOption, error)` and registering via
`platform.WithRPCService` + `achievementv1connect.NewAchievementServiceHandler`. It holds:

- three recorder adapters (`memoryAchievementRecorder`, `storeAchievementRecorder`, `accountAchievementRecorder`),
  each type-asserting the producer's opaque tx to `interface{ DB() dbgen.DBTX }` and binding
  `achievementpg.NewStore(handle)` onto it — the shipped `economyLedger` pattern in `cmd/api/twinkle.go`, so the two
  contexts share the transaction and never the queries. **As-built: the binding is LATE** — a claim pays through
  `twinkle` and `store`, which are built after `account`, so the achievement service cannot exist when the producers are
  constructed. The root hands them one `achievementRecorderBinding` holder and fills it once, the shape the invite-reward
  granter already uses for the twinkle↔account cycle; an unbound recorder **refuses**, so a producer reporting too early
  fails its transaction rather than dropping the fact. The worker, which runs only the withdrawal sweep and settles no
  signup, binds an account recorder that refuses rather than a no-op;
- two granter adapters over `twinkle.Service` and `store.Service`; `achievement` imports neither;
- the boot-time counter-key reconciliation, plus a boot-time reward-ornament check asserting every catalog reward's
  `ornamentID` resolves in `store`'s catalog — the composition root is the only place both catalogs are visible, so
  an invalid reward id fails the boot instead of half-paying a claim (the richer 1:1 **pairing test**,
  `apps/api/cmd/api/catalog_consistency_test.go`, is 74's per plan 71 — this boot check complements it);
- a hard failure when any recorder or granter is nil — **unconditional constructor refusal**, the shipped
  `twinkle.NewService` pattern (a nil dep errors in every environment, not only production), proved by an integration
  test in the shape of the as-built `TestProductionTwinkleInviteEarnFailsClosedWithoutItsAdapter`
  (`cmd/api/twinkle_integration_test.go`). `NoAchievementRecorder` exists for tests only.

### RPC contract (`cosimosi.achievement.v1`, Connect, unary — §2.7)

Added to the proto file [74.achievement-catalog-model](74.achievement-catalog-model.md) creates:

```proto
// [A4] the explicit claim: pays the reward and stamps claimed_at. A mutation — POST, never GET.
rpc ClaimAchievement(ClaimAchievementRequest) returns (ClaimAchievementResponse);

message ClaimAchievementRequest  { string achievement_id = 1; }
message ClaimAchievementResponse {
  int64  granted_twinkle     = 1;  // GENERAL only — there is no kind field
  string granted_ornament_id = 2;  // empty = no ornament ([A3] rare)
  int64  twinkle_total       = 3;  // the balance after the credit, for the reveal
}
```

The request carries **no `user_id`** — the scope comes from `platform.UserScope` — and **no amount, no
reward, and no counter**: a client cannot propose what it earned or advance a counter, because no RPC in this unit
accepts one. Progress is only ever a consequence of a real product action (§2.9#8). `ClaimAchievement` is not
`NO_SIDE_EFFECTS`, so this unit adds **no** `packages/client-cache/src/http-policy.ts` entry (the
classification requirement is discharged by 74's `ListAchievements`†). The handler is thin: map, call, map errors (§2.9#7).

`rpc/reasons.go` declares `ACHIEVEMENT_NOT_FOUND`, `ACHIEVEMENT_NOT_ACHIEVED`, `ACHIEVEMENT_INPUT_REQUIRED`,
`ACHIEVEMENT_SCOPE_REQUIRED`, `ACHIEVEMENT_REWARD_UNAVAILABLE` (a granter refusal — the claim is recorded and will
heal on replay). The FE mapping and copy for these reasons are [76.achievement-ui](76.achievement-ui.md)'s; an
unmapped reason degrades to `Internal` by the shipped taxonomy. A withdrawn scope never reaches this handler — the
`platform` interceptor refuses it before any context read ([62.withdrawal-usecase](62.withdrawal-usecase.md)).

### Golden-parity stance

**None, deliberately.** Nothing in this unit is a pure function the client re-runs: progress evaluation, claim
idempotency and payout are server-authoritative orchestration, and the FE reads results (`ListAchievements`,
`ClaimAchievement`) rather than recomputing them (§2.9#8; a headless unit carries no parity question —
[00.overview](00.overview.md) §4). `@cosimosi/achievement` mirrors types
and formats a progress label from server-supplied `progress`/`threshold`; it must define no evaluation function, and
no golden fixture is added. The one number `memory` reads for a threshold comparison (`decay_recovered`) is a generated
`values` constant, so the FE could not disagree with it.

## Acceptance Criteria

1. Every producing context declares its own `AchievementRecorder` port whose only payload is
   `(scope, tx, counterKey, delta)` and whose only return is `error`; no signature on the path carries a memory id,
   name, mood, strength, stage, text, or timestamp, and no return value can flow back into the producing write.
   ([A6][I11])
2. The recorder is called from exactly these sites, each inside the transaction that produced the fact:
   `memory.PersistEncoded`, `memory.Recall`, `memory.RecallDiaryStars`, `memory.ViewSemantic`, `memory.Release`
   (the 놓아주기/soft-delete path — never `LetGo`, which seals neurons and releases nothing),
   `store.Decorate`, and `account`'s invite settlement (`ResolveInviteSettlement`). A rolled-back action advances no
   counter. (§2.8)
3. Every key this unit emits is a member of [74.achievement-catalog-model](74.achievement-catalog-model.md)'s closed
   16-counter vocabulary and is exported as a constant by its producing context; no producer invents a key, and no
   family member is built from anything but a closed enum in the producing context. ([A2])
4. `cmd/api` refuses to boot when the union of the producers' emitted keys differs in either direction from the keys
   the catalog reads, and when any catalog reward names an ornament id absent from `store`'s catalog. ([A2][A3])
5. A past-dated diary that launches no `EpisodicMemory` advances **no** counter — the recorder call sits after the
   monotonic launch guard, where the write-earn grant already sits. ([I10][T1][G6])
6. `decay_recovered` is emitted at the recall moment from the pre-recall decay stage of the same anchor snapshot the
   spend is priced from, and only the resulting count (never the stage) crosses the port. ([A2] 망각·회복)
7. `RecordProgress` refuses a non-positive delta, writes the counter through 74's `TouchCounter`/`AddCounter`/
   `RaiseCounter` primitives, marks each candidate whose target the counter now meets via 74's `MarkAchieved`
   (`ON CONFLICT DO NOTHING`), and `achieved_at` is stamped by Postgres `now()` exactly once, never overwritten;
   **no `progress` column exists and this unit adds no SQL statement**. ([A2])
8. `achievement` holds **no time source**: `AchievementServiceDeps` has no `Now` field, condition evaluation reads
   only `(progress, threshold)`, and no streak or real-time condition can be expressed. ([A1a])
9. `achievement` reads and writes **only its own two tables** (`achievement_counters` · `achievement_progress`,
   through 74's store) — it queries no `diaries`, `episodic_memories`, `neuron_activations`, `synapses`,
   `twinkle_ledger_entries` or `ornament_ownerships` table, and imports no other context. (§2.2)
10. A met condition pays nothing: the reward is credited only by an explicit `ClaimAchievement` call, which stamps
    `claimed_at` before any credit. An unachieved or unknown achievement is refused with nothing written. ([A4])
11. Claiming twice credits once: `claimed_at` is set under the `(user_id, achievement_id)` uniqueness, both payout
    legs are idempotent on the derived claim id (`achievement:<claimID>` in the ledger, `ON CONFLICT DO NOTHING` on
    ownership), and a repeat claim replays the same result instead of refusing — so a crash between the claim and the
    payout heals and no reward is lost or doubled. ([A4][G7])
12. The reward is **exactly one leg** — `GENERAL` Twinkle or, rarely, an ornament, never both (74's XOR `Reward`);
    **`SMALL` is unrepresentable** — no reward type, port, or proto field carries a `TwinkleKind`, and the earn path
    credits general only. ([A3])
13. A claim's credit is an ordinary append-only ledger entry with reason `achievement_claim`, visible in the `/me`
    stardust history; this unit adds no `EntryReason`, no ledger DDL, and no second ledger. ([G3][G7])
14. A claim changes no star's position, strength, emotion, forgetting state or gist stage, and deletes nothing — the
    only rows written are `achievement_progress`, one ledger entry, and at most one ownership row. ([A6][I11][I1])
15. `ClaimAchievementRequest` carries no `user_id`, no amount and no counter; every read and write is scoped to the
    authenticated user; `pnpm lint:persistence` passes with no new allowlist entry; the handler contains no policy.
    ([U1], §2.9#7)
16. Production fails to boot with any recorder or granter unbound; the no-op recorder is reachable from tests only.
