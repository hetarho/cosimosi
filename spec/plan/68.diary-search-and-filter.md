# 68. diary search and filter

> Diary search and filter — the read side of a real diary archive: keyword search over the **immutable `Diary.body`**,
> a date range, a 13-mood filter, a newest/oldest sort, keyset pagination, and the per-day mood read the calendar
> needs. Search never touches `CurrentText` / `DecayStages` / `SemanticStages` ([D10]) and never advances the universe
> clock or spends Twinkle ([D11][T3][G4]). Released (soft-deleted) diaries are excluded by an anti-join, so Restore
> makes them reappear for free ([X2]). It leaves every pixel to [69.diary-list-completion](69.diary-list-completion.md)
> and [70.diary-calendar-view](70.diary-calendar-view.md). Scope: BE | Status: built
>
> Layer U. Home: `apps/api/internal/memory` — the shipped `GetDiaries` use-case (`diaries.go`) extended in place plus a
> new `GetDiaryCalendar` use-case, its `DiaryReader` port, `memory/pg` + `db/queries/memory/diaries.sql`, migration
> `00020`, and the `memory.v1` contract; it also owns the one client seam that the request shape forces (the
> `GetDiaries` query key in `packages/api-client`). It fills the archive **read** seam and opens no write seam at all.

## Purpose

The diary archive shipped as a reverse-chronological list and nothing more ([47.diary-reader-page](47.diary-reader-page.md)):
one page size, one order, no way to find anything. PRD §1.2 names that as the third of the product's three problems —
"다시 찾기 어렵다" — and [D7]–[D9] promise the basics any diary app has: a sort toggle that survives a large archive, a
date range, a 13-mood filter, and keyword search over what the user actually wrote. This unit is the backend that makes
those true, over the tables [16.memory-aggregate-schema](16.memory-aggregate-schema.md) already owns.

The load-bearing rule is [D10]. Forgetting in cosimosi operates on _derived representations_ — `EpisodicMemory.CurrentText`,
`DecayStages`, `SemanticStages` — while the `Diary` body is the immutable archive whose reading is already free and
unlimited ([G4][I2][D4]). A search that could match a word forgetting had already removed would restore it for free, and
would break the forgetting metaphor ([F1]) and the [G1] recall economy in the same query. So the search surface is
`diaries.body` and only `diaries.body`; the guard is that no port, row, or DTO in this unit has a field for a memory
text at all, and `ORDER BY` may read nothing but `diary_date` and `id`. [D10]'s own words: "검색은 조회이지 연결이 아니다."

Two smaller gaps close with it. First, the shipped list has a real defect: `db/queries/memory/diaries.sql` applies no
release filter, so a diary inside its 30-day restore window still lists ([X2]). This unit is the owner of those queries,
so the exclusion lands here as an anti-join on `release_groups` — not as a new `diaries.deleted_at` column, which would
duplicate the release ledger and make Restore inexact. Second, a `Diary` has no emotion of its own (emotion lives
on `EpisodicMemory`), so both the mood filter and [D12]'s per-day mark need a defined answer for "this diary's mood".
Two different answers are pinned deliberately, and this unit implements both.

## Scope / Non-goals

**In scope**

- **`GetDiaries` extended in place** ([D7][D8][D9]) — the request gains `query`, `moods`, `from`, `to`, `sort`; no
  new list RPC exists. The response gains nothing. Still unary, `NO_SIDE_EFFECTS`, per-user scoped, keyset-paginated.
- **Keyword search over `diaries.body`** ([D9][D10]) — `pg_trgm` + a GIN trigram index + `ILIKE '%…%'`, migration
  `00020`; a minimum query length; user wildcards escaped before binding.
- **The date-range filter** ([D8]) — inclusive `from`/`to` over `diary_date`, either side optional.
- **The 13-mood filter** ([D8][M2]) — "any live `EpisodicMemory` of this diary has mood M", as an `EXISTS` semi-join, never
  a `JOIN`.
- **The newest/oldest sort toggle + pagination** ([D7]) — two static sqlc queries (`ListDiariesPageDesc` /
  `ListDiariesPageAsc`) and a direction-carrying cursor; no dynamic `ORDER BY` anywhere.
- **Released-diary exclusion** ([D10][X2][X3]) — an anti-join on `release_groups` in every list/search/filter/calendar
  query, plus the narrowing of the shipped `diaries_test.go` expectation and the [D10] wording amendment.
- **`GetDiaryCalendar`†** ([D12]) — a new read returning, per written day in a bounded window, that
  day's per-mood weights (weight = summed `EffectiveStrength`); day-grained keyset pages; **no color and no diary id**
  cross the wire.
- **New domain nouns + their UL rows** — `DiaryQuery`, `DiaryFilter`, `DiarySort`, `DiaryDayMood`, each registered in the ubiquitous language first.
- **Migration `00020_diary_search_trgm.sql`** — `CREATE EXTENSION pg_trgm` + `diaries_body_trgm_idx`.
- **The forced client seam** — `createGetDiariesInfiniteQueryOptions(transport, input)` and an input-less
  invalidation key, with `use-release.ts` / `use-restore.ts` widened; and the single `getDiaryCalendar` classification in
  `packages/client-cache/src/http-policy.ts`.

**Non-goals**

- **No UI.** The keyword field, the mood chips, the sort toggle, infinite scroll and the `(diaryBody, query)`
  highlighter are [69.diary-list-completion](69.diary-list-completion.md); the month grid, the representative-color
  pick and the day modal are [70.diary-calendar-view](70.diary-calendar-view.md). Which of this unit's filter fields
  get a control of their own is a presentation decision belonging to those two — the `from`/`to` range, for one, is
  driven by a link and by the calendar's day read rather than by a form field. This unit renders nothing and owns no
  i18n key.
- **No body preview truncation and no server-side snippet.** [D6]'s preview is an FE truncation of `body` at
  `diary_reader.body_preview_length`, owned by 69; this unit adds **no** `snippet` field, so there is no
  server-side text derivation that could ever be re-pointed at `CurrentText`.
- **No relevance ranking.** `ORDER BY` is `(diary_date, id)` only. Trigram similarity is used by the _index_, never as a
  sort key — a body-derived similarity ordering would be admissible and this unit **declines** it: [D7] promises a
  chronological archive, and a relevance score is a second ordering contract to keep honest.
- **No semantic/embedding search.** pgvector diary search is out of v2 by PRD §8.3.
- **No morphological analysis.** No `tsvector`, no Korean analyzer, no new base image.
- **No spend, no clock, no write.** No `SpendGate`, no clock port, no `EconomyTx`, no `UPDATE`/`DELETE`/`INSERT` in this
  unit's queries ([D11][T3][I2]). The [D3] jump stays [47.diary-reader-page](47.diary-reader-page.md)'s.
- **No changes to the alive-predicate or the release ledger.** Liveness of a memory is `deleted_at IS NULL` and the
  release record is `release_groups` — both owned by [48.deletion-rules](48.deletion-rules.md) /
  [49.release-usecase](49.release-usecase.md) and reused verbatim, never re-derived.
- **No new table and no `diaries` column.** The archive gains an index and an extension, nothing else.

### The read input: `DiaryQuery` · `DiaryFilter` · `DiarySort` (new domain nouns)

```go
type DiarySort string   // "NEWEST" | "OLDEST" — the only two, closed set

type DiaryFilter struct {
    Keyword string      // trimmed; "" = no keyword. The ONLY text field in this unit.
    Moods   []Mood      // empty = no mood constraint
    From    *time.Time  // inclusive diary_date lower bound
    To      *time.Time  // inclusive diary_date upper bound
}

type DiaryQuery struct {
    Filter DiaryFilter
    Sort   DiarySort
    PageSize  int        // clamped to values.DiaryReaderPageSize
    PageToken string     // decoded and direction-checked by the use-case
}
```

- **`DiaryFilter` has one text field and it is a _predicate over `diaries.body`_.** There is no field for a memory text,
  no `include_current_text` flag, no free-form ordering string. [D10] is therefore unexpressible in this type, not merely
  forbidden — the structural guard [00.overview](00.overview.md) §3 requires.
- **Validation is total, and rejects rather than silently narrowing** (a silently empty page is indistinguishable from an
  empty archive): keyword shorter than `diary_reader.search_min_query_length` after trimming → `ErrDiarySearchQueryTooShort`;
  a mood string outside the 13 (`memory.AllMoods()`) → `ErrDiaryMoodFilterInvalid`; a non-ISO date or `From > To` →
  `ErrDiaryDateRangeInvalid`; an unparsable or direction-mismatched cursor → the shipped `ErrDiaryPageTokenInvalid`.
- **Wildcard safety.** The keyword is escaped in the use-case (`\` → `\\`, then `%` and `_` prefixed with `\`) before it
  is bound, and the SQL keeps Postgres' default `\` escape character. Without this, a body containing `%` — or a user
  typing one — matches every diary, which reads as a broken filter and scans the whole archive.
- **`DiarySort` defaults to `NEWEST`** so the shipped behavior is preserved when the field is absent.
- **Cursor.** `DiaryCursor` gains the direction: the token is `base64url("<diary_date>|<id>|<newest|oldest>")`. A cursor
  whose direction disagrees with the request's `sort` is refused — flipping the toggle mid-scroll must start a fresh page,
  never continue from a boundary that means the opposite thing. The tiebreak stays `id` (a backend-minted nanoid); it is
  **not** switched to `created_at`, which is absent from `diaries_user_diary_date_idx`.
- **UL registration**: `DiaryQuery`, `DiaryFilter`, `DiarySort`, `DiaryDayMood` are added to
  `spec/ubiquitous-language.md` **§1 (memory-context nouns)** — not §1.1, whose plain-English exception covers only
  `account`/`store`/`achievement`/`demo` (PRD §3.1 rule ⑦). They keep `EpisodicMemory`/`Mood` vocabulary.

### Korean keyword search: trigram, not morphology ([D9][D10])

`00020_diary_search_trgm.sql` (Up) creates `pg_trgm` and one index; (Down) drops both, since nothing else in the schema
uses the extension:

```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;
-- [D9] partial-match search over the IMMUTABLE body only ([D10]). Codepoint trigrams, so Korean
-- substrings match without an analyzer; combined with diaries_user_diary_date_idx by bitmap AND.
CREATE INDEX diaries_body_trgm_idx ON diaries USING GIN (body gin_trgm_ops);
```

`tsvector` is rejected on measurement, not taste: on `pgvector/pgvector:0.8.3-pg17` a `'simple'` config tokenises Korean
on whitespace with 조사 attached, so `to_tsquery('simple','커피')` does not match "커피를" and the [D9] MUST would silently
under-return; `pgroonga`/`pg_bigm` are absent from the image and from Supabase. The predicate is
`d.body ILIKE '%' || $keyword || '%'`, which the trigram index serves; the minimum query length exists because a
one-character trigram query degenerates to a sequential scan. Benchmarks run against a fresh `pnpm db:reset`, never the
drifted local dev DB.

### The two direction queries ([D7]) and the filter predicates

All search/filter SQL is **static sqlc with nullable args** — the `sqlc.narg(cursor_date)::date IS NULL OR …` shape the
file already uses. A hand-built dynamic pgx string is forbidden here even though §2.6 licenses one for genuinely dynamic
SQL: `scripts/check-persistence-isolation.mjs` scans only `db/queries/**/*.sql`, so a dynamic string would escape the
[U1] gate entirely. `ListDiariesPage` is **replaced** by two queries — one per direction, identical but for the
comparison and the `ORDER BY` — so there is exactly one code path per direction and none built at runtime:

```sql
-- name: ListDiariesPageDesc :many
SELECT d.id, d.body, d.diary_date
FROM diaries AS d
WHERE d.user_id = sqlc.arg(user_id)
  AND (sqlc.narg(cursor_date)::date IS NULL
       OR (d.diary_date, d.id) < (sqlc.narg(cursor_date)::date, sqlc.narg(cursor_id)::text))
  AND (sqlc.narg(from_date)::date IS NULL OR d.diary_date >= sqlc.narg(from_date)::date)
  AND (sqlc.narg(to_date)::date   IS NULL OR d.diary_date <= sqlc.narg(to_date)::date)
  AND (sqlc.narg(keyword)::text   IS NULL OR d.body ILIKE '%' || sqlc.narg(keyword)::text || '%')
  AND (cardinality(sqlc.arg(moods)::text[]) = 0
       OR EXISTS (SELECT 1 FROM episodic_memories AS em
                  WHERE em.user_id = d.user_id AND em.diary_id = d.id
                    AND em.deleted_at IS NULL
                    AND em.mood = ANY(sqlc.arg(moods)::text[])))
  AND NOT EXISTS (SELECT 1 FROM release_groups AS rg
                  WHERE rg.user_id = d.user_id AND rg.diary_id = d.id)
ORDER BY d.diary_date DESC, d.id DESC
LIMIT sqlc.arg(page_limit);
```

`ListDiariesPageAsc` differs only in `>` and `ORDER BY … ASC`; `diaries_user_diary_date_idx (user_id, diary_date, id)`
serves both. The `SELECT` list carries `id`, `body`, `diary_date` and nothing else — `ORDER BY` reads only
`diary_date`/`id`, satisfying the body-only ordering rule by construction. `ListDiarySplitRefs` is unchanged and still runs as the second
step of the page, so the mood chips keep coming from live memories only.

### The mood filter is existence, not representation ([D8])

"This diary matches mood M" iff **any of its live `EpisodicMemory` has mood M**, expressed as the `EXISTS` semi-join
above and index-served by `episodic_memories_user_diary_idx (user_id, diary_id)`. A `JOIN` is wrong twice over: a diary
launches 2–5 memories ([E2]), so it would duplicate rows and corrupt the keyset page. A _representative_ mood is also
rejected — it would make a four-mood diary unfindable by three of its own moods.

Two corollaries, both decided: **a diary whose memories were all let go (or that never launched any) holds no mood and
therefore never matches a mood filter**, while it still _lists_ unfiltered ([I1], and consistent with
[47.diary-reader-page](47.diary-reader-page.md)'s "an empty diary still lists"); and multiple moods are **OR**, because
one diary rarely carries two moods that a user would want ANDed and an AND would return almost nothing.

### Released diaries are excluded by anti-join ([D10][X2])

A diary is excluded from list, search, filter and calendar iff a `release_groups` row exists for it — the presence of the
row _is_ the released state (`GetReleaseGroupForDiary`'s comment: "A row's presence means the diary is currently
released"; Restore and the sweep both delete it). Consequences this unit accepts explicitly:

- **No `diaries.deleted_at` column is added.** It would duplicate the release ledger, and Restore — which reverses effects
  and then deletes the group — would need a second write to stay exact. The anti-join gives reappearance for free.
- **This is a behavior change to plan 47's shipped query, and it belongs here** because this unit owns
  `ListDiariesPage*`. The shipped test in `apps/api/internal/memory/pg/diaries_test.go` ("An empty (all-deleted /
  never-launched) diary must still list") is **narrowed**: a never-launched or all-let-go diary still lists; a **released**
  diary does not. A new test asserts both halves.
- After the 30-day sweep the diary row is hard-deleted (`release.sql#DeleteReleaseDiary`), so the anti-join is moot.
- **"봉인" in [D10] never means a diary.** [X4] seals semantic `Neuron`s and [I2] keeps the body intact, so plan 68 amends
  [D10]'s wording to "released (soft-deleted) diaries" in `spec/PRD.md` §5.6.

### `GetDiaryCalendar` — per-day mood inputs, colorless ([D12])

`diaries` has no emotion column and no `UNIQUE (user_id, diary_date)`, so one day can carry many moods across several
diaries. The read is the same two-step shape as the list page:

1. `ListDiaryDaysInWindow(user_id, from_date, to_date, cursor_date, page_limit)` — the **distinct** written days in the
   window, released diaries anti-joined out, ascending, `LIMIT page_limit + 1` to detect a next page.
2. `ListDiaryDayMoodInputs(user_id, dates[])` — for those days, one row per **live** memory of a non-released diary:
   `(diary_date, mood, base_strength, recall_count)`. No text, no id, no color — the calendar cannot leak a body or a
   memory text because the row type has nowhere to put one.

The use-case then groups by `(day, mood)` and sums `memory.EffectiveStrength(baseStrength, recallCount)` per group,
yielding `DiaryDayMood{DiaryDate, Mood, Weight}`. **Weight is `EffectiveStrength`** for consistency with [M4]/[V3], which
is precisely why the grouping happens in Go and not in SQL: `EffectiveStrength` is a nonlinear read-time pure function of
`(base_strength, recall_count)`, so `SUM` over its inputs is not its sum, and re-implementing the formula in SQL would
create a third copy of a golden-parity-pinned function. `GROUP BY (diary_date, mood)` is honored as the **grain of the
response**, computed over the pure function rather than inside the query: SQL returns the per-mood inputs and the pure
fn computes the blend.

- **The client does the blend and the representative pick**, with `toEmotionSlices` (`packages/emotion/src/slices.ts`),
  inheriting its `weight desc, then mood.localeCompare` tie-break and its drop-≤0 normalization. **No color ever crosses
  the wire** ([M6], `spec/policy/ux/emotion-palette.md`).
- **A written day with no live mood** (a past-dated diary that launched nothing per [T1]; every memory let go per [X4])
  is returned as a day with an **empty** mood list. Plan 70 marks it with a neutral outline; it must not be given
  `NEUTRAL`'s color, which would assert an emotion the user never recorded ([M3]). The empty list is the structural
  carrier of that distinction: a day absent from the response was never written.
- **Pages are day-grained**, so a day is never split across pages: the cursor is `base64url("<diary_date>")` and needs no
  tiebreak because the day list is distinct — the one deliberate variation on the shipped keyset cursor's `"<sort key>|<id>"` shape.
- **Direction is fixed ascending** and there is no `sort` field: a month grid renders in day order, and the sort toggle is
  a list concern.
- **Click-through carries no ids.** [D12]'s "클릭 시 해당 일기로" is served by a second `GetDiaries` read bounded to
  `from = to = <day>` — the date range _is_ the calendar's seam back to the writing, so the calendar response stays free
  of diary ids.

### RPC contract (`memory.v1.MemoryService`, Connect, unary — §2.7)

```proto
enum DiarySort { DIARY_SORT_UNSPECIFIED = 0; DIARY_SORT_NEWEST = 1; DIARY_SORT_OLDEST = 2; }

message GetDiariesRequest {
  int32  page_size  = 1;   // existing: 0 = server default; clamped to diary_reader.page_size
  string page_token = 2;   // existing: opaque, direction-carrying
  string query      = 3;   // [D9] keyword over the immutable body ONLY ([D10])
  repeated string moods = 4; // [D8] bare mood names; empty = unfiltered
  string from       = 5;   // [D8] ISO DATE, inclusive; empty = unbounded
  string to         = 6;   // [D8] ISO DATE, inclusive; empty = unbounded
  DiarySort sort    = 7;   // [D7] UNSPECIFIED = NEWEST
}

rpc GetDiaryCalendar(GetDiaryCalendarRequest) returns (GetDiaryCalendarResponse) {
  option idempotency_level = NO_SIDE_EFFECTS;
}
message GetDiaryCalendarRequest  { string from = 1; string to = 2; string page_token = 3; }
message GetDiaryCalendarResponse { repeated DiaryDayDto days = 1; string next_page_token = 2; }
message DiaryDayDto     { string diary_date = 1; repeated DiaryDayMoodDto moods = 2; }
message DiaryDayMoodDto { string mood = 1; float weight = 2; }
```

- **`GetDiariesResponse` and `DiaryDto` are untouched** — [D6]'s row needs the per-memory dot list it already has
  (`DiarySplitRef{episodic_memory_id, name, mood}`), so no representative-mood field is added. No `snippet`
  field, no highlight offsets: highlighting is FE-only over `body`.
- **No request carries a `user_id`** — scope comes from `platform.UserScope`.
- **`GetDiaryCalendarRequest` has no `page_size`** — the server always pages at `diary_reader.calendar_month_page_size`,
  so an unbounded page is not requestable.
- **Classification is two-sided and exactly once**: the proto option plus one `getDiaryCalendar` entry with
  `userScopedUnaryReadPolicy` in `packages/client-cache/src/http-policy.ts`; the production transport hard-fails on a
  missing/duplicate classification before I/O, which is the guard (§2.7).
- **The handler stays thin** (§2.4): `rpc/server.go` parses ISO dates and the enum into `DiaryQuery`, calls the use-case,
  maps back, and maps domain errors through `reasons.go` — new reasons `MEMORY_DIARY_SEARCH_QUERY_TOO_SHORT`,
  `MEMORY_DIARY_MOOD_FILTER_INVALID`, `MEMORY_DIARY_DATE_RANGE_INVALID`, `MEMORY_DIARY_SORT_INVALID`, alongside the shipped
  `MEMORY_DIARY_PAGE_TOKEN_INVALID`.

### The client read seam this contract forces

Because the query key embeds the request input, `createGetDiariesInfiniteQueryOptions(transport, input)` replaces
`(transport, pageSize)`, and `useDiaryArchive()` takes the filter/sort input. The invalidation helper moves the other
way: `createGetDiariesInfiniteQueryKey(transport)` is built **without `input`**, which connect-query 2.x renders as a
partial key matching every filter/sort variant — so a Release or Restore invalidates the whole archive rather than only
the default view. Both call sites (`packages/universe/src/react/use-release.ts`, `use-restore.ts`) are widened with it,
and the note that the _finite_ `createGetDiariesQueryKey` does not match the infinite query is preserved.

### Free by construction ([D11][T3][G4])

`GetDiaries` and `GetDiaryCalendar` receive no clock port, no `SpendGate`, no `EconomyTx` and open no transaction; the
queries file contains no `INSERT`/`UPDATE`/`DELETE`. There is nothing to disable and nothing to review — the same way the
shipped `diaries.go` proves its freeness ("It is free ([G4]): no clock advance ([T3]), no write, no Twinkle spend"). The
one paid archive action, [D3]'s jump, lives in [47.diary-reader-page](47.diary-reader-page.md) and is untouched.

### Golden-parity stance

**No pure function is added and no new TS↔Go mirror is created.** Keyword matching is a Postgres predicate, not domain
math, so it has no TS twin and must not get one — a TS keyword matcher would be a second search implementation with a
different notion of case and wildcards. The calendar's weight reuses the **existing** parity pair
(`memory.EffectiveStrength` ↔ `packages/memory-logic` `effectiveStrength`, already pinned by
`apps/api/internal/memory/testdata/*-golden.json`), and the blend reuses `toEmotionSlices`, which is presentation-side
and single-sourced. Sort/filter/pagination semantics are contract behavior, tested server-side, not mirrored.

## Acceptance Criteria

1. `GetDiaries` accepts `query`, `moods`, `from`, `to`, `sort` on the **existing** RPC — no new list RPC exists — and
   remains unary, `NO_SIDE_EFFECTS`, per-user scoped and keyset-paginated ([D7][D8][D9]).
2. Keyword search matches a **case-insensitive substring of `diaries.body`** and of nothing else; `CurrentText`,
   `DecayStages`, `SemanticStages`, `memory_provenance` and neuron text are not read by any statement in this unit, and no
   response field or read port in it can carry them ([D9][D10][I2]).
3. `ORDER BY` reads only `diary_date` and `id`, in both directions, via two static sqlc queries; there is **no**
   runtime-built `ORDER BY` and no relevance/similarity sort key ([D7]).
4. Migration `00020_diary_search_trgm.sql` creates `pg_trgm` and a GIN `gin_trgm_ops` index on `diaries.body`, with a
   `Down` that drops both; a Korean substring query (e.g. "커피" against "커피를 마셨다") returns the diary ([D9]).
5. A keyword shorter than `diary_reader.search_min_query_length` after trimming is **refused** with a typed reason, not
   silently ignored; `%`, `_` and `\` typed by the user match literally.
6. The date filter is inclusive on both ends over `diary_date`, each side independently optional, and `from > to` or a
   non-ISO date is refused with a typed reason ([D8]).
7. A diary matches the mood filter iff **at least one of its live `EpisodicMemory` rows** has one of the requested moods,
   implemented as an `EXISTS` semi-join; page size and cursor stability are unaffected by a diary having 2–5 memories
   ([D8][E2]). An unknown mood name is refused.
8. A diary with **no live memory** (never launched, or all let go) **never matches a mood filter**, yet still appears in
   an unfiltered list with zero mood chips ([I1][X3][X4]).
9. A **released** diary is absent from the list, search results, filtered results and the calendar; after `Restore` it
   reappears in all four with no additional write, and the exclusion is an anti-join on `release_groups` — **no
   `diaries.deleted_at` column exists** ([D10][X2][I1]).
10. Flipping `sort` mid-scroll with a stale `page_token` is **refused** (`MEMORY_DIARY_PAGE_TOKEN_INVALID`); with a fresh
    request the oldest-first page is exactly the reverse of the newest-first page over the same filter, and same-date ties
    break on `id` ([D7]).
11. `GetDiaryCalendar` is unary, `NO_SIDE_EFFECTS`, per-user scoped, classified exactly once in
    `packages/client-cache/src/http-policy.ts`, and returns per written day the day's `(mood, weight)` pairs where weight
    is the sum of `EffectiveStrength` over that day's live memories of that mood ([D12]).
12. **No color and no diary id crosses the wire** from the calendar; a written day whose memories are all gone returns an
    **empty** mood list (never a `NEUTRAL` row), and a day absent from the response was never written
    ([M3][M6][I11]).
13. Calendar pages are **day-grained** — no day is split across two pages — the page size is server-owned
    (`diary_reader.calendar_month_page_size`, no request field), and days are ascending ([D12]).
14. `GetDiaries` and `GetDiaryCalendar` **advance no universe time, write nothing and spend no Twinkle**: neither receives
    a clock port or a `SpendGate`, and `db/queries/memory/diaries.sql` contains no `INSERT`/`UPDATE`/`DELETE`
    ([D11][T3][G4][I2][I10]).
15. Every statement is user-scoped and `pnpm lint:persistence` (`scripts/check-persistence-isolation.mjs`) passes with no
    new `globalQueries` or `platformTables` entry; all SQL is plain sqlc, with no hand-built pgx string ([U1]).
16. `DiaryQuery`, `DiaryFilter`, `DiarySort` and `DiaryDayMood` appear in `spec/ubiquitous-language.md` §1 **before** they
    appear in code, and [D10]'s "봉인·소프트 딜리트된 일기" wording is amended to "released (soft-deleted)" in
    [PRD.md](../PRD.md) §5.6.
17. `createGetDiariesInfiniteQueryOptions` takes the request input, the invalidation key is built **without** input so it
    matches every filter/sort variant, and both `use-release.ts` / `use-restore.ts` use it — a release or restore leaves no
    stale filtered page ([X2]).

## Policy / Values Impact

- **policy / domain:** `spec/policy/domain/diary-archive.md` states:
  - **Search reads the immutable original only.** The searchable surface is `Diary.body`; `CurrentText`, `DecayStages` and
    `SemanticStages` are never matched, ranked, ordered by, or excerpted, because free restoration of a forgotten word
    would break forgetting and the recall economy at once ([D10][G1][F1]).
  - **Ordering is chronological.** `(diary_date, id)`, newest or oldest; relevance ranking does not exist in v2 ([D7]).
  - **A diary's mood is an existence fact, not a representative one.** A diary matches mood M iff a live `EpisodicMemory`
    of that diary has mood M; a diary with no live memory matches no mood and still lists ([D8][I1]).
  - **A day's mood is a weighted blend, resolved client-side.** Per-day weights are summed `EffectiveStrength` per mood;
    the representative is the top slice; no color crosses the wire; a written day with no live mood is neutral-outlined,
    never `NEUTRAL` ([D12][M3][M6]).
  - **Released diaries are invisible and reversibly so.** Exclusion is a `release_groups` anti-join, never a copied flag
    ([X2][I1]).
  - **The archive read is free and time-frozen.** List, search, filter and calendar spend nothing and advance no clock;
    only [D3]'s jump does ([D11][T3][G4]).
  - `spec/policy/ux/diary-reader.md` states that a released diary disappears from the archive and returns on Restore.
- **tech:** the as-built read is recorded in [tech/memory-persistence.md](../tech/memory-persistence.md): the two
  direction queries and their nullable-arg shape, the trigram index and
  why `tsvector` was measured and rejected, the `EXISTS` semi-join, the `release_groups` anti-join, the direction-carrying
  cursor codec, the day-grained calendar cursor, and the Go-side `(day, mood)` grouping over `EffectiveStrength`.
- **spec/values.yaml** — this unit introduces **two** keys in the existing `diary_reader` group (groups are closed, keys are not — [00.overview](00.overview.md) §4) and reuses one:
  - `diary_reader.search_min_query_length` — the shortest accepted keyword; below it the read is refused, because a
    one-character trigram query degenerates to a full scan. Pinned at 2; **confirmed at implement**.
  - `diary_reader.calendar_month_page_size` — how many written **days** one `GetDiaryCalendar` page returns; server-owned
    and not requestable. Must cover a full month in one page (a month is ≤31 days, while `page_size` is 20). Number
    **confirmed at implement**.
  - _Reused, not redefined:_ `diary_reader.page_size` — both the default and the hard cap of a `GetDiaries` page.
  - _Owned by siblings, surfaced here:_ `diary_reader.body_preview_length` and `diary_reader.search_debounce_ms`
    ([69.diary-list-completion](69.diary-list-completion.md)); `release.soft_delete_retention_days`
    ([49.release-usecase](49.release-usecase.md)) which decides when a released diary's row disappears entirely.
  - _Deliberately **not** values:_ the `EffectiveStrength` formula and the `toEmotionSlices` blend (formulas are code,
    pinned by golden fixtures); the 13-mood set and the mood→color table (array/table content, and 13 is a derived
    length); the `DiarySort` values and the reason strings (code identifiers); the trigram index, the extension and every
    DDL detail (DB schema); the proto messages, field numbers and cursor encoding (transport contract); the SQL predicate
    shapes (query text). No trigram similarity threshold exists because no similarity ranking exists.
