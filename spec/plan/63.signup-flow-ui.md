# 63. signup flow ui

> Signup flow UI — the entry path the v1 gate left half-built: a **sign-up surface** beside the shipped sign-in one (both
> providers, both apps), a **single nickname step** that is a gate rather than a wizard page, and **invite-link entry**
> that binds without ever asking the user to type a code. Credential creation lands in `packages/auth` beside the shipped
> facade; the nickname step is rendered by an app-layer profile gate, so a session without a `users` row can reach no
> product route. It leaves the `/me` profile editor to [64.my-page](64.my-page.md) and the post-signup tour to
> [80.onboarding-tour](80.onboarding-tour.md), handing the latter a one-shot signal.
> Scope: FE | Status: implemented
>
> Layer P. Home: `pages/login` extended (+ a public `/signup` and `/invite/$token` on web, a `SignUp` screen in the mobile
> login stack), `features/sign-up/`, an app-layer **profile gate** provider on both apps, and the shared entry-path modules
> in `packages/auth`. It fills the sign-up funnel [53.auth-universe-gate](53.auth-universe-gate.md) and
> [change 02](../changes/archive/02.google-oauth-sign-in-on-web-and-mobile.md) both declared out of scope; it does **not**
> touch `gateDecision` — [81.landing-page](81.landing-page.md) owns it — or the session machine's state set (change 02).

## Purpose

v1 shipped a login door with no doorbell. [53.auth-universe-gate](53.auth-universe-gate.md) built the route gate
(authenticated → universe, settled signed-out → login) and [change 02](../changes/archive/02.google-oauth-sign-in-on-web-and-mobile.md)
added Google beside email+password, but both explicitly excluded "no sign-up funnel" — so today the only way a new person
gets an account is for someone to create it in the Supabase dashboard. There is also no `users` row anywhere in the
product (identity is 100% Supabase), which means no nickname, no timezone, and no invite.
Epic K's headless units build that row and its use-cases; this unit is the surface that fills it.

Three product requirements converge here. **[U6]** says the whole of sign-up is _one_ field — a nickname — because the
product's core objection is "일기 쓰는 게 귀찮다" and a registration form is the same friction one screen earlier.
**[U7]** says the timezone is never asked: the client detects it and the server stores it, because it is the boundary for
the daily `SMALL` reset ([G2]), the diary default date ([W5]), and the monotonic launch check ([T1]) — three things a
first-time user cannot possibly reason about. **[U8]** says an invite is _link-bound_: arriving through a link binds the
invite automatically, and there is no code field anywhere — [67.twinkle-relabel-and-ledger-ui](67.twinkle-relabel-and-ledger-ui.md)
deletes the shipped `twinkle_charge_invite_code_label` field for exactly this reason.

The structural problem this unit solves is subtler than a form. Because no per-user request may carry a user id (the
scope always comes from the JWT), `SignUp` needs an authenticated scope — so the Supabase credential must exist
**before** the nickname is known.
That opens a window in which a valid JWT belongs to a user with no profile: a Google sign-in that is really a sign-up
looks identical to a returning sign-in, and an email-confirmation link can land days later on a cold app. This unit
answers all of those with one thing — an **app-layer profile gate** whose only question is "does a profile exist" —
rather than a multi-step wizard each entry path has to re-enter at the right step. The absence of a `users` row is the
only signal; there is no `isNewUser` flag anywhere ([U2] stays intact — the first universe is still empty and
[53](53.auth-universe-gate.md)'s first-run welcome is untouched).

## Scope / Non-goals

**In scope**

- **A sign-up surface beside the shipped sign-in one** ([U5]) — the same `pages/login` slice extended with a `signUp`
  mode, on a public web route `/signup` and a `SignUp` screen in the mobile login stack, offering **both** providers:
  Google (the same `signInWithGoogle` action — Google has no separate sign-up) and email+password (a new
  `signUpWithPassword` on the `packages/auth` adapter/facade). Reciprocal navigation between sign-in and sign-up on both
  apps.
- **Credential creation in `packages/auth`** ([U5]) — `AuthAdapter.signUpWithPassword` + its Supabase and fake
  implementations + the facade method, returning `'signedIn' | 'confirmationRequired'`. **No new session-machine state**
  and **no `gateDecision` arm** (change 02's must-not-change list, and
  [81.landing-page](81.landing-page.md) owns that function).
- **The single nickname step** ([U6][U7]) — one field, rendered by an app-layer **profile gate** on both apps for any
  authenticated session whose `GetProfile` read returns no profile. It submits `SignUp` with the nickname plus the
  **auto-detected** timezone ([U7]) and the negotiated locale (the precedence
  [60.account-profile-model](60.account-profile-model.md) pins), and asks nothing else.
- **The profile gate** — a provider inside the authenticated subtree (web: above `PaletteBootstrap` in
  `AuthenticatedLayout`; mobile: above `MobilePaletteBootstrap` in `NavigationRoot`) that withholds routed children until
  a profile exists. This is the structural guard for [U1]: no product read can mount for a profile-less session because
  no product route mounts at all.
- **Invite-link entry** ([U8]) — the link shape `<origin>/invite/<token>` (plus `cosimosi://invite/<token>` on mobile),
  a public web route `/invite/$token` that captures the token and replaces itself with `/signup`, a mobile capture on the
  shipped inbound-link seam (the `isAuthCallbackUrl` precedent), a **pending-invite holder** that survives the OAuth
  round trip, and a token-agnostic acknowledgment on the sign-up surface.
- **A one-shot signup-completion signal** ([O3]) — set at the moment `SignUp` succeeds and readable exactly once, for
  [80.onboarding-tour](80.onboarding-tour.md) to start the tour "가입 직후 … 최초 1회만".
- **`signup_*` / `invite_*` i18n keys** in both catalogues, literary and restrained; **web + mobile parity** — both
  apps, both providers, no waiver.
- **`account.v1` client wrappers** for `GetProfile` and `SignUp` in `packages/api-client/src/account.ts` (the shared home
  the palette gate already reads through), extended by [64.my-page](64.my-page.md) rather than duplicated.

**Non-goals**

- **No `users`/`invites` schema, no `SignUp`/`GetProfile`/`GetInviteLink` implementation, no invite settlement, no signup
  bonus.** [60.account-profile-model](60.account-profile-model.md) owns the tables and the profile contract;
  [61.signup-and-invite-usecase](61.signup-and-invite-usecase.md) owns `SignUp`, the four-part valid-signup
  conjunction, and the deferred rewards. This unit calls them.
- **No profile editing.** Nickname / language / timezone editing, the linked-provider list, and the withdraw control are
  [64.my-page](64.my-page.md)'s `/me` profile and account tabs ([U9]). This unit writes the profile once, at birth.
- **No onboarding tour.** The tour, its steps, its skip affordance, and whether "seen" is persisted are
  [80.onboarding-tour](80.onboarding-tour.md) ([O1][O2][O4][O5]); this unit only emits the signal.
- **No landing page and no `gateDecision` change.** [81.landing-page](81.landing-page.md) owns the `'landing'` arm, `/`,
  and the trailing-slash policy. This unit consumes the shipped mapping read-only and adds only public sibling
  routes.
- **No inviter-side share surface.** Rendering the user's own invite link (`GetInviteLink`†, copy-to-clipboard, the
  reward explainer) belongs to [64.my-page](64.my-page.md); this unit owns the link **shape** and its capture, exported as
  one helper so the two cannot drift.
- **No provider linking or merge UI** ([U5]'s "한 사용자가 두 수단을 함께 연결할 수 있다") — change 02 excluded it and
  [64.my-page](64.my-page.md) shows the linked set read-only. Supabase's own identity-linking setting decides what
  happens when a Google sign-in matches an existing email; no app surface arbitrates it.
- **No password-reset, no email-OTP, no password policy in the client.** The project's Supabase settings own password
  strength; the surface renders the refusal it is given, so the client holds no rule that can drift from that setting.
- **No withdrawn-account restore surface.** The gate's third arm (profile read refused) renders a neutral
  retry-or-sign-out state; [62.withdrawal-usecase](62.withdrawal-usecase.md) owns whether a withdrawn refusal offers
  `RestoreAccount` there.
- **No universal/App-Link configuration** — `https://…/invite/<token>` opens the web surface on a phone; making it open
  the native app is deploy work — and **no new tuning scalars** (see Policy).

`features/sign-up` carries **no `model` and no `api` segment**: both would be byte-identical in the two apps and fail
`lint:fsd:layout` R4, so every pure piece lives in `packages/auth` and every RPC wrapper in `packages/api-client`
(the `createGetPalettePreferenceQueryOptions` precedent the palette gate already reads through). `apps/web/steiger.config.js`
gains one scoped `'fsd/insignificant-slice': 'off'` block for `features/sign-up`.

### The four surfaces and the one gate

| Where the visitor is                                        | What renders                                       | Owner                         |
| ----------------------------------------------------------- | -------------------------------------------------- | ----------------------------- |
| signed out, `/login` (web) · `Login` (mobile)               | sign-in: Google + email/password + "가입하기" link | 53, extended                  |
| signed out, `/signup` (web) · `SignUp` (mobile)             | sign-up: Google + email/password + invite ack      | **this unit**                 |
| signed out, `/invite/<token>` · `cosimosi://invite/<token>` | token captured, replaced by the sign-up surface    | **this unit**                 |
| authenticated, **no profile** (any route, any app)          | the nickname step, instead of routed children      | **this unit**                 |
| authenticated, profile present                              | the universe / the requested route                 | 53, untouched                 |
| authenticated, profile read refused                         | a neutral retry-or-sign-out state                  | this unit (arm), 62 (restore) |

Both public routes sit under `rootRoute`, outside `authenticatedRoute` (which carries `authGuardBeforeLoad` and
`PaletteBootstrap`), and both hold on a `'hold'` decision and bounce a `'universe'` decision exactly as the shipped
`LoginRoute` does — read through `gateDecision`, never re-implemented. Paths carry no trailing slash, matching the
shipped `/login` and `/diary`; the global trailing-slash policy remains plan 81's. `loginReturnTarget` is extended to
reject `/signup` and any `/invite/...` pathname in addition to `/login`, because returning a freshly signed-in user to a
public entry path would bounce them straight back out.

On mobile the login stack becomes two screens (`Login`, `SignUp`) and neither is a deep-link target — the shipped rule
that "only the authenticated stack's screens are link targets" stands, which is why the invite token is captured on the
link seam rather than by a route.

### Credential creation ([U5]) — one adapter method, no new session state

`AuthAdapter` gains `signUpWithPassword(credentials): Promise<AuthSession | null>`, implemented with
`client.auth.signUp`; `null` means Supabase created the user but returned no session (the project's email-confirmation
setting is on). `AuthFacade.signUpWithPassword(credentials): Promise<'signedIn' | 'confirmationRequired'>` translates
that: a session drives the existing `AUTHENTICATED` path, and a `null` settles the machine back to `signedOut` with the
shipped `SIGN_OUT` event — **nothing failed, so `failed` would be a lie, and a new `confirmationPending` status would
change `gateDecision`'s domain**, which [81.landing-page](81.landing-page.md)'s ownership of that function forbids and
change 02's must-not-change list already ruled out. A string
union rather than a boolean makes the two outcomes impossible to conflate at the call site. `FakeAuthAdapter` implements
it with an immediate fake session, so the keyless dev/test path keeps working (change 02's precedent).

Google sign-up is not a distinct action: `signInWithGoogle` creates the Supabase user when absent, and its redirect
origin is fixed and allowlisted (`${window.location.origin}/` on web, `cosimosi://auth-callback` on mobile) — this unit
does **not** add a redirect URL, so the Supabase allowlist and `DEPLOY.md` §5 are untouched. The consequence is that
nothing about the return trip can tell a first Google sign-in from the thousandth; the profile gate is what makes that
irrelevant.

### The profile gate — the nickname step is a gate, not a route ([U6][U1])

The gate reads `GetProfile`† (Query, `enabled` on a non-null `userId`, the `PaletteBootstrap` shape) and resolves to
exactly three arms: **profile present** → render children; **profile absent** → render `NicknameStep`; **read refused**
→ render a neutral retry-or-sign-out state. It sits _above_ `PaletteBootstrap` on both apps, so a profile-less session
issues no palette read either, and the nickname step renders outside the palette-dependent gate — consistent with
[tech/auth.md](../tech/auth.md)'s shipped rule that entry surfaces sit outside it.

**Absence must be an unset message field, not an error code.** This unit requires `GetProfileResponse` to carry an
optional `Profile` (absent = no `users` row) rather than signalling absence with a `NOT_FOUND` reason. Reason: a normal,
expected state expressed as a transport error forces the gate to sniff error reasons, and TanStack Query would treat the
most ordinary moment in an account's life as a failure (retry, error boundary, `throwOnError`). With an unset field the
three arms above are a total function over the response, and the "refused" arm means what it says.

Because the step is a component the gate renders — not a route, not a screen, not a stack — it cannot be navigated to,
bookmarked, linked, or skipped by URL, and every entry path converges on it for free: a password sign-up that returned a
session, a Google sign-in that was really a sign-up, an email-confirmation link clicked three days later on a cold app,
and a user who force-quit mid-signup all land in the same place with no wizard state to restore.

### The nickname step's payload ([U6][U7])

`SignUp` is called with exactly three user-facing inputs, plus the captured invite token when one is held (the
fourth field on [61](61.signup-and-invite-usecase.md)'s `SignUpRequest`) and nothing else:

- **nickname** — the one field. Validated by `packages/auth/src/nickname.ts`: trimmed, non-empty, length counted in
  **Unicode code points** (`[...s].length`) so a Korean or emoji nickname counts as the user sees it, bounded by
  `VALUES.account.nicknameMinLength` / `nicknameMaxLength` (keys owned by plan 60). Nicknames are **not unique** —
  `users` has no unique index on it — so there is no availability check, no debounce, and no lookup RPC.
- **timezone** — auto-detected, never asked ([U7]): `Intl.DateTimeFormat().resolvedOptions().timeZone` on web; on mobile
  a `readDeviceTimeZone()` seam beside the shipped `readDeviceLocale()` in `shared/native/` (Hermes' `Intl` coverage is
  not guaranteed, and a native seam is where that uncertainty belongs — §3.5). Detection failure sends the literal
  `"UTC"`, never an empty string — [61](61.signup-and-invite-usecase.md) **rejects** an unresolvable zone with
  `ACCOUNT_TIMEZONE_INVALID` rather than guessing, so the client must supply the fallback. **The client detects, the
  server validates**, so there is no shared IANA table to drift and no client-side zone list. A wrong guess is never
  terminal — `/me` edits it (plan 64), and the monotonic reset anchor means a later change cannot mint a fresh `SMALL`
  grant.
- **locale** — the locale the app is currently rendering, from the shipped i18n negotiation, which the locale
  precedence [60.account-profile-model](60.account-profile-model.md) pins then treats as the server-authoritative value
  from that point on.

`SignUpRequest` carries **no `user_id`** (the scope is the JWT) and **no provider field**: this unit
requires plan 61 to derive the `auth_providers` row from the authenticated token's identity, so a client cannot claim
`GOOGLE` while signing up with a password. Both absences are contract shape, not validation.

### Invite-link entry ([U8]) — capture, hold, bind, forget

The link is `<origin>/invite/<token>`, composed FE-side from the token `GetInviteLink`† returns; `inviteLinkPath(token)`
in `packages/auth` is the single definition, so plan 64's share surface and this unit's capture route cannot disagree.
Mobile additionally accepts `cosimosi://invite/<token>`, captured on the shipped inbound-link seam with the same
exact-address discipline as `isAuthCallbackUrl` (the token must be the whole remainder of the path) and filtered out of
the navigation linking config — a callback address, not a screen.

Capture must survive a departure from the app: the web `/invite/$token` route writes the token into the pending-invite
holder and **replaces** itself with `/signup`, so the token leaves the address bar and the history entry; a Google
sign-up then leaves the origin entirely and returns to the fixed allowlisted root. The holder is therefore backed by
`sessionStorage` on web (survives the full-page OAuth round trip, dies with the tab) and by module memory on mobile (the
process survives the system-browser trip), behind one injected storage port bound in each app's auth provider — the
`SupabaseAuthClientOptions.storage` / `createInMemorySecureTokenStorage` pattern. The holder is **not** registered in the
user-scope reset registry: its whole purpose is to survive the anonymous→user scope change that the registry exists to
clear, so registering it would erase every invite at the instant of sign-in. Its lifecycle is explicit instead — the
token is cleared when `SignUp` consumes it, and when the gate resolves _profile present_ (an established account has
entered, so no `SignUp` will ever be sent from this client). Since `SignUp` is the only message with a field for the
token, and it is reachable only when no profile exists, a held token cannot attach to anyone but a brand-new account.

The sign-up surface shows a **token-agnostic** acknowledgment — that the visitor arrived through an invite, with **no
inviter identity and no amount**. No RPC resolves a token before signup, so a link holder cannot learn whose link it is
(there is no message to ask), and settlement is deferred to the invitee's first star launch, so naming a figure up front
would be a promise the product does not keep at that moment. A token that turns out to be expired, self-referential, or
from a withdrawn inviter is **inert** — `SignUp` still creates the profile, and this unit therefore has **no
invite-failure branch**: "stranded outside your own universe because of someone else's stale link" is unrepresentable.

### Control state (§3.2) and the [O3] handoff

- **Credential step** — `signup.machine.ts`: `form → creating → confirmationSent | failed`, with `signedIn` handled by
  the session machine and the route gate (the surface unmounts). `confirmationSent` is the reason this machine exists at
  all: it is the one phase the session machine must not learn.
- **Nickname step** — the shipped `asyncCommandMachine` (`packages/state-machine`, `idle → submitting → succeeded |
failed` with a monotonic `attempt` so a late response is discarded). This unit is its first production consumer; a
  bespoke second copy of the same lifecycle would be exactly the duplication §3.2's catalog exists to prevent. The two
  steps are separated by an authentication boundary and possibly a cold start, so they are deliberately **not** one
  machine — a machine whose initial state is a parameter is two machines.
- **Data** stays in Query (the profile) and in the two module-scoped holders; machine context holds control metadata
  only.
- **The [O3] signal** — `signup-completion.ts` records completion at the instant `SignUp` succeeds and offers a
  take-once read. This unit owns _when signup happened_; [80.onboarding-tour](80.onboarding-tour.md) owns _whether the
  tour has been seen_ and any persistence of that. The flag is set while the scope key is already the new user, so it
  **is** registered in the reset registry (`resetSignupUserState()`, added once to
  `@cosimosi/auth/user-state`'s shared inventory, per [tech/auth.md](../tech/auth.md)) — unlike the invite
  holder, and the seam documents why the two differ.

### Copy (i18n) — literary and restrained

Every string resolves through `packages/i18n` in both `en.json` and `ko.json`, under the `signup_*` and `invite_*`
prefixes, keys naming a UI role (`signup_nickname_label`, not `signup_users_nickname`). The voice is the shipped login
voice — 다시 오셨네요 / 들어가기: quiet, first-person-free, no exclamation, no decorative emoji, no translation-ese. The
nickname step names what the field is for rather than instructing ("여기서는 어떤 이름으로 불릴까요"), the confirmation
state states the fact plainly, and the invite acknowledgment is a single line with no reward figure. `pnpm lint:raw-strings`
is the gate; `pnpm gen:messages` + `pnpm check:gen` keep the generated modules fresh. [I12] applies: these are public
surfaces, so no claim about brains or therapy appears on them.

### Golden-parity stance

**No pure function here mirrors TS↔Go, and none may.** The nickname rule is the only pure predicate this unit adds, and
it is deliberately **advisory**: the server re-validates and its refusal is authoritative, so the surface renders the
server's reason rather than assuming its own check was complete. Adding a golden fixture would assert a parity the design
does not want — a client that believed its own check would silently diverge the day plan 60 tightens the rule. The
timezone follows the same split (client detects, server validates), and no other value is computed here: the profile, the
provider set, and every reward figure are read or granted server-side.

## Acceptance Criteria

1. A **sign-up surface** exists on both apps — a public `/signup` route on web and a `SignUp` screen in the mobile login
   stack — offering **both** methods: Google and email+password, with reciprocal navigation to and from the sign-in
   surface ([U5][U6]).
2. `packages/auth` exposes `signUpWithPassword` on the adapter and the facade, returning `'signedIn' |
'confirmationRequired'`; the Supabase and fake adapters both implement it, and the **session machine's status set and
   `gateDecision`'s arms are unchanged** (change 02).
3. A Supabase sign-up that returns no session leaves the surface in a `confirmationSent` state and the session settled
   `signedOut` — never `failed`, never stuck in `signingIn`; clicking the confirmation link later lands the user in the
   nickname step with no wizard state to restore ([U5][U6]).
4. An **app-layer profile gate** on both apps reads `GetProfile`† and renders exactly one of: routed children (profile
   present), the nickname step (profile absent), or a neutral retry-or-sign-out state (read refused). It sits above the
   palette bootstrap, so **no product route and no product read mounts for a profile-less session** ([U1][I11]).
5. Absence of a profile is an **unset message field**, not an error reason: the gate performs no error-reason sniffing,
   and the "refused" arm is reached only by a genuine transport/authorization failure ([U1]).
6. The nickname step asks for **exactly one field** and submits `SignUp` with the nickname, the **auto-detected**
   timezone, and the negotiated locale — the timezone is never presented as a question and no other field exists on the
   surface ([U6][U7]).
7. Nickname validation is trimmed, non-empty, and bounded by `VALUES.account.nicknameMinLength` /
   `nicknameMaxLength` counted in **Unicode code points**; there is **no** nickname availability check, lookup RPC, or
   uniqueness claim, and the server's refusal is rendered as authoritative ([U6]).
8. `SignUpRequest` carries **no `user_id`** and **no provider field** — the scope and the `AuthProvider` are derived
   from the authenticated token — and it has **no field** for any memory, palette, ornament, or amount
   ([I11][U1]).
9. Arriving at `<origin>/invite/<token>` (web) or `cosimosi://invite/<token>` (mobile) captures the token, **replaces**
   the URL/route so the token leaves the address bar and history, and shows the sign-up surface; **no code-entry field
   exists anywhere in the app** ([U8]).
10. The captured token survives the Google OAuth round trip on both apps and is sent with `SignUp`; it is cleared when
    `SignUp` consumes it and when the gate resolves _profile present_; it is deliberately **not** in the user-scope reset
    registry, and that exception is documented at the seam ([U8], [tech/auth.md](../tech/auth.md)).
11. The invite acknowledgment names **no inviter and no reward amount**, and an expired / self-referential / withdrawn-inviter
    token is **inert**: `SignUp` still succeeds and the user still reaches their universe — there is no invite-failure
    branch ([U8][G6]).
12. On `SignUp` success a **one-shot completion signal** is recorded and readable exactly once, and it is cleared by the
    shared user-scope reset registry consumed by both apps ([O3], [tech/auth.md](../tech/auth.md)).
13. The credential step's control state is one XState machine (`form → creating → confirmationSent | failed`) and the
    nickname submit reuses the shipped `asyncCommandMachine`; the profile is Query data and machine context holds control
    metadata only (§3.2).
14. A first-run user who completes signup lands on the **empty universe with the gray latent field** and the single
    일기 쓰기 affordance — [53.auth-universe-gate](53.auth-universe-gate.md)'s first-run welcome is reused, not
    reimplemented, and nothing is seeded ([U2][V7]).
15. **All** user-visible copy resolves through the i18n seam in both `en.json` and `ko.json` under `signup_*` / `invite_*`
    (`pnpm lint:raw-strings` and `pnpm check:gen` pass), in a literary, restrained voice with no reward figure and no
    [I12]-violating claim on the public surfaces.
16. **web + mobile parity** ([00.overview](00.overview.md) §4): the same surfaces, the same gate, the same shared
    modules from `packages/auth` and
    `packages/api-client`; `features/sign-up` carries no `model`/`api` segment, and `pnpm lint:fsd:layout`,
    `pnpm lint`, `pnpm typecheck`, `pnpm test:web`, `pnpm typecheck:mobile`, and `pnpm build:web` pass with **no BE
    change** (no proto, migration, or query authored here).
