# 51. Palette customization

> A per-mood emotion-color preference over the authored default table, applied through plan 17's
> unchanged `setMoodPalette` seam. One stored preference, one fallback: a feeling either has a color
> the user chose or it keeps the authored one.
> Scope: FS | Status: built ([job 62](../jobs/archive/62.palette-customization.md),
> [job 108](../jobs/archive/108.per-mood-emotion-color-onboarding.md),
> [job 109](../jobs/archive/109.retire-the-named-palette-registry.md))

## Purpose

Color perception is personal and cultural. A memory must still mean what it meant when written, but
the color used to present that meaning should match the reader's own emotional vocabulary. Palette
customization therefore changes only the downstream `Mood → Color` projection. It never changes a
memory's mood, axes, strength, position, connection, or forgetting behavior ([I3][I11][P2]).

The preference authority is `mood_colors(user_id, mood, color)`. A user may override any subset of
the thirteen moods; every absent row resolves to the unchanged authored default color.

An earlier build offered a catalog of named thirteen-color tables instead, stored as one
`palette_preferences.palette_id` per user. [P1] asks that the user be able to change the mood↔color
mapping — it never asked for named sets — and the per-mood editor answers it more directly, so the
catalog, the id, its two RPCs and its table were retired
([job 109](../jobs/archive/109.retire-the-named-palette-registry.md)). What survives of the second
authored table is its thirteen colors, kept as `ALTERNATIVE_MOOD_COLORS`: a second complete table the
demo surface can swap in and the axis guardrail is checked against, carrying no id and reachable from
no preference.

The per-mood surface is introduced immediately after first signup and remains available from My
page. Skipping creates no preference row or durable seen flag.

## Scope

### In scope

- One authored default table in `packages/emotion` (`defaultMoodPalette`) plus
  `ALTERNATIVE_MOOD_COLORS` as authored content — no ids, no registry.
- Account-scoped per-mood `GetMoodColors` / `SetMoodColor`, with at most one row per user and mood.
- Aggregate-only `GetMoodColorStats(mood)` recommendations, backed by anonymous counts.
- An app-layer bootstrap that resolves per-mood rows over the authored default before releasing
  palette-dependent children, gating on `GetMoodColors` alone.
- A first-signin web/mobile screen after nickname and before the universe, showing one real star per
  mood against the night sky.
- A web/mobile per-mood editor in My page.
- OkLab/OkLCH conversion, hue buckets, lightness snapping, and warn-only near-duplicate detection.
- The existing warn-only palette-axis check.

### Non-goals

- No social palette sharing, following, or individual-account drill-down from statistics.
- No purchase, unlock, achievement, ornament, or Twinkle gate; colors stay free ([P10]).
- No edit to emotion facts, star brightness, layout, connections, forgetting, or meaning.
- No renderer knowledge of accounts or preferences. Rendering receives resolved colors only.
- No durable onboarding seen/skipped record. The take-once in-memory signup handoff owns exposure.
- No generative accessibility engine. The picker is bounded by the axes a stored color keeps: free
  hue, gamut-bounded chroma, and the three authored lightness steps.

## Design

### The one apply seam

`moodColor(mood)` remains the only color entry point for meaning-bearing presentation.
`setMoodPalette(resolved)` remains the only swap operation. Neither API accepts a memory, position,
strength, or connection.

The resolved table is:

```text
defaultMoodPalette complete MoodPalette
  → overlay zero to thirteen mood_colors rows
  → setMoodPalette(resolved)
  → every consumer reads moodColor(mood)
```

The web and mobile app-layer palette bootstraps hold palette-dependent children until
`GetMoodColors` settles and the resolved table is applied — one read, and the readiness test is that
the thirteen live `moodColor` values equal the resolved ones. An unavailable read settles too, as an
empty overlay on the authored default, so an unreachable preference never leaves a user waiting on a
gate that cannot open. Live edits use the same seam and do not refetch `GetUniverse`.

A scope transition clears the previous account's colors through `resetMoodPalette()` before the next
account's read applies its own; colors are per-user, so the incoming universe must not flash someone
else's sky.

`ALTERNATIVE_MOOD_COLORS` is authored recommendation content only. Both authored tables are complete
and pass the warn-only axis check; the default table is additionally pairwise separated above the
configured near-duplicate threshold.

### Per-mood persistence and write transaction

`mood_colors` stores:

```text
(user_id, mood, color, updated_at)
PRIMARY KEY (user_id, mood)
```

`mood` is the closed thirteen-value set. `color` is lowercase `#rrggbb`. Missing rows are meaningful
absence, not an implicit database default.

`SetMoodColor` validates the authenticated, provisioned account; validates mood and color; snaps the
color to an emotion lightness step; derives its hue bucket; then runs one transaction:

1. serialize the `(user_id, mood)` write, including the first write where no row can be row-locked;
2. read the previous row;
3. decrement its exact aggregate swatch when the color changed;
4. upsert the one per-user row;
5. increment the new exact aggregate swatch.

An identical retry commits without moving a counter. The transaction-level advisory lock prevents
two concurrent first writes from contributing twice.

Withdrawal removes `mood_colors` with the other account dependents. Anonymous historical counters
contain no account key.

### Recommendation aggregate

`mood_color_counts` contains only:

```text
(mood, hue_bucket, color, count, first_counted_at)
PRIMARY KEY (mood, hue_bucket, color)
```

There is deliberately no `user_id`, and `first_counted_at` is not one either — it stamps when the
color first entered the aggregate across every account, and resets if a deleted row's color returns.
Twelve chromatic buckets divide the OkLCH hue circle by the configured degree width; colors at or
below the configured chroma floor use bucket 12, the near-neutral bucket.

`GetMoodColorStats(mood)` groups exact colors by bucket and chooses the most-chosen exact color as
the bucket swatch. Buckets are ordered by count, then by earliest `first_counted_at`, then by
hue_bucket; the same order breaks a tie between two colors competing to be one bucket's swatch, with
lexical color last. A bucket's share is `bucket_count / total_mood_count` and is always present —
there is no sample floor, so a single choice reports its bucket at `1.0`. The response exposes
exactly `bucket`, `share`, and `swatch_color`.

The client presents typed presets built from that list — authored, `palette.popular_preset_count`
aggregate-backed ones in the order received, and random. The authored preset takes its share from its
own bucket in the same pool, which is then skipped in the ranked slots. The client never re-sorts the
aggregate and never fills empty slots with authored colors dressed up as choices; a write invalidates
the cached read for that mood, since it changed the aggregate the shares came from.

### Color arithmetic

`packages/emotion/src/oklab.ts` is the TypeScript conversion seam. The account context has a small Go
port for server-authoritative validation and storage; a checked-in fixture pins the two
implementations.

- Stored lightness snaps to the nearest existing emotion ladder step: `0.80`, `0.72`, or `0.63`.
- Hue and chroma are preserved within the unavoidable 8-bit sRGB encoding tolerance.
- Near-neutral classification uses `palette.near_neutral_chroma_max`.
- `nearDuplicateMood` compares OkLab ΔE against `palette.similar_delta_e_min`. It returns a notice
  target and never rejects a choice.
- `checkPaletteAxisConsistency` remains a separate warn-only quality check.

### First-signin color screen

The profile gate still asks exactly one product question: nickname. On successful signup it consumes
the take-once signup-completion signal and shows `features/choose-mood-colors` before routed universe
children.

The screen renders thirteen instances of the shipped star body using the shared deterministic field
generator and a real `SkySphere`; it authors no coordinates and reads no universe memory. The shared
`universe-render/MoodStarLayer` adapter receives only a complete resolved color table and
`onSelect`—never an account or preference—and does not alter the existing episodic `StarLayer`.
Selecting a star selects its mood. Selecting one of the three swatches optimistically updates the
resolved table and persists that mood. The other twelve remain visible for comparison.

The always-reachable skip/continue action writes nothing and releases the universe immediately. The
gate records the signup-completion handoff again before release so plan 80's take-once tour trigger
still receives it. No absence-of-color heuristic is used because a legitimate skip also has no rows.

### My page editor

The feeling-colors tab shows the thirteen resolved colors and nothing to choose. Opening one hands
the editing to `Dialog`, which is a centred modal on a wide screen and a bottom sheet on a narrow
one. The dialog composes the four presets, a free OkLCH picker (hue · chroma-as-a-fraction-of-gamut ·
the three lightness steps), and a live warn-only risk notice; a risky color takes one more explicit
confirmation before it is kept. Nothing writes until Save, at which point the choice applies
optimistically through `setMoodPalette`, persists, and rolls back to the prior resolved table on
failure — the dialog staying open so the save can be pressed again. A near duplicate displays a
notice without blocking.

than tuning values.

## Acceptance criteria

1. `packages/emotion` publishes no palette id, registry, or id-keyed lookup; the authored default and
   `ALTERNATIVE_MOOD_COLORS` are complete tables and both pass the warn-only axis check.
2. `mood_colors` is the only stored color preference; no palette-id table or RPC exists.
3. A user may store at most one lowercase validated color per mood; an absent row inherits the
   corresponding authored default color.
4. Bootstrap overlays per-mood rows on the authored default from `GetMoodColors` alone and releases
   palette-dependent children only after the resolved table is applied; a scope transition leaves no
   color from the previous account applied.
5. Signup shows nickname, then the thirteen-star color screen, then the universe on web and mobile.
   Skip is always reachable, writes no row/flag, and preserves plan 80's take-once handoff.
6. Choosing a recommendation updates the selected star live and persists only that mood.
7. Every mood offers exactly the configured number of recommendations. A below-floor bucket shows no
   ratio; an at/above-floor bucket shows its share.
8. Aggregate storage has no user id or individual read. It uses twelve configured hue buckets plus
   one near-neutral bucket and shows the most-chosen exact color per bucket.
9. Write-row and aggregate-counter changes are atomic, idempotent, and safe under concurrent first
   writes.
10. Stored colors land on an emotion lightness step while preserving the selected hue/chroma within
    encoding tolerance.
11. Near-duplicate ΔE produces a non-blocking notice.
12. The My page editor applies through the unchanged seam with no `GetUniverse` refetch.
13. Rendering stays preference-agnostic; emotion meaning, brightness, coordinates, connections, the
    nickname field shape, and warn-only axis behavior are unchanged.
