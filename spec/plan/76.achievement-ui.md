# 76. achievement ui

> Achievement UI — the presentation half of Epic O: the **achievements tab** inside `/me` (grouped list, honest
> progress, the 받기 button, the reward reveal) plus a **light unlock notice** that never interrupts the universe
> ([A5]). Claiming is deliberately manual ([A4]) — the product refuses to auto-grant so the user gets a moment of
> noticing what they earned — and the notice is a **diff of a read, never a push**, because plan 75's recorder returns
> `error` alone. It also widens the app's toast seam: the shipped host is error-only, so this unit promotes a single
> queued viewport both owners push into. Scope: FE | Status: **built** (job 115)
>
> Layer P. Home: a NEW `packages/achievement` mirror + `features/{achievement-list,achievement-notice}` on both apps,
> a `progress` primitive pair in `packages/ui`, and one toast host per app. It fills the last Epic O seam and leaves
> the ledger row, the ornament's name and the catalog itself to siblings.

## Purpose

Epic O's machinery is finished before a single pixel exists: [74.achievement-catalog-model](74.achievement-catalog-model.md)
owns the 39-row catalog, the counters and `ListAchievements`†;
[75.achievement-tracking-usecase](75.achievement-tracking-usecase.md) owns the recorders and `ClaimAchievement`. But
[A4] makes the reward **unreachable without a UI**: a met condition arms a button and pays nothing until the user
presses it. Ship 74 and 75 alone and every achievement a user earns sits stranded in `achievement_progress` with
`claimed_at IS NULL` forever. This unit is the only thing that turns progress into currency.

That matters more in v2 than it sounds. Payment is deferred to v3, so `GENERAL` Twinkle — the tier that buys
ornaments ([P9]) — comes from exactly three places, and achievements are one of them ([G3]). A user who cannot find,
read, or claim their achievements is a user with no way to fund decoration except writing.

The design problem is the notice. [A5] wants the user told **at the moment of achievement**, "우주 몰입을 방해하지
않는 수준". The server cannot tell us: the recorder port's only return is `error`
([75.achievement-tracking-usecase](75.achievement-tracking-usecase.md)), there is no event bus, no streaming
(ARCHITECTURE §2.7) and no polling (§3.2). So the notice must be inferred from a read —
and the honest way to do that is to diff the `ListAchievements` response the actions already invalidate. That
constraint turns out to be the feature's best property: nothing about an achievement can ever be _pushed_ into the
universe, so an achievement can never interrupt writing, recall, or a render frame. It can only be noticed afterwards.

The second problem is the toast itself. The repo has exactly one toast owner — `WebErrorProvider` /
`MobileErrorProvider`, each holding its own `useState` and rendering the shipped `Toast` into a fixed bottom portal.
A second independent owner would portal into the identical slot and overlap it. So this unit does not add a second
host; it promotes the one that exists into a **single queued viewport** both owners feed.

## Scope / Non-goals

**In scope**

- **`packages/achievement`** (NEW, `@cosimosi/achievement` — one of v2's new FE packages): the `ListAchievements` DTO
  mirror, the id→copy projection, progress/claim-state formatting, the unlock diff, and the React seam (query,
  invalidate, claim mutation). Shared verbatim by both apps ([A2][A4]).
- **`features/achievement-list`** — the `/me` achievements tab body ([U9][A4]): rows grouped by axis, a determinate
  progress meter, the reward line, the 받기 button, and the reward reveal.
- **`features/achievement-notice`** — the [A5] unlock notice: mounted once inside each app's authenticated shell, it
  diffs `ListAchievements` and pushes at most `achievement.unlock_notice_max` quiet toasts.
- **The toast seam widening**: `ToastQueueContext` + `usePushToast` in `packages/ui` (platform-pure, the
  `packages/errors/src/react.ts` shape), one forked host per app (`app/providers/toast-provider.tsx`), and the
  existing error providers rewired to push instead of render. One toast element exists in the tree, ever.
- **`packages/ui` `progress` primitive pair** (`progress.tsx` + `progress.native.tsx`) — none exists; the
  achievements tab is the app's first determinate meter.
- **All `achievement_*` i18n keys** — 39 title/body pairs, 9 axis labels, the affordance and reveal copy, and
  the FE mapping + copy for plan 75's five `ACHIEVEMENT_*` refusal reasons in `packages/errors`.
- **The steiger + boundary blocks** for the two new slices, including the import ban that keeps this vertical away
  from the meaning layer ([A6][I11]).

**Non-goals**

- **No catalog, no condition, no target, no reward amount is computed here.** Every number rendered arrives on the
  wire from `ListAchievements` ([74.achievement-catalog-model](74.achievement-catalog-model.md)); the FE holds no
  condition table and no evaluator (that plan's golden-parity stance is binding).
- **No claim logic, no payout, no idempotency.** `ClaimAchievement`, the two granter legs and the replay semantics are
  [75.achievement-tracking-usecase](75.achievement-tracking-usecase.md). This unit calls the RPC and renders the
  result.
- **No proto, no Go, no migration, no `http-policy.ts` entry.** `ListAchievements`† is classified by plan 74;
  `ClaimAchievement` is a mutation and needs none — only `NO_SIDE_EFFECTS` reads are classified.
- **No tab shell, no route, no tab id.** `/me`, the five tabs and `/me?tab=achievements` are
  [64.my-page](64.my-page.md). As-built the composition is **two** tables — web's `pages/me/model/tabs.ts`
  (`ME_TABS`/`parseMeTab`, web-only) + mobile's inline `meTabs`/`tabViews` in `pages/me/ui/MePage.tsx` — each with its
  own `AchievementsPending` placeholder. This unit edits exactly one row **in each** and retires
  `me_achievements_pending` (which also retires the mobile `App.test.tsx` assertion that referenced it).
- **No balance figure and no ledger row.** The stardust tab, `GetLedger`, the relabel and the synthetic daily-refill
  marker are [67.twinkle-relabel-and-ledger-ui](67.twinkle-relabel-and-ledger-ui.md); this unit only invalidates the
  balance after a claim so that tab is correct when opened.
- **No ornament name, image, price or preview.** [71.ornament-catalog-model](71.ornament-catalog-model.md) owns the
  catalog and [73.decoration-panel](73.decoration-panel.md) owns every `store_*` string ([P11]'s
  "가격 대신 획득 조건" line included). This unit reads **no** `store_*` key and imports **no** store package — an
  ornament reward renders as one `achievement_*` line, and the item itself is met in 우주 꾸미기.
- **No new XState machine.** The claim is the shipped `asyncCommandMachine` from `@cosimosi/state-machine` (see
  Design); authoring a per-app feature machine would fail `lint:fsd:layout` R4 anyway.
- **No badge, count or dot on the `/me` tab label, and no notification on the universe HUD** beyond the [A5] toast —
  a manual claim must not become a nagging surface.
- **No demo surface.** `/demo` is outside `authenticatedRoute`, so the notice host cannot mount there and
  `ListAchievements` is never called on a public route ([I13] isolation — [79.demo-page](79.demo-page.md)).

## Design

### Placement (FSD §3.1 decision procedure)

```
packages/achievement/src/
├── achievement.ts            AchievementView (proto DTO → FE mirror), AchievementAxis re-export
├── achievement-copy.ts       achievementTitle/achievementBody/axisLabel  (the moodLabel precedent)
├── progress.ts               progressRatio(), claimState() → 'locked' | 'claimable' | 'claimed'
├── unlock-diff.ts            newlyAchieved(previous, next) — pure set diff, no clock
├── react/achievements.ts     useAchievements() · useInvalidateAchievements()
├── react/claim.ts            useClaimAchievement()
└── index.ts · react.ts

apps/{web,mobile}/src/features/
├── achievement-list/         ui (AchievementList · AchievementRow · RewardRevealDialog) — the tab body
└── achievement-notice/       ui (AchievementNoticeHost) — the [A5] watcher, mounted once

packages/ui/src/primitives/progress.tsx | progress.native.tsx   NEW
packages/ui/src/toast-queue.ts                                  NEW — platform-pure context + hook
apps/{web,mobile}/src/app/providers/toast-provider.tsx          NEW — the single forked host
apps/{web,mobile}/src/app/providers/error-provider.tsx          EDITED — pushes instead of rendering
```

Two slices rather than one, because they are two different user moments: reading and claiming is a deliberate visit
(`features/achievement-list`, composed by `pages/me`), while being told is ambient (`features/achievement-notice`,
mounted by the app shell). Collapsing them would put a page-scoped list inside an always-mounted host. Each new
single-reference slice gets its own scoped `'fsd/insignificant-slice': 'off'` block in
`apps/web/steiger.config.js`. The mirrors, formatting and hooks live in `packages/achievement`, not `entities/` —
every v2 domain mirror is a package, and a byte-identical `model` module in both apps fails `lint:fsd:layout` R4.

`features/achievement-notice` is mounted **inside the authenticated subtree only**: web in `AuthenticatedLayout`
(`apps/web/src/app/routes/route-screens.tsx`), mobile in the authenticated branch of
`apps/mobile/src/app/navigation/NavigationRoot.tsx`. That placement is the guard for three separate things — a
signed-out visitor never fetches `ListAchievements`, `/demo` (a public route outside `authenticatedRoute` —
[79.demo-page](79.demo-page.md)) cannot
mount the watcher, and sign-out unmounts the snapshot ref so no achievement state survives a user change.

### The tab — grouped, honest, one claim at a time

`ListAchievements` returns the **whole** catalog in a server-fixed order (axis, then target ascending), so the list
renders it verbatim and sorts nothing. Rows group under the nine [A2] axis headings; an unachieved row is present and
readable, never hidden, because [A1]'s "제품을 원래 방식대로 쓰면 도달하는 지점" is only legible if the user can see
where they are. Each row carries: title, one-line body, a determinate progress meter reading `progress`/`target`
verbatim from the wire, the reward line, and the affordance.

The affordance is `claimState(entry)`, three states and no fourth:

| state       | condition              | affordance                       |
| ----------- | ---------------------- | -------------------------------- |
| `locked`    | `!achieved`            | progress meter, no button        |
| `claimable` | `achieved && !claimed` | the enabled 받기 button ([A4])   |
| `claimed`   | `claimed`              | a quiet 받았어요 line, no button |

`claimState` is a pure function over two server booleans — there is no local "optimistically claimed" state and no
optimistic patch, so a failed claim can never leave a row looking paid. A header line above the list states how many
rewards are waiting (`achievement_claimable_count`), which is the whole reason a manual claim is tolerable: [A4]
trades convenience for a moment of noticing, and a user who cannot find the waiting rewards gets the cost without the
benefit. The count is the only summary; there is no badge on the tab label or the universe HUD (a nag would undo the
same trade).

Reward rendering: a stardust reward shows `achievement_reward_twinkle` with the server-resolved `rewardTwinkle`; an
ornament reward shows the single line `achievement_reward_ornament`. **The ornament is not named here.** [73] owns
every `store_*` string and [P11] puts the item's identity in the decoration catalog next to its acquisition
condition; a second name for the same object on a second surface is exactly the drift the one-key-one-role i18n rule
exists to prevent, and 73 and 76 are built in parallel ([00.overview](00.overview.md) §5.6).

### The claim and the reveal ([A4])

One claim may be in flight at a time — an exclusive phase, so §3.2 puts it in XState. It does **not** get a new
machine: `asyncCommandMachine` (`packages/state-machine`, `idle → submitting → succeeded | failed | cancelled`) is
exactly this lifecycle, and its context already holds a command id and nothing else. `features/achievement-list`
binds it with the pressed `achievementId` as the command id. The structural consequence is worth stating: because a
single machine instance owns the phase, a second row's button cannot start a second claim, so the double-claim window
narrows to the server's `UNIQUE (user_id, achievement_id)` guard rather than being defended in the UI.

`useClaimAchievement()` (in `packages/achievement`) wraps the mutation and invalidates **only** the
`AchievementService` key. The other two invalidations are composed at the feature, which is the layer permitted to
know about more than one context: the shipped `useInvalidateTwinkleBalance()` (`@cosimosi/twinkle/react`) so the
balance and the stardust tab reflect the credit ([G7]), and — only when `grantedOrnamentId` is non-empty — [71]'s
`GetCatalog` invalidation so the newly owned ornament is owned in the decoration panel. Keeping those out of
`packages/achievement` keeps the package free of a `@cosimosi/store` dependency it would otherwise need.

On `succeeded` the row opens **`RewardRevealDialog`** — the shipped `Dialog` primitive pair, not a toast. This is the
one place the product deliberately stops the user: [A4]'s stated purpose is the moment of recognition, and a
self-dismissing toast is precisely a moment that can be missed. The dialog names the amount and the new total (plan
75's `twinkleTotal`), names an ornament reward as an ornament, and offers a single dismissal (`common_dismiss`). It
offers **no navigation** — sending the user to 우주 꾸미기 from a reward would turn claiming into a funnel. `/me` is a
quiet account surface, not the universe, so a modal here breaks no immersion ([A5] governs the universe, not this tab).

Refusals map through `packages/errors` and surface on the shared toast host, with one non-obvious case pinned by
[75.achievement-tracking-usecase](75.achievement-tracking-usecase.md): `ACHIEVEMENT_REWARD_UNAVAILABLE` means the claim
**was recorded** and the payout leg failed, and the next claim replays it. Its copy therefore says the reward is kept
and to try again, and **the button stays enabled** — disabling it would strand the reward in exactly the crash window
the replay exists to heal. `ACHIEVEMENT_NOT_ACHIEVED` and `ACHIEVEMENT_NOT_FOUND` mean the client's list is stale; both
trigger an `AchievementService` invalidation alongside the toast. There is no `ALREADY_CLAIMED` reason to map — a
repeat claim succeeds as a replay.

### The unlock notice is a diff of a read ([A5])

`AchievementNoticeHost` mounts `useAchievements()` once per session and, on every resolution, runs the pure
`newlyAchieved(previous, next)` against a `useRef` snapshot of the previous `{id → achieved}` map. Ids that flipped
`false → true` and are still unclaimed become notices.

Three properties follow, each structural rather than checked:

1. **The first resolution notifies nothing.** `newlyAchieved(undefined, next)` returns `[]` by construction, so a
   returning user with twelve unclaimed achievements is not greeted by twelve toasts — the first read seeds the
   snapshot silently.
2. **No polling and no extra fetch.** The read refreshes only when something invalidates it. The invalidation is
   `useInvalidateAchievements()`, called from the same resolved-action handlers that already call
   `useInvalidateTwinkleBalance()` — `widgets/{recall-flow,star-detail,diary-reader,stardust}` — **plus** the two
   progress-recording actions that move no Twinkle: the **Release (full-delete) resolution** in
   `widgets/deletion-flow` (the counter's producer is `memory.Release`; a let-go records nothing —
   [50.deletion-ui](50.deletion-ui.md); note this widget calls no invalidation today, so this is a new seam, not an
   addition to an existing handler) and the save resolution in [73]'s decoration panel — **this unit owns adding that
   one call into 73's save handler** (73 and 76 build in parallel; whichever lands second wires it, and this plan's
   checklist carries it so it is never dropped). That list is exhaustive
   against plan 75's producer call sites for the in-session cases; the invite settlement happens at signup, before the
   watcher ever mounts, and surfaces on the next read.
3. **A burst is capped.** A single diary launch can complete several achievements at once, so the queue takes at most
   `achievement.unlock_notice_max` notices per resolution and drops the rest — the tab, not the toast, is where
   achievements are confirmed ([A5]: "실제 확인·수령은 마이페이지 업적 탭에서 한다").

The notice copy is one line naming the achievement and where it waits. It carries **no reward figure, no button, and
no navigation** — a toast that offers to take you somewhere is not "우주 몰입을 방해하지 않는 수준". Dwell is
`values.achievement.claimToastMs`.

The queue itself is component state in the host, not a Zustand store, and this is deliberate against §3.2's
"collections in Zustand": the queue is read by nobody else and must not outlive its host, because a store surviving
sign-out would carry one user's unlock into another's session. Its lifetime _is_ the guarantee.

### One toast host, one viewport

`WebErrorProvider` renders `<Toast>` into a fixed bottom portal; a second owner doing the same would land in the
identical slot. So this unit promotes the seam instead of duplicating it:

- `packages/ui/src/toast-queue.ts` — `ToastQueueContext`, `usePushToast()`, `ToastEntry {id, variant, message,
durationMs}`. Platform-pure (React only, no DOM, no i18n), exported from both `index.ts` and `index.native.ts`,
  modelled on `packages/errors/src/react.ts`: shared context + hook, forked provider component. `message` is a
  **resolved string**, so `packages/ui` stays domain- and locale-free.
- `apps/{web,mobile}/src/app/providers/toast-provider.tsx` — holds the queue, renders **the head entry only** through
  the shipped `Toast`, shifts on dismiss or timeout.
- `error-provider.tsx` on both apps keeps `ErrorToastContext` and `presentAppError` exactly as they are; `showError`
  now pushes `{variant: presentation.severity, message: presentation.message, durationMs:
VALUES.errors.toastAutoDismissMs}` instead of holding its own state and `Toast`. No consumer of `useErrorToast`
  changes.

At most one `Toast` element exists in the tree, so two owners cannot overlap — the collision is unrepresentable rather
than avoided by placement. The achievement notice pushes with `variant: 'info'` and
`values.achievement.claimToastMs`; an error, being the thing that must be read, keeps its own severity and dwell.

### Copy resolved from the id, never from the wire

Plan 74 pins that `AchievementEntry` carries **no user-facing string** — ids, integers, enums and flags only. So
`packages/achievement/src/achievement-copy.ts` is the projection, in the exact shape of
`packages/emotion/src/mood-label.ts`: a `Record` from achievement id to `{title, body}` message accessors
(`m.achievement_<id>_title` / `_body`), plus `axisLabel(axis)` over the nine axes. Static accessors, so
`pnpm gen:messages` / `check:gen` / `lint:raw-strings` all see them.

An id with no copy entry falls back to `achievement_untitled` and **still renders its progress and its 받기 button**.
That is the decided behavior, not an oversight: copy completeness is a content gate, claimability is a correctness
one, and a catalog row added server-side must never make an earned reward unreachable. A `packages/achievement` test
asserts the `Record` covers every id the app knows, and the residual risk — a server catalog row with no FE copy —
degrades to a plainly-labelled but fully claimable row.

Voice: restrained and plain. The 받기 button carries [A4]'s own word (`받기`); the claimed state is `받았어요`; the
notice states the achievement and that it waits in 나. No exclamation, no decorative emoji, no congratulation the
product has not earned.

### Golden-parity stance

**None, and none is possible.** Plan 74 pinned that the server is the only evaluator: `progress`, `achieved`,
`claimed` and `rewardTwinkle` arrive resolved, and no condition, target, or reward formula exists FE-side to drift
from a Go counterpart. The two pure functions this unit adds — `progressRatio(progress, target)` (display arithmetic
over two server integers) and `newlyAchieved(previous, next)` (a set diff over server booleans) — have no Go
counterpart by construction and are unit-tested locally, with no fixture and no `testdata` file. Parity here is
web↔mobile parity only: `packages/achievement` is consumed verbatim by both apps and only `ui` is forked (§3.5;
[00.overview](00.overview.md) §4 gives this unit no parity waiver).

## Acceptance Criteria

1. The `/me` achievements tab renders the full catalog returned by `ListAchievements` in the **server-fixed order**,
   grouped under the nine [A2] axis headings, with unachieved rows present and readable; the FE sorts, filters and
   evaluates nothing, and no condition, target or reward amount is computed client-side. ([A2][A4][U9])
2. Each row shows a determinate progress meter reading `progress`/`target` **verbatim from the wire**, rendered
   through a NEW `packages/ui` `progress` primitive pair with `role="progressbar"` / `accessibilityRole="progressbar"`
   and correct value/min/max. ([A2][U9])
3. A row is exactly one of `locked` / `claimable` / `claimed`, derived by a pure function from the two server
   booleans; the 받기 button exists **only** in `claimable`, and no optimistic state can make an unpaid row look paid.
   ([A4])
4. Pressing 받기 issues `ClaimAchievement{achievement_id}` and nothing else — the request carries no `user_id`, no
   amount, no ornament id and no counter — and the mutation fires only from a press handler, never from an effect,
   mount, or focus. There is no auto-claim path in the codebase. ([A4][U1])
5. A successful claim opens a reward reveal naming the granted `GENERAL` amount and the new total (and, when present,
   that an ornament was granted), dismissible and offering **no** navigation; the reveal is a dialog, not a
   self-dismissing toast, so the recognition moment [A4] asks for cannot be missed. ([A3][A4])
6. A claim invalidates the `AchievementService` read and the twinkle balance, and — only for an ornament reward —
   [71]'s `GetCatalog`; the stardust tab shows the credit as an ordinary ledger row on next open. No surface polls.
   ([G7], ARCHITECTURE §3.2)
7. Only one claim can be in flight at a time, enforced by a single `asyncCommandMachine` instance whose context holds
   the achievement id and no server data; **no new machine file is authored** in either app. (ARCHITECTURE §3.2)
8. A repeat claim is treated as success, not an error: no `ALREADY_CLAIMED` mapping exists, and
   `ACHIEVEMENT_REWARD_UNAVAILABLE` surfaces copy stating the reward is kept, **leaving the button enabled** so the
   replay can heal it. `ACHIEVEMENT_NOT_ACHIEVED` / `ACHIEVEMENT_NOT_FOUND` additionally invalidate the list.
   ([75.achievement-tracking-usecase](75.achievement-tracking-usecase.md))
9. The [A5] unlock notice is derived **only** by diffing consecutive `ListAchievements` results — no push, no
   subscription, no polling, and no RPC in this unit that could report an achievement. ([A5], ARCHITECTURE §2.7)
10. The first resolution after mount enqueues nothing, so a returning user with unclaimed achievements sees no toast
    burst at sign-in; at most `values.achievement.unlockNoticeMax` notices are enqueued per resolution. ([A5])
11. The notice carries the achievement's name and where it waits — no reward figure, no button, no navigation — and
    dismisses after `values.achievement.claimToastMs`. ([A5])
12. `useInvalidateAchievements()` is called from every in-session progress-recording resolution: the four surfaces
    that already invalidate the twinkle balance, plus the release/let-go resolution and the decoration save. ([A5],
    plan 75's call sites)
13. Exactly **one** `Toast` element can exist in the tree: `packages/ui` owns a queued toast context, one forked host
    per app renders the head entry, and both the error path and the achievement notice push into it. `useErrorToast`
    consumers and `presentAppError` are unchanged.
14. `packages/achievement` and both feature slices depend on **none** of `@cosimosi/memory`, `@cosimosi/memory-logic`,
    `@cosimosi/universe`, `@cosimosi/emotion`, `@cosimosi/store` or `@cosimosi/3d-renderer`, enforced by package
    manifests plus a scoped `no-restricted-imports` group; no type, prop or handler in this unit names a memory, star,
    position, strength, mood, decay stage or gist stage. ([A6][I11], [00.overview](00.overview.md) §3)
15. No `store_*` message key is read and no ornament is named on this surface; an ornament reward renders as one
    `achievement_*` line. ([P11])
16. Every string resolves through `packages/i18n` in **both** `en.json` and `ko.json` under the `achievement_*`
    prefix, regenerated with `pnpm gen:messages` and gated by `check:gen`; `pnpm lint:raw-strings` passes; an
    achievement id with no copy entry falls back to a plain label and remains fully claimable.
17. The tab and the notice ship on **web and mobile** with `packages/achievement` consumed verbatim and only `ui`
    forked; `me_achievements_pending` and its copy are retired with **both** placeholder rows they described (web's
    `TAB_VIEWS` row and mobile's inline `tabViews` row), including the mobile `App.test.tsx` assertion on that key.
    ([00.overview](00.overview.md) §4, [64.my-page](64.my-page.md))
18. `/me?tab=achievements` remains a valid deep-link target with the list as its landing content — [67] is **already
    shipped** and already routes its insufficient-balance recovery here (today it dead-ends on the placeholder), so
    this is a live regression surface, not a future contract. ([64.my-page](64.my-page.md))
